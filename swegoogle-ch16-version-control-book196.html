版本控制与分支管理

Software Engineering at Google · Ch 16 · Version Control and Branch Management · Titus Winters · 2020

EN →

这一章讲什么？

几个人一起改同一份文件，迟早会出现一个文件夹：「方案 v5 最终版」「方案 v5 最终版-改」「方案 v5 最终版-小王改」。到底哪份才是最新的？写程序的人也有这个问题，只是文件多了几百万倍、改的人多了几万倍。管这件事的工具叫版本控制。这一章讲的是：Google 五万名工程师怎么共用一份代码，而且不乱。

打个比方

想象一本几万人一起写的百科全书。版本控制就像一个超级管理员，它记得每一页在每一天长什么样，谁改了哪一句、什么时候改的，随时能翻回去。这本书只有一本正本放在中央书架上，大家都以它为准，没人需要问「你手里那本是不是最新的」。

旧世界为什么难

很多团队怕改坏正本，于是各自把书复印一份，在复印件上写几周、几个月，最后再一次性誊回正本。听起来稳妥，可等到誊回去那天，正本早被别人改得面目全非：几百处冲突要一处处对，出了错也说不清是谁那段惹的祸。有的公司甚至专门安排一个人、每周开会，就为了商量「这周先誊谁的」。

核心机制直觉

  • 只认一本正本：不管大家手里有多少份草稿，「写完」的定义只有一个——誊进了中央那本。
  • 少量多次往正本里写：每次只改一小段、当天就誊回去。改得小，冲突就小，出了问题也一眼看出是谁。没写完的章节先誊进去，但盖上布不给读者看，等写好再掀开。
  • 同一样东西只许有一份：如果有人嫌某个公用工具有毛病，自己偷偷抄一份改了用，别人就会不小心同时用上两份、打起架来。规矩是：有问题就修那唯一的一份，不许另起炉灶。

带来了什么 / 该怎么选

好处是整个公司像在同一张桌子上干活：谁改了什么人人看得见，一次改动能顺手修好全公司的用法，新人来了拿到的就是那本正本。诚实的代价是：把所有人的代码放进一本书，需要非常强的工具撑着，普通工具撑不住这个体量，而且不同项目保密要求不一样时，一本书就不太好管。

一句话记住

让大家别有选择：只有一本正本、每样东西只有一个版本、改动少量多次直接写进主线，团队越大越省事。

一句话

你以为分支是隔离风险的安全网，本章说那多半是错觉：版本控制首先是政策而不是工具，而规模化的关键政策是拿走选择——提交只有一个真相源、依赖只有一个版本、开发直接在主干上小步进行；长命开发分支只是把合并风险攒到最后一起爆。

Glossary · 术语表

  • 版本控制系统（VCS）：记录文件每次修改历史的系统，能回到任意旧版本，也能协调多人同时修改。
  • 仓库（repository / repo）：被管理的那批文件加上它们的全部历史记录。
  • 提交（commit）：把一组修改作为一个整体存进仓库；「原子」意思是要么全部生效、要么都不生效。
  • 分支（branch）与合并（merge）：分支是从某个点分出去的一条平行修改线；合并是把两条线的修改拼回一起，改了同一处就会冲突。
  • 主干（trunk / head / main）：仓库默认的那条主线。
  • cherry-pick：只挑某一个修改，单独搬到另一条分支上。
  • 依赖（dependency）：你的代码要用到的别的库；「传递依赖」是依赖的依赖。
  • 持续集成（CI）：每次提交都自动构建并跑测试，尽早发现改坏的地方。
  • 功能开关（feature flag）：代码已经上线，但用配置决定这段功能开不开，没做完就先关着。

坐标

Part IV「工具」的第一章，上接 Part III 的测试、评审与废弃——它们正是本章「主干能保持稳定」的底气；下启代码搜索（Ch17）、构建系统（Ch18）、依赖管理（Ch21）和大规模变更（Ch22），这些都建立在「一个仓库、一个版本」之上。现实对应：Git 工作流之争、单体仓 vs 多仓、主干开发 vs 特性分支。

这章要解决什么

全书的论题是「软件工程 = 编程在时间上的积分」，而版本控制就是工程师管理代码与时间交互的头号工具。文件系统是「文件名 → 内容」的映射，VCS 把它扩展成 VCS(文件名, 时间, 分支) → 内容——多了时间这一维，就能回到过去；多了分支这一维，就能平行修改。

用不用 VCS 已无争议：作者说，经验丰富的工程师对任何超过一两天的项目都会本能地用它，连单人项目也不例外。真正的问题是第二层：怎么用。在 Google 的体量下——约 5 万名工程师共用一个仓库、每个工作日 6–7 万次提交——分支怎么开、依赖怎么选、「完成」以哪里为准，这些政策一旦留出选择空间，协调成本就会随人数超线性增长。本章要回答的就是：哪些选择该被拿走。

核心内容，讲透

一、集中式 vs 分布式：差别比想象的小

作者先泼一盆冷水：只要能原子地提交一批文件，所有现代 VCS 在语义上就等价，其余都是用户体验——选 VCS 就像选文件系统格式，更重要的是你往里装什么、怎么用。早期的 RCS 靠给文件加独占锁防止同时编辑，人一多就卡在锁上；CVS 允许多人同时检出，但提交不原子，可能损坏或丢改动；Subversion 补上了原子提交。它们都是集中式：唯一的中央仓库，提交必须送到服务器。

2000 年代中期起，Git、Mercurial 代表的分布式 VCS（DVCS）流行开来。核心区别只有一个问题：哪份拷贝算仓库、能在哪提交？DVCS 里每个克隆都是完整仓库，可以离线提交、再推给任意别的仓库，「中心」只是政策约定。作者建议：拿不准就用 Git，跟大家一样本身有价值。

但 Google 主仓用的是自研集中式系统 Piper。原因是规模：DVCS 默认把整个代码库连同历史下载到本地，而组织越大，每个人实际碰到的文件比例越小，这些传输几乎全是浪费；需要本地文件的时刻主要是构建，而分布式构建（Ch18）做得更好。Google 也试过往 Git 靠拢，被代码库体量和海勒姆定律卡住——例如许多脚本默认「提交号单调递增就是时间顺序」，Git 的哈希提交号打破了这种隐藏依赖。

二、真相源：DVCS 也绕不开中心

集中式系统把真相源（Source of Truth）写进了设计：主干上最新提交的就是当前版本，改动重新提交到它上面才算「完成」。DVCS 没有天然的中心，理论上可以无协调地互传补丁，结果退回「方案 v5 最终版-小王改」的世界。作者的追问很尖锐：没有中心，怎么保证一次发布包含了每个人过去几周做完的功能？除了人人签字，有没有人力开销随团队规模亚线性增长的办法？答案是没有——最后总有人维护一张「哪些功能可以上」的清单，这其实又发明了一个中心。新人入职从哪拿一份已知可用的代码？同样的问题。

所以管得好的 DVCS 项目都会声明某个仓库的某条分支为真相源，GitHub、GitLab 的流行正是这个模式。真相源可以分层：Red Hat 工程师有自己的内核真相源，定期往上游推，Linus 则有另一个——只要「改动该往哪推」没有歧义，就躲开了 DVCS 的混乱。

三、长命开发分支：攒着的风险

本章的一个关键认知：任何进行中的工作都等价于一条分支——本地没提交的改动，和分支上已提交的改动在概念上没区别，只是更难被找到。

在单元测试还不普及的年代，「先在特性开发分支（dev branch）上测完一整轮再合进主干」有其道理：它要解决的产品不稳定是真问题。但作者说，用大量开发分支换稳定「本质上是被误导的」：同一批提交终归要合进主干；小合并比大合并容易；作者本人合自己的改动，比攒一堆无关改动以后再合容易；合并后测试挂了，涉及一个人时好查，涉及一整条分支就难以隔离，修起来更糟。

组织是怎么上瘾的？看到「合并长命分支导致不稳定」，就得出「合并很危险」，于是去放慢、协调症状本身——分支越开越多、在分支上再开分支，最后有个倒霉蛋专职当「合并协调人」，每周开会定「本周合并策略」（作者在脚注里提到一次非正式的 Twitter 投票，约 25% 的工程师经历过定期合并策略会）。这些合并和重测全是纯开销。替代范式是主干开发（trunk-based development）：重度依赖测试和 CI、保持构建常绿、没做完的功能在运行时关掉；人人同步主干、直接提交，没有合并会、没有大合并，也没有「该用哪个版本的库」的争论——只能有一个。

发布分支（release branch）则基本无害：问题不在分支这项技术，而在用法。开发分支预期要合回主干，发布分支预期最终被丢弃，只通过少量 cherry-pick 从主干接收关键修复。DORA 研究发现最高效的组织几乎没有发布分支——能一天多次从主干发布，修了直接重新部署更省事；但如果要给客户发实体设备，知道「现场跑的是哪个版本」依然有价值。

System Design · Day 22 上线与发布 — 功能开关、灰度与自动回滚：主干开发里「没做完的功能在运行时关掉」靠的就是这一整套发布机制

四、一个版本规则：拿走依赖上的选择

Piper 的扩展性本身不够，Google 协作靠的是一条政策：One Version。它把「单一真相源」从「提交到哪」延伸到「依赖什么」：仓库里每个依赖都只能有一个版本可选。第三方包在稳态下只签入一个版本；内部包不许不改名地分叉——分叉后必须能和原版安全地链进同一个项目。

反例最能说明它为什么必要：某团队发现 Abseil 之类基础库有 bug，不就地修，而是复制一份、改掉 bug、不改库名和符号，还告诉邻近团队「我们这有个改进版」。几个团队开始依赖这个分叉。此后只要某个项目同时间接依赖原版和分叉版，好的情况是构建失败，坏的情况是两份不匹配的同名库被链进同一个程序，出现难以理解的运行时 bug。分叉给代码库染了色：任何目标的传递依赖里只能有其中一份，「加一个新依赖」这么简单的事，都可能要跑全仓测试来确认没越界。

Java 的 shading（把库的内部依赖改名藏起来）能对付函数，但遇到在包之间传递的类型就理论上、实践上都不成立——任何让同一程序里共存多版本的技巧都卡在这里。作者在 TL;DR 里说得很重：这类绕路的功夫完全是损失的劳动，只是在给技术债打补丁。最终凝成一句规则：开发者永远不该面对「我该依赖这个组件的哪个版本」的选择。它不是铁律——升级第三方库时可能短暂并存两版，但会禁止新用户依赖旧版、逐步迁移——可对组织来说，这种「不给选择」是高效扩展的关键。

五、（几乎）没有长命分支

One Version 隐含的第一条推论：开发分支要最少、最短命。长命分支会让选择悄悄回来：基础团队在平行分支上做新版 Widget，别的新项目问「能依赖你的新 Widget 吗？」——它只存在于另一条分支上，选择就出现了。正确做法是新 Widget 提交进主干、运行时先关着、能藏就用可见性藏起来，或者把新旧两版设计成能同时链进一个程序。大规模变更（Ch22）也要求主干开发：改全仓已经够累，若还有数不清的隐藏分支要一起改，代价无边，在 DVCS 里甚至找不全那些分支。

Google 约 1,000 个在单体仓里工作的团队中，有长期开发分支的只有寥寥几个（作者估计肯定少于 10 个），理由几乎都是跨时间的兼容性：磁盘上数据格式的读写双方要长期一致，或要承诺旧版客户端能连新版服务器。作者提醒，跨时间的依赖比不随时间变化的代码昂贵、复杂得多，别轻易许诺。另一个保护是「构建视界（build horizon）」：生产中的每个任务最多六个月就必须重新构建、重新部署，给版本漂移封了顶。

为什么重要 / 落到真实系统

架构评审讨论「要不要拆仓」「要不要上 GitFlow」时，这章给的判据是：先问它会不会让开发者重新面对版本选择、会不会让合并攒大。面试里谈分支策略，能讲清「进行中的工作即分支」「发布分支要丢弃、开发分支要合回」「分叉要改名」，就比背 Git 命令高出一截。

易错点与争议

  • 「Google 用单体仓，所以单体仓是正解」——作者明确说不。要坚守的是 One Version；单体仓只是让它最容易做到的一种形态。
  • 「分支是坏东西」——坏的是用法。发布分支基本无害；真正拖累生产力的是要合回主干的长命开发分支。
  • 「我在本地憋着没推，就没开分支」——进行中的工作就是分支。憋得越久，合并越大。
  • 「shading 能解决多版本冲突」——只对函数有效，对跨包传递的类型无解。而且这份功夫本身是纯损耗。
  • 「集中式过时了」——两种模型在常见用法下基本可互换。DVCS 最终也要靠政策指定真相源。
  • 局限：本章前提是组织内部有算力、能协调、有一定集中权威；开源世界更看重自由与少协调，作者承认多仓在那里运转良好。作者还反思：投资可扩展的 VMR 和配套工具，或许比把 Piper 做大是更好的投资。主干开发与高绩效的关系引自 DORA，是统计上的预测关系，不是因果证明。

要点

① VCS 把文件系统扩成 (文件名, 时间, 分支) → 内容，是管理代码与时间交互的头号工具；技术只占一半，另一半是政策。

② 现代 VCS 只要能原子提交，语义上就等价；集中 vs 分布式的真区别是「哪份算仓库」。

③ 规模越大，全量下载越浪费：Google 用自研集中式 Piper，约 5 万工程师、每天 6–7 万次提交。

④ 必须有单一真相源（一个仓库的一条分支），否则协调成本随人数超线性上涨；DVCS 也要靠政策补上。

⑤ 进行中的工作等价于分支；长命开发分支把合并风险攒大，解法是主干开发 + 测试 + CI + 运行时开关。

⑥ 发布分支基本无害：预期被丢弃、只接少量 cherry-pick；能持续部署就可省掉。

⑦ One Version：开发者永远不该选「依赖哪个版本」；不改名的分叉会把代码库染色，shading 救不了类型。

⑧ 长命分支只留给跨时间兼容这类罕见需求；构建视界把生产版本漂移封在六个月内。

⑨ 单体仓不是唯一正解：要的是它的功能，多仓 / 虚拟单体仓同样可行——选择带来成本。
