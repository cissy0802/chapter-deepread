光能跑还不够

A Philosophy of Software Design · Ch 3 · Working Code Isn't Enough (Strategic vs. Tactical Programming) · Ousterhout · 2nd ed 2021

EN →

这一章讲什么？

上一章说，软件的复杂是一点一点攒出来的。这一章追问：为什么大家明知道，还是一直在攒？答案藏在写代码时的心态里——是「先让它跑起来再说」，还是「顺手把房子收拾好」。这两种心态，决定了一个项目一年后是越写越快，还是越写越慢。

打个比方

两个人各自搬进新家。第一个人东西随手一放，「先住进来再说」，头一周特别快活；第二个人每天多花十来分钟，把东西归位、给柜子贴个标签，起初显得磨蹭。三个月后，第一个人每找一样东西都要翻半天，第二个人伸手就拿到。头几天谁快，和一年后谁快，常常是反过来的。

旧世界为什么难

多数程序员的日常是「接一个需求、做完、交差」。在这种节奏里，最顺手的做法永远是绕着问题打补丁：这里加个特殊判断，那里复制一段代码，「下次再整理」。每一次都合情合理，而且真的更快。麻烦在于「下次」很少到来，补丁叠补丁，系统变成一个谁都不敢动的线团。团队里甚至会出现一种「明星」：交活极快、人人夸，但他走过的地方，别人要花更多时间收拾。

核心机制直觉

  • 两种心态。「战术派」的目标是让眼前这件事跑通；「战略派」的目标是把系统设计好，而且它恰好也能跑。
  • 像存钱，不像突击。战略派不是先花半年画完美蓝图，而是每天往「设计」这个储蓄罐里投一点：动手前多想一个方案，发现结构不对就顺手修，而不是绕过去。
  • 投多少？作者的建议大约是每份工作时间里拿出一到两成。少到不拖进度，多到日积月累能看出差别。
  • 为什么值。乱放的东西会让以后每一次寻找都变慢，就像欠债要一直付利息；而收拾好的房子，以后每一次都省事。

带来了什么 / 该怎么选

它把「代码写得好不好」从个人洁癖，变成了一笔可以谈的账：今天多花一点时间，换明天每次修改都快一点。作者的结论很明确：默认选战略派，哪怕在赶时间的创业公司。一句诚实的代价：前几个月确实会慢一些，而且「后来会快多少」目前只是经验判断，没人精确测量过。

一句话记住

能跑只是及格线；每天多花一点时间把设计弄好，像存钱一样——起步慢一点，一年后快得多。

一句话

你以为「先跑起来、以后再重构」是务实，Ousterhout 说那是战术编程（tactical programming）——每一次都更快，加起来却更慢。他要你换成战略编程（strategic programming）：首要目标是做出好的设计，而它恰好也能跑；办法不是一次性大设计，而是每次都拿出约 10–20% 的时间持续做小投资。

Glossary · 术语表

  • 需求 / 任务（feature / task）：一次要交付的新功能或一个要修的 bug，是日常开发的基本单位。
  • 补丁（patch / hack）：不改底层结构、只在出问题的地方加一段特殊处理来让它工作。
  • 重构（refactoring）：不改变程序对外行为，只调整内部结构，让它更好懂、更好改。
  • 技术债（technical debt）：为图眼前快留下的设计缺陷；之后每次修改都要多付一点「利息」。
  • 复杂度（complexity）：上一章的定义——任何让系统难以理解和修改的结构性因素。
  • 接口 / 抽象（interface / abstraction）：模块对外暴露的「怎么用我」，以及它替使用者藏起来的细节。
  • 代码评审（code review）：代码合入前由同事阅读、提意见的流程。
  • 瀑布式（waterfall）：先把设计全部做完、再统一编码的开发方式；与之相对的是边做边改的迭代式（incremental / agile）。

坐标

全书第 3 章，是从「复杂度是什么」（第 2 章）转向「怎么对付它」的那道门：第 2 章说复杂度是增量累积的，本章回答是什么心态让它累积，并给出全书其余技巧的前提——你得愿意为设计花时间。下启第 4 章「深模块」，那是第一件具体武器。现实里对应每一次「这周先上线，下周再整理」的排期会议。

这章要解决什么

后面十几章讲的深模块、信息隐藏、把错误定义掉……每一条都要多花时间。如果团队的默认节奏是「做完就交」，这些技巧永远排不进日程。所以作者先要解决一个更根本的问题：把「为设计花时间」从额外负担，变成工作的一部分，并说清它为什么划算。

场景锚（示意）：一个 6 人团队维护一个上线两年的服务。最初加一个字段，半天搞定；如今同样的需求要改 7 个文件、绕开 3 个历史特判、再补一轮回归测试，要 3 天。没有哪一次提交「搞坏了」系统，每一次都只是「先这样，回头再说」。不解决心态问题，这个曲线只会继续往上走——直到有人提议「推倒重写」，而重写往往又从战术编程开始。

核心内容，讲透

一、战术编程：每一步都合理，合起来是灾难

是什么：战术编程的主要目标是让某个东西尽快跑起来——一个新功能，或一个 bug 修复。乍看完全合理，有什么比能跑的代码更重要？问题在于它目光短浅：你只盯着眼前这个任务，不会花时间找最好的设计。

机制：每个任务都顺手引入一点复杂度——一个特判、一段复制的代码、一个绕过去的补丁——每一次都能说服自己「这一点没关系，任务要紧」。这正是上一章「增量累积」的发动机。作者还点出一个细节：一旦战术地写起来，想回头修设计就更难了，因为修一个设计问题往往要动好几处，而战术心态天然会选「再加一个补丁」。

战术龙卷风（tactical tornado）：作者描绘的极端形态——一个产出极快的程序员，交付速度远超同事，却完全以战术方式工作。实现一个功能，没人比他快；管理层常把他当英雄。但他身后留下的是一片狼藉，后来的工程师要花大量时间收拾，反而显得进展更慢。这里的反直觉之处是：团队里看起来最快的那个人，可能是让整个团队变慢的那个人，而常规绩效指标看不到这一点。

二、战略编程：好设计，恰好也能跑

成为好设计者的第一步是意识到：光能跑还不够。为了更快完成任务而引入不必要的复杂度，是不可接受的。最重要的是系统的长期结构——系统里大部分代码都是在扩展现有代码，所以你最重要的工作，是让将来的扩展更容易。

战略编程要求一种投资心态（investment mindset）：先花一点时间改进系统设计，换取以后的速度。作者把投资分成两类：

  • 主动投资（proactive）：写新类时多想几个备选设计、挑最干净的那个（呼应第 11 章「设计两次」）；预想几种系统将来可能的改动方式，让它们容易做；写好文档注释。
  • 被动投资（reactive）：无论设计多用心，都会出错；而且随着使用，设计问题会自己浮现。发现设计问题时，别忽略它、别绕着它打补丁，多花一点时间修好它。

要点在「每次」：战略编程不是某个时刻的重构运动，而是每个开发者在每一次改动里的默认动作。

三、投多少？10–20%，持续地、小额地

作者明确反对另一个极端：一开始就做巨额前期设计（比如瀑布式先把整个系统设计完）不会奏效，因为很多设计问题只有用起来才看得到。最好的办法是持续地做大量小投资，他建议拿出全部开发时间的 10–20%。

这个数的逻辑：小到不会明显影响排期，大到长期能带来可观收益。所以第一个项目大约会比纯战术方式慢 10–20%；但更好的设计很快开始回本——作者的判断是，用不了多久，你的开发速度就会比战术方式快至少 10–20%。这里的数字是作者的经验建议，不是测量结果。

四、技术债：利息比本金多，而且很少还清

作者用技术债的比喻收束战术编程：战术地写代码，就是在借未来的时间。但它和金融债有两点不同——技术债很少被完全还清，于是你要一直付利息；而且最终付出的总额通常远大于当初借的。拖延的机制也很直接：问题越拖越大，解决方案就越吓人，人就越想继续拖——「以后再收拾」一旦开始，很容易变成「永远不收拾」。

五、创业公司也不例外

最常见的反驳是「我们是创业公司，必须快」。作者承认压力是真的，很多创业公司确实战术地写代码，想着「成功了再招人来清理」。他的回应有三层：① 一旦代码变成意大利面，几乎不可能修好，你可能要为这个产品的整个生命周期付高额的开发成本；② 回本比想象得快；③ 一家公司成败最重要的因素是工程师的质量，而优秀的工程师在意设计——重视设计的公司更容易招到人。

书中的对照案例：Facebook 早年的口号是「Move fast and break things」，代码库后来以混乱著称，于是口号改成了「Move fast with solid infrastructure」（大意如此）；而 Google 与 VMware 一直有很强的工程文化、重视代码质量，同样大获成功。作者的结论是：两种路线都有人成功，但在一家在乎设计的公司里工作要愉快得多。

为什么重要 / 落到真实系统

面试里被问「你怎么在交付速度和代码质量之间取舍」，本章给了一个可复述的答案框架：不是二选一，是比例——默认每个任务带 10–20% 的设计投资，因为技术债的利息会吃掉更多。架构评审里，它提醒你去看那些「交付最快」的改动留下了什么，而不只看交付速度本身。

实证与出处 · 公开可查

  • Facebook：口号的转向。Zuckerberg 在 2014 年 F8 开发者大会宣布把「Move fast and break things」改为「Move fast with stable infra」，理由是修 bug 拖慢了速度。原书本章正是以此说明战术文化的代价。出处：Facebook F8 开发者大会，2014；Ousterhout 原书第 3 章引用
  • 技术债的原始定义就是本章的论点。Ward Cunningham 在提出「技术债」一词时写道：交付第一版代码就像借债，少量债务能加快开发，只要及时用重写偿还；危险在于债不还——花在「不太对」的代码上的每一分钟，都是利息。出处：Ward Cunningham，The WyCash Portfolio Management System，OOPSLA 1992 经验报告
  • 诚实的另一面：这条曲线没被证明。Martin Fowler 的「设计耐力假说（Design Stamina Hypothesis）」画了与图 1 几乎相同的两条曲线，并明确称其为假说——因为软件生产力本身无法客观测量，所以无法证实；他认为交叉点往往比人们想的来得早，通常是几周而非几个月。出处：Martin Fowler，bliki「DesignStaminaHypothesis」，2007

易错点与争议

  • 「战略编程 = 前期大设计」。恰恰相反，作者明确反对瀑布式大设计；他要的是持续的小投资。
  • 「先跑起来，以后再重构」。这句话本身没错，错在「以后」——本章的核心观察就是它很少到来，而且越拖越难开始。
  • 「最快的人就是最好的工程师」。战术龙卷风的产出看得见，他留下的清理成本分摊到别人头上、看不见。评估工程师要看留下的系统，不只看交付数。
  • 「10–20% 是测出来的」。是作者的经验建议；图 3.1 他自己注明只是定性示意，没有实测曲线。复述时要说清这一点。
  • 「创业公司例外」。作者的立场是不例外；他承认两种路线都有成功者，但认为战术代码的成本会伴随产品一生。
  • 争议：真的永远不该战术吗？本书没有为「注定丢弃的原型」或「验证市场的一次性脚本」开口子；业界不少人认为这类代码可以有意识地战术写，前提是真的会扔掉——Fowler 的技术债象限把这叫「审慎且有意的债」。风险在于原型往往没被扔掉。
  • 争议：个人投资需要组织买单。如果绩效只按交付数算，个人的 10–20% 投资会被视为「慢」；作者把它归为文化问题，但没有给出组织层面的具体机制。

要点

① 能跑只是及格线：为了更快完成任务而引入不必要的复杂度，不可接受。

② 战术编程只盯眼前任务，每次留一点复杂度，正是上一章「增量累积」的发动机。

③ 战术龙卷风：看起来最快的人，可能让全队变慢；常规指标看不出来。

④ 战略编程：首要目标是好设计，它恰好也能跑；大部分代码都在扩展旧代码，所以要为将来的扩展而写。

⑤ 两类投资：主动（想备选设计、写注释、预想变化）与被动（发现设计问题就修，不绕过）。

⑥ 投多少：持续拿出 10–20% 的开发时间；反对瀑布式巨额前期设计。

⑦ 起步慢 10–20%，作者判断很快就能快回 10–20% 以上——这是经验判断，曲线没有实测。

⑧ 技术债很少还清、利息比本金多；「以后再收拾」越拖越难开始。

⑨ 创业公司也不例外：Facebook 改口号，Google、VMware 重视设计照样成功；好工程师在意设计。
