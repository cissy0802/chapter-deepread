静态分析

Software Engineering at Google · Ch 20 · Static Analysis · Caitlin Sadowski · 2020

EN →

这一章讲什么？

写文章有「拼写检查」：你还没交稿，软件就在错别字下面画红线。写代码也有同样的东西，叫「静态分析」——程序还没跑，机器先把代码读一遍，挑出可能的毛病。这一章讲 Google 怎么让几万名工程师真的愿意看这些红线，而不是一律无视。

先说个怪事

你会以为，检查工具越聪明、抓到的问题越多越好。Google 的经验恰恰相反：一个工具只要十次里有一两次报错了，大家就会养成「看都不看直接关掉」的习惯，连那几次真报也一起被扔掉。决定检查工具生死的，不是它抓得多全，而是它少冤枉人。

旧世界为什么难

想象小区门口的烟雾报警器，每次炒菜都响。响到第三周，住户就把电池拔了——真着火那天，它一声不吭。早年的代码检查工具就是这样：报告一大堆，其中不少是误会，或者说得没人看得懂；而且往往是在一份几千条的清单里出现，不知道该谁去改、为什么要现在改。

核心机制直觉

  • 只在你改的地方提醒：不去翻旧账，只看你这一次动过的那几行。你刚写完，印象最深，改起来最顺手。
  • 放在同事审稿的时候：Google 的代码进库前都要同事过目。检查结果就贴在审稿页上，像审稿人旁边多了一位不知疲倦的助理；你想无视它，还得说服审稿的同事。
  • 能顺手改的，直接给出改好的版本：点一下就修好，不用你自己琢磨。
  • 每条提醒旁边都有一个「没用」按钮：谁点得多，就去查那条规则；改不好，就把它下线。
  • 绝对可靠的规则，升级成「交不了稿」：先由机器把全公司的老问题一次清干净，再规定以后谁写出这种错，程序就编不过去。

带来了什么 / 该怎么选

结果是这套检查每天要看五万多次改动，被认为「冤枉人」的比例不到二十分之一；作者每天约三千次一键采纳机器给的修改。诚实的代价是：为了不冤枉人，很多「可能有问题、但说不准」的情况它干脆不报——它故意放过一部分真问题，换来大家肯看。

一句话记住

代码检查工具不是抓得越多越好，而是要在你刚改完、同事正在看的时候，只说几句准话、并顺手递上改法——被信任，才会被听见。

一句话

你以为静态分析的难点是「分析技术够不够强」，本章说真正的瓶颈在人愿不愿意看：Google 把用户感知的误报压到 10% 以下、只报本次改动、结果塞进代码评审并附一键修复，静态分析才从「没人理的报告」变成每天被采纳几千次的工程基础设施。

Glossary · 术语表

  • 静态分析（static analysis）：不运行程序、只读源代码来找问题；对应的「动态分析」是观察运行中的程序。
  • 误报（false positive）/ 漏报（false negative）：误报是把没问题的代码报成有问题；漏报是有问题却没报出来。
  • linter：最常见的轻量静态分析，主要查风格和简单的错误模式。
  • AST（抽象语法树）：编译器把代码解析成的树状结构，很多检查就是在树上匹配「坏形状」。
  • 代码评审 / Critique：代码合入前由同事检查；Critique 是 Google 内部的评审工具（见第 19 章）。
  • 提交前检查（presubmit）：送审或提交时自动运行、可以挡住提交的检查。
  • 单体仓库（monorepo）：全公司代码放在一个仓库里，Google 的有几十亿行。
  • IDE：集成开发环境，工程师写代码用的编辑器。

坐标

Part IV「工具」第五章，紧接 Ch19 Critique：上一章说评审工具把分析结果内联进 diff，本章讲那些结果从哪来。它也服务于 Ch15「废弃」和 Ch22「大规模变更」——防止迁移中有人又用回旧 API。现实对应：Error Prone、clang-tidy、ESLint、SonarQube、GitHub 代码扫描。

这章要解决什么

静态分析能在代码进库前抓到一类 bug：会溢出的常量表达式、永远不会被执行的测试、运行时才崩的非法日志格式串。在 Google，它的用途更广：把最佳实践固化成规则、推动代码跟上新 API、在废弃旧系统时防止回退。

难点在于，学术界几十年都在研究「更强的分析」，把工具做得可扩展、可用却是较新的课题；Google 早期几次接入尝试都失败了。不解决的后果是：报告没人看，真报淹没在噪声里，工具被绕开。所以本章的问题是：在几十亿行的代码库上，什么样的静态分析才会被工程师真正接受？

核心内容，讲透

一、可扩展：只看这次改动，而不是整个代码库

代码库几十亿行，不可能每次全量分析。Tricorder 的分析是可分片、增量的：只分析受这次待提交改动影响的文件，通常只展示被编辑文件或行上的结果。分析器向全公司征集，结果直接给相关工程师看，不经中央团队转手。

「只看新代码」也是可用性决定。给一段在生产里跑得好好的旧代码「修」警告，收益不明、风险真实：书里的例子是，为消除「死代码」警告给它加一个调用，结果一段从没测过的代码突然开始运行。所以只聚焦新引入的警告，存量问题除非特别重要（安全漏洞、严重 bug），否则不翻旧账。附带的好处是：看到警告的人，正是对这段代码上下文最熟的人。

二、有效误报：误报由用户说了算

学术研究传统上追求少漏报；实践中，低误报率才是工程师愿意用的前提——谁愿意在几百条假报里翻那几条真的？本章最核心的概念是有效误报（effective false positive）：开发者看到这条结果后，没有采取任何正向动作，它就算有效误报。

  • 技术上正确、但消息让人看不懂，用户没动作——算误报。
  • 技术上正确、但无关紧要——算误报。
  • 反过来，分析器其实判错了，但开发者觉得改了更清楚、乐意改——不算。书里的例子：Java 里对哈希表调用 contains，它等价于 containsValue，而开发者多半本意是 containsKey；即便本意真是查值，改成 containsValue 也更清楚。

这个定义把指标从「规则在逻辑上对不对」挪到「用户有没有因此行动」，于是消息措辞、重要程度、时机都被纳入了衡量。书中脚注也留了口子：发现严重问题的安全类分析，评审者可能容忍高得多的误报率。

三、Tricorder：平台、准入门槛与规模

Tricorder 是 Google 的静态分析平台，它与之前失败尝试的关键区别是执着于只给用户有价值的结果。它采用微服务架构：Tricorder 把分析请求连同改动元数据发给分析服务器；服务器通过基于 FUSE 的文件系统读取改动中的源文件版本，并能访问缓存的构建输入输出；各分析器的结果写入存储层，每个类别最新的结果显示在 Critique 的 diff 里，呈灰色评论框。

任何工程师都能写分析器（analyzer）或往现有分析器里加检查（check）。新检查必须满足四条准入标准：

  • 可理解：任何工程师都看得懂输出。
  • 可操作、易修复：修复可能比编译错误更费心思，所以结果要附上怎么修的指引。
  • 有效误报低于 10%：开发者至少 90% 的时候觉得它指出的是真问题。
  • 对代码质量有显著影响：不一定关乎正确性，但开发者应当认真对待、主动选择去修。

规模数字：每天分析五万多个代码评审改动，常常每秒跑好几次分析；覆盖三十多种语言、一百多个分析器，大多数由 Tricorder 团队之外的人贡献，其中七个本身是插件系统，又挂着几百个检查；整体有效误报率略低于 5%。

接进来的工具五花八门。Error Prone（Java）和 clang-tidy（C++）扩展编译器、在 AST 上找反模式。书里的例子：对 long 字段的哈希写法 (int)(f ^ (f >>> 32))，若 f 改成了 int，右移 32 位等于没移，f 和自己异或得零——照样能编译。把这条检查在 Error Prone 里开成编译错误时，修掉了代码库里 31 处。也有跨文件的：IfThisThenThat 要求两个文件的某段必须同步修改；Chrome 的 Finch 分析器检查 A/B 实验配置；二进制体积检查在产物显著变大时提醒。注意几乎所有分析器都是过程内（intraprocedural）的，只看单个函数内部——跨函数分析技术上可行，但需要额外的基础设施投入。

四、把反馈闭环做成产品功能

「不度量就无法修复。」每条结果旁有 Not useful 按钮，点击后可直接给分析器作者提 bug，结果信息自动预填；审阅人可点 Please fix 要求作者处理。Tricorder 团队盯着 Not useful 点击率相对 Please fix 频率偏高的分析器，不改进就下线。没有这条通道之前，很多开发者直接忽略看不懂的结果。

有时修复简单到只是改一句提示语。Error Prone 曾上线一条检查，抓 Guava 中只接受 %s 的类 printf 函数被传了过多参数；团队每周都收到 Not useful 报告，说「占位符和参数个数明明对得上」——其实是用户在用 %s 以外的占位符。提示语改成直说「这个函数只接受 %s」后，报告就停了。

修复建议同理：能自动修的就自动修，修复本身就是一份文档。可以在 Critique 里一键应用，也能用命令行对整个改动批量应用。风格问题交给格式化工具，人类审阅人不该花时间挑格式。数字：审阅人每天点几千次 Please fix，作者每天约 3000 次应用自动修复，Not useful 每天约 250 次。

System Design · Day 50 把 Code Review 当信号检测系统 — 把「有效误报 < 10%」展开成误报预算、分诊门控与按分析器治理的完整设计

五、定制：按项目，不按个人

先用高置信结果攒下信任，再开放可选分析器给特定项目。例如 Proto Best Practices 分析器标出可能破坏数据格式的 protocol buffer 改动——只有序列化数据被存下来（比如写进日志）时才算破坏，没有存储数据的项目不必开。有的可选分析器根据反馈改进、用户变多后，转正成默认开启。

关键洞察：定制只能在项目级，不能在个人级。项目级保证全组看到一致的结果，避免一个人在修、另一个人在引入。早期 Critique 允许每个人选置信度、屏蔽某些分析；Tricorder 把这些个人设置全部删掉，立刻收到一堆「结果好烦」的抱怨。团队没有恢复设置，而是追问原因，挖出了被掩盖的 bug：C++ linter 也在 Objective-C 文件上跑、结果全错；HTML linter 误报极高、几乎没有信号，平时被大家屏蔽了——于是直接停用。结论：个人定制会藏住 bug、吞掉反馈。

六、插入点：越早越好，但越早越要准

代码评审是甜蜜点：几乎所有代码进库前都要评审，作者正处于「改代码」的心态，顺手就改；送审后作者本就要等人，分析跑几分钟也不耽误；审阅人会施加同伴压力；分析器替审阅人挑掉常见问题，让评审本身能扩展。而且分析能看到整个改动的上下文——死代码分析在「先写函数、后加调用」的半成品上会误判。

presubmit 补上「警告可被无视」的缺口：它能挡住提交。内置检查很简单——提交说明里不能有 DO NOT SUBMIT、代码文件要带对应测试、格式正确；团队可以要求某类 Tricorder 问题清零，或写自定义 presubmit，让新项目执行比遗留项目更严的标准。代价是会妨碍大规模变更，所以部分团队检查对描述里带 CLEANUP= 的改动放行。

编译器是最硬的一格：构建失败是无法忽略的警告。进编译器的检查要更快，且满足三条：可操作易修复（尽量附机械可应用的修复）、零有效误报（绝不让正确代码编不过）、只管正确性，不管风格和最佳实践。

上线新检查必须先清掉代码库里的所有存量，否则编译器一演进就把现有项目打红。这意味着检查的价值必须高到值得修完所有旧实例。Google 能以 MapReduce 方式在集群上并行编译整个代码库，此时检查必须产出修复，才能把清理自动化。

还有一条硬规矩：永远不发编译器警告。Google 反复发现开发者会忽略警告，所以一条检查要么开成错误，要么不在编译输出里出现；编译参数全库统一，这个决定是全局的。最常用的语言遵循这条，但并非每种语言都是。Go 走到极致：未使用的变量和 import 在别的语言里只是警告，在 Go 里是错误。

最后是 IDE：分析通常要在 1 秒内、理想 100 毫秒内完成，还要在多个 IDE 里结果一致（Google 不强制统一 IDE），所以比接入评审更乱。另有一个例外：安全团队、规划清理的人需要浏览代码时看全库结果。

为什么重要 / 落到真实系统

给仓库接 linter、SAST 或 AI 评审机器人，本章给了三把尺子：有效误报有没有被度量（有没有「没用」按钮、按分析器统计）、结果是不是出现在作者刚改完的那一刻、能不能一键修。评审里讨论「这条规则要不要开成阻断」时，可以直接套编译器三条：机械、零误报、关乎正确性——三条都满足才阻断，否则留在评审里当建议。

易错点与争议

  • 「误报率是分析器的技术属性」——不是。有效误报由用户行为定义：消息看不懂、问题不重要，技术上再对也算误报。改一句提示语就能降误报。
  • 「检查越多越安全」——反了。噪声会让人整体忽略，连真报一起作废。Google 宁可下线 HTML linter，也不让它稀释信任。
  • 「给每个人开关最友好」——书里试过，结果是藏 bug。个人屏蔽让坏分析器长期没人修。
  • 「顺手把旧代码的警告也修了」——小心。修警告本身可能引入 bug，稳定旧代码收益不明。
  • 局限：几乎全是过程内分析，跨函数的空指针、资源泄漏这类问题抓得少；Facebook Infer 走的正是组合式跨过程分析的路线。「误报 < 10%」是面向通用检查的经验线，安全类分析可以容忍更高。「全局无警告」依赖单体仓库与统一编译参数，多仓库组织难照搬。

要点

① 静态分析的瓶颈不在分析技术，而在工程师愿不愿意看；Google 早期几次接入都失败了。

② 可扩展：只分析受本次改动影响的文件、只报被编辑的行；分析器向全公司征集，结果直达相关工程师。

③ 有效误报＝看完没有正向动作；看不懂、不重要都算。指标从「规则对不对」挪到「人有没有行动」。

④ Tricorder 准入四条：可理解、可操作易修复、有效误报 < 10%、影响显著；整体略低于 5%。

⑤ 反馈闭环是产品功能：Not useful 直通作者，相对 Please fix 偏高就整改或下线；改提示语也能消灭「误报」。

⑥ 能自动修就自动修：每天约 3000 次一键应用；风格问题交给格式化工具，不占审阅人时间。

⑦ 定制只做项目级：个人开关会藏住 bug、吞掉反馈。

⑧ 插入点分层：评审是主战场；presubmit 挡提交；编译器只收机械、零误报、关乎正确性的检查，先清存量再开、永不发警告。

⑨ 局限：以过程内为主，跨函数 bug 漏得多；做法深度依赖单体仓库与统一工具链。
