Continuous Integration

Software Engineering at Google · Ch 23 · Continuous Integration · Rachel Tannenbaum · 2020

中文 →

What is this chapter about?

Tens of thousands of engineers push changes into the same software every day. Any one of those changes can break somebody else's work. This chapter is about how Google lets machines stand guard instead of people: every incoming change is automatically assembled and checked, and the earlier a bad change is caught, the better. That practice is called "continuous integration."

A strange thing first

You'd think the safest approach is "before any change goes in, run every single check, and only let it in if everything passes." Google deliberately doesn't. Before a change goes in, it runs only a small handful of fast, dependable checks and lets it in first; the big checks run afterwards. If something turns out wrong, the change is undone with a click. The result is both faster and steadier.

Why the old world was hard

Picture a restaurant kitchen. If every dish had to pass a full inspection before leaving the stove, cooks would spend most of their time waiting, the food would go cold, and the guests would leave. If nothing were checked, problems would surface only when a guest phoned in a complaint — by which point it's hard to tell which cook, at which step, went wrong. The later a problem is found, the harder and costlier it is to trace. Worse, some checks are themselves "sometimes right, sometimes wrong," blaming innocent cooks — and soon nobody trusts them.

The core mechanism, intuitively

  • Layers of checks: taste a spoonful before plating (a check that takes minutes), do a bigger inspection before serving, and keep someone walking the dining room while guests eat. Each layer is cheaper and faster than the next.
  • Let it through, take it back if wrong: when a big check finds a problem, the person on duty drops everything — and the usual fix is simply to pull that change back out, restoring a known-good state first.
  • Rehearse on a sealed stage: checks don't talk to real outside systems; they run on a little self-contained stage with all props brought along. Run the same play twice and you get the same result — nobody gets blamed because a neighbor's power went out.
  • Tag the broken checks: a check that can't be fixed right away gets a note saying who is responsible for fixing it. It stops blocking everyone, but it can't be forgotten.

What it buys you / how to choose

Every day more than fifty thousand changes and over four billion checks pass through this system at Google, and engineers wait only about ten minutes on average to hand a change in. A small company needn't copy all of it, but it should ask how much it already pays for problems that only show up after launch. The honest cost: the checking machinery itself takes lots of machines and people to maintain, and it will never be perfectly error-free.

One line to remember

Continuous integration isn't "check everything, then let it in"; it's deciding "what to check, when": fast and reliable checks first, slow and difficult ones later, and undo on error.

In one line

You think CI means "run all the tests on every commit"; this chapter says CI is fundamentally a scheduling decision: which tests run when, against what kind of system under test. Fast, reliable tests go in presubmit; slow, nondeterministic ones go in post-submit and on release candidates; production gets probed with the same suite; and bad changes are handled by rollback, not by blocking. It works more like alerting shifted left than a gate that must always be green.

Glossary

  • Head / trunk: the latest version of the code in the repository; integrating directly there is trunk-based development.
  • Presubmit / post-submit: automated checks run before a change is committed / after it has landed.
  • System under test (SUT): the set of programs and environment actually brought up and exercised by a test.
  • Unit test / end-to-end test: a test of one small function or class / a test of a whole path from entry to exit.
  • Flaky test: a test that sometimes passes and sometimes fails with no change to the code.
  • Rollback: undoing a commit entirely, returning to the state before it.
  • Release candidate (RC): a deployable bundle of code, configuration and dependencies produced by an automated process.
  • Staging: a shared pre-production test environment that mimics production.
  • Canary: sending a new version to a small slice of production traffic first, then rolling out fully if all looks well.
  • Microservice / RPC: an application split into many independently deployed services that talk via remote calls.

What problem this chapter solves

The classic definition is Martin Fowler's: team members integrate their work frequently, each integration verified by an automated build (including tests) to detect integration errors as quickly as possible. The chapter argues that this is no longer enough: the change that breaks your application increasingly comes from an upstream microservice on the other side of a network call, from ingested data and models, from evolving operating systems and cloud platforms — released by other teams on their own schedules. Hence a second definition: CI is the continuous assembling and testing of our entire complex and rapidly evolving ecosystem.

What happens without it? Quality rests on hoping every contributor is careful. Google's scale pushes this to the extreme: one monorepo, more than 50,000 unique changes and more than four billion individual test case runs a day — on average more than one change per second. Any bad change is immediately visible to the whole company.

The core, explained

1. Feedback loops: the further right, the costlier

The later a bug is caught, the more it costs — almost exponentially. The person triaging it is less likely to know the code, the author has to dig to remember why they changed it, and the blast radius spreads from one engineer to the team and finally to users. CI's first principle is therefore fast feedback loops (also called shifting left on testing): catch each change as far left as possible.

Feedback must also be accessible and actionable. Google has a unified test-reporting system where anyone can look up any build or test run with full logs (minus user PII), plus a Google-wide statistical flake classifier — so you don't have to work out alone whether your change broke someone else's test or the test was just flaky.

2. Two heads, release candidates and production probers

The Continuous Build (CB) integrates the latest changes at head and builds and tests them, which yields two heads: true head (the latest commit) and green head (the latest change the CB has verified). Engineers often sync to green head for stability while coding, then to true head before submitting.

The first step of Continuous Delivery (CD) is release automation: continuously cutting release candidates from head (most Google teams cut at green head), then promoting each one through a series of environments with progressively larger tests. Two details matter most. First, static configuration should be promoted with the RC and tested alongside the code that uses it — the book notes that a large share of production bugs come from "silly" configuration problems. Second, RC artifacts should not be rebuilt between environments; containers and orchestration (Docker, Kubernetes, at Google usually Borg) enforce that consistency.

Why rerun on the RC the tests CB just ran? Four reasons: a sanity check that nothing odd happened when the code was cut and recompiled; auditability, since results hang off the RC; cherry-picks, which make the RC diverge from what CB tested; and emergency pushes, cut from true head with only the minimal test set. Finally, the same suite runs against production as probers: verifying production against the tests, and the tests' relevance against production. Defense in depth, not a bet on one layer.

3. Why presubmit isn't enough — and shouldn't be greedy

If earlier is cheaper, why not run everything in presubmit? Three reasons. Cost: making engineers wait hours to submit is far more expensive than machines, and since tests pass far more often than they fail, dropping exhaustiveness lets you pick tests by scope or by a model predicting which will catch failures. False blame: being blocked by flakiness unrelated to your change. Mid-air collisions: while presubmit runs, the repository moves; two changes touching completely different files can together break a test. Each one is rare, but at Google's scale it happens most days. Small repositories can serialize submits to avoid it; Google cannot.

Hence the rule of thumb: presubmit gets only fast, reliable tests, typically the small tests of the project being changed. Accept some loss of coverage, catch the rest in post-submit, and accept some number of rollbacks. Whether larger tests belong in presubmit varies by team: either make them hermetic (below), or let them be unreliable in presubmit but disable them aggressively when they start failing.

4. CI is alerting

In a sidebar, Titus Winters compares CI to production monitoring: both exist to identify problems automatically, as soon as possible; CI is simply alerting shifted left. That lets CI borrow SRE's hard-won policies:

  • A test should fail only when an important invariant is actually violated. A test that flakes every few runs is just like a spurious alert paging the on-call every few minutes. If it isn't actionable, it shouldn't alert.
  • A 100% green rate on CI is as awfully expensive as 100% uptime for a service — which SRE already gave up in favor of error budgets.
  • Policies of the form "nobody can commit if the latest CI results aren't green" are probably misguided: failures must be investigated first, but if the root cause is understood and clearly won't affect production, blocking commits is unreasonable. We should also be more liberal in accepting changes that disable a failed test.

5. Hermetic testing: trading fidelity for determinism

A hermetic test runs against an entirely self-contained environment with no external dependencies such as production backends. It has two properties: determinism — run the same app and test code twice and get the same result, so a failure points at your code or test (system time, randomness and races can still interfere); and isolation — production problems can't affect it, and it can't affect production.

There are three tiers: fakes (cheap, but they need upkeep and have limited fidelity); a fully sandboxed stack (DisplayAds has one that starts about 400 servers from scratch on every presubmit); and, more popular for large systems, record/replay — record live backend responses, cache them, replay them hermetically. The difficulty with record/replay is the cache-hit balance: hit the cache too much and you get false positives (tests pass when they shouldn't); too little and you get false negatives (constant re-recording, often blocking submission).

Google Assistant is the success story: after making presubmit fully hermetic, runtime dropped by a factor of 14 with virtually no flakiness; before, on some days more than 50 changes bypassed and ignored test results. The price: nonhermetic tests moved to post-submit, where failures now accumulate — and some teams just disable them.

Assistant also exploits its move to microservices for post-submit failure isolation: for each of N microservices, an environment runs that service built at head alongside production (or near-production) versions of the other N−1, so a failure isolates to the newly built server. Naively that costs O(N²) servers (N environments × N services each); with hotswapping — a request can tell a server to call a different backend address — only N head-built servers are needed, all reusing the same production backends, cutting cost to O(N).

6. TAP: optimistic integration + Build Cop + rollback

TAP (Test Automation Platform) is Google's global continuous build, the gateway for almost every change. Its core bet is optimistic integration: each team defines only a fast subset of tests (usually unit tests) as presubmit; empirically, a change that passes presubmit has a 95%+ chance of passing everything else, so it's let in for others to use, while larger, slower tests run asynchronously after submission. The average wait to submit is around 11 minutes, often in the background.

The price of letting changes in is that bad ones land, so two things come with it. Culturally, committing new work on top of known-failing tests is strongly discouraged. Organizationally, each team has a Build Cop responsible for keeping the project's tests passing no matter who broke them: when notified, they drop everything, find the offending change, and prefer rollback — fixing forward is riskier. Any change can be rolled back with two clicks, and TAP now auto-reverts when it's highly confident about a culprit. The book puts it neatly: tests give us confidence to change; rollbacks give us confidence to undo — neither works without the other.

Culprit finding is hard: there are too many changes a day for TAP to run every test on every change, so it batches related changes, which obscures which one broke a test. TAP automatically splits a failing batch and reruns each change in isolation, and developers have tools to binary-search a batch. On resources, most tests run on the distributed build-and-test system Forge; Forge and Blaze maintain a near-real-time global dependency graph, from which TAP runs only the minimal set of downstream tests. A neat incentive: changes that trigger fewer tests get scheduled sooner — on a busy day, 100 versus 1,000 triggered tests can mean tens of minutes of difference — nudging engineers toward small, focused changes.

7. Takeout: four CI makeovers

Google Takeout began in 2011 as a data export product and became a platform: APIs for at least 10 other products, and 90+ product plug-ins. Each scenario leaves one reusable practice:

  • Config kept breaking dev deploys: on presubmit, spin up a temporary sandbox per customized instance and check that servers start healthy — this prevented 95% of broken servers from bad configuration and halved nightly deploy failures. End-to-end tests couldn't go into presubmit, so they moved to post-submit every two hours against an RC cut from green head, cutting the culprit set by 12×.
  • Indecipherable logs: refactor into a parameterized suite with per-item red/green and put a link that searches the logs right in each failure message — the Takeout team's involvement in debugging plug-in failures fell by 35%.
  • Testing "all of Google": most failures came from other products' backends; running the same suite continuously against production too lets you separate your new build's problems from upstream releases.
  • Never green: disable failing tests that can't be fixed now by tagging them with a bug filed to the owning team; when the bug closes and the test keeps passing, prompt cleanup of the tag. The book names the metric MTTCU (mean time to clean up).

One criterion: how fast, how stable and how high-fidelity a test is decides which slot in a change's life it belongs in.

Why it matters / real systems

The chapter redefines CI from "a tool" into a scheduling problem. Asked in an interview how to design CI for a large team, the answer isn't "run everything every time" but tiers: fast and reliable presubmit; post-submit with dependency-graph test selection, batching and automatic culprit finding; RC promotion through environments; production probers as the last line — plus a Build Cop and one-click rollback.

Industry evidence · publicly verifiable

  • Google · the book (2020): TAP handles more than 50,000 unique changes and runs more than four billion test cases a day; changes that pass presubmit empirically pass the rest 95%+ of the time, with an average submit wait of about 11 minutes; Assistant's hermetic presubmit is 14× faster. Pitfalls and debates

  • "CI = run every test on every commit" — at scale, the opposite. Google's presubmit is deliberately incomplete, trading post-submit, rollback and Build Cops for an 11-minute submit wait.
  • "When CI is red, stop the line for everyone" — this chapter is in tension with the classic view. Humble and Farley's Continuous Delivery says fix a broken build before anything else; this chapter calls blanket commit freezes "probably misguided" when the root cause is understood and production is unaffected. They agree on handling it immediately; they differ on whether to freeze everyone.
  • Retries are painkillers, not a cure. The chapter lists "allow multiple attempts" as a common tactic; Kubernetes went the other way and banned automatic retries because they hide real bugs. Which path fits depends on whether you have platform-level flake statistics.
  • Disabled tests become debt: Takeout's lesson is that disabling must carry a bug, be trackable and prompt automatic cleanup — or the suite becomes a growing pile of commented-out old tests.
  • Limits: TAP's optimistic integration rests on a monorepo, a near-real-time global dependency graph and enormous compute. The book admits that a hermetic stack for a large microservice system is very costly, and that isolating failures across upstream services (like Takeout's upstream-staging environment) remains hard.

Key takeaways

① CI's modern definition: the continuous assembling and testing of a whole fast-moving ecosystem; at its core, deciding which tests run when, against what system under test.

② Bugs cost more the later they're caught, so build fast feedback loops whose results are accessible and actionable.

③ Presubmit can't be greedy: cost, false blame from flakes, mid-air collisions. Rule of thumb: only fast, reliable tests.

④ The repo has a true head and a green head; RCs are usually cut at green, static config is tested with the RC, and artifacts aren't rebuilt across environments.

⑤ Rerun tests on the RC for sanity, audit, cherry-picks and emergency pushes; run them again on production as probers.

⑥ CI is alerting shifted left: a flaky test is a false page; chasing 100% green is as costly as chasing 100% uptime.

⑦ Hermetic tests buy determinism and isolation (Assistant: 14× faster); record/replay is a balancing act between false passes and false failures.

⑧ TAP: 50,000+ changes and 4B+ test cases a day; optimistic landing + Build Cop + rollback first + batch splitting and bisection + dependency-graph test selection.

⑨ Disable failing tests only with a bug attached, tracked and auto-cleaned — the suite stays green without forgetting known issues.
