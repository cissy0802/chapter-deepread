Write The Comments First

A Philosophy of Software Design · Ch 15 · Write The Comments First · Ousterhout · 2nd ed 2021

中文 →

What is this chapter about?

When programmers write code, they often leave short notes beside it telling the next person "what this part does and how to use it." Those notes are called comments. Most people's habit is to finish the program, get it working, and add the comments at the end — if they remember. This chapter makes one suggestion that runs against that habit: flip the order. Write the explanation first, then the code.

An analogy

Imagine you're inventing a new board game. One way is to build the board and print all the cards, then play and see. Another is to take a sheet of paper and write the rules in a few sentences. If five sentences cover it, the game is probably good. If two pages still don't make it clear, you know the rules are a mess before you've spent a cent on cards. The author says writing a program's explanation is writing that rule sheet.

Why the old way is hard

"I'll add it at the end" sounds efficient, but it's the easiest step to skip: once the program runs, people rush to the next task. Even when the notes do get written, the reasons behind the design are half forgotten by then, so the notes just read the code back aloud, which helps no one. Worse, the explanation could have exposed a design flaw — but written last, the flaw is already built into the walls.

How it works, intuitively

  • Write the sign on the door first. When building a new part, first write what it's for as a whole; then, for each thing it offers, write a line on "how to use it and what you get," leaving the insides empty.
  • Check whether it reads smoothly. If the explanation flows, keep the structure; if it's awkward, change the structure now, while a change is just a few sentences and costs almost nothing.
  • Fill in the insides last. If you realize halfway that you need a new piece, write its sign first, then build it.
  • Getting stuck is an alarm. If something just won't explain simply, it's like the canary that faints first in a coal mine: a warning that the thing itself is designed to be too complicated.

What you get / how to choose

The moment the code is done, the explanation is done too — and it's better, because it was written while your thinking was clearest. The author even says this turns comment-writing into one of the most enjoyable parts of design. One honest cost: when you change your mind mid-design, the early notes have to change with it, which takes some discipline.

One line to remember

Explain first, code second: if the explanation flows, the design is probably right; if it doesn't, fix the design first.

One line

You think comments are "documentation work" done after the code; Ousterhout says comments belong inside the design process. Write the interface comments before the code and they stop being an after-the-fact chore and become a design tool: if something's comment won't come out simple, the thing itself is usually badly designed.

Glossary

  • Comment: text inside the code meant for humans, not executed by the machine.
  • Interface comment: written at a class or method declaration; tells callers how to use it and what happens, not how it works inside.
  • Implementation comment: written inside a method; explains what a piece of code does and why.
  • Signature: a method's name, parameters and return type — only the skeleton of its interface.
  • Instance variable: a data field an object keeps for its whole life.
  • Abstraction: a simplified view that keeps only what users need and hides the rest.
  • Deep module: the core idea of Chapter 4 — a simple interface over a lot of functionality; the opposite is a shallow module.
  • Red flag: the book's recurring warning signs of design trouble.

The problem this chapter solves

Chapter 12 knocked down the excuses for not commenting, but a practical problem remains: even when everyone agrees to write them, comments still often come out poor. The author observes that many developers put documentation off until the end, after coding and unit testing are done. He considers this one of the surest ways to get low-quality documentation:

  • Often it never happens. Once the code runs, people move on; the backlog of unwritten comments grows, and the bigger it gets, the less anyone wants to touch it.
  • When it does, it misses the point. By then the design decisions have faded, so the author can only look at the code and describe the code — exactly the "repeat the code" comments Chapter 13 criticizes.
  • It wastes the most valuable use. Comments could expose problems during design; written afterwards, those problems are already hundreds of lines of implementation.

The chapter asks: where in the development process should comments be written so that they are good and also improve the design?

Core ideas, in depth

1. The author's order: comments before bodies

The book describes how the author writes a new class:

  • First the class interface comment: what abstraction the class provides as a whole;
  • Then the interface comments and signatures of the most important public methods, with empty bodies;
  • Iterate at this level until the basic structure "feels right";
  • Next, declarations and comments for the most important instance variables;
  • Only then fill in the method bodies, adding implementation comments as needed;
  • If writing a body reveals a need for a new method or variable, again write its interface comment before its implementation.

The direct result: when the code is done, the comments are done too, with no backlog. Note it is not "write a complete document, then start coding" — comments and code advance together; it's just that for every new interface the words come before the implementation.

2. Benefit one: better comments

Writing first, the author's head is full of abstractions and design intent, not implementation details, so interface comments naturally describe "what this is and how to use it" rather than restating code. That is exactly the kind Chapter 13 asks for: a level above the code, supplying intuition the code can't express. Write them last and you are steeped in details; climbing back to that level is hard.

3. Benefit two (the most important): comments are a design tool

The author calls this the biggest payoff of commenting first. As Chapter 12 argued, comments are the only way to fully capture an abstraction: a signature is just a skeleton; parameter meanings, side effects and preconditions live in the comment. So writing an interface comment means writing down the abstraction and seeing whether it holds up.

Hence the chapter's red flag, Hard to Describe: the comment for a method or variable should be simple and yet complete; if you struggle to write such a comment, the thing you're describing may have a design problem. Typical signs:

  • The interface comment is long and convoluted: callers must know too much, so the interface is probably shallow;
  • The comment has to explain implementation details for people to use it correctly: information has leaked into the interface;
  • The comment is a chain of "if… then… unless…" special cases: maybe Chapter 10's trick of defining them out of existence applies.

The author likens comments to the canary in the coal mine of complexity: miners carried canaries because the birds succumbed to gas first. When a comment won't flow, the design is raising an early alarm, and fixing it now costs a few lines of prose and a signature. This also makes Chapter 11's "design it twice" practical: write the interface comment for each candidate; the one that comes out shorter and smoother is usually the deeper one.

CS Papers · Parnas 1972 · On Decomposing Systems into Modules — the origin of information hiding: each module hides one design decision and its interface exposes only what it must, which is exactly the abstraction an interface comment writes down

4. Benefit three: early comments are fun

The author admits he enjoys this stage: commenting first means thinking about the overall shape of the system, the most creative part of design, whereas retrofitting comments is a chore done under duress. Once comments stop being a debt and become the design itself, the attitude changes too.

5. Are early comments expensive?

The usual worry is "no time." The author offers a rough estimate: typing code and comments is only a small fraction of total development time, most of which goes to thinking, debugging and understanding; even if comments are half of what you type, writing them probably accounts for around 10% of total development time. In return you get better designs and less misuse and debugging, so he believes the investment likely saves time overall.

The other worry is "the design will change and I'll have to rewrite them." His answer: comments written first evolve with the design, updated as you change it; it's retrofitting at the end that creates a pile of work requiring you to reconstruct everything from memory.

The chapter also invites a comparison with test-first development (TDD, test-driven development: write a failing unit test, then the code). Both put "something before the implementation," but different things:

Table 2 · Comments first vs tests first

DimensionComments first (Ousterhout)Tests first (TDD)
What comes firstThe abstraction: what this class / method is and how to use itA test case for one specific behavior
Unit of workA class, or a group of related methodsOne test, often a few lines of code

Rule of thumb: the more public the interface and the harder the boundary is to change later, the more it pays to comment first; a small helper used once inside one function can have a very short interface comment, but the order still holds.

Why it matters / in real systems

The idea recurs at every scale: "interface comment first" for a method, "design doc first" for a project, "press release first" for a product. The common thread is testing an idea with prose that must be clear before investing in an implementation.

Industry evidence · publicly verifiable

  • Ousterhout vs Robert C. Martin, a written debate: the two argued publicly over method length, comments and TDD. Ousterhout's summary: without interface comments, interface specifications are incomplete, which is guaranteed to result in confusion and bugs; he estimates the cost of missing comments is easily 10–100× that of incorrect ones. Martin holds that every comment is a failure to express intent in code — "a necessary evil." On testing, Ousterhout proposes writing code in units of a few methods or a class and then its tests (both agreed to call this "bundling"), precisely so that development centers on design rather than tests. Source: GitHub · johnousterhout/aposd-vs-clean-code
  • The Go proposal process: notable changes to the language, libraries and tools go through proposals; those needing elaboration get a design doc from the author, and implementation follows once review comments settle — "explain it in prose before writing code," made into community policy. Source: GitHub · golang/proposal
  • Amazon's "Working Backwards": Amazon CTO Werner Vogels describes starting a new product by writing the customer-facing press release and FAQ; if it can't be written clearly, work doesn't start — "comments first" at product scale. Source: Werner Vogels, All Things Distributed blog, "Working Backwards," 2006 (site unreachable from this run; text citation only)

Day to day: when reviewing a new class, read only its interface comments first — can you tell in a minute what it offers? Before building, share the key methods' comments and signatures as a draft; reviewing that is far cheaper than reviewing hundreds of lines of implementation. When handing a task to an AI coding assistant, writing the function's interface comment first and letting it fill in the body follows the same logic.

Pitfalls and debates

  • "Comments first = waterfall, a full document up front." No. The author works class by class, alternating comments and code, with words first for each new interface; no complete design is required in advance.
  • "Early comments go stale, so skip them." Early comments change along with the design; Chapter 16 covers maintaining comments while modifying code.
  • "Comments first means implementation comments first." What comes first is mainly the interface comment; implementation comments are added as needed while writing bodies.
  • "If I can't write the comment, it's a writing problem." The author says the opposite: usually it's a design problem — that's what the "Hard to Describe" red flag is for.
  • The evidence is experiential. The benefits come mainly from the author's own and classroom experience, with no controlled study; the 10% is a rough estimate. The debate with the TDD camp is unresolved, and the author simply suggests trying it for a while before judging.

Key takeaways

① Comments left to the end almost guarantee poor documentation: often skipped, and when written, they restate the code.

② The author's order: class interface comment → key methods' comments and signatures (empty bodies) → instance variable comments → bodies; new methods get their comment first too.

③ Result: when the code is done, the comments are done; no backlog.

④ Benefit one: written while design intent is clearest, comments describe abstractions, not implementation.

⑤ Benefit two (the biggest): comments are a design tool, the canary of complexity; red flag "Hard to Describe" — if a comment can't be simple and complete, the design has a problem.

⑥ Benefit three: early comments are part of design, and fun to write.

⑦ Cost: writing comments is roughly 10% of total development time (the author's rough estimate), in exchange for better designs.

⑧ Versus TDD: what comes first is an abstraction, not a single test; the two can be combined.
