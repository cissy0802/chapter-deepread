Critique：Google 的代码评审工具

Software Engineering at Google · Ch 19 · Critique: Google's Code Review Tool · Caitlin Sadowski, Ilham Kurnia, Ben Rohlfs · 2020

EN →

这一章讲什么？

程序员改了代码，不能直接放进公司的总仓库，得先让一位同事看过、点头。这一步叫「代码评审」。你用过的 GitHub、公司里的各种「提交请求」，都是干这件事的工具。这一章讲 Google 内部最受欢迎的那一个——Critique：它没讲「怎么评审」，讲的是一个好用的评审工具长什么样。

先说个怪事

Critique 加过的功能里，被用户夸得最狠的，不是什么高科技，而是把「现在该谁动手」的名字加粗。上线后大家都想不起以前是怎么过的——以前要靠互相发消息问「这个改动卡在谁那儿」。

旧世界为什么难

评审像几个人传阅一份合同：作者寄出去，几位审阅人各自批注，作者改完再寄回来，来回好几轮。麻烦在于：谁也说不清现在球在谁脚下；批注里哪些是「必须改」、哪些是「随口一提」分不清；机器能查出的小毛病（多了个空格、格式不对）也要人来挑；最后到底算不算「通过」，也没个明确的信号。几万人每天传阅几万份合同，这些小摩擦加起来就是巨大的时间浪费。

核心机制直觉

  • 先让机器过一遍：作者一上传改动，各种自动检查就跑起来，挑出的毛病直接标在改动旁边，常常还附带「一键修好」。人来看时，琐碎问题已经清掉了。
  • 批注分两种颜色：「必须处理」和「仅供参考」。审阅人先写完一整轮，再一次性发出去，像寄一封完整的信，而不是想到一句发一句。
  • 球在谁脚下，名字就加粗：每个改动都记着「现在在等谁」。你打开首页，第一栏就是等你处理的那些，别的可以放心不看。
  • 只有「同意」，没有「否决」：审阅人要么点头，要么写下具体哪里要改。不允许只扔一个「不行」却不说为什么。点头、该批的人都批了、必须处理的批注清零——页面就变绿，可以提交。

带来了什么 / 该怎么选

换来的是：大多数改动只要两个人达成一致就能进库，速度快；几年后有人想知道「这行代码当初为什么这么写」，翻出当年的评审记录就有答案。诚实的代价是：它和 Google 内部的代码仓库、编辑器、检查工具绑得太紧，外面根本用不了——Google 自己做开源项目时，用的是另一个工具。

一句话记住

好的评审工具不替人沟通，它只做三件事：让机器先挑小毛病、让人一眼看出该谁动手、让「能不能提交」变成一个清清楚楚的绿灯——剩下的，交给同事之间的信任。

一句话

你以为评审工具的价值在于「功能多、流程严」，本章说恰恰相反：Critique 赢在克制——工具不发明沟通协议，只把评审流程里「该谁动手、还差什么、机器已经查出什么」变成一眼可读的状态，信任和沟通仍由人负责。

Glossary · 术语表

  • 代码评审（code review）：代码合入主干前，由作者以外的人检查一遍改动。
  • 改动 / 变更（change, CL）：一次待提交的代码修改，Google 内部叫 changelist。
  • diff（差异）：把改动前后两个版本逐行对比、标出增删的视图。
  • 快照（snapshot）：作者某一时刻上传的改动版本；评审中每改一轮就多一个快照。
  • 静态分析（static analysis）：不运行程序、只读代码就找出问题的自动检查，linter 是其中一类。
  • 提交前检查（presubmit）：提交或送审前自动运行的钩子，比如跑测试、检查格式。
  • 单体仓库（monorepo）：全公司代码放在同一个仓库里；Google 的叫 Piper。
  • 代码所有权（ownership）：每个目录有指定的负责人，改它要经负责人批准。

坐标

Part IV「工具」第四章，是 Ch9「代码评审」的工具篇：Ch9 讲流程与文化，本章讲承载它的系统。它上接代码搜索（Ch17）与构建（Ch18），下引静态分析（Ch20）和大规模变更（Ch22）。现实对应：GitHub Pull Request、GitLab Merge Request、Gerrit、Phabricator。

这章要解决什么

评审流程本身 Ch9 已立好：每个改动至少一人看过、所有者批准、可读性达标。但流程写在纸上不等于跑得顺。Google 几万名工程师每天产生大量改动，大多数小于 100 行，却也有涉及成百上千个文件的大规模重构。如果工具慢、状态不清，每个改动都会在「等谁」「还差什么」上空转。

本章结论里有一句很直白：花在评审上的时间，就是没花在写代码上的时间。评审工具处在每一次提交的关键路径上，任何摩擦都要乘以全公司的改动数。所以工具要解决的不是「能不能评审」，而是：作者能否在送审前自己发现问题、审阅人能否快速看懂改动、双方能否随时知道下一步、「能提交」的条件能否被一眼判定。

核心内容，讲透

一、四条设计原则：简单压倒一切

Critique 的设计受 Google 评审文化塑造，归成四条原则：

  • 简单：界面加载快、少做选择、支持快捷键、整体评审状态有清晰的视觉标记。
  • 信任为基础：评审不是为了拖慢别人，而是赋能别人。比如信任作者会改好小问题，不再设一轮复核；改动对全公司公开可看、可评。
  • 通用沟通：作者直言「沟通问题很少能靠工具解决」，所以优先提供通用的评论方式，鼓励把要求写清楚、甚至直接给出修改建议，而不是把数据模型和流程搞复杂。
  • 工作流集成：能一键跳到代码搜索、网页编辑器、测试结果。

其中简单影响最大：很多有意思的功能被否决，理由是不愿为一小撮用户让模型变复杂。简单与集成之间也有张力：团队考虑过做一个集编辑、评审、搜索于一体的「Code Central」，最终放弃——功能从 Critique 链出去，在各自的子系统里实现，评审始终是唯一主角。

二、六个阶段，工具各补一刀

Critique 评审发生在提交之前（precommit）。典型流程：①创建改动、上传快照，自动触发分析器；②作者满意后发给审阅人；③审阅人评论；④作者修改、回复，③④反复多轮；⑤审阅人给出 LGTM；⑥作者提交，presubmit 全过则入库。流程也留了口子：审阅人可以把改动转给别人，作者可以搁置，紧急时还能先强制提交、事后补评审。

每推进一个阶段，Critique 都发布事件通知，别的工具订阅这些事件来做事：一个 Chrome 扩展在轮到你时弹窗；邮件系统发通知，还能把邮件回复转成评论。这是关注点分离——Critique 只负责发事件，其余系统自己在上面搭。作者也坦白：有人爱即时弹窗，也有人嫌打断心流而不装。

三、送审之前：让作者先戴上审阅人的帽子

改动越大越难懂，所以优化 diff 是评审工具的核心需求。Critique 的 diff 以优化过的最长公共子序列算法为底，再叠加：语法高亮、由 Kythe 提供的跨引用跳转、按词边界的行内字符级 diff、可调的忽略空白，以及移动检测——一段代码挪了位置会被标成「移动」，而不是朴素算法那样「这里删、那里加」。为让并排 diff 放得下 Java 每行 100 字符，界面去掉了边框和内边距。文件级还能拖拽选任意两个快照对比，所有快照都预取。

关键一招是：作者看到的就是审阅人将看到的，包括 diff 和自动分析结果，还能在工具里做轻量修改、附上预先的说明、关联 bug。先自己当一回审阅人，送出去的改动更干净，也少误会。

四、分析结果：可操作性只有「是 / 否」两档

每上传一个快照，就触发静态分析（Ch20 的 Tricorder）。结果以状态小方块（chip）挂在改动描述下：分析器可把某条发现标红以示醒目，仍在运行的显示黄，其余是灰。为了简单，不提供任何其他标记或高亮方式——可操作性是二元的。发现像评论一样嵌在 diff 里，但样式不同；很多还附带修复建议。书里的例子：linter 发现行尾多余空格，作者两次点击就看到问题代码，再点一次预览修复，再点一次应用。

贵的检查放在别处：跑测试耗资源，所以放进 presubmit（送审时、提交时各跑一次），而不是像静态分析那样每个快照都跑。presubmit 失败会被显著标出、阻止送审或提交，并邮件通知作者。常见的 presubmit 还包括自动抄送邮件组、强制项目的代码风格和改动描述格式。

五、找审阅人：规模大了这本身就是难题

小团队里找人看似简单，也要考虑负载均衡和谁在休假。团队可以给评审设一个邮件别名，由 GwsQ（得名于最早使用它的 Google Web Server 团队）按配置挑出具体的人。跨项目时更难，Critique 会推荐一组足以批准该改动的审阅人，考虑四个因素：谁拥有被改的代码、谁最近改过（最熟悉）、谁有空（没休假、最好同时区）、团队的 GwsQ 配置。这对动辄波及大量文件的大规模变更尤其重要。

六、评论：默认「未解决」，整轮发布

评论是用户在 Critique 里仅次于看改动的第二常见动作，而且谁都能评——不只作者和指定审阅人，路过的人也可以留下「顺路评审（drive-by review）」。

  • 两种状态：评论默认是未解决（unresolved），表示作者必须处理；审阅人也可以写已解决的评论，表示可选或仅供参考。作者处理时点 Done（改了）或 Ack（看到了），都会把线程置为已解决。
  • 整轮原子发布：评论边看边起草，看完整个改动后一次性发布，让审阅人表达一个完整的想法，而不是想到一句发一句。
  • 从发现到评论一键：审阅人看到相关分析发现，点「Please fix」就生成一条未解决评论；也能直接在线编辑文件给出修改建议，作者可一键应用。
  • 个人进度：审阅人可逐文件勾「已看」；作者一旦改了某文件，所有人对它的勾都被清掉。

七、注意力集合：「该谁了」是最值钱的一个比特

一个改动常有多位审阅人——工程师、负责该功能的 UX、背着寻呼机的 SRE。Critique 为每个改动维护一个注意力集合（attention set）：改动当前卡在哪些人身上。在集合里的人要及时响应，名字在界面上加粗。用户发布评论时 Critique 会尽量聪明地更新它，用户也能手动调整。

上线后用户「很难想象以前的样子」，普遍反应是：没有它我们以前怎么过的？此前只能靠作者和审阅人互相聊天确认谁在处理。它也凸显了评审的回合制本质：任何时刻总有至少一个人该行动。配套的是首页仪表盘：由 Changelist Search 驱动，它索引全公司所有改动（提交前与提交后）的最新状态，支持正则查询；每个分区就是一条查询，默认第一栏是「需要你处理的」。作者说别处尽量不给自定义，但仪表盘允许——就像每个人整理邮箱的方式都不同。

八、打分：LGTM、Approval、未解决评论数

Google 把「能否提交」拆成三部分：

  • LGTM（looks good to me）：「我看过，它符合我们的标准，处理完未解决评论后可以提交。」
  • Approval：「作为把关人，我允许它进入代码库。」（对应 Ch9 的所有权等批准。）
  • 未解决评论数。

规则：至少一个 LGTM + 足够的 Approval + 零未解决评论 = 可以提交，页面顶部变绿。注意无论 Approval 如何，每个改动都需要一个 LGTM，保证至少两双眼睛看过。LGTM 和 Approval 是硬条件，只有审阅人能给、提交前随时可撤回；未解决评论是软条件，作者回复时自己就能标为已解决。

这套方案是刻意简化的结果：早期 Critique 有「Needs More Work（需要返工）」和「LGTM++」两档，后来改成 LGTM / Approval 永远是正面信号。要求第二轮评审就只留评论、不给 LGTM；改动基本没问题后，审阅人信任作者处理小修改，工具不要求反复 LGTM，无论改动多大。它还改变了文化：审阅人不能只投反对票而不给有用反馈，所有负面意见都得落到一个具体要修的东西上；连「未解决评论」这个说法都是特意挑的，听起来比较客气。软条件则体现信任：审阅人可以「LGTM + 几条未解决评论」，事后不再逐条核对——作者和审阅人时区差很大时，这能省下整整一个来回。

提交之后，Critique 还是改动考古工具：全公司都能浏览一般可见文件的改动历史、评论与演化，用来理解「为什么这么改」「bug 怎么引入的」；提交后也能继续评论、回滚。

为什么重要 / 落到真实系统

评审工具常被当成「装了就行」的基础设施，本章给了一套评估判据：能不能一眼看出该谁动手、能不能一眼看出还差什么、机器能查的有没有在人看之前查掉、diff 能不能识别移动。架构评审里讨论「要不要给 PR 加一道必审规则」，也可以借本章的区分：哪些是硬条件（谁有权放行），哪些是软条件（信任作者）。

易错点与争议

  • 「好工具能解决评审里的沟通问题」——作者明说不能。工具能增强体验，替代不了信任和沟通；用户是人，再好的工具也会沟通出岔子。
  • 「没有否决票 = 没法挡住坏改动」——不对。不给 LGTM / Approval 就挡住了；变的只是挡的方式：必须附上具体要修的东西。
  • 「LGTM 和 Approval 是一回事」——不是。LGTM 说「质量过关」，Approval 说「我作为把关人放行」；每个改动都需要 LGTM，Approval 按所需权限另算。
  • 局限与时代背景：Critique 只在 Google 内部存在，书中细节无法外部验证，也不能直接照搬——它的「一键进编辑器」依赖云端工作区和单体仓库。软条件依赖高信任文化，在信任薄弱或合规要求严格的环境里，团队往往会要求逐条复核。

要点

① 流程定好了还不够，工具决定流程跑得顺不顺：评审在每次提交的关键路径上，摩擦乘以全公司改动数。

② 四条原则里「简单」影响最大：宁可不做小众功能；功能链出去，不做一体化 Code Central。

③ 送审前让作者看到审阅人将看到的：diff 带行内字符级对比、移动检测、跨引用，加上自动分析结果。

④ 分析结果的可操作性是二元的（红 / 不红），常附一键修复；贵的测试放 presubmit，不每个快照跑。

⑤ 评论默认「未解决」，整轮原子发布；Done / Ack 一键解决；谁都能顺路评审。

⑥ 注意力集合把评审变成回合制，「该谁了」加粗显示，是用户口中「以前怎么过的」那个功能。

⑦ 可提交 = ≥1 LGTM + 足够 Approval + 零未解决评论；前两者是硬条件，后者是软条件，体现信任。

⑧ 评分只有正面：负面意见必须落成具体可修的评论。Gerrit 则相反，有 -2 否决、高度可配置，适合开源与异质环境。
