不同层，不同抽象

A Philosophy of Software Design · Ch 7 · Different Layer, Different Abstraction · Ousterhout · 2nd ed 2021

EN →

这一章讲什么？

大一点的软件都是一层叠一层搭起来的，就像你在手机上存一张照片：你只看到「一个文件」，下面有一层在管「内存里的缓存块」，再下面一层在跟存储芯片打交道。每一层讲的「话」都不一样。这一章的主张很简单：每一层都该提供一种跟上下邻居不同的东西；如果相邻两层讲的是同一种话，多出来的那层多半是白搭的。

先说个怪事

有一种代码，打开一看，里面一个方法只有一行：把收到的请求原封不动地转给另一个零件。就像公司里一个职位，老板交代的事他一字不改转给下属，下属的回复他再一字不改转回老板。多了一个人，事情没多做一点，沟通却多了一层。更怪的是，这种代码常常被当成「分层清晰」的好设计。

旧世界为什么难

「分层」听起来天然是好事，于是很多人见到问题就加一层：加一个包装、加一个转手的类、把某个设置一路从最上面传到最下面。每一层单看都很整齐，合起来却是一长串只会转手的环节。读代码的人要穿过好几层才能找到真正干活的地方，改一个东西要同时改好几处。

核心机制直觉

  • 每一层换一种说法。好的分层像翻译接力：最上面说「文件」，中间说「一块块的数据」，最下面说「芯片上的位置」。每换一层，复杂的细节就被藏掉一些。
  • 只会转手的环节要清理。要么让上层直接找真正干活的那层，要么把活重新分一分，让每层都真有事干，要么干脆把两层合成一层。
  • 「包一层」要慎重。给一个零件外面套一个壳子加点小功能，壳子得把原零件的每个按钮都再转一遍，往往得不偿失。能直接把功能加进原零件，就别套壳。
  • 一路传到底的「口信」换个放法。一个设置从顶层一路传到底层，中间每一层都不用它却都得经手。更好的办法是放进一个大家都能拿到的「公共柜子」，谁要用谁去取。

带来了什么 / 该怎么选

判断一层值不值得存在，只问一句：它有没有替别人挡掉一些麻烦？挡掉了，就值；只是转手，就是负担。一句诚实的代价：那个「公共柜子」也有毛病，什么都往里放，最后谁依赖了什么就看不清了。

一句话记住

每一层都该换一种说法；只会转手的层、只会套壳的包装、一路经手的口信，都是在给系统加负担。

一句话

你以为层数多 = 结构清晰，Ousterhout 说层的价值只取决于它换了多少抽象：设计良好的系统里，每一层都提供一种不同于上下邻居的抽象；一旦相邻两层抽象相似，就说明分解出了问题。直通方法、直通变量、浅装饰器，都是这个问题的症状。

Glossary · 术语表

  • 层（layer）：系统按调用关系叠起来的一级，上层调用下层的接口，下层不知道上层存在。
  • 抽象（abstraction）：对某样东西的简化视图，只露出重要的部分、藏掉细节；比如「文件」就是对磁盘块的抽象。
  • 深模块 / 浅模块：第 4 章的概念——接口简单而功能强大叫「深」；接口和它提供的功能差不多复杂叫「浅」。
  • 方法签名（signature）：方法的名字加上参数和返回值的类型。
  • 委托（delegation）：一个对象把调用转交给它持有的另一个对象去完成。
  • 装饰器（decorator）：一种设计模式，用一个对象包住另一个同类对象，接口不变，额外加一点功能。
  • 分发器（dispatcher）：根据请求的内容，挑一个合适的处理函数把请求转过去的代码。
  • 全局变量（global variable）：整个程序任何地方都能直接读写的变量。
  • 线程安全（thread safety）：多个线程同时访问同一份数据时不会出错。

坐标

全书第 7 章。前三章（深模块、信息隐藏、通用接口）都在看单个模块；这一章把视线转到层与层之间，下一章「把复杂度向下沉」接着讨论复杂度该落在哪一层。现实里对应每一次「要不要再包一层 / 再加一个 Service 类」的评审。

这章要解决什么

分层是软件工程最古老的工具之一，经典例子作者在开篇就摆出来：文件系统最上层提供「文件」（一个可变长的字节数组），中间一层是「内存里的定长磁盘块缓存」，最下层是设备驱动，负责在存储和内存之间搬块；TCP 提供「可靠送达的字节流」，下面那层只能「尽力而为」地在机器间发长度有限的包。每往上一层，抽象就变一次，复杂度就被吸收一部分。

问题在于，「分层」太容易被当成目的本身。很多代码库里能数出五六层：Controller、Service、Manager、Repository、DAO……但其中好几层只是把同一个调用换个名字再往下传。每一层接口都要人去读、去记、去维护，而它没替任何人挡掉复杂度。本章要给出识别这种「假分层」的信号，以及怎么修。

核心内容，讲透

一、直通方法：只转手、不干活

直通方法（pass-through method）指一个方法几乎什么都不做，只是用相同或相近的签名去调用另一个方法。作者展示了一个 GUI 文本编辑器里的 TextDocument 类：它持有一个 TextArea，好几个公开方法（如取光标位置、插入字符串）的方法体只有一行——把调用原样转给 TextArea。

它为什么是坏信号？直通方法让类变浅：接口变宽了，功能一点没增加；它还在两个类之间制造依赖——TextArea 的签名一改，TextDocument 得跟着改。更根本的是它暴露了职责划分混乱：两个类到底谁负责什么说不清。作者把它列为红旗：Pass-Through Method。

修法有三种（书中配图同时画出了原始状态）：

  • 暴露下层：让调用方直接拿到下层对象去调用，删掉中间的转发。
  • 重新分配职责：把功能在两个类之间重划一遍，让每个类都有清楚、不重叠的职责，转发自然消失。
  • 合并：如果两个类本来就分不开，就合成一个类。

二、接口重复什么时候没问题

签名一样不等于有罪。判据是：每个同签名的方法是否提供了有用且不同的功能。两个合理例子：一是分发器——Web 服务器收到请求，按 URL 选一个处理函数转过去，它的签名常和处理函数一样，但「选哪个」本身就是实打实的功能；二是同一接口的多种实现——操作系统里各种磁盘驱动提供同一套接口，各自实现不同，这降低了上层的认知负担：学会一套接口就能用所有设备。

三、装饰器：天生容易浅

装饰器用一个对象包住另一个对象，接口一模一样，再加一点功能。书里的例子是 Java I/O：BufferedInputStream 包住 FileInputStream，给它加上缓冲。动机正当——把特殊扩展和通用核心分开——但代价是：为了加一个小功能，装饰器要把底层的每个方法都直通一遍，大量浅方法由此而生；而且装饰器类容易泛滥，每种组合都要调用方自己去拼。

作者给了四个先问的问题：能不能直接把功能加进底层类（比如缓冲本就该是默认行为）？如果功能只服务某个场景，能不能合进那个使用场景？能不能合进已有的某个装饰器？最后，这个功能真的需要包住底层吗——能不能做成独立的类？比如给窗口加滚动条，滚动条可以单独实现，不必把窗口的所有方法都包一遍。

四、接口要和实现长得不一样

同一个原理落到单个类上：类的接口通常应当和它的内部实现不同。若内部按「行」存文字，接口就照搬成 getLine / putLine，那么上层要在行中间插入或删除时，就得自己拆行、拼行——实现细节被原样推给了调用方，类是浅的。换成面向字符的接口（在任意位置插入、删除一段范围），类内部多做了按行映射的活，但上层省掉了大量拆拼代码。接口和实现越像，这个类越可能是浅的。

五、直通变量与上下文对象

直通的另一种形态是直通变量（pass-through variable）：一个值从顶层方法开始，经过一长串方法一路往下传，中间那些方法都不用它，只是为了让最底下那个方法拿到。书中例子：命令行参数里指定了安全通信要用的证书，main 读到它，经 m1、m2 一路传到真正打开连接的 m3。坏处是中间每一层都被迫知道它的存在；哪天要新增一个这样的变量，整条链上每个签名都要改。

三种解法：若顶层和底层已经共享某个对象，就把变量放进那个对象；用全局变量，但这会让同一进程里无法跑两个独立的系统实例（比如测试时）；作者最常用的是上下文对象（context）——存放一个系统实例的全局状态（配置项、共享子系统、性能计数器），每个系统实例一份，大多数对象在构造时拿到它的引用、存进自己的成员变量，于是新增一项全局状态只需要往 context 里加个字段。

作者也承认 context 不完美：没有纪律时，它会变成一个什么都往里扔的大杂烩，制造不明显的依赖；多线程下还有并发问题，所以他建议 context 里的变量尽量不可变。但他说自己还没找到比它更好的办法。

六、收束：每件设计基础设施都要挣回自己的成本

本章结论可以压成一句：系统里每加一个设计元素——接口、参数、函数、类、定义——都在增加复杂度，因为开发者得去学它；它要带来净收益，就必须消掉一些本来会存在的复杂度。直通方法、直通变量、浅装饰器的共同点，是它们增加了要学的东西，却没消掉任何东西。

为什么重要 / 落到真实系统

后端项目里最常见的反模式就是按模板分层：每个实体都配一套 Controller → Service → Repository，Service 里一半方法只是 return repo.findById(id)。评审时可以直接用本章的问题去戳：这一层换了抽象吗？它替调用方挡掉了什么？反过来，也别矫枉过正——一层如果承载了事务边界、权限校验、跨实体编排，那它确实提供了不同的抽象，签名相似也不算直通。

实证与出处 · 公开可查

  • Go 的 bufio：装饰器的标准样子。官方文档写明 bufio「包住一个 io.Reader 或 io.Writer，创建另一个同样实现该接口、但提供缓冲的对象」。它之所以不浅，是因为 io.Reader 只有一个方法——装饰一个单方法接口几乎没有直通成本；同样的手法放到几十个方法的类上，就是本章说的浅装饰器。出处：pkg.go.dev · bufio
  • Go 的 context：一个反着来的设计选择。官方文档要求「不要把 Context 存进结构体，而是显式地传给每个需要它的函数」，并作为第一个参数；同时限定「context 的 Values 只用于跨进程和 API 的请求范围数据，不要用来传可选参数」。这恰好是 Ousterhout 推荐做法（构造时存进成员变量）的反面：Go 宁可接受直通变量，换来依赖显式可见和按请求取消——也印证了作者自己说的，context 一旦当杂物箱用就会出问题。出处：pkg.go.dev · context
  • Java I/O：书中的装饰器反例。打开文件并按对象读取，需要先建 FileInputStream、再包 BufferedInputStream、再包 ObjectInputStream；缓冲这种几乎人人都要的功能被做成了要手动套上的装饰器。出处：Ousterhout，A Philosophy of Software Design，第 4、7 章
论文精读 · End-to-End Arguments in System Design — 同一问题的另一个角度：一项功能放在哪一层才真正有价值，放错层就只是重复劳动

易错点与争议

  • 「签名相同就是直通」。不对。分发器、同一接口的多种实现都签名相同但各有功能。看的是有没有增加有用的、不同的功能。
  • 「层越多越解耦」。没有新抽象的层不解耦，反而让一处改动传遍多层（改一个签名，转发链上每层都要改）。
  • 「装饰器模式是最佳实践」。它是工具不是目标。为加一个小功能去包一个大接口，通常应先考虑直接加进底层类。
  • 「context 解决了一切」。作者自己说它不理想：依赖变隐式、容易膨胀、有并发风险。它是「直通变量更糟」时的次优解。
  • 争议：显式传参 vs 隐式上下文。Go 官方选择显式传 context，理由是可读、可取消、可测试；依赖注入框架和「请求作用域」则走隐式路线。两派都同意一点：别让无关参数无限往签名里加，分歧在于可见性和便利哪个更值钱。新手要警惕的是另一个方向：把「删掉直通层」当成合并一切的借口，做出一个什么都管的巨类。

要点

① 好系统里每一层都提供一种不同于邻居的抽象；相邻层抽象相似是分解出错的信号。

② 经典正例：文件系统（文件 → 块缓存 → 驱动）、TCP（可靠字节流建在尽力而为的包之上）。

③ 直通方法让类变浅、制造跨类依赖；修法是暴露下层、重分职责或合并。

④ 签名重复不一定有罪：分发器、同一接口的多种实现都各自提供了功能。

⑤ 装饰器天生容易浅：先问能否直接加进底层类、并入使用场景、合进已有装饰器或做成独立类。

⑥ 类的接口应当和实现不同；照搬内部表示的接口是浅的。

⑦ 直通变量的去处：共享对象、全局变量、上下文对象；context 最常用，但要防膨胀、字段宜不可变。

⑧ Go 的 context 反其道而行（显式传参），说明这是可见性与便利之间的真实权衡。

⑨ 总判据：每个设计元素都要消掉比它带来的更多的复杂度，否则就是负担。
