Software Engineering at Google · Ch 15 · Deprecation · Hyrum Wright · 2020

中文 →

What is this chapter about?

You've probably seen a notice like this: "This old version of the app will stop working next month — please upgrade." Inside big companies the same thing happens constantly, except the thing being retired is a program: an old system has been replaced by a new one, but hundreds of other programs still rely on it. This chapter is about how to switch off something everyone is using without dragging everyone down with it.

An analogy

A city builds a new bridge. The old one is crumbling and still costs money to maintain every year. So the city hangs a sign at the old bridge: "Please use the new bridge." What happens? Most new drivers take the new bridge — the regulars keep taking the old road. Habit, and the old route is saved in their navigation. The old bridge spends year after year "about to be torn down," and never is.

Why the old world was hard

Taking something away is harder than building it. The more people use it, the more of them depend on it in ways you never imagined: a trucking company sends its lorries over the old bridge because the new one has a lower height limit. However good the new bridge is, it is never exactly the same, so every old user has to be checked again. Some people are attached to it — they built it. Worst of all, demolition costs visible money, while the cost of leaving it alone is invisible, so nobody wants to pay for it.

The core intuition

  • A sign isn't enough: reminders stop newcomers but don't move the regulars. If you really mean to remove it, set a deadline and stick to it.
  • Send a dedicated moving crew: don't make every household move itself — everyone will stall. The team tearing down the bridge comes round and reroutes people; the more moves they do, the better their tools and know-how get.
  • Close the bridge a few times first: before demolition, shut it for half a day, then a day, then a week, and see who shouts "I still need it!" That's how you find the people who didn't even know they were using it.
  • Block new roads to the old bridge: no new roads may lead to it — otherwise one household moves out and another moves in, and you never finish.

What it buys you / how to choose

Removing a redundant bridge saves the upkeep, and the new bridge no longer has to match the old one's specs, so it can be upgraded freely. But don't close every road in town at once — take down a few bridges at a time, and finish each one. The honest cost: this needs dedicated people for months, and often nobody gives you credit, because on the day it's finally gone, no one is using it anymore.

Remember it in one line

Code is a liability, not an asset: turning off an old system takes an owner, a deadline and a moving crew — "please use the new one" alone never gets it switched off.

In one line

You think deprecation means slapping @deprecated on an old API and waiting for users to leave. The chapter says that almost never works: code is a liability; functionality is the asset. Turning off a widely depended-on system is an engineering project that needs an owner, a deadline, a dedicated migration team and tooling — and it is best considered when the system is first designed.

Glossary

  • Deprecation: the whole process of migrating users off an obsolete system in an orderly way and eventually removing it — not just a "deprecated" label.
  • Turndown / removal: the end point of deprecation — actually shutting the service off or deleting the code.
  • Dependency and transitive dependency: if A uses B, A depends on B; if A uses B and B uses C, A indirectly depends on C.
  • Symbol: a named thing in code — a function, class or constant.
  • Monorepo: all of a company's code in one repository, so who-depends-on-whom can be looked up globally (see Ch16).
  • Hyrum's Law: with enough users, every observable behavior of a system will be depended on by somebody, whatever the documentation promises.
  • Large-scale change (LSC): the tooling and process for changing thousands of call sites across the whole repo at once (see Ch22).
  • Static analysis: tools that find problems by reading code without running it; Google's platform is called Tricorder.
  • Build visibility: an allowlist in the build system declaring which targets may depend on this one; any other dependency fails to build.

What problem this chapter solves

All systems age. The bits don't decay, but as the surrounding languages, libraries and techniques move on, an old system drifts away from its ecosystem: it needs dedicated maintenance, esoteric expertise, and ever more work. Age alone is not a reason to deprecate — LaTeX has been refined for decades and is still excellent. What should be deprecated is a system that is demonstrably obsolete, with a replacement offering comparable functionality.

Running old and new side by side costs more than it looks: if they must interoperate you need complicated translation code; once they depend on each other, removing either gets harder; and most insidiously, the new system has to stay compatible with the old one, which slows its evolution. This chapter is what Google learned deprecating large, heavily used internal systems — and the author admits it is one of the few topics in the book where "Google is still learning."

The core ideas, in depth

1. Code is a liability; functionality is the asset

The chapter's premise in one line: code is a liability, not an asset. What's valuable is the functionality code provides; for the same functionality, one maintainable, understandable line beats 10,000 lines of spaghetti. So the thing to maximize isn't the amount of code but functionality delivered per unit of code — and the cheapest way is often not writing more, but deleting code and systems no longer needed.

But deprecation has a capacity limit. The book's analogy: everyone loves freshly paved roads, but if the city closed every road at once to repave, nobody could go anywhere. An organization can only absorb so much deprecation at once — for the teams doing it and for the customers forced to migrate. So choose deprecation projects carefully, and once chosen, finish them.

2. Why deprecation is so hard

  • Hyrum's Law at its extreme: removing a system is "the ultimate change" — not altering behavior but taking it away entirely. The more users, the more usages merely "happen to work" rather than being "guaranteed to work," and removal shakes all of those unexpected dependents loose.
  • Old and new rarely match one-to-one: if the new system were identical, migrating would bring no benefit; because it differs, every use of the old one must be re-evaluated in the context of the new.
  • Emotional attachment: when Google systematically removed old code, it really did meet "I like this code!" One answer is making the repo searchable historically — deleted code can be found again, so deletion no longer feels like destruction.
  • Politics and funding: deprecation costs real money, while the cost of doing nothing is diffuse and invisible, so it's hard to convince stakeholders to let it displace feature work. The research methods of Ch7 (measuring engineering productivity) can supply evidence.

That leads to a counterintuitive conclusion: evolving a system in place is often cheaper than replacing it. Google has observed that migrating to entirely new systems is extremely expensive and the cost is frequently underestimated; incremental in-place refactoring doesn't avoid deprecation, but cuts it into smaller pieces that each deliver value.

3. Designing for deprecation

In other engineering disciplines this isn't radical: a nuclear power plant's decommissioning decades later is part of its design, even with funds set aside for it (the book cites a 1997 IAEA technical report). Software rarely thinks this way: engineers prefer building new things, and corporate culture (Google's included) rewards shipping fast. Google encourages teams to ask two questions while designing: How easy will it be for my consumers to migrate to a potential replacement? Can I replace parts of my system incrementally?

More fundamentally: whether to support a project long term is decided when the organization decides to build it. Once a system exists, there are only three options: support it, carefully deprecate it, or let it stop working when some external event breaks it. So don't start projects your organization isn't committed to supporting for its expected lifespan.

4. Advisory vs. compulsory

Deprecation is a continuum, from "we hope to turn this off someday" to "this goes away tomorrow, be ready." The book splits it in two.

Advisory deprecation has no deadline and the organization isn't willing to commit resources — "aspirational" deprecation. It's good for advertising a new system and attracting early adopters, provided the new system can already handle production loads and is ready to be supported indefinitely, not still in beta. Only when the new system's benefits are transformative rather than incremental will notifications plus self-service migration tools drive adoption on their own — and even then, never to completion. Google's experience: putting up a deprecation warning and walking away leads to slightly fewer new uses, but rarely to teams actively migrating. The reason is a kind of pull: the more existing uses the old system has, the more new code copies them. As friends in SRE like to say: "Hope is not a strategy."

Compulsory deprecation comes with a removal date; systems still depending on it after that date will break. Three requirements:

  • Centralized expertise (counterintuitive): the way to scale isn't for every customer team to learn how to migrate, but to concentrate migration expertise in one team of experts — usually the team removing the old system. They have the incentive to help, and their experience and tools carry across the organization.
  • Enforcement: the schedule can change, but the deprecating team must be empowered to break noncompliant users after sufficient warning and real migration help; otherwise customers will always rank it behind features.
  • Staffing: a compulsory deprecation with nobody doing the work looks mean-spirited to customers — an unfunded mandate. So Google strongly advocates that compulsory deprecations be actively staffed by a specialized team through completion.

Even with policy behind it there are political hurdles: if the last remaining user is critical infrastructure the whole company depends on, would you really break it to make a date? If that team can veto progress, the deprecation isn't really compulsory.

Flushing out hidden dependencies: the monorepo and dependency graph give Google deep insight into usage, but some teams don't even know they depend on the old system, and static analysis can miss it. The answer is dynamic: in the months and weeks before turndown, announce planned outages of increasing duration and see what breaks — much like Google's DiRT disaster-recovery exercises, these often uncover unknown dependencies between running systems, letting dependents plan or negotiate the timeline. At the code level, Google occasionally renames implementation-only symbols to see who depends on them unknowingly.

5. Deprecation warnings: actionable + relevant

Warnings can prevent new uses but rarely migrate existing ones, and they accumulate: A depends on B, B on C, C's warning surfaces when A is built — enough of them and users ignore them all, what health care calls alert fatigue. So every warning needs two properties:

  • Actionable: an average engineer can act on it in practice — "replace this call with its updated counterpart," or an email laying out the steps to move data.
  • Relevant: it shows up when the user is actually doing the thing. A deprecated function is best flagged while the engineer is writing the call, not weeks after check-in; a data-migration email belongs months before removal, not the weekend before.

Google's approach is mark liberally, surface sparingly: old functions are freely marked deprecated, but tools like ErrorProne and clang-tidy flag them only on newly changed lines; intrusive warnings such as for deprecated targets in the dependency graph are added only for compulsory deprecations where the team is actively moving users away.

6. Run deprecation as a project

It needs explicit owners. Without them, no number of warnings produces progress. The alternatives are worse: never deprecate anything, or delegate it to users — which is just an advisory deprecation that will never finish organically. The hardest case is the abandoned project: the original owners moved to the successor, the old system chugs along "in the basement," still a dependency of something critical, everyone hoping it fades away. It won't. The owning team must make removal its primary goal, not a side project, or it always loses on priority; such important-not-urgent cleanup is also a great use of 20% time.

It needs incremental milestones. When building, every feature launch is a win; in deprecation it can feel like the only milestone is "turning out the lights and going home" — and if the team did its job, almost nobody outside notices, because by then nobody uses it; some deprecations never get there at all. So set measurable incremental milestones that deliver value, such as deleting a key subcomponent, and celebrate them like a launch.

7. Three kinds of tooling: discovery, migration, backsliding prevention

Discovery runs throughout: Code Search and Kythe statically find who uses a library, and sampling shows which behaviors customers unexpectedly depend on; dynamic dependencies come from production logging and runtime sampling. New information may make you revisit the deprecation decision itself. Finally, the global test suite is the oracle for whether every reference to an old symbol is gone — and customers are responsible for having enough tests that removing the old system won't hurt them. Migration relies mainly on the LSC process and code generation and review tooling. Backsliding prevention is the most overlooked: without it, users keep adding uses from familiarity or from examples elsewhere in the codebase, and the deprecation team plays a counterproductive, demoralizing game of whack-a-mole. At the micro level, owners add compiler annotations to deprecated symbols (like Java's @deprecated), Tricorder surfaces new uses at review time, sometimes with a push-button fix; at the macro level, visibility whitelists (allowlists) in the build system stop new dependencies, and automated tooling periodically prunes them as users migrate away.

Why it matters / in real systems

Asking "how will we turn this off one day?" in a design review is cheapest then — few dependents, interfaces still malleable. In an interview about "migrating an old library that hundreds of services depend on," laying out the chain discover → migrate centrally → outages of increasing length → block backsliding → delete beats "send an email asking everyone to upgrade."

Pitfalls and debates

  • "Adding @deprecated means it's deprecated" — that's only the start of an advisory deprecation. It deters some new uses; existing ones don't disappear.
  • "Old things should be deprecated" — age is not a reason. The bar is "demonstrably obsolete + a comparable replacement exists."
  • "Letting each customer team migrate itself is fairest" — it doesn't scale. Expertise is spread over hundreds of teams, each ranking it behind features; concentrating it in one expert team reuses tools and gets it done.
  • "A rewrite is cleaner than patching" — often false once turndown costs are counted. The book's TL;DR says it plainly: including turndown costs, evolving in place is usually cheaper than replacing.
  • Limits: the chapter covers only internal technical systems whose owners can see usage; the monorepo and global dependency graph are a big precondition. For public APIs or end-user products where callers are invisible, both discovery and enforcement are much harder. The author also admits Google is still learning — sometimes it works, sometimes it doesn't.

Key takeaways

① Code is a liability, functionality the asset: maximize functionality per unit of code; deleting redundant systems is the cheapest lever.

② Deprecate what is demonstrably obsolete with a replacement, not what is merely old; coexistence slows the new system's evolution.

③ It's hard because of Hyrum's Law (removal is the ultimate change), no one-to-one match, emotional attachment, and invisible costs.

④ Counting turndown costs, evolving in place usually beats replacing; long-term support is decided when the project starts.

⑤ Advisory has no deadline and only nudges; compulsory needs a deadline, enforcement and a staffed expert team — or it's an unfunded mandate.

⑥ Planned outages of increasing duration and renamed internal symbols flush out unknowing dependents.

⑦ Good warnings are actionable + relevant; mark liberally, surface sparingly, only on newly changed lines, to avoid alert fatigue.

⑧ Run it as a project: explicit owners and celebrated intermediate milestones; abandoned projects never fade away on their own.

⑨ The toolkit: discovery (code search / logs / global tests), migration (LSC), backsliding prevention (annotations + visibility allowlists).
