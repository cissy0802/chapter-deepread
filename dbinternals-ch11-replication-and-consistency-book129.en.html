Replication and Consistency

Database Internals · Ch 11 · Alex Petrov · 2019

中文 →

What is this chapter about?

You change your profile picture, hit refresh, and the old one is still there; two seconds later the new one shows up. Chapter 11 of Database Internals is about what happens in those two seconds — your data is actually stored in several copies at once, and they are not always the same. What the chapter delivers is a language for saying precisely which copy a read is allowed to return.

A strange thing first

Think of your data as an important document, copied three times and handed to three people — that way no single person going on holiday loses it. But trouble follows: you update the copy held by the first person, and the other two still hold the old text. Ask the second person and you get the old answer. Stranger still: ask the first and get the new answer, then ask the second and get the old one — from the asker's point of view, the data went backwards.

Why the old world found this hard

The obvious fix is "when you change it, make all three change at once, nobody jumps ahead." But that means every change waits for the slowest person to nod. A round trip between data centers in the same city is about 1 millisecond; across an ocean it is tens of milliseconds — pushing "always read the latest" to its limit means every read and write pays for several extra rounds of asking, and if even one person is unreachable, nobody can change anything. Go the other way for speed, and you accept the occasional stale read. This is an unavoidable trade, not laziness.

Consistency is not a switch, it is a row of tiers

The most important idea in the chapter: "consistent or not" is not a yes/no question but a row of priced promises, from expensive to cheap —

  • The most expensive tier: whoever you ask, whenever you ask, it looks as if only one copy exists.
  • The middle tiers are the practical ones: at least let you read what you just wrote (you always see your new picture; others can lag); at least never let your reads go backwards; at least never invert cause and effect (nobody should see the reply before the original post).
  • The cheapest tier: it only promises "if you stop changing things, the copies will eventually match" — without saying whether that means milliseconds or minutes.

Which tier you buy depends on what happens if you read a stale value: an account balance and a like counter clearly should not buy the same one.

And some data needs no negotiation at all

The end of the chapter has a lovely idea: some data can be designed so that any two versions always merge cleanly. To count likes, let each machine track only the share it saw, and when merging, take the larger number per machine and add those up — duplicates, reordering and resends cannot change the result. This kind of data never needs the machines to negotiate who is right; it converges on its own. The cost: only some data types can be designed this way, and "it merged" is not the same as "the merge is what a human wanted".

Remember this one line

Extra copies exist so you don't lose the data, but copies always differ for a while. So don't ask "is the data consistent?" — ask "which tier of promise am I willing to pay how much latency for?" Between "always the latest" and "eventually the same" there are several very good bargains.

In one line

Replication buys availability; the consistency model is the bill replication runs up. Once there are several replicas, "the database returned a value" stops being self-evident — you must first agree on which return values are legal. This chapter turns that agreement into a precisely definable spectrum: from register semantics (safe / regular / atomic) up through linearizable, sequential, causal, session and eventual consistency, and on to CRDTs that converge with no coordination at all. The takeaway: consistency is a contract, not a performance dial — what you get by tuning a quorum is usually not the tier you think it is.

Glossary

  • Replica: a full copy of the same data on a different machine; the replication factor (RF) is the number of copies, written n here.
  • Quorum: how many replicas must acknowledge an operation before it counts as done; a "majority quorum" is n/2 + 1.
  • Network partition: a network failure splits the cluster in two; both halves are alive but cannot reach each other.
  • Version vector / logical clock: counters, not wall-clock time, that record "who came before whom" so you can tell whether two writes are causally related or concurrent.
  • Read repair: on a read, noticing that a replica is behind and writing the newer value back to it.
  • Tombstone: a delete is not a real delete but a "deleted here" marker — otherwise a lagging replica would resurrect the old data.
  • Last-write-wins (LWW): on conflict, compare timestamps and the larger wins; simple, but it silently drops the losing write.

What this chapter is solving

Availability comes from redundancy, redundancy means several replicas, and several replicas will differ for a while — so a question that looks like it needs no definition becomes a contract that must be defined: which copy should a read return?

Concretely: a three-replica key-value store spread over three availability zones returns as soon as the write lands on replica A, and the very next read is routed to replica B. Cross-AZ replication takes about 1–2 ms round trip, and during those 1–2 ms B is holding the old value. What happens if you don't solve it? Not something as gentle as "occasionally a bit stale" — the system loses its reasonability: retry the same request twice and get two answers, with no way to tell which one is the bug. So what the chapter does is break the adjective "consistent" into a set of decidable, priced contracts.

The core, properly explained

First, put CAP back in its box: it covers far less than you think

Almost every misunderstanding about consistency starts with "CAP: pick two". Petrov is careful to point out that CAP holds only under a very narrow model: an asynchronous network, no clocks, messages that may be lost arbitrarily. Its C means linearizability specifically, and its A means "every request reaching a non-failing node must return in finite time" — not "highly available" in the everyday sense. The real conclusion is: only when a partition actually happens are you forced to choose between C and A; for the vast majority of the time, with no partition, you can have both.

A more engineering-friendly framing is Fox and Brewer's 1999 harvest and yield: yield is the fraction of requests that complete, harvest is how complete the answer is. Allowing "results from only 90% of the index shards" is much closer to how real systems degrade than all-or-nothing — you are trading harvest for yield, which turns availability from 0/1 into a continuous quantity.

Think of storage as a single cell: three kinds of register

To discuss "what counts as a legal read" precisely, you need a minimal model. The chapter borrows the shared-memory view: treat the whole distributed store as one readable, writable cell (a register), then ask — when a read and a write overlap in time, what may the read return? Three tiers:

  • Safe register: a read during the overlap may return any value, even one never written. That sounds absurd, but it captures the "no guarantees whatsoever" tier exactly.
  • Regular register: a read returns either the old or the new value, never garbage — but two successive reads may see new, then old.
  • Atomic register: there is a flip point; once one read sees the new value, every later read must see it too — which is exactly what linearizability looks like on a single object.

The value of this ladder: it turns "consistency" from an adjective into a decidable set of execution histories — given a history of reads and writes, you can answer "is this legal?"

The spectrum: linearizable → sequential → causal → eventual

With register semantics in hand, the familiar models line up on a spectrum — the higher up, the more coordination, the higher the latency, and the more fragile under partition.

  • Linearizability: every operation sits in one total order that agrees with real time, each taking effect at some point between its invocation and its return. Intuition: the whole cluster pretends to be a single machine. It is also composable — if each object is linearizable, so is the collection. Cost: every operation makes a round of majority coordination, roughly 1–2 ms across AZs and tens of milliseconds across continents.
  • Sequential consistency: a total order exists and agrees with each process's own program order, but need not agree with real time. Intuition: the same film, possibly screened late — others may still read the old value, but everyone sees the same order. ZooKeeper reads are this tier: answered locally, possibly behind; for linearizability you must call sync first.
  • Causal consistency: only causally related operations must be ordered identically everywhere; concurrent ones may be seen in different orders by different nodes, using version vectors to carry "which earlier writes I depend on". Intuition: nobody may see the reply before the original post. Its weight: while insisting on availability plus partition tolerance, this is the strongest reachable model (the COPS/Eiger line of results).
  • Eventual consistency: promises only that "replicas converge once writes stop", with no time bound at all — the weakest useful guarantee, and the most abused word in the field.

Session guarantees: move the promise from the system to your session

Every tier on the spectrum is a system-wide property, which is why they are expensive. The common engineering compromise is to shrink the promise to a single client session: these session guarantees hold only for "your session", and are therefore far cheaper:

  • Read your own writes: after you change your picture, you definitely see the new one; others may lag.
  • Monotonic reads: the values you read may never go backwards.
  • Monotonic writes: two writes you issue in order land on every replica in that order.
  • Writes follow reads: when you write based on a value you read, that causal chain is not reordered elsewhere either.

The cheapest implementation is stickiness: pin a client to one replica and the first two come almost free. The cost is that the guarantee dies with that replica — serious cases need a version token ("no earlier than the version I last saw") rather than a routing trick.

Tunable consistency: w + r > n does not give you linearizability

The Dynamo lineage (Cassandra, Riak, DynamoDB) hands the choice to each individual operation: a write waits for w replicas to acknowledge, a read waits for r replicas to answer, out of n total. When w + r > n, the read and write sets must overlap, so at least one responder has seen the latest write. The Dynamo paper (SOSP 2007) gives n=3, w=2, r=2 as the common configuration.

Here is the trap most worth remembering: w + r > n only guarantees that someone has seen the latest write — it does not guarantee linearizability. The write may have failed part-way (only one of w succeeded, so it returned an error while that replica still holds the new value) or may still be in flight — and then two successive reads can see new, then old, breaking monotonic reads.

To close the gap, a read must write the highest value it saw back to the lagging replicas (an ABD-style two-phase read, which in practice is read repair), turning the read path from one round into two. In other words: what you tune with a quorum is the trade between availability and staleness, not which contract you are on.

Witness replicas: vote without storing data

Majority fault tolerance needs enough replicas, but most of the cost of "enough" is storage, not voting. The chapter offers a neat saving: a witness replica normally keeps only metadata, not the data itself, yet still votes; only when full replicas become unreachable does it temporarily accept data and hand it back afterwards. So 2 full + 1 witness preserves three-replica majority tolerance at roughly two thirds of the storage. Cassandra's transient replication and Spanner's witness replicas are exactly this idea.

Strong eventual consistency and CRDTs: converging without coordination

The pain of eventual consistency is that conflicts need an arbiter. The usual arbiter is LWW — compare timestamps, larger wins. But one clock going backwards and the winner may be the older value, while the losing write is silently discarded, without even an error.

A CRDT (conflict-free replicated data type) takes another route: design the data type so that merging needs no arbitration at all. Require the merge to be commutative, associative and idempotent — then reordering, duplication and resends cannot change the result, and replicas that receive the same set of updates (in any order) must reach the same state. That property is strong eventual consistency: it turns convergence from an operational promise into a mathematical property of the data type, with no consensus required.

Take the grow-only counter (G-Counter): each replica increments only its own slot, merging takes the per-slot maximum, and the value is the sum of the slots.

Add a second slot for decrements and you get the PN-Counter; sets bring G-Set, the observed-remove set (OR-Set) and other variants. Implementations split two ways: state-based (CvRDT) ships whole states, operation-based (CmRDT) ships only operations — cheaper on bandwidth but requiring delivery guarantees.

The costs are real: only some data types can be made into CRDTs; handling deletes correctly needs tombstones, so metadata grows over time; and above all convergence is not semantic correctness — replicas can perfectly agree on a result nobody wanted.

The decision rule is plain: first ask "what happens if we read a stale value?" If the answer is "the user sees an old avatar", session guarantees are enough. If it is "we oversell 1,000 units" or "two nodes both believe they are the leader", you can only pay for linearizability — and you must implement it with consensus, not by turning r up.

Why it matters / how it lands in real systems

The practical value of this chapter is that it translates a vague requirement into an implementable contract. The most common mistake in architecture review is treating consistency as a performance dial: "feels a bit inconsistent, let's set r to 3" — latency rises, the anomaly stays, because r cannot cure backwards reads. Interviews are the same: being able to explain why w + r > n is not linearizability carries far more weight than reciting "CAP, pick two".

Against real systems: etcd (the single source of truth for Kubernetes) defaults to linearizable reads while keeping faster serializable reads as an escape hatch; ZooKeeper reads are sequential, and linearizability needs an explicit sync; Cassandra / DynamoDB hand the tier to each call; Spanner reaches external consistency with TrueTime and commit-wait; MongoDB has offered causally consistent sessions since 3.6; Riak and collaborative editing engines take the CRDT route.

Pitfalls and open arguments

  • "CAP: pick two" is a bad summary. With no partition you can have both C and A; the forced choice only arises during a partition — Brewer himself published a correction in 2012.
  • The biggest trap: w + r > n is not linearizability. It guarantees overlap, not order; for linearizability you need write-back on reads, or simply consensus.
  • "Eventually consistent" does not mean "consistent in a moment". There is no time bound — production must measure actual replication lag rather than trusting the word.
  • Linearizability composes; weaker models may not. Bolt two individually causally consistent subsystems together and the cross-system causal chain can break.
  • LWW silently drops writes. Ordering by physical clocks means one clock stepping backwards lets an old value overwrite a new one, with no error at all.
  • CRDTs are not a cure-all. They cover only certain data types, tombstones and version metadata grow, and most importantly convergence ≠ semantic correctness — the Dynamo paper's own shopping-cart example: after a merge, a deleted item can come back.
  • Where the book sits, and the other side. In 2019 the CRDT section was still on the theoretical side; the local-first wave since (Automerge, Yjs) engineered it and exposed metadata size as a genuine problem. The counter-argument persists too: many hold that application developers actually want linearizability, and that patching over a weak model is more error-prone than paying for a strong one.

Takeaways

① Replication buys availability, and the consistency model is the bill; once there are several replicas, "what a read returns" must be written down as a contract.

② CAP's model is narrow: C means linearizability specifically, A means "a request must return in finite time", and only a real partition forces the choice; harvest/yield is the better framing.

③ The three registers (safe / regular / atomic) turn consistency into a decidable set of execution histories; atomic = linearizability on one object.

④ The spectrum from pricey to cheap: linearizable → sequential → causal → session → eventual. Causal is the strongest model reachable under availability plus partition tolerance; linearizability composes, weaker models may not.

⑤ Session guarantees are the best value: read-your-writes, monotonic reads, monotonic writes, writes-follow-reads — sticky routing gives the first two almost free, and the guarantee dies with the replica.

⑥ The one to remember: w + r > n guarantees overlap, not order, so it is not linearizability; closing the gap needs write-back / read repair, turning one round into two.

⑦ Levels have a price: LOCAL_QUORUM about 1–2ms, EACH_QUORUM 80–150ms across continents — the same line of code, two orders of magnitude of p99.

⑧ Witness replicas vote without storing data: 2 full + 1 witness = three-replica tolerance at about two thirds of the storage; LWW, by contrast, silently drops writes when a clock steps back.

⑨ CRDTs make convergence a mathematical property of the data type (commutative / associative / idempotent), with zero coordination and no lost writes; the costs are limited types and growing metadata, and convergence is not semantic correctness. The rule stays one line: first ask what happens if you read a stale value.
