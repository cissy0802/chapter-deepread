设计酒店预订系统

System Design Interview Vol 2 · Ch 7 · Alex Xu & Sahn Lam · 2022

EN →

这一章讲什么？

你在订房 App 上挑好房间、点下「预订」，那一两秒里系统要办一件很凶险的事：确认这间房还在、记在你名下，同时不能把同一间房也卖给正在点同一个按钮的另一个人。这一章就是从零把这套系统搭出来。

先说个怪事

你大概以为这种系统难在「人太多」。算一下：五千家酒店、一百万间房，就算住满七成、平均住三晚，一天也只有二十多万笔预订——摊到每秒大约三笔。三笔！比一个小论坛的发帖量还低。难的从来不是量，而是那三笔里可能有两笔在抢同一间房，而且抢错了要赔钱。

旧世界为什么难

想象前台那本纸质登记簿。客人打电话订房，前台翻到 3 月 5 日那页，看见还剩一间，写下名字。麻烦在于同一秒另一个同事也翻着同一页、也看见「还剩一间」、也写了个名字。两个人都收了钱，房只有一间——这就是超卖。纸簿子如此，两台服务器同时读同一行数据，一模一样。

它怎么做到的

第一步是换个卖法。酒店卖的不是「301 号房」，而是「大床房 · 3 月 5 日 · 还剩几间」这一格额度——就像电影院卖的是「周六晚场还剩多少座」，具体坐哪儿进场再说。于是「在几万间房里找一间空的」变成了「把一格数字减一」，简单太多。

第二步是管住这一格。两种活法：一种是改之前先把那一页扣在手里，谁也别看，改完再放开——保险，但排队的人一多就堵；另一种是先记下这一页的版次，真要改时核对版次变没变，变了说明有人插了队、自己重来一遍——平时更快，抢得凶时会反复重来。

第三步治另一种重复：你手抖点了两下「提交」。办法是进下单页时先发你一张票号，同一张票号只兑一次订单——像排队取号，号在手里，重复喊也只算一个人。

该怎么选

平常的酒店，第二种（核对版次）就够了，甚至可以直接让数据库守着「订出去的不许超过总数」这条规矩；只有演唱会前一晚全城抢一家酒店那种场面，才值得给这一格单独排队。代价是：你偶尔会在最后一步看到「刚好被订走了」——系统宁可让你白点一次，也绝不把同一间房卖给两个人。

一句话记住

订房系统的难点不是流量（每秒只有几笔），而是有限库存上的正确性：把房间换算成「房型 × 日期」的一格额度，再用「一次只让一个人改这一格」和「一张票号只兑一次」把它守住。

一句话

这一章表面在教你设计订房系统，真正教的是：有些系统难在正确性，不难在规模。粗略估算下来它每秒只有约 3 笔预订，却必须在同一行库存上顶住并发、还不能因为一次重试多卖一间房。骨架只有四件事：把可售资源抽象成「房型 × 日期」的库存行、用一次数据库事务把扣库存与写订单绑成原子操作、用幂等键（idempotency key）挡重复提交、用乐观锁或数据库约束挡超卖。拆成多个服务之后，才不得不请出 2PC / Saga / TCC 这些贵得多的工具。

Glossary · 术语表

  • 房型（room type）：酒店按「大床房 / 双床房 / 套房」这类等价房间成批售卖，房号通常入住时才分配。
  • 库存（inventory）：某家酒店、某个房型、某一天还能卖几间——本章所有并发问题都发生在这一行上。
  • 超卖（oversell）：卖出的数量超过实际可用数量，是本章要防的核心错误。
  • 超售（overbooking）：故意多卖一点（如总量的 110%）对冲取消与放空，是业务策略、不是 bug。
  • 事务（transaction）/ ACID：一组读写要么全成、要么全不成，中间状态不被别人看见。
  • 悲观锁（pessimistic locking）：改之前先锁住这行、别人只能等；SQL 里常写作 SELECT ... FOR UPDATE。
  • 乐观锁（optimistic locking）：不加锁，读时记下版本号，写时校验它没被改过；被改过就重读重试。
  • 幂等（idempotency）：同一个请求发多次，效果与发一次相同；靠请求带一个唯一的幂等键实现。
  • 竞态（race condition）：两个请求交错执行，各自都读到旧值又各自写回，结果谁也不对。
  • 2PC / Saga / TCC：跨服务做「一件事」的三种办法——两阶段拍板 / 本地事务加补偿 / 先预占再确认或取消。

坐标

卷二第 7 章。前六章（附近服务、地图、消息队列、监控、广告聚合）清一色是吞吐与流式问题，这一章第一次转向事务型、库存有限的系统——全书从「扛得住」切到「算得准」的分界线；下启第 11 章支付、第 12 章数字钱包。现实对应：Booking.com / Airbnb / 携程的下单链路，以及任何「有限库存 + 钱」的系统：票务、航空舱位、电商秒杀、餐厅订座。

这章要解决什么

订房的全部难点集中在一个瞬间：两个人同时点了最后一间房的「预订」。不解决会怎样？超卖不是一条错误日志，是真金白银的赔付——客人到店没房，酒店得掏差价把他送去别家（业内叫 walk the guest），还赔上口碑。可怕超卖就把并发全串行化，又会让热门酒店在大促时订不动。这一章要走的是窄路：既不多卖一间，也别把系统锁死。

核心内容，讲透

先算一笔：它其实是个小系统

书里的场景是一家连锁：5000 家酒店、约 100 万间房。按 70% 入住率、平均住 3 晚估算，每天新增预订约 1,000,000 × 0.7 ÷ 3 ≈ 23 万笔；摊到一天 86400 秒，写入约 3 QPS。按漏斗往前推（看详情页的远多于真付钱的），读侧是数百 QPS量级。库存有多少行？5000 家 × 约 20 个房型 × 未来两年 730 天 ≈ 7300 万行，每行只有几个整数——几个 GB，一台关系库装得下。

结论很反直觉：这一章不需要分片、不需要 NoSQL、不需要消息队列削峰。估算在这里的作用不是证明「能扛」，而是劝你别过度设计——把全部注意力还给那 3 笔写。

关键抽象：你卖的不是房号，是「房型 × 日期」的一格

这是整章的地基。数据模型只需两张关键表：订单表（reservation：幂等键、酒店、房型、入住 / 离店日、间数、状态）和库存表（room_type_inventory：hotel_id, room_type_id, date, total_inventory, total_reserved）——一家酒店、一个房型、一天，占一行。于是问「3/5 到 3/8 有没有房」就是看这三行是否都有余量；下单就是把这三行的 total_reserved 各加 1，再插一条订单。

为什么这样设计？① 照抄业务——酒店本来就按房型卖、房号入住时才分配，模型贴着现实走，后续改动最少；② 把搜索变成算术——「在几万间房里找一间空的」退化成「一行上加减一个整数」，并发控制才有明确落点；③ 把「多晚」变成「多行」——跨三晚就是三行写在同一个事务里，任何一晚满了整单失败，语义天然正确。代价也在这个乘法里：行数 = 酒店 × 房型 × 天数，所以必须设一个可售窗口（如未来两年）并定期滚动生成与清理。

两种「重复」，治法完全不同

看起来都是「订了两次」，病根完全不同——这是本章最值得记住的分类，也是面试里最容易被绕进去的地方。

第一种：同一个用户重复提交（超时重试、手抖双击）。治法是幂等：用户进入下单页时就生成一个预订号当幂等键随请求带上，订单表在这个键上建唯一索引；第二次提交撞上唯一约束，就不建新单、直接返回第一次的结果。最容易写错的是时机：键必须在「可能被重试的那一刻」之前就固定，每次点击都新生成一个，幂等就是假的。

第二种：两个用户抢同一格。两个请求都读到「余 1」、都算出「还能订」、都写回「已订 +1」——读-改-写竞态。幂等键在这里一点忙都帮不上：这是两个各自都合法的请求，只能靠并发控制。

守住那一格：三种做法

悲观锁。SELECT ... FOR UPDATE 先把库存行锁住，改完提交才放开，后来者排队。正确、直观；代价是这一行上的并发被彻底串行化，持锁期间别人全在等，事务一长就拖出超时与死锁。

乐观锁。给库存行加一个 version 整数：读时带出来，写时用 UPDATE ... SET total_reserved = ?, version = version + 1 WHERE version = <读到的值>；受影响行数为 0 就说明有人先改过，重读重试。低争用下几乎没有开销，高争用下退化成重试风暴。

数据库约束。让库存行自己守规矩，如 CHECK (total_reserved <= total_inventory)（要留超售就写 <= total_inventory * 1.1）。最省代码，越界的写被数据库直接拒绝；代价是规则散在 schema 里不好随代码演进、各家数据库支持不一，应用仍得处理「被拒绝」这条路径。

按本章 3 QPS 的量级，作者选的是乐观锁或数据库约束——悲观锁在这里是拿最贵的工具去打最小的钉子。还有一条不能省的纪律：扣库存与写订单必须在同一个事务里，分开做、中间崩一次，就会留下「扣了库存却没有订单」（房间凭空消失）或「有订单却没扣库存」（超卖）。

超售：故意多卖一点，是生意不是 bug

把约束从「不超过总量」放宽成「不超过总量 × 系数」（书里用 110% 举例），系统就允许卖出比实际更多的房。为什么？取消与放空（no-show）是常态，严格按库存卖会让房间空着跑。代价是超售兑现不了就得把客人送去别家、承担差价与口碑。所以那个系数不是技术参数，是拿历史取消率换赔付成本的业务决策。

拆成微服务之后：一致性要自己花钱买

只要预订服务和库存服务各自拿着一个库，「扣库存 + 写订单」就跨了进程，ACID 不再免费。三条路：2PC 靠协调者两阶段拍板，强一致，但全程持锁、协调者挂掉会留下悬而未决的事务；Saga 把事务拆成一串本地步骤，失败时按相反顺序执行补偿，不持锁、能扩展，但只有最终一致性，而且补偿不是回滚——退款可能有手续费、取消可能有罚金，补偿自带业务语义；TCC 先 Try 预占库存、再 Confirm 或 Cancel，持锁比 2PC 短，代价是每个服务都要写三套逻辑。

这一章的立场很克制：能不拆就别拆。几个 GB、3 QPS 写，一个库的一次事务能解决的事，不值得用分布式事务换一张好看的架构图。

热点怎么办？平时不存在的问题，会在「演唱会前一晚、全城抢同一家酒店」时集中爆发。三条对策：把一格分桶（10 间的额度拆成 5 格各 2 间，并发打散到 5 行，代价是「有房但恰好在别的桶」）；给这一格排队，把重试风暴换成可预测的等待；以及把读挡在外面——列表页读缓存与只读副本、拿到的余量只能当提示，只有真下单那一步回主库校验。

为什么重要 / 落到真实系统

这套「库存行 + 一次事务 + 幂等键」的骨架，几乎是所有有限库存系统的通用解：票务（某个票档）、航空（航班 × 舱位 × 日期）、电商下单（SKU 库存）、餐厅与共享办公订座——换个名词就能搬。落地上：MySQL / PostgreSQL 的 SELECT ... FOR UPDATE 与唯一索引最常见；DynamoDB 用条件写与事务接口、并在事务写里附客户端令牌做幂等；Spanner 用悲观锁 + 自动重试；阿里与蚂蚁把 TCC / Saga 做成框架（Seata）开源。

面试里它的价值在于：这是少数能把事务、隔离与幂等考实的题目，面试官几乎一定追问三件事——「两个人同时订最后一间怎么办」「用户点了两次怎么办」「扣库存和写订单放在几个事务里」。答得上这三问，这一章就没白读。

大厂实证 · 这些主张不是书里说的，是公司自己公开说的
  • Sabre（全球旅行分销）说自己「每秒处理数千次预订更新」，预订库必须跨多个可用区提供服务，还需要「跨多条记录的 ACID 事务，因为航司常同时改动多名乘客、多个航班」——印证了「预订类系统写量不大，要的是跨行原子性与高可用」。A. Gasparovic（Sabre Labs 首席架构师）, Google Cloud Blog, 2022-01 ↗
  • Google Cloud 公开了 Spanner 的悲观锁细节，直言争用常来自「表里存在热点键」、结果是事务被 abort；官方建议「只把关键路径的代码放进事务」，并指出只读事务「不持锁、不阻塞别人、永不 abort」——这就是悲观锁代价的官方版本。M. Gupta「Understanding transactional locking in Cloud Spanner」, Google Cloud Blog, 2022-11 ↗

易错点与争议

  • 把它当秒杀题做：一上来就分片、上 Redis 预扣、加队列削峰——在 3 QPS 下全是过度设计。书里那段估算的真正用途就是劝你别这么干。
  • 幂等键 ≠ 并发控制：幂等只挡「同一个请求被重发」，挡不住两个用户抢同一格；反过来乐观锁也挡不住重复提交（两次提交都是合法请求）。两种病要各治一遍。另外键必须在首次请求发出前就固定、并带过整条重试链，在「提交」按钮上现生成等于没有幂等。
  • 乐观锁在热点行上会退化：同一格上几百个并发写，重试可能比成功还多，p99 很难看。该分桶就分桶、该排队就排队，别指望重试自己解决争用。
  • 缓存余量的一致性：放缓存提速是对的，但那个数字只能当提示，下单必须回库校验，否则「看起来有房」会直接变成超卖。反过来，接受「点进去才发现刚被订走」是正确的取舍。
  • 超售系数不是行业标准：书里的 110% 是示意值，真实系数要用历史取消率、放空率与赔付成本算，还随季节和城市变；当常量抄进生产很危险。
  • 时代局限与书外的坑：本书成于 2022，此后 DynamoDB（其事务实现于 USENIX ATC 2023 公开）、Spanner、TiDB 把跨分片事务的价格压了下来，「2PC 太贵」值得按你用的数据库重算一遍。另外书里没展开、真实工程一定会踩的是日期与时区：库存以「日期」为键，跨时区、夏令时、酒店当地对「入住日」的定义，都可能让同一笔预订落到不同的行上。

要点

① 这一章难在正确性不难在规模——约 3 QPS 的写、库存 7300 万行几个 GB，一台关系库就够。

② 核心抽象：卖的不是房号，而是「房型 × 日期」的一格额度（total_inventory 与 total_reserved），一晚一行。

③ 跨多晚的预订 = 多行库存各 +1 加一条订单，必须在同一个事务里，否则会漏出「房间消失」或「超卖」。

④ 两种「重复」分开治：同一请求被重发 → 幂等键 + 唯一索引；两人抢同一格 → 并发控制。互相替代不了。

⑤ 并发控制三选一：悲观锁（正确但串行化）、乐观锁（本章默认，高争用退化为重试风暴）、数据库约束（最省代码）。

⑥ 超售（如 110%）是业务决策：拿历史取消率换赔付成本，不是技术参数。

⑦ 拆服务后一致性要花钱买：2PC 持锁阻塞、Saga 只有最终一致且补偿 ≠ 回滚、TCC 每个服务写三套逻辑。能不拆就别拆。

⑧ 热点（大促抢房）才是真敌人：分桶、排队、把读挡在缓存与只读副本上，缓存余量只能当提示。
