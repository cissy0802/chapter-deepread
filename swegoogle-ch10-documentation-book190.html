文档

Software Engineering at Google · Ch 10 · Documentation · Tom Manshreck · 2020

EN →

这一章讲什么？

你用过的每个手机 App、每个网站，背后都有工程师写给同事看的「说明书」：这个功能怎么用、那个按钮背后在做什么、新人第一天该从哪里看起。这一章讲 Google 怎么让这些说明书不烂、不过时、找得到。

先说个怪事

工程师几乎人人抱怨「文档太差」，可轮到自己，几乎人人不写。原因不是懒：写文档的好处多半落在别人和未来身上，而麻烦全落在当下的自己身上。

旧世界为什么难

Google 早年把文档放在一个公司内部的维基上，谁都能写。结果是：同一件事有好几份说法、没人知道哪份是对的；写的人换了组，页面就没人管；发现错了也不知道该找谁。文档和代码住在两个地方，代码一改，文档就悄悄变成「谎话」。

核心机制直觉

  • 让文档住进代码的家：说明书就放在代码旁边的文件夹里。改代码的人顺手改说明，像修电器时把贴在机身上的说明贴纸一起换掉。
  • 每份都有主人：就像小区的每个公告栏都有一位负责人，过时了有人撕、有错了知道找谁。
  • 写之前先想清楚给谁看：给第一次来的游客画地图，和给本地老司机画地图，画法完全不同。
  • 一份只干一件事：菜谱就写做菜步骤，别在菜谱里塞进这道菜的历史和营养学讲座——想讲，另写一份。
  • 贴上「保质期」：每份说明书标注上次检查的日期，太久没人看过，系统就提醒主人复查，像冰箱里的牛奶会提醒你该扔了。

带来了什么 / 该怎么选

你的团队该怎么做？把最常用的那几份说明搬到代码旁边，改代码时一起改、一起让同事看；没用的大胆删掉。诚实的代价是：这会让每次改动多花一点时间，而且没有专职写作的人帮忙，文字质量全靠工程师自己。

一句话记住

文档就是代码：同一个家、同一套检查、有主人、会过期。

一句话

你以为文档写不好是「工程师不会写作」；本章说，主要是流程把文档放错了地方——它离开代码、没有主人、没人评审、不会过期。Google 的解法是把文档当代码：同一个仓库、同一次改动、同一套评审，再加上「先认清读者、一份只干一件事」的写作纪律。

Glossary · 术语表

  • 改动 / 变更列表（CL）：一次要合入代码库的修改，相当于 GitHub 的 pull request。
  • 源码控制（source control）：Git 一类的版本管理系统，记录每次改动、谁改的、能回退。
  • 代码评审（code review）：改动合入前由同事阅读并批准的流程（见第 9 章）。
  • 维基（wiki）：谁都能在线编辑的网页集合，如公司内部的 Confluence。
  • Markdown：一种用 #、* 等符号标记标题和列表的纯文本格式，源码本身就能读。
  • API：一段代码对外提供的调用接口，比如一个函数的名字、参数和返回值。
  • 代码注释（comment）：写在源码里、给人看不给机器执行的说明文字。
  • 设计文档（design doc）：动手写代码前，描述方案、目标和备选方案的文档，供同事评审。

坐标

Part III「流程」第三章。上承 Ch9 代码评审（文档改动走同一条评审流程），下启 Ch11 起的测试（文档和测试一样，是「收益在未来」的工程纪律）。现实对应：README、API 注释、设计文档、内部 wiki，以及「docs as code」这套做法。

这章要解决什么

本章开篇的观察是：Google 工程师调查里，文档常年排在最大痛点之列，但真正写的人很少。作者给出几条「为什么不写」：工程师把写作看成独立于编程的另一门手艺；写文档的工具和代码工具不在一处，切换成本高；而最根本的是收益在下游——写的人当下付出，读的人（包括三个月后的自己）才受益。

但文档对写的人其实也有直接回报：写 API 说明会逼你想清楚接口该长什么样；它是日后维护的路线图；它让代码显得专业、值得信任；它还能挡掉大量重复提问。不解决会怎样？Ch1 说软件工程是「对时间积分的编程」——代码活十年、经手上百人时，没文档的知识只存在于某几个人脑子里，人一走，知识就跟着走。本章要回答：怎么让文档在这种时间与规模下依然可信。

核心内容，讲透

一、文档就是代码：七条同构

本章的核心论断：文档和代码耦合得如此紧，应该尽可能像代码一样对待。具体落成七条：

  • 有内部规范：像代码风格指南一样，有统一的文档风格与格式约定。
  • 放进源码控制：有历史、能回退、能看出谁改了什么。
  • 有明确的所有者：有人对它的正确性长期负责。
  • 改动要评审：文档改动和代码改动一起评审（见本节第五条）。
  • 问题能被追踪：读者发现错误能像报 bug 一样报给所有者。
  • 定期评估：像测试一样，周期性检查它还对不对。
  • 尽量不重复：一件事只有一份权威说法，其他地方链过去。

为什么这样设计？因为这七条每一条，代码都已经有现成的基础设施——仓库、评审、OWNERS、bug 系统。把文档挂到这些已有的轨道上，就不必另造一套没人用的流程。本章 TL;DR 也说：文档的改动应该借用已有的开发者工作流。

二、案例：从 GooWiki 搬回代码旁边

Google 早年把大部分工程文档放在内部维基 GooWiki 上。维基门槛低、谁都能写，但规模一大就暴露问题：很多页面没有明确所有者，过时也没人管；同一主题出现多份互相矛盾的页面；读者发现错误，也没有渠道报给谁。维基写起来容易，维护起来没人负责。

转折是把文档搬进源码控制：文档以 Markdown 写在代码目录里，由内部系统 g3doc 渲染成网页。于是文档天然有了所有者（目录的 OWNERS）、有了评审（同一个 CL）、有了历史；工程师也不必离开写代码的环境。原书坦承，这次迁移并非一帆风顺，有人不愿改变习惯；但它让「改代码顺手改文档」第一次变得自然。

三、认清读者：最常见的错误是写给自己

本章说，写文档最重要的错误是不知道读者是谁。读者可以按几个维度区分：经验水平（老手还是新手）、领域知识、目的（终端用户还是要改代码的开发者）。另有两组好记的划分：

  • 寻找者（seekers）vs 偶遇者（stumblers）：前者知道自己要找什么，需要的是能快速定位、内容一致；后者只有模糊的想法，需要的是清晰的概述和引导。
  • 使用方（customers）vs 提供方（providers）：API 的使用者只关心怎么调；团队成员才需要实现细节、值班手册。两类内容应分开写，别混在一份里。

本章引帕斯卡那句「如果我有更多时间，就会给你写一封更短的信」：短而准比长而全难写，但对读者更友好。

四、五类文档，各管一件事

  • 参考文档（reference）：最常见的是代码注释——文件注释说明这个文件做什么；类注释说明类的用途和用法；函数注释以动词开头说清它做了什么、返回什么（「Returns…」「Deletes…」）。它是 API 的一部分。
  • 设计文档（design doc）：动工前写，按团队模板讲目标、实现策略、关键决策及其权衡、备选方案的优劣，常要求覆盖安全、隐私等考量；评审通过后，它主要作为决策的历史记录。
  • 教程（tutorial）：把读者从零带到能跑起来的「Hello World」。最好的写作时机是你自己第一次上手时，边做边记、每步编号，不预设读者已装好任何东西，并区分「你要做的」和「系统会做的」。
  • 概念文档（conceptual）：讲一个系统或 API 背后的原理与全貌，是最难写的一类，为了清晰常要牺牲一部分完整与精确。
  • 落地页（landing page）：像交通警察，只负责把人指到正确的地方；面向使用方的入口和团队内部的值班、流程信息要分开。

五、三种评审，三个问题

和第 9 章三重批准同构，一份重要文档应该回答三个不同的问题：

  • 技术评审——对不对？由懂这块的工程师确认准确性，通常就是代码评审的一部分。
  • 读者评审——看得懂吗？找一位不熟悉这个领域的人读，他卡住的地方就是文档缺的地方。
  • 写作评审——写得一致吗？由技术写作者或熟悉风格的人检查措辞、结构与规范。

六、写作哲学：5W、一份一事、会过期

开头先答 5W：给谁看（Who）、目的是什么（What）、何时写成与最后复查（When）、应该放在哪里（Where）、读完能做什么（Why）。文档要有开头、中间、结尾，按节组织，别是一面文字墙。

好文档三要素是完整（completeness）、准确（accuracy）、清晰（clarity），但很少能在一份里同时做满：API 注释重准确与完整，概念文档重清晰。所以本章要求每份文档只服务一个目的——想同时做教程、参考和设计说明的文档，三样都做不好。

文档会过期，要能被废弃。旧文档比没文档更糟，因为它会误导。原书介绍的做法是在文档里写入「新鲜度」日期（freshness），记录上次复查时间；超过设定期限（书中举例为三个月）没人碰，系统就提醒所有者复查。不再适用的文档应明确标注废弃或直接删除。

关键权衡与选型

表 1 · 文档放哪：三种常见做法

做法好处诚实的代价适合
维基 / 在线文档平台门槛低、非工程师也能写、富文本脱离代码改动，最易过期；所有者常常不明跨团队的流程、产品说明、会议纪要
仓库内 Markdown（Google 的选择）和代码同一个 CL 改、同一套评审与所有者，有历史非工程师参与难；排版能力有限；要有渲染工具README、API 用法、值班手册、贴近代码的指南
代码注释离代码最近，改函数时最难忽略只能讲局部；写成「复述代码」就是噪音函数 / 类的契约、「为什么这样写」

表 2 · 五类文档：给谁、追求什么、最常见的坑

类型主要读者优先追求常见坑
参考 / 注释寻找者、API 使用方准确、完整复述代码在做什么，不说契约与边界
设计文档评审者、未来维护者权衡与备选方案当成活文档持续引用，实际早已与实现脱节
教程新手每一步都可执行跳步、默认读者已配好环境
概念文档偶遇者清晰想面面俱到，结果谁都看不懂
落地页所有人指路把值班信息和使用说明混在一起

选型判据：文档离代码越近、越随代码一起被评审，就越不容易说谎；离代码远的内容（产品、流程）可以留在 wiki，但要从 README 链过去，保证只有一份权威版本。另一条判据关于人：原书认为大多数团队内部文档应由工程师自己写；技术写作者最该投入在跨越团队或公司边界的文档上，比如对外 API 文档——那里读者与作者的知识落差最大。

为什么重要 / 落到真实系统

「docs as code」如今是业界主流：GitHub 仓库的 README 与 docs/ 目录、Python 的 docstring 与 Sphinx、Rust 的 cargo doc 和会被当测试跑的文档示例，都在走同一条路——文档跟代码同仓、同版本、同评审。Chromium 等 Google 开源项目里随处可见的目录级 README 也是这套做法。面试或架构评审被问「怎么保证文档不过时」，好答案不是「定期整理 wiki」，而是「文档进仓库、和代码同 CL 评审、有所有者、有新鲜度提醒」。

大厂实证 · 公开可查

  • Google · 同一个 CL：Google 公开的文档指南写道「在与代码改动相同的 CL 里修改文档」，并说好的评审者至少可以坚持让 docstring、头文件、README 随改动一起更新。google/styleguide · Documentation Best Practices ↗
  • Google · 少而新：同一指南的「最小可行文档」：一小组新鲜准确的文档，胜过一大堆年久失修的「文档」；文档要像盆景一样活着但常被修剪。还写道「重复是邪恶的」——别自写一份通用技术的指南，链过去。google/styleguide · Documentation Best Practices ↗
  • Google · 不切换工具：文档指南的「哲学」一页写道「尽量减少上下文切换会让人更快乐」，工程师应能用读写代码的同一套工具来处理文档；并主张纯文本源码本身就该可读。google/styleguide · Philosophy ↗
  • Google · 迁移的亲历者：Google 技术写作者 Riona MacNamara 在 Write the Docs 2015 的演讲《Documentation, Disrupted》讲述了推动工程文档进入源码、改变工程文化的过程。Write the Docs NA 2015（文字出处）
  • 反方视角 · 敏捷宣言：2001 年《敏捷宣言》写下「可工作的软件高于详尽的文档」。它并不反对文档，而是反对为写而写——与本章「少而新、一份一事」其实同向，但常被误读成「不用写文档」。Agile Manifesto，2001（文字出处）

易错点与争议

  • 「文档越多越好」——错。过时文档会误导，比没有更糟；Google 的指南主张少而新、默认删除。
  • 「代码即文档、好代码不需要注释」——只对一半。好命名能替代大量注释，但代码说不出「为什么这样做」、也说不出函数对调用方的契约。
  • 把设计文档当活文档。设计文档记录的是当时的决策；实现上线后应视为档案，现状去看贴近代码的文档。
  • 一份文档想服务所有人。新手、老手、使用方、维护方的需求互相冲突，硬塞一份只会让每个人都找不到自己要的。
  • 「搬进仓库就解决了」——不够。没有所有者和新鲜度机制，仓库里的 Markdown 一样会烂；工具只是让纪律变便宜，不能替代纪律。
  • 语境局限。g3doc、OWNERS、全员单体仓是 Google 特有的基础设施；原书也承认文档在 Google 仍是进展缓慢的领域，技术写作者相对工程师数量很少，许多做法只覆盖了工程文档、未必适用于面向用户的产品文档。

要点

① 文档写不好主要是流程问题：收益在下游、工具在别处、没有主人。

② 核心论断：文档与代码紧耦合，就该像代码一样对待——规范、源码控制、所有者、评审、问题追踪、定期评估、不重复。

③ 案例：GooWiki 无主、重复、过时 → 文档进代码目录、由 g3doc 渲染，随 CL 一起评审。

④ 最大的错误是不知道读者：寻找者 vs 偶遇者、使用方 vs 提供方，分开写。

⑤ 五类文档：参考 / 注释、设计文档、教程、概念文档、落地页，各管一件事。

⑥ 三种评审：技术（对不对）、读者（懂不懂）、写作（一致吗）。

⑦ 开头答 5W；完整、准确、清晰难兼得，所以一份文档只服务一个目的。

⑧ 文档会过期：写新鲜度日期、到期提醒所有者、不适用就废弃或删除。

⑨ 易错：多不等于好；好代码不能替代契约与「为什么」；搬进仓库也要配所有者和复查机制。
