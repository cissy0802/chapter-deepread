把错误定义掉

A Philosophy of Software Design · Ch 10 · Define Errors Out of Existence · Ousterhout · 2nd ed 2021

EN →

这一章讲什么？

你用手机删一张照片，照片其实已经不在了——系统是弹出一句「出错了：照片不存在」，还是安安静静地告诉你「删好了」？程序里到处是这种选择。很多人觉得报错越多越严谨。这一章说：每多一种「出错」，就多一个所有人都得处理的麻烦；最好的错误处理，是让这个错误根本不会发生。

打个比方

你让家人「把灯关了」。灯本来就是关着的，好的家人会说「好了」，而不是跑回来跟你说「报告，灯已经是关的，无法执行关灯」。你要的其实是「灯是关着的」这个结果，不是「按一下开关」这个动作。把要求说成结果，原来那个「错误」就消失了。

旧世界为什么难

处理意外的代码，平时几乎不会被走到，所以最容易藏着没人发现的毛病。更麻烦的是，一个零件只要宣布「我可能出这种错」，所有用它的人都得各自写一段应对；十个人用，就是十份应对，十个可能写错的地方。

核心机制直觉

  • 换个说法，让错误消失。就像关灯：把「删掉它」理解成「确保它不在了」，本来就不在，也算成功。
  • 在底层悄悄兜住。寄快递丢了，快递公司自己补发，你只管收货——你甚至不知道中途丢过。
  • 集中到一个地方处理。商场不让每个柜台都设失物招领，统一送到服务台，一处办好。
  • 少见又救不回来的，就干脆停下。就像电脑彻底卡死时直接重启，比为每一种奇怪情况写一套抢救流程更省事。

带来了什么 / 该怎么选

用的人要操心的事少了，出错的机会也跟着少了。判断标准很简单：用的人知道了这个错误，能做点什么吗？不能，就别让它出现在他面前。一句诚实的代价：这招不能滥用——如果用的人确实需要知道（比如消息真的没送到），硬藏起来就是在骗他。

一句话记住

别急着报错，先想想能不能换个定义，让这个错误根本不存在。

一句话

你以为多抛异常是严谨、是「把问题暴露出来」；Ousterhout 说异常是复杂度最大的来源之一，而降低它的最好办法不是把每个异常处理得更好，而是减少必须处理异常的地方——首选是重新定义接口语义，让错误情况根本不存在。

Glossary · 术语表

  • 异常（exception）：打断正常执行流程的少见情况，比如参数不合法、文件打不开、网络丢包。本章把「返回错误码」也算在内。
  • 抛出 / 捕获（throw / catch）：发现问题的代码把异常「扔」出来，上层用 try/catch 接住并处理；没人接就一路往上冒。
  • 调用方（caller）：使用某个方法或模块的那段代码。
  • 接口（interface）：调用方必须知道的一切。一个方法会抛哪些异常，也是接口的一部分。
  • 深模块（deep module）：第 4 章的概念，接口简单、背后做的事多。异常越多，接口越复杂，模块越浅。
  • 重传（retransmission）：网络协议发现数据包丢了，自动再发一次。
  • NFS：网络文件系统（Network File System），让一台机器像访问本地磁盘一样读写远程服务器上的文件。
  • 文件描述符（file descriptor）：进程打开文件后拿到的「把手」，之后靠它读写，关闭后失效。
  • 子串（substring）：从一个字符串里按起止位置截出的一段。

坐标

全书第 10 章。第 8 章说「把复杂度向下沉」、第 9 章讲合与分；这一章把同样的思路用到异常处理上——异常是接口里最容易被忽视的那部分复杂度。下一章转向「设计两次」。现实里对应每一次「这里要不要抛个异常 / 返回个错误码」的决定，以及 rm -f、mkdir -p、DROP TABLE IF EXISTS 这类接口设计。

这章要解决什么

作者先说明异常为什么不成比例地制造复杂度：

  • 处理起来本来就难。遇到异常，要么想办法继续把事做完（比如丢包就重发），要么放弃并向上报告；放弃更难，因为得把已经做了一半的状态恢复成一致的样子。
  • 处理代码会生出新异常。书中的例子：为了应对丢包而重发，可原包其实只是慢了，结果对方收到两份——处理「丢失」又制造了「重复」。
  • 语言语法很啰嗦。书里一段 Java 示例，try/catch 的代码比正常逻辑还长，把主线淹没了。
  • 几乎没被执行过。异常处理代码很少运行，也很难测试，bug 能潜伏很久。作者引用 OSDI 2014 的一项研究：分布式数据密集型系统里，超过 90% 的灾难性故障源于错误处理不当。

再加上一个人为因素：抛异常很容易，处理异常很难。作者举了自己的教训——他在设计 Tcl 语言时，让 unset（删除变量）在变量不存在时报错。可 unset 最常见的用法是清理临时状态，清理时往往并不确定变量有没有被创建过；结果几乎所有人都得把 unset 包在 catch 里吞掉这个错误。一个类抛的每种异常都是接口的一部分，异常越多，模块越浅。不解决，复杂度就会沿着调用链扩散到每个调用方。

核心内容，讲透

作者给出四种减少异常处理位置的技法，按优先级排：定义掉、屏蔽、聚合、直接崩溃；外加一条推广——把特殊情况也设计掉。

一、把错误定义掉：改语义，而不是加处理

核心动作是把接口从「执行某个动作」改成「保证某个结果」。Tcl 的 unset 若定义为「保证这个变量不存在」，变量本来就不在时，结果已经达成，没什么可报的。作者举了两个更有分量的例子。

删除被打开的文件。在 Windows 上，文件被某个进程打开时不能删除，用户得去找出是哪个进程占着它、把它关掉，有时干脆只能重启。Unix 的做法是：删除时立刻从目录里移除文件名，正在使用它的进程照常读写；等最后一个进程关闭它，数据才真正释放。删除者不会遇到「文件忙」，使用者也不会遇到「文件突然没了」——两边的错误同时被定义掉了。

Java 的 substring。substring(begin, end) 的下标一旦超出字符串范围就抛 IndexOutOfBoundsException，调用方只好先检查、再截取。作者主张改成：返回下标落在 [begin, end) 里、且确实存在的那些字符——越界的部分自然为空。Python 的切片就是这样："Python"[4:42] 得到 'on'，不报错。会有人反对说「这样会掩盖 bug」，作者的回答大意是：错误类越多，调用方要写的代码越多、出错的地方越多；减少 bug 最好的办法是让软件更简单。

二、屏蔽异常：在底层就地兜住

能在低层处理掉的异常，就别让高层知道。TCP 是经典例子：网络会丢包，但 TCP 在协议内部重传，应用只看到一条可靠的字节流。另一个是 NFS：服务器崩溃或无响应时，客户端不向应用返回错误，而是挂起并不断重试，直到服务器恢复，同时在控制台打出「NFS server xxx not responding still trying」。用户确实会抱怨程序卡住，但作者认为这比另一种选择好得多：如果把错误抛给应用，每个应用都要处理「文件服务器不见了」，而它们大多也只能退出，用户还得重跑。屏蔽本质上就是第 8 章的把复杂度向下沉：一处处理，所有上层受益。

论文精读 · End-to-End Arguments（端到端论证） — 底层「兜住」丢包能做到多完整、哪些保证最终只能由端点自己检查，正好是屏蔽异常的边界

三、异常聚合：一个 catch 接住一大类

与其在每个产生异常的地方各自处理，不如让它们一路冒到一个统一的地方，用一段代码处理一大类异常。书中的例子是 Web 服务器：几十个 URL 处理函数都要读请求参数，参数缺失时，学生常在每个函数里各写一段报错逻辑；更好的做法是让取参数的方法抛出同一种「参数不存在」异常，由最顶层的分发器统一捕获、生成错误响应。处理代码从几十份变成一份，新增 URL 时也不用再写。

聚合的另一种形态是把罕见的错误「升级」成一个已有的、更常见的恢复路径。作者以自己参与的 RAMCloud 存储系统为例：一些少见的故障不单独写修复逻辑，而是交给本来就必须存在、也经常被演练的崩溃恢复机制统一处理。好处是那段恢复代码天天在跑，比一段极少执行的专用处理可靠得多。

四、直接崩溃：别为救不回来的事写代码

有些错误既罕见、又几乎没法有意义地处理，那就打印诊断信息后直接终止。典型是内存耗尽：C 里 malloc 返回空指针时，调用方其实很难做出有用的事；Tcl 的做法是包一层 ckalloc，分配失败就直接 panic，于是成千上万个调用点都不用检查返回值。程序内部检测到状态已不一致，也属此类。但要看应用：一个复制式存储系统遇到磁盘 I/O 错误就不能一崩了之，因为它的职责正是在硬件出错时保住数据。

五、把特殊情况也设计掉

同样的思路适用于一般的特殊情况。编辑器里若有「当前没有选区」这个特殊状态，代码到处都要先判断「有没有选区」；如果改成永远有一个选区，只是可能为空（起点等于终点），这些判断就全没了——对空选区执行「删除选中内容」，什么也不发生，天然正确。

六、过犹不及：调用方需要知道的，必须暴露

定义掉或屏蔽一个异常，前提是模块外部不需要这个信息。作者举的反例是网络通信：若一个网络模块把所有错误都吞掉，应用就无从得知消息丢了，也就无法采取补救。判断标准是：调用方拿到这个错误后，能不能、需不需要做些不同的事？需要，就把它留在接口里。

为什么重要 / 落到真实系统

这一章是 API 评审时最实用的一把尺子：每新增一种异常或错误码，就问它会让多少个调用点多写一段处理。对分布式系统尤其要紧——那里的错误路径最多、最难复现，结果式、可重复执行的接口（重试多少次结果都一样）能把大量「上次做到一半怎么办」的分支直接消掉。

实证与出处 · 公开可查

  • 错误处理是故障的主要来源。Yuan 等人分析了 Cassandra、HBase、HDFS、Hadoop MapReduce、Redis 的真实故障报告，结论是：灾难性故障中 92% 源于对「明确发出的非致命错误」处理不当，其中不少处理代码只是空的 catch 或一句 TODO。这正是作者引用的那项研究。出处：Yuan et al., "Simple Testing Can Prevent Most Critical Failures", OSDI 2014
  • Go 标准库把「不存在」定义成成功。os.RemoveAll 的文档注释写明：路径不存在时，RemoveAll 返回 nil（无错误）。出处：golang/go · src/os/path.go
  • PostgreSQL 提供可选的 IF EXISTS。文档对该选项的说明是：表不存在时不抛错误，改为发出一条提示（notice）。这是「定义掉」与「让调用方选择」之间的折中。出处：postgres/postgres · doc/src/sgml/ref/drop_table.sgml
  • Python 切片：书中 substring 主张的现成实现。官方教程写道，越界的切片下标会被「优雅地处理」；但对单个下标越界仍然报 IndexError——取一段可以为空，取一个字符却无法凭空给出。出处：python/cpython · Doc/tutorial/introduction.rst

易错点与争议

  • 「定义掉 = 吞掉异常」。不是。吞异常是错误仍然存在、只是没人管；定义掉是改了语义，那种情况本来就是合法结果，并且在接口文档里写清楚。
  • 「异常越多越安全」。每种异常都要求每个调用方写处理，而处理代码最少被执行、最容易有 bug——上面 92% 那个数字就是代价。
  • 「屏蔽总是好的」。NFS 的卡住、网络模块吞掉丢包，都说明屏蔽的前提是上层不需要知道。藏过头会让问题在更远处、以更难诊断的形式爆出来。
  • 「直接崩溃是偷懒」。对罕见且无法挽救的错误，崩溃比一段从没被测过的恢复代码更可靠；但对把容错当本职的系统，这条不成立。
  • 争议：宽松语义会不会掩盖 bug？主张「快速失败」的一派认为越界就该立刻报错，早暴露早修。Ousterhout 的立场是看整体：多数调用方根本不在乎越界，为少数真写错的情况让所有人背负检查，得不偿失。两种观点各有适用场景，关键看调用方拿到错误能不能做点不同的事。

要点

① 异常是复杂度的大户：处理难、会生出新异常、语法啰嗦、几乎不被执行。

② 研究表明，分布式系统的灾难性故障九成以上源于错误处理不当。

③ 抛异常容易、处理难；一个类抛的每种异常都是接口的一部分，异常越多模块越浅。

④ 目标不是把异常处理得更好，而是减少必须处理异常的地方。

⑤ 首选「定义掉」：把接口从执行动作改成保证结果——unset、Unix 删文件、按交集截取子串。

⑥ 其次屏蔽（TCP 重传、NFS 重试）和聚合（顶层分发器一个 catch）。

⑦ 罕见且救不回来的错误直接崩溃，如内存耗尽；但存储这类系统必须处理 I/O 错误。

⑧ 特殊情况同理：用空选区代替「没有选区」，判断全消。

⑨ 边界：调用方需要据此做不同的事时，异常必须留在接口里。
