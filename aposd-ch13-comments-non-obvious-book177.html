注释写「不明显」的东西

A Philosophy of Software Design · Ch 13 · Comments Should Describe Things that Aren't Obvious from the Code · Ousterhout · 2nd ed 2021

EN →

这一章讲什么？

上一章说「注释必须写」，这一章回答下一个问题：写什么？作者的答案只有一条：只写光看代码看不出来的东西。就像你给邻居留钥匙时写的纸条——不用写「这是一把钥匙」，要写的是「门有点卡，往上提一下再转」。

先说个怪事

很多人写注释，写的是「下一行把计数加一」。读代码的人当然看得出来，这句话等于没写。可是真正重要的事——这个计数从 0 还是从 1 开始、数到哪里为止、为什么要数——反而一个字都没有。最常见的烂注释，不是写错了，而是写了一遍代码已经说过的话。

旧世界为什么难

写代码的人对代码太熟了，分不清哪些是「谁都看得懂的」、哪些是「只有我知道的」。于是他把显而易见的写了一遍，把只有自己知道的那部分漏掉了。接手的人只好去翻其他文件、去问人、去猜。

核心机制直觉

  • 别复述代码。检验办法：一个从没看过这段代码的人，能不能只看代码就写出你这句注释？能，这句就是废话。
  • 往细里补：精确。比如一个「超时」，要说清单位是秒还是毫秒、填 0 是什么意思。像菜谱里写「盐少许」，不如写「一小勺」。
  • 往粗里补：直觉。一大段复杂代码前面，用一句话说它「想干什么」——像地图上标「这一片是商场」，而不是把每家店名都列一遍。
  • 给用的人和给改的人，分开写。用的人只需要知道「怎么用、会有什么后果」，像家电说明书；改的人才需要知道「里面怎么做、为什么这样做」，像维修手册。两本别混成一本。
  • 跨文件的约定，写在别人会去找的地方。「改了这里，记得也改那个文件」，要写在改的人一定会经过的位置。

带来了什么 / 该怎么选

照这样写，读的人不用把代码翻个底朝天，就能放心地用它、改它。一句诚实的代价：判断「什么不明显」需要换位思考，作者本人往往最难看出来，常常要靠同事看过才知道。

一句话记住

注释的价值，等于它说出了多少代码没说的东西——要么更细，要么更高，别站在和代码同一层。

一句话

你以为好注释就是「把代码解释一遍」；Ousterhout 说，和代码处在同一层的注释几乎没有价值。注释的价值在于它比代码更低一层（补精确：单位、边界、空值含义）或更高一层（补直觉：这段想干什么、为什么），并且要把接口注释（给使用者）和实现注释（给维护者）分开。

Glossary · 术语表

  • 接口注释（interface comment）：写在类或方法声明前、给使用者看的说明，告诉人怎么用、会有什么效果。
  • 实现注释（implementation comment）：写在方法内部、给修改这段代码的人看的说明。
  • 抽象（abstraction）：只留下使用者需要的信息、把其余细节藏起来的简化视图。
  • 副作用（side effect）：方法除了返回值以外对外界造成的改变，比如改了某个全局状态、写了文件。
  • 前置条件（precondition）：调用一个方法之前必须已经成立的条件。
  • 不变量（invariant）：某个数据结构在任何时候都保持成立的性质，例如「这个列表至少有一项」。
  • 红旗（red flag）：书中贯穿全书的设计警示信号，看到它就该停下来想想。
  • Javadoc / Doxygen：从特定格式的注释自动生成 API 文档的工具。

坐标

这章要解决什么

写注释的理由是：写代码用的语言（编程语言）表达力不如写代码的人脑子里的想法。很多重要信息——为什么这样写、一个变量的单位、一个方法的副作用——在代码里根本没有位置。注释就是要把这些补上。

可现实中大量注释在做反方向的事：复述代码。这种注释写的人花了时间、读的人花了时间、维护时还要跟着改，却没有带来任何新信息；更糟的是它让人以为「这里已经有注释了」，真正缺的信息就再也没人补。本章给出一套判据，让每一行注释都承担代码承担不了的那部分。

核心内容，讲透

一、先定约定：写在哪、什么格式

作者建议先给团队定好注释约定：每个类和方法的接口注释、每个类成员变量的注释、方法内部的实现注释、跨模块的设计说明，各放在哪、用什么格式（例如 Javadoc、Doxygen、Go 的 godoc 风格）。约定的作用是让人知道该去哪里找信息，也让写的人知道自己欠着哪几处。

二、别复述代码

本章第一条红旗：注释复述代码（Comment Repeats Code）。判据很具体：一个没看过这段代码的人，能否只凭旁边的代码写出这句注释？能，这句就没价值。一个常见变体是注释里用的词和变量名、方法名一模一样，只是把名字拼成了句子。

修正办法：换别的词。名字已经说过的事别再说一遍，转而写名字说不出的：这个值的含义、它的边界、为什么需要它。

三、更低一层的注释：补精确

这类注释最常用在变量声明上，包括类的成员变量、方法参数和返回值。变量名和类型通常太含糊，作者列出的典型缺口：

  • 单位：秒还是毫秒，字节还是字符；
  • 边界：区间的两端是否包含在内；
  • 空值：允许 null 吗，null 代表什么；
  • 资源归属：谁负责释放、关闭这个资源；
  • 不变量：例如「这个列表总是至少有一项」。

写变量注释时作者的建议是想名词，不想动词：描述这个变量代表什么，而不是代码怎样操作它。示意：// 当前在响应缓冲区里的读取位置 不如 // 响应缓冲区中下一个尚未读取的字节的偏移量；等于长度表示读完——后者说清了指向哪个字节、何时算结束。

四、更高一层的注释：补直觉

这类注释写在一段代码之前，告诉读者这段整体在做什么、为什么，让人不读每一行也能把握结构。书里举了一个来自真实系统代码的块注释：原注释逐条描述条件（如果某个请求处于某状态、且它的最后一个键小于当前键，就把当前键放进去），几乎是代码的另一种写法；改写后只一句——大意是「尝试把当前这个键并入一个已有的、发往同一服务器但尚未发出的请求」。读者立刻知道这段代码的目的，细节再去看代码。

作者给的自问清单：这段代码想做什么？能解释全部的最简单说法是什么？这段代码里最重要的是什么？工程师往往擅长写细节，写高层注释更难，因为它要求跳出代码想整体。

五、接口注释：给使用者的那本说明书

本章最长的一节。核心原则：把接口注释和实现注释分开。接口注释提供使用一个类或方法所需的信息，不应该描述内部怎么实现。第二条红旗正针对此：实现细节污染接口文档（Implementation Documentation Contaminates Interface）。

类的接口注释给出这个类提供的抽象的高层描述；方法的接口注释通常包括：

  • 一两句话的高层行为描述，以调用者的视角写；
  • 每个参数和返回值的精确含义与约束；
  • 副作用，即对系统未来行为的影响；
  • 可能抛出的异常；
  • 调用前必须满足的前置条件。

书中以一个缓冲区类的拷贝方法为例，大意是：说明它把缓冲区中一段字节拷到外部位置；offset 是要拷的第一个字节的下标，length 是字节数，dest 必须至少有 length 字节的空间；返回值是实际拷贝的字节数——若请求的范围越过缓冲区末尾会少于 length，完全不重叠时返回 0。最后这句正是使用者最容易踩坑、而签名完全表达不了的信息。

作者还给了一个判据：使用者只读外部可见的声明和接口注释，就应该能理解这个模块的抽象。做不到，要么注释缺了，要么接口本身太复杂。

六、实现注释：写「做什么、为什么」，不写「怎么做」

实现注释的主要目的是帮读者理解代码在做什么，而不是怎么做——怎么做看代码就够了。很多短方法根本不需要实现注释；长方法里，在几个主要代码块前各写一句「这块在做什么」很有用；循环前说明每轮做什么也有帮助。

此外要写为什么：一段看起来多余的代码是为了修某个 bug、绕开某个怪问题，就把原因写下（必要时附缺陷编号），否则后人会以为它多余而删掉。

七、跨模块的设计决策

最难写的是横跨多个模块的约定，例如：新增一种状态码，需要同时在另一个文件的表格里补上它的文字描述。这种依赖不在任何单一模块里，开发者很容易漏掉。作者的办法：

  • 把说明放在开发者一定会经过的地方——如状态码枚举的声明旁边，写明「新增时还要改哪里」；
  • 没有天然位置时，建一个设计说明文件（designNotes），按主题分节，在相关代码处留一句简短引用，如「见 designNotes 里的某某节」。

关键权衡与选型

表 1 · 四类注释：给谁看、写什么、典型错误

类型读者该写典型错误
接口注释使用者行为、参数与返回值含义、副作用、异常、前置条件写进实现细节（红旗）；只复述方法名
成员 / 变量注释使用者与修改者单位、边界、null 含义、归属、不变量（想名词）描述代码怎么操作它（想动词）
实现注释修改者每块在做什么；反常写法的原因逐行解释「怎么做」
跨模块注释未来的修改者「改这里还得改哪里」及原因没有位置就干脆不写

表 2 · 「更细」还是「更高」：怎么选

场景更低一层：精确更高一层：直觉
适用位置变量、参数、返回值代码块之前、类与方法的总述
补的缺口名字和类型说不清的细节读完每一行也拼不出的整体意图
难点要想全所有边界情况要跳出代码，找到最简单的说法
代价细节多，需随代码同步抽象措辞容易空泛，需同事检验

一句判据：写完一句注释，问「没看过这段代码的人，凭代码能写出它吗」——能就删掉或换成更细 / 更高的说法。

为什么重要 / 落到真实系统

实证与出处 · 公开可查

  • Google C++ 风格指南：函数的声明注释描述函数的用法，定义处的注释描述它的运作；声明注释一般不写函数怎样完成任务，那留给定义处。实现注释一节明确：不要陈述显而易见的东西，提供更高层的注释说明代码为什么这样做。出处：google/styleguide · cppguide.html
  • Python PEP 257：函数或方法的 docstring 应概括其行为，并说明参数、返回值、副作用、抛出的异常以及调用限制——与本章接口注释的清单几乎一一对应。出处：python/peps · pep-0257.rst
  • Linux 内核编码规范：注释一般应说明代码做什么，而不是怎么做，并尽量避免在函数体内写注释——与本章「实现注释写做什么」同向，但对函数内注释更保守。出处：torvalds/linux · coding-style.rst

落到日常：代码评审时看到 i++ // i 加一 式注释，可以直接引本章「复述代码」红旗；看到公开方法没有说明返回值边界，可以要求补接口注释。接口注释本质上就是 API 的契约，对外公开以后改起来代价更高。

易错点与争议

  • 「注释越详细越好」。不对。逐行解释「怎么做」的注释正是复述；该详细的是精确信息（单位、边界），不是步骤。
  • 「接口注释里说清楚实现，用户更放心」。恰恰相反，这是红旗：实现细节一进接口文档，使用者就开始依赖它，抽象就漏了。
  • 「什么是明显的，作者说了算」。作者对代码最熟，最难判断。评审时同事觉得哪里看不懂，那里就不明显——第 18 章会把这点讲透。
  • 与 Linux / Clean Code 的分歧。Linux 规范和《Clean Code》都倾向少写函数体内注释、把复杂逻辑拆成小函数；Ousterhout 更接受长而深的方法加块注释。两种取向在业界并存。
  • 接口注释很难写，不一定是写作问题。说不清一个方法做什么，常常说明接口本身有问题，这正是第 15 章「先写注释」的出发点。

要点

① 注释的价值 = 代码没说出的信息；和代码同一层的注释几乎无价值。

② 红旗一「复述代码」：没看过代码的人凭代码能写出它，它就该删；别重复名字里的词。

③ 更低一层补精确：单位、边界是否包含、null 含义、资源归属、不变量；变量注释想名词。

④ 更高一层补直觉：这段想做什么、最简单的说法、最重要的是什么。

⑤ 接口与实现分开；红旗二「实现细节污染接口文档」。

⑥ 方法接口注释五样：行为、参数与返回值、副作用、异常、前置条件。

⑦ 只读声明和接口注释就该能理解抽象，否则注释缺了或接口太复杂。

⑧ 实现注释写做什么和为什么；跨模块约定放在必经之处，或集中到 designNotes。

⑨ Google C++ 指南、PEP 257、Linux 规范都印证了这套分层；函数内注释多少仍有分歧。
