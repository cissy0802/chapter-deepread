Comments Should Describe What Isn't Obvious

A Philosophy of Software Design · Ch 13 · Comments Should Describe Things that Aren't Obvious from the Code · Ousterhout · 2nd ed 2021

中文 →

What is this chapter about?

The previous chapter said comments must be written. This one answers the next question: what should they say? The author's answer is a single rule: write only what you can't see by reading the code. Think of the note you leave a neighbor with your spare key. You don't write "this is a key." You write "the door sticks — lift it a little before you turn."

A strange thing first

Lots of people write comments like "add one to the counter on the next line." Anyone reading the code can see that, so the sentence says nothing. Meanwhile the things that matter — does the count start at zero or one, where does it stop, why are we counting at all — are missing. The most common bad comment isn't wrong; it just repeats what the code already said.

Why the old world was hard

The person who wrote the code knows it too well to tell "obvious to anyone" apart from "known only to me." So they restate the obvious and leave out the part only they know. Whoever comes next has to dig through other files, ask around, or guess.

How it works, intuitively

  • Don't repeat the code. The test: could someone who has never seen this code write your comment just by looking at it? If so, it adds nothing.
  • Go finer: precision. For a "timeout," say whether it's seconds or milliseconds and what zero means. A recipe that says "a teaspoon" beats one that says "a pinch of salt."
  • Go higher: intuition. Before a big, tricky block, say in one sentence what it's trying to do — like a map labeling an area "shopping mall" instead of listing every store.
  • Write separately for users and for fixers. Users need "how to use it and what happens," like an appliance manual. People changing the code need "how it works inside and why," like a repair manual. Don't merge the two.
  • Put cross-file rules where people will look. "If you change this, also change that other file" belongs exactly where the person making the change will pass by.

What it buys you / how to choose

Written this way, readers can use and change the code with confidence without turning it inside out. One honest cost: judging what isn't obvious means putting yourself in a stranger's shoes, and the author is usually the worst judge — often it takes a colleague reading it to find out.

One line to remember

A comment is worth exactly what it says that the code doesn't — go finer or go higher, but never sit at the same level as the code.

In one sentence

You'd think a good comment explains the code; Ousterhout says a comment at the same level as the code is nearly worthless. A comment earns its keep by being lower-level than the code (adding precision: units, boundaries, what null means) or higher-level (adding intuition: what this block is for, and why) — and by keeping interface comments (for users) apart from implementation comments (for maintainers).

Glossary

  • Interface comment: the text before a class or method declaration, written for callers — how to use it and what it does.
  • Implementation comment: text inside a method body, written for whoever modifies that code.
  • Abstraction: a simplified view that keeps only what a user needs and hides the rest.
  • Side effect: any change a method makes to the outside world beyond its return value, such as updating shared state or writing a file.
  • Precondition: something that must already be true before a method is called.
  • Invariant: a property a data structure keeps at all times, e.g. "this list always has at least one entry."
  • Red flag: the book's recurring design warning sign — when you see one, stop and rethink.
  • Javadoc / Doxygen: tools that generate API documentation from specially formatted comments.

What problem this chapter solves

We comment because a programming language is less expressive than the ideas in the programmer's head. Plenty of important information — why something is done this way, a variable's unit, a method's side effects — has no place to live in the code. Comments exist to carry it.

Yet a large share of real comments do the opposite: they restate the code. Such a comment costs the writer time, costs the reader time, and has to be kept in sync, all without adding information. Worse, it makes the spot look "already commented," so the information that's actually missing never gets written. This chapter gives a set of tests so every line of comment carries what code can't.

The core ideas, in depth

1. Pick conventions first: where, and in what format

The author recommends agreeing on conventions up front: interface comments for every class and method, comments for every class member variable, implementation comments inside methods, and notes on cross-module design — where each goes and in what format (Javadoc, Doxygen, Go's godoc style and so on). Conventions tell readers where to look, and tell writers which slots they still owe.

2. Don't repeat the code

The chapter's first red flag: Comment Repeats Code. The test is concrete: could someone who has never seen this code write the comment just from the code next to it? If so, it has no value. A common variant uses exactly the same words as the variable or method name, just strung into a sentence.

The fix: use different words. Don't repeat what the name already says; write what the name can't — the value's meaning, its limits, why it's needed.

3. Lower-level comments add precision

These matter most on variable declarations: class member variables, method arguments and return values. Names and types are usually too vague. The typical gaps the author lists:

  • Units: seconds or milliseconds, bytes or characters;
  • Boundaries: whether each end of a range is inclusive;
  • Null: is it allowed, and what does it mean;
  • Ownership: who is responsible for freeing or closing a resource;
  • Invariants: e.g. "this list always contains at least one entry."

For variable comments the author's advice is to think nouns, not verbs: describe what the variable represents, not how the code manipulates it. Illustration: // current position in the response buffer is weaker than // offset of the next unread byte in the response buffer; equals length when fully read — the second says which byte and when we're done.

4. Higher-level comments enhance intuition

These go before a block of code and tell the reader what the block does as a whole, and why, so they can grasp the structure without reading every line. The book shows a block comment from real systems code: the original spelled out every condition (if some request is in a certain state and its last key is smaller than the current key, put the current key into it) — practically the code rewritten in English. The revision is one sentence, roughly: "try to append the current key onto an existing request to the same server that hasn't been sent yet." The reader instantly knows the purpose; the details are in the code.

The author's self-check questions: What is this code trying to do? What is the simplest thing I can say that explains everything in it? What is the most important thing about it? Engineers tend to be good at details; higher-level comments are harder because they require stepping outside the code.

5. Interface comments: the user's manual

The chapter's longest section. Its core principle: separate interface comments from implementation comments. An interface comment gives what you need to use a class or method and should not describe how it works inside. The second red flag targets exactly this: Implementation Documentation Contaminates Interface.

A class's interface comment gives a high-level description of the abstraction it provides. A method's interface comment usually covers:

  • a sentence or two of high-level behavior, from the caller's point of view;
  • the precise meaning and constraints of each argument and the return value;
  • any side effects that affect the system's future behavior;
  • any exceptions it can throw;
  • any preconditions that must hold before calling it.

The book's example is a copy method on a buffer class. In substance its comment says it copies a range of bytes from the buffer to an external location; offset is the index of the first byte to copy, length the number of bytes, and dest must have room for at least length bytes; the return value is the number of bytes actually copied — fewer than length if the range runs past the end of the buffer, and 0 if there is no overlap at all. That last part is exactly what callers trip over, and the signature can't express it.

The author's yardstick: a user should understand a module's abstraction from its externally visible declarations and interface comments alone. If they can't, either the comments are missing something or the interface itself is too complex.

6. Implementation comments: what and why, not how

The main job of implementation comments is to help readers understand what the code is doing, not how — the code shows how. Many short methods need none at all. In a long method, a one-line "what this block does" before each major block helps a lot; so does a note before a loop on what each iteration does.

Also write down why: if code that looks redundant exists to fix a bug or work around an odd problem, say so (with a bug number if there is one), or someone will later delete it as useless.

7. Cross-module design decisions

The hardest comments cover conventions that span modules — for example, adding a new status code also requires adding its text description to a table in another file. That dependency lives in no single module, so developers easily miss it. The author's remedies:

  • put the note where a developer is sure to pass — e.g. next to the status-code enum declaration, saying what else must change;
  • when there's no natural spot, keep a design notes file (designNotes) split into topical sections, and leave a short pointer in the relevant code, such as "see the section on X in designNotes."

Why it matters / in real systems

The chapter's "keep interface and implementation apart" and "say why, not how" appear nearly word for word as rules in mainstream style guides:

Evidence and sources · publicly verifiable

  • Google C++ Style Guide: declaration comments describe use of the function; comments at the definition describe operation, and declaration comments generally don't describe how the function does its task — that's left to the definition. Its implementation-comment section says: do not state the obvious; provide higher-level comments that describe why the code does what it does. Source: google/styleguide · cppguide.html
  • Python PEP 257: a function or method docstring should summarize its behavior and document its arguments, return values, side effects, exceptions raised, and restrictions on when it can be called — almost item for item this chapter's interface-comment list. Source: python/peps · pep-0257.rst
  • Linux kernel coding style: generally, comments should tell what the code does, not how, and comments inside a function body should be avoided where possible — aligned with "implementation comments say what," but more conservative about in-function comments. Source: torvalds/linux · coding-style.rst

Day to day: when review turns up an i++ // increment i comment, cite the "Comment Repeats Code" red flag; when a public method doesn't document its return-value edge cases, ask for an interface comment. An interface comment is effectively the API contract, and once published it is costly to change.

Pitfalls and debates

  • "More detailed comments are always better." No. A line-by-line account of "how" is repetition. What should be detailed is precision (units, bounds), not steps.
  • "Explaining the implementation in the interface comment reassures users." The opposite — it's a red flag. Once implementation details enter the interface docs, users start depending on them and the abstraction leaks.
  • "The author decides what's obvious." The author knows the code best and judges worst. Whatever a reviewer finds confusing isn't obvious — Chapter 18 develops this.
  • The disagreement with Linux and Clean Code. Both lean toward few comments inside function bodies and splitting complex logic into small functions; Ousterhout is more comfortable with long, deep methods plus block comments. Both camps are alive in industry.
  • A hard-to-write interface comment isn't always a writing problem. If you can't say what a method does, the interface itself is often the problem — the starting point of Chapter 15, "Write the Comments First."

Takeaways

① A comment is worth the information the code doesn't carry; one at the code's own level is nearly worthless.

② Red flag one, "Comment Repeats Code": if someone new could write it from the code, delete it; don't reuse the words in the name.

③ Lower level adds precision: units, inclusive bounds, meaning of null, ownership, invariants; think nouns for variables.

④ Higher level adds intuition: what this tries to do, the simplest phrasing, the most important thing.

⑤ Keep interface and implementation apart; red flag two, "Implementation Documentation Contaminates Interface."

⑥ A method interface comment covers five things: behavior, arguments and return value, side effects, exceptions, preconditions.

⑦ Declarations plus interface comments alone should explain the abstraction; if not, comments are missing or the interface is too complex.

⑧ Implementation comments say what and why; cross-module rules go where people pass, or into designNotes.

⑨ Google's C++ guide, PEP 257 and the Linux style all echo this layering; how much to comment inside functions is still debated.
