单元测试

Software Engineering at Google · Ch 12 · Unit Testing · Erik Kuefler · 2020

EN →

这一章讲什么？

上一章说，自动检查能让很多人放心地天天改同一份程序。这一章往下走一步：Google 工程师写得最多的那种检查——只检查一小块代码的「单元测试」——怎么写，才能帮忙而不是添乱。

先说个怪事

你以为测试越多越安全，这一章开头讲了个反例。工程师 Mary 只加了二十几行代码，提交时却收到满屏的报错。她花了一整天逐个排查，发现一个真问题都没有：只是那些检查死记着程序内部「零件长什么样」，她挪了挪零件，检查就全红了。本该帮她省时间的测试，反倒吃掉了她几天。

旧世界为什么难

坏测试有两种病：一是脆，跟真问题无关的小改动也会让它失败；二是看不懂，失败了没人知道它当初想检查什么、该怎么修。在 Google，一个工程师一天就可能跑上千个测试，一次全公司范围的改动能牵动几十万个。哪怕只有一小部分测试乱报警，浪费的时间也是天文数字。

核心机制直觉

  • 从正门进：验车时，验车员只踩刹车、打方向盘，不去拆发动机看螺丝。修车师傅换了个零件，只要车照样能停，检查就该照样通过。
  • 看结果，不看过程：你寄一封信，只要确认它到了对方手里，不必规定邮递员必须走哪条街。死盯路线的检查，换条路就报错，信丢了反而发现不了。
  • 一个检查只问一件事：别写一个「把这个功能测一遍」的大杂烩，而是拆成一句句「当余额为零时，取钱会被拒绝」。名字本身就像一句说明书。
  • 检查要一眼看对：测试没有别的测试来检查它，所以别在里面玩花样计算，答案直接写出来。
  • 宁可啰嗦，也要写全：菜谱卡上把用料写全，比写「见第 37 页」更好用。测试里重复几行没关系，只要读的人不用到处翻。

带来了什么 / 该怎么选

按这套写法，测试写好以后基本不用再碰：改内部、加功能、修毛病都不该动它，只有程序「对外承诺的行为」真变了才需要改。Google 说，守这些规矩的测试，价值比不守的高出几个数量级。诚实的代价是：这样写一开始更费劲，要多想一步「用户会怎么用它」，还得容忍一些重复。

一句话记住

好的单元测试只在「真坏了」时报警，而且一报警，人就看得懂哪里坏了。

一句话

你以为单测写得多就好，本章说，维护性才是单测的命门——好测试写完就不该再改，失败时只因为真 bug、而且一眼看出原因。做法归成两条：防脆（从公开 API 进、验状态不验交互）和求清晰（测行为不测方法、不写逻辑、失败信息说人话、宁要 DAMP 不要 DRY）。

Glossary · 术语表

  • 单元测试（unit test）：范围较窄的测试，通常只验证一个类或一个方法；大小上一般是「小测试」（单进程、不碰网络磁盘，见第 11 章）。
  • 被测系统（system under test, SUT）：这个测试正在检查的那段代码。
  • 公开 API（public API）：一段代码对外部使用者提供的调用入口；与之相对的是只供内部使用的「实现细节」。
  • 重构（refactoring）：只改内部写法、不改对外行为的代码改动。
  • 测试替身 / mock：用来顶替真实依赖的假对象；mock 框架能记录「它被怎样调用过」（第 13 章详述）。
  • 断言（assertion）：测试里「检查结果是否等于预期」的那一句，不满足就让测试失败。
  • setup 方法：测试框架在每个测试运行前自动执行的准备代码，如 JUnit 的 @Before。
  • DRY：Don't Repeat Yourself，每个概念只在一处定义、尽量消除重复的编程原则。
  • 大规模变更（large-scale change, LSC）：一次横跨全仓成千上万个文件的自动化改动（第 22 章详述）。

坐标

Part III「流程」，测试四连章的第二章。上承 Ch11 测试总览（大小与范围两个维度），下启 Ch13 测试替身（本章反复说「少用 mock」，下一章展开）、Ch14 更大范围的测试。现实对应：JUnit / Truth / Go testing 的日常单测写法。

这章要解决什么

单测是 Google 写得最多的测试。本章给出的经验配比是约 80% 单测、20% 范围更大的测试（第 11 章把后者再拆成 15% 集成 + 5% 端到端）；一个工程师平均每个工作日直接或间接跑上千个单测，一次大规模变更就能触发几十万个测试。单测之所以划算：小而快、确定，能边写代码边写，覆盖率容易做高，失败好定位，还能当用法示例。

但量大意味着它的维护成本也被放大。本章用 Mary 的故事开场：几十行的小功能，提交后满屏失败，没有一个是真 bug，全是测试对代码内部结构的假设被打破；她看不懂这些测试原本想干什么，修补时塞进去的 hack 又让它们更难懂。测试反而拖累了生产力，却没有提升代码质量。原书把病因归成两类：脆（brittle）——无关的无害改动也会让它失败；不清晰（unclear）——失败后很难判断哪里错、怎么修、它本来测什么。不解决会怎样？原书说：每次改动都要人手调测试，叫它「自动化测试套件」就有点勉强了。

核心内容，讲透

一、目标：「写完就不变」的测试

原书先回答一个问题：测试写好后，预期要改它几次？答案按生产代码的四类改动来定：

  • 纯重构：不改接口地改内部（为性能、为可读）。测试的职责就是证明行为没变，所以不该改。要改，说明这不是纯重构，或测试写错了抽象层级。
  • 新功能：加新测试覆盖新行为，已有测试不该改。
  • 修 bug：bug 的存在说明套件漏了一个用例，补上这个用例，已有测试同样不该改。
  • 行为变更：唯一预期要改测试的情形。而且它本来就最贵——用户依赖着现有行为，改它要和用户协调。

原书的提法很精准：行为变更时改测试，说明你在打破一份显式契约；前三类情形里改测试，说明你打破了一份无意中形成的契约。有了这条，扩展系统只需写几条新测试，而不是碰遍所有旧测试；Google 大量重构靠大规模变更完成，这点尤其要紧。

二、从公开 API 测：用户怎么用，测试就怎么用

防脆的头号手段：像用户那样调用被测系统，只走公开 API，不碰实现细节。原书的例子是一个转账处理器：公开方法 processTransaction，内部有私有的 isValid（金额小于余额）和 saveToDatabase（把记录拼成 "me,you,100" 写库）。偷懒的写法是去掉 private 直接测这两个方法、断言库里那串字符串——方法改个名、拆进辅助类、换个序列化格式，测试全挂，而用户毫无感知。

好的写法只用公开方法：给「me」设余额 150、「you」设 20，转 100，断言余额变成 50 和 120；再写一条余额不足时两边不变。覆盖面一样，但测试变成了契约：它挂了，就意味着某个真实用户也会挂（脚注把这叫「先走前门」原则）。

难点在于「公开」不等于语言里的 public：这里的公开 API，指这个单元暴露给团队之外第三方的接口。Java 里为了包间访问而声明的 public 类未必是；Python 没有可见性、只靠下划线约定；Bazel 还能进一步限制谁能依赖。原书给了三条经验法则：只服务一两个类的辅助类不算独立单元，通过它的使用方来测；谁都能直接用、无需找所有者商量的包或类，几乎一定是单元，要直接测；只有所有者能用、但提供通用功能的支持库也算单元，直接测——会有冗余覆盖，但能防止某个使用方被删后留下空洞。

三、测状态，不测交互

第二种依赖实现细节的方式，不在「调用了什么」，而在「怎么验证结果」。状态测试（state testing）：调用后观察系统本身变成了什么样；交互测试（interaction testing）：检查系统对它的协作者做了哪些预期调用。后者更脆，道理和测私有方法一样：它检查的是怎么得到结果，而你通常只该关心结果是什么。

原书的反例：createUser("foobar") 之后 verify(database).put("foobar")。它会两头出错——若 bug 让记录写入后立刻被删，测试照样通过（该红不红）；若重构改用另一个等价的写库 API，测试失败（不该红却红）。改成 assertThat(accounts.getUser("foobar")).isNotNull()，直接表达我们真正在乎的东西。交互测试泛滥的头号原因是过度依赖 mock 框架，所以 Google 倾向：只要真实对象快且确定，就用真对象而不是 mock。

四、测行为，不测方法

失败不可避免，而且失败本身是好事——它就是单测提供价值的方式。测试失败只有两种原因：被测系统有问题，或测试本身有问题。工程师要多快分辨出是哪种，取决于测试的清晰度。测试常比写它的人活得久；不清晰的生产代码还能靠「谁调用它」推断用途，不清晰的测试最坏情况是看不懂就删了——等于它可能好几年都在提供零价值。

工程师的本能是一个生产方法配一个测试方法。原书的反例 testDisplayTransactionResults 同时断言「你买了某商品」和「余额偏低警告」——多半是后加第二条消息时把断言堆进了旧测试，既违反「写完不变」，又让测试随方法一起膨胀。更好的做法是每个行为一个测试。行为指：系统在某个状态下、面对一串输入时，对如何响应作出的一项保证，可以用 given / when / then 说出来——「给定账户为空，当尝试取钱，则交易被拒」。方法和行为是多对多：大多数方法实现好几个行为，有的行为又要多个方法配合。

由此带出三条写法。结构：把 given / when / then 三段用空行或注释分开（就是常说的 arrange / act / assert），读者能按三层粒度读——先看名字，再看注释，最后看代码；最常见的违例是把断言穿插在多次调用之间。多步流程可以交替 when / then，但绝大多数单测只要一个 when、一个 then。命名：测试名常常是失败报告里第一个、甚至唯一可见的东西，所以要写清动作和预期结果，如 divide_byZero_throwsException；生产代码不会这么啰嗦，但测试名没人调用、只给人读。卡住时用 should 开头，连上类名读成一句话：「BankAccount should not allow withdrawals when balance is empty」。名字里需要用「and」，多半是一次测了两个行为。

五、测试里别写逻辑，失败信息要说人话

清晰的测试应当一眼看出是对的。这在测试里做得到，因为每个测试只处理一组特定输入，而生产代码要泛化处理所有输入。生产代码有测试兜着复杂逻辑，测试代码没有——觉得需要给测试写测试，就说明出问题了。逻辑指运算符、循环、条件。原书的例子只有一个字符串拼接：baseUrl + "/albums"，而 baseUrl 以斜杠结尾；把期望值完整写出来，立刻看到 photos.google.com//albums 多了一个斜杠——生产代码犯同样的错时，原测试抓不到。

失败信息理想上应让人不打开测试就能诊断：写清期望、实际和相关参数。「Test failed: account is closed」是坏例子（到底是期望关闭还是不该关闭？）；好例子是「Expected an account in state CLOSED, but got account: {name: "my-account", state: "OPEN"}」。工具能帮忙：JUnit 的 assertTrue(colors.contains("orange")) 只拿到一个布尔值，只能报「expected true but was false」；Google 开发的 Truth 写成 assertThat(colors).contains("orange")，能报出「[red, green, blue] should have contained orange」。没有这类库的语言就手写，如 Go 的惯例 Add(2, 3) = %v, want %v。

六、代码复用：DAMP，而不是 DRY

生产代码讲 DRY：改一处就够，代价是读者要顺着引用链跳来跳去。这笔账在测试里算法不同：好测试本来就该稳定、而且系统变了你希望它挂，所以 DRY 的「好改」收益变小；同时复杂度的代价变大，因为测试没有别的测试兜底。于是测试应当追求 DAMP（Descriptive And Meaningful Phrases，描述性、有意义的表述）：只要让测试更简单清楚，一点重复没问题。原书的反例把造用户、注册、校验全藏进带循环和三元表达式的辅助方法里——测试体很简洁，但不完整，辅助方法里还藏着一个 bug。DAMP 不是取代 DRY，而是补充：抽辅助方法的目的应是让测试更有描述性，而不只是减少重复。

具体到三种常见复用：共享常量如 ACCOUNT_1，看不出为什么选这个值，还诱人在不完全合适时复用——改用带合理默认值的构造辅助方法，测试只写自己在乎的字段（Java 用 Builder 模拟具名参数；脚注说默认值甚至可以略加随机，防止有人暗中依赖它）。共享 setup 最适合构造被测对象和协作者；但如果某个测试依赖 setup 里的具体值（如 setup 里写死的「Donald Knuth」），就该在测试体里显式覆盖它。共享校验：每个测试末尾调用同一个大 validate() 是坏习惯，看不出意图，一个 bug 让一大片测试一起红；好的校验辅助只断言一个概念上的事实，比如「用户对该账户有访问权」，把必需的循环藏起来。跨套件共享的测试基础设施更像生产代码：调用方多、难改，要当独立产品对待、必须有自己的测试。

选型的总判据就是那句：测试体应包含读懂它所需的全部信息，且不含任何无关信息（完整 + 简洁）。前一张表的两组选择互相强化：经公开 API、验状态的测试，正好也最容易写成一个行为一个测试。交互验证不是禁止——第 13 章会讲它的正当场景——但它应当是例外，而不是 mock 框架顺手带来的默认。

为什么重要 / 落到真实系统

这一章的规模背景是：一个人一天跑上千个单测，一次大规模变更触发几十万个。在这个量级上，哪怕一小部分测试是脆的，代价都会摊到每一次全仓改动上——测试是否「写完就不变」，直接决定大规模重构做不做得动。面试被问「怎么写好单测」，好答案不是「覆盖率多少」，而是本章那串 TL;DR。

易错点与争议

  • 「脆 = 不稳定」——不是一回事。脚注区分了：脆测试是对无害改动确定性地失败；不稳定（flaky）是代码没变却时过时不过。
  • 「public 关键字就是公开 API」——错。本章的公开指团队外第三方能用的接口，和语言可见性未必对齐。
  • 「为了覆盖率去掉 private 直接测」——反模式。同样的覆盖完全可以从公开 API 拿到，而且不锁死实现。
  • 「单测就要把依赖全 mock 掉」——Google 倾向相反。真对象快且确定就用真对象；verify 式断言既会误报又会漏报。
  • 「测试也要 DRY」——只对一半。为了减少重复而把关键信息藏进辅助方法，是本章点名的坏味道；抽取要以「更有描述性」为目的。
  • 「一个方法一个测试」——直觉但会烂掉。方法与行为是多对多；名字里出现 and，就该拆。
  • 争议：经典派 vs mock 派。业界长期有「状态验证为主」与「交互验证为主、外部依赖一律替身」两派之争；本章明确站经典派一侧，但交互验证在「调用本身就是行为」（如确实要发出一封邮件）时仍有用，第 13 章会讨论边界。

要点

① 单测的命门是维护性：好测试写完不再改，失败只因真 bug、且原因一目了然。

② 两种病：脆（无害改动也挂）和不清晰（挂了看不懂）；规模越大越贵。

③ 四类改动里只有行为变更该改旧测试；重构、新功能、修 bug 改了旧测试，就是测试太脆。

④ 从公开 API 测：测试挂 ⇔ 用户会挂；「公开」指团队外第三方的接口，不是 public 关键字。

⑤ 测状态不测交互：verify(db).put 会该红不红、不该红却红；能用真对象就别 mock。

⑥ 测行为不测方法：given / when / then、一个行为一个测试，名字里出现 and 就拆。

⑦ 测试里不写逻辑：一个字符串拼接就能藏住双斜杠 bug。

⑧ 失败信息给出期望、实际与参数；Truth 和 Go 的 want 惯例是现成工具。

⑨ DAMP 不是 DRY：构造辅助带默认值、setup 只造对象、校验辅助只断言一件事，测试基础设施要有自己的测试。
