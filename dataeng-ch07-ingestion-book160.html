这一章讲什么？

公司每天早上的销售报表，数字来自订单系统、支付系统、App 埋点、合作方发来的表格——它们散在几十个地方。这一章讲的是：怎么把数据从这些「别人家」稳稳地搬进自己的数据平台。这一步叫采集。它看起来只是搬运，却是整条数据流水线最容易出事的地方。

先说个怪事

我们总说「批处理」和「实时流」是两种东西。可仔细想想：订单一笔一笔在发生，从来没有停过。所谓「每天一批」，只是我们在一条永不停歇的河上，每隔 24 小时拦了一道闸。批和流不是两类数据，而是你决定多久开一次闸。

旧世界为什么难

  • 上游不归你管。业务系统的同事改了一个字段名，你的流水线半夜就断了，而没人通知你。
  • 一次全搬太重。每天把整个订单库从头抄一遍，抄的时候还会拖慢正在接单的系统。
  • 送达不是一次成功。网络会抖，东西可能迟到、乱序，甚至同一份被送了两遍。

核心机制直觉

  • 只抄新增的那几页。不必每天重印整本账本，只抄昨天之后改过的那几页；更好的办法是直接看账房的「流水记录」，谁改了什么一条不漏。
  • 先进仓库，再拆箱。老做法是在路上就把货拆好、分拣好再入库；如今仓库够大够便宜，干脆原样先搬进去，要用时再在仓库里整理——慢一步，但原件永远在。
  • 快递不保证顺序。先寄的包裹可能后到，同一件还可能被重复派送。所以收件处要能认出「这件我收过了」，迟到的也要有地方补登。
  • 拒收的件放「问题件柜」。地址写错、拆不开的包裹单独放一边，别让它堵住整条传送带。

带来了什么 / 该怎么选

多数团队的默认做法是：能定时批量搬就批量搬，只有业务真的需要「秒级看到」时才上实时流；能买现成的搬运工具就别自己写。一句诚实的代价：实时流让数据更新鲜，但它要求一直有人盯着、处理迟到和重复，成本和复杂度都明显更高。

一句话记住

采集是把数据从别人家搬进自己家：批和流只是开闸的频率不同；只搬变化、原样先入库、准备好迟到和重复，比追求「实时」更要紧。

一句话

你以为采集只是「把数据从 A 拷到 B」，其实它是数据生命周期里最脆弱的一环：源头不归你管、会变、会抖、会重发。本章要建立的认知是：所有数据天生是无界的，批处理只是人为划的边界；采集设计的核心不是选一个工具，而是先回答一串问题——数据多大、多频繁、推还是拉、能否重放、迟到和重复怎么办——再在批与流、ETL 与 ELT 之间按真实需求取舍。

Glossary · 术语表

  • 源系统（source system）：产生数据的上游系统，如业务数据库、SaaS 应用、App 埋点，通常归别的团队管。
  • 数据管道（data pipeline）：把数据从源头经过若干步骤送到目的地的一整套流程。
  • 批处理（batch）/ 流处理（streaming）：攒一段时间的数据一起处理 / 数据一到就逐条或小批处理。
  • 数据仓库（data warehouse）：为分析查询优化、结构严格的中心化数据库，如 Snowflake、BigQuery。
  • schema：数据的结构说明——有哪些字段、各是什么类型。
  • 消息队列 / 事件流平台：生产者把消息写进去、消费者按自己节奏读走的中转站，如 Kafka、Kinesis、Pub/Sub。
  • 偏移量（offset）：消费者在消息流里「读到第几条」的书签，可以往回拨来重读。
  • 幂等（idempotent）：同一操作执行一次和执行多次结果相同，比如「把余额设为 100」而非「余额加 100」。
  • API：系统对外提供的程序调用接口，常见的是按 HTTP 请求、返回 JSON。

坐标

Part II「生命周期详解」第三章。上接第 5 章「数据从哪来」与第 6 章「存在哪」，下启第 8 章查询与转换。第 5 章讲源系统本身，本章讲把数据从源系统挪进存储的那段路。现实里对应 CDC 同步、Kafka 接入、Fivetran / Airbyte 这类托管连接器、每晚跑的导数任务。

这章要解决什么

设想一家电商：订单库 5 亿行，每天约 200 万行新增或修改；App 埋点高峰每秒 5 万条事件；另有十几个 SaaS 系统（CRM、广告平台）只提供 API。分析师要求「早上 9 点前看到昨天的数」，风控则想「几秒内看到异常下单」。不懂采集的典型后果：

  • 拖垮源库。每晚对 5 亿行全表扫描导出，正在接单的主库延迟飙升。
  • 静默丢数或重复。上游改了字段、网络重试多送一遍，报表数字悄悄偏了，几周后才被发现。
  • 为不需要的实时付费。把只需日报的场景做成 7×24 的流式管道，运维成本翻倍，没人因此多赚钱。

作者把采集定义为把数据从一处移到另一处，并区分了「采集」与「集成」：采集是从源到存储的那一段搬运，集成则是把多个来源的数据拼成一个新数据集。

核心内容，讲透

一、先问问题：有界 vs 无界，以及频率是一条连续谱

作者给了一串设计前必须回答的问题：采集的数据会被谁用、能否复用？源与目的地是什么、数据量多大、多频繁？格式是什么、下游能否直接用？如果是流，是否需要先在途中转换？其中最根本的一对概念是有界数据（bounded）与无界数据（unbounded）：有界数据有明确的起止（如「9 月 1 日的订单」），无界数据则持续不断地产生。书里的立场很鲜明——数据在被人为划出边界之前，都是无界的。业务事件本来就是一条流，「每日一批」只是我们为了方便处理切出来的。

由此，采集频率不是「批 / 流」二选一，而是一条从「每年一次」到「每天」「每小时」「每分钟微批（micro-batch）」再到「近实时」的连续谱。作者提醒，即便数据以流的方式采集进来，下游也常常以批的方式处理（比如每小时训练一次模型）——频率要分别看每一段。

二、六个工程考量：同步异步、吞吐、可靠性、负载、推拉

同步 vs 异步采集。同步管道里，源、采集、目的地环环相扣，后段一步失败，前面几小时的工作可能都得从头重跑。异步管道则以事件为单位、经过缓冲（如 Kafka）流动，各段独立失败、独立重试。

序列化与反序列化。源把数据编码成字节、目的地再解开，两端必须对格式和版本达成一致，否则数据「到了也读不了」。

吞吐与可扩展。管道要扛住峰值和积压：下游停机几小时恢复后，积压的数据会像洪水一样涌来。作者建议优先用托管服务，它们大多内置弹性伸缩。

可靠性与持久性。可靠指管道按预期运行、失败能恢复；持久指数据不丢。关键洞察是：很多源数据一旦没采到就永远没了（比如只在内存里停留的事件），所以冗余与自愈的投入要按「丢了会怎样」来衡量，而不是追求零风险。

负载（payload）。要看清数据的种类（表格、图片、文本）、形状、大小、schema 与数据类型，尤其是schema 演化：上游加字段、改类型、改名是常态。对策是自动检测 schema 变化，或用 schema 注册表（schema registry）给每个版本编号、让读写两端按版本解析；更根本的是和上游团队建立沟通。

推 · 拉 · 轮询。推（push）是源主动发出；拉（pull）是采集系统主动去取；轮询（poll）是定期去问「有没有变化」，有才拉。CDC、消息流多是推，定时导数多是拉。

三、批采集：快照还是增量，ETL 还是 ELT

快照 vs 增量抽取。每次全量抄一份（快照）最简单，但贵；只抽取上次以来变化的部分（差量 / 增量）省资源，却要求源能可靠地标出「什么变了」。以开头那张 5 亿行的订单表为例，每天 200 万行变化，增量抽取的数据量只有全量的约 0.4%。

基于文件的导出。源系统自己把数据导成文件，推到对象存储或 SFTP。好处是源方掌控安全与访问，不必开放数据库直连。

ETL vs ELT。ETL 是先抽取（Extract）、在途中转换（Transform）、再加载（Load）进数仓；ELT 是先把原始数据原样加载进数仓或数据湖，再在里面用 SQL 转换。云数仓把存储做便宜、算力做弹性之后，ELT 成为主流：原始数据留底，转换逻辑可以反复改写重跑。作者同时警告两点：一是 ELT 若只做了「EL」而没人做「T」，数据湖会变成沼泽；二是 ETL 并没有死——数据需要先脱敏、先压缩，或目的地不擅长转换时，在途转换仍然合理。

插入、更新与批大小。列式数仓擅长一次写入一大批，最怕逐行插入和频繁小更新——每一条都可能触发重写一个文件。所以采集时要攒批，按目的地的特性决定批大小。数据迁移（如整库从本地搬上云）则建议先用小样本试跑、核对 schema 差异，最难的往往不是搬数据，而是把上下游所有管道接到新系统上。

四、流采集：迟到、乱序、重复、重放与死信

流采集把问题从「搬多少」换成了「什么时候、以什么顺序、送几次」。书里逐条列了要考虑的事：

  • schema 演化：流里的消息随时可能变形，用 schema 注册表管版本。
  • 迟到数据：事件发生时间（event time）与被采集时间（ingestion time）可能差很远——比如手机离线一小时后才把埋点补传上来。要定一个截止规则：多晚的数据还接受、算进哪个时间窗口。
  • 顺序与多次投递：分布式的消息系统通常只保证至少一次投递，可能重复、可能乱序。下游必须设计成幂等，按唯一 ID 去重。
  • 重放（replay）：Kafka、Kinesis、Pub/Sub 这类平台会在保留期内留着消息，消费者可以把偏移量拨回去重读历史——修了 bug 能补算。
  • 保留期（TTL）：消息存多久。太短，下游故障恢复时数据已过期；太长，积压的旧消息会堵住管道。
  • 消息大小：流平台对单条消息有上限，Kafka 默认约 1 MB，Kinesis 也是 1 MB 量级；大文件应放对象存储、消息里只放引用。
  • 错误处理与死信队列（dead-letter queue）：解析失败、反复处理不了的消息转进单独的「死信」主题，主流继续前进，之后再排查重放。
  • 位置：采集点尽量靠近数据产生的地方，跨区域、跨云搬运要付带宽和出口流量费。

五、采集的十几种途径：从数据库直连到卡车

本章后半是一份「工具箱」。最重要的几样：

  • 数据库直连（JDBC / ODBC）：通用但按行序列化、单线程导出大表很慢，常要按分区并行拉取。
  • 变更数据捕获（CDC）：批式 CDC 按 updated_at 字段查「上次以来改过的行」——简单，但只能拿到每行的最新状态，中间的多次修改和删除会被漏掉；持续 CDC 读数据库的变更日志（如 MySQL binlog、PostgreSQL WAL），把每一次增删改变成事件写进流平台，不丢中间态、对源库查询压力也小得多。代价是要有日志读取权限，并管住源库日志的保留。
  • API：最常见也最碎片化，每家 SaaS 的分页、限流、鉴权都不同。作者的建议是能用现成客户端库和托管连接器就别手写。
  • 托管数据连接器（Fivetran、Airbyte、Stitch 等）：把数百个源的对接打包成服务，用书里常说的话，是把「无差异化的苦活」外包出去，让工程师把时间花在有价值的地方。
  • 消息队列与事件流平台：异步采集的主干。
  • 对象存储做交换站：跨团队、跨公司交换文件最安全可扩展的方式之一；SFTP / SCP、EDI 则是老派但仍常见的通道。
  • Webhook：常被称为「反向 API」——由数据提供方在事件发生时回调你的接口，接收端要扛得住突发并保证不丢。
  • 文件导出与格式：CSV 依然泛滥，但分隔符、换行、编码、无 schema 都会出错；尽量用带 schema 的格式（Parquet、Avro、ORC）。
  • 网页抓取：最后手段，要顾及对方负载与法律边界。
  • 物理搬运设备：数据量到百 TB 以上时，网络搬运可能要几个月，于是有 AWS Snowball 这类寄送硬盘，乃至能装 100 PB 的集装箱卡车 Snowmobile。
  • 数据共享：云数仓之间直接授权读取，不复制、不搬运。

最后，作者强调采集是人的问题：上游软件工程师决定数据长什么样、何时变；把他们拉进来、约定好变更通知，比任何工具都管用。DataOps 方面，要监控管道的运行、延迟与数据量——量突然掉一半往往是上游悄悄坏了——并对数据做质量测试。

关键权衡与选型

表 1 · 批采集 vs 流采集

方式适合代价
每日 / 每小时批日报、财务对账、离线训练；绝大多数分析场景新鲜度以小时计；全量快照会给源库压力
微批（分钟级）运营看板、近实时汇总调度更频繁，小文件变多，需定期合并
流（秒级）风控、实时推荐、监控告警要处理迟到、乱序、重复；7×24 值守，成本与复杂度最高

表 2 · 抽取方式

方式好处代价
全量快照最简单，结果自洽数据量大时慢且贵；反复扫源库
批式 CDC（按更新时间）只取变化，实现简单漏掉中间态与硬删除；依赖源表维护好时间戳
日志式 CDC每次变更都捕获，低延迟，对源库查询压力小需日志权限与额外组件（如 Debezium + Kafka）；运维更重

表 3 · ETL vs ELT

模式何时选代价
ETL需在入库前脱敏 / 过滤；目的地算力有限；大幅压缩数据量原始数据不留底，转换逻辑改了难以回溯重算
ELT云数仓 / 湖仓；转换逻辑常变；需要可重算原始层越堆越多，没人治理就成数据沼泽；数仓算力账单上涨

判据：先问下游真正需要多新的数据——作者的态度是，只有当业务价值确实超过成本时才上真正的流式；再问源能否可靠地告诉你「什么变了」；最后问是否要保留原始数据以便重算——要，就倾向 ELT。

为什么重要 / 落到真实系统

面试里「把业务库同步到数仓」这道题，好的答案会这样落地：用日志式 CDC 把 MySQL 的变更写进 Kafka，按主键分区以保证单行有序；消费端按主键做幂等 upsert，批量写入数仓；原始变更事件同时落到对象存储留底，可重放；SaaS 数据交给托管连接器；监控每张表的延迟与日数据量，量异常即告警；schema 变更走注册表并通知下游。每一步都对应本章一个考量。

开源实证

  • Debezium：日志式 CDC 的代表实现。项目自述是「为变更数据捕获（CDC）提供低延迟数据流的开源平台」；架构上复用 Kafka 与 Kafka Connect，每个连接器监视一个上游数据库、把所有变更记进 Kafka 主题，每张表的变更「按它们在上游数据库发生的顺序」投递；客户端可随时停下，重启后「恰好从中断处继续」——这正是本章所说的有序、可重放、对源库影响小。出处：debezium/debezium README，GitHub
  • Airbyte：托管连接器把苦活打包。项目自述为「面向 ELT 管道与 AI 智能体的开源数据搬运」，提供「600 多个连接器」覆盖 API、数据库、数仓、数据湖——对应书里「别重造轮子、把无差异化的对接外包」的建议，也说明 ELT 已是行业默认叙事。出处：airbytehq/airbyte README，GitHub

易错点与争议

  • 「实时一定更好」。多数分析需求按小时、按天就够；先问谁会因为秒级数据做出不同决定。
  • 「消息系统保证恰好一次」。常见默认是至少一次，重复与乱序要靠下游幂等与去重兜底。
  • 「按 updated_at 增量就够了」。它看不到硬删除和中间态，且依赖上游每次都正确更新时间戳。
  • 「ELT 就是先倒进去再说」。只装不管，湖会变沼泽；转换和治理的责任只是挪了位置。
  • 「上游 schema 是稳定的」。它一定会变，要么自动检测、要么用注册表和约定来管。
  • 「CSV 是通用格式」。分隔符、引号、换行、编码问题层出不穷，无 schema 更难排错。
  • 「采集只是技术活」。最大的风险来自和上游缺乏沟通；书里把与上游工程师的协作当成采集的一部分。
  • 时代局限。书出版于 2022 年，托管连接器与日志式 CDC 此后更为普及；但「批是流的边界」「至少一次 + 幂等」这些基本判断并未改变。

要点

① 采集 = 把数据从源系统搬进存储；它是生命周期里最脆弱的一环，因为源头不归你管。

② 数据天生无界，批只是人为划的边界；频率是从按年到逐条的连续谱，每一段可以不同。

③ 设计前先回答：数据量、频率、同步还是异步、推拉还是轮询、可靠性要求、schema 会怎么变。

④ 能增量就别全量；按时间戳的批式 CDC 漏删除和中间态，日志式 CDC 每次变更都不漏。

⑤ ELT 是云数仓时代的默认，原始数据留底、可重算；但没人做转换和治理就成沼泽，ETL 在脱敏等场景仍合理。

⑥ 流采集要提前准备迟到、乱序、重复、重放、保留期、消息大小与死信队列；「恰好一次」靠至少一次 + 幂等。

⑦ 列式数仓怕逐行小写，采集要攒批；能买托管连接器就别手写对接。

⑧ 监控延迟与数据量，和上游工程师约定变更通知——人的问题比工具更关键。
