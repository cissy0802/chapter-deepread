Pull Complexity Downward

A Philosophy of Software Design · Ch 8 · Pull Complexity Downward · Ousterhout · 2nd ed 2021

中文 →

What is this chapter about?

Anyone who builds software keeps running into a hassle that can't be avoided: if the network drops, should we try again, and how long should we wait first? Someone has to deal with it. The question is who — the person who builds the part, or everyone who uses it? The chapter's answer is blunt: better that the builder works a little harder than that every user has to.

An analogy

Picture two restaurants. One menu says: "Choose your own cooking: minutes on high heat, minutes on low, grams of salt." The other just says "braised pork" and leaves the heat and salt to the chef. The first one looks more "flexible," but it has quietly handed the chef's job to every diner. One chef thinking it through once beats a hundred diners each guessing.

Why the old way is hard

Builders have a natural shortcut: whenever they're unsure, they "let someone else decide." Not sure what to do when something goes wrong? Report an error and let the caller sort it out. Not sure which approach is best? Add a setting and let users fill it in. The part gets easier to build today. But a question that one person should have thought through now has to be thought through by every user — and they usually know less about the insides than the builder does.

How it works, intuitively

  • Users outnumber builders. A part is usually written by one or two people and used in dozens or hundreds of places. Keep the hassle inside and it hurts once; push it out and it hurts everywhere.
  • A setting is often a way of passing the buck. Instead of making people guess "how many seconds before retrying," let the part watch how long recent requests took and work out a wait time from that. If the network slows down, the wait grows with it, and nobody has to come back and change anything.
  • If you must offer a setting, pick a good default. Most people should get good results without touching it; only unusual cases need to change it.
  • Don't stuff everything inside, either. Only take on hassles that sit close to the part's real job. Cramming in unrelated work just turns the part into a mess.

What it buys you / how to choose

When you hit a hassle, ask one question: can the user make a better decision here than I can? If not, take it on yourself. One honest cost: the inside of the part gets harder to write and harder to test, and the builder really does carry more of the load.

Remember it in one line

Give an unavoidable hassle to the one person who understands it best, to handle once — don't spread it across every user to handle again and again.

One-line summary

You think handing decisions to the caller "respects flexibility." Ousterhout says it usually means pushing your own problem onto more people: when a module meets complexity it can't avoid, and that complexity is related to what the module does, the module should absorb it internally — because it is more important for a module to have a simple interface than a simple implementation.

Glossary

  • Module: a unit of code with an interface and an implementation — a class, library, service, or subsystem.
  • Interface: everything a user must know to use the module well, including function signatures and informal rules such as "when does this fail."
  • Implementation: the code inside the module that does the work; users don't need to read it.
  • Caller: the code that uses the module.
  • Deep module: from Chapter 4 — a simple interface in front of a lot of functionality; this chapter is another route to depth.
  • Exception: an error signal a function throws to its caller when it can't finish normally; the caller has to handle it.
  • Configuration parameter: a value set from outside by a user or operator to control the module's behavior, such as a timeout or a cache size.
  • Round-trip time (RTT): the time between sending a request and getting the response.
  • Retransmission timeout (RTO): how long a sender waits for an acknowledgment before deciding the data was lost and sending it again.

Where it sits

Chapter 8. Chapters 4–7 covered deep modules, information hiding, general-purpose interfaces, and layering. This chapter asks a different question: once some complexity is unavoidable, which side of the interface should it live on? It sets up Chapter 10, "Define Errors Out of Existence." In practice it maps onto every "let's add a config option here" or "just throw and let the caller handle it" decision.

What problem the chapter tackles

When writing a module, the instinct is to solve the easy problems and punt the hard ones. The author names the two most common punts: unsure how to handle a condition, throw an exception and let the caller deal with it; unsure which policy to use, define a few configuration parameters and leave the system administrator to work out good values. It makes your life easier in the short term, but it amplifies complexity: a problem one person should have solved now has to be solved by many.

Why "many"? Because most modules have more users than developers. Picture an internal HTTP client library maintained by two people and called by 200 services (a hypothetical but common scale). Spending an extra week inside the library getting the retry policy right saves 200 teams from each guessing whether the timeout should be 3 seconds or 30 — and a wrong guess often shows up as a cascading-timeout outage. Better for the developers to suffer than the users.

The core ideas, explained

1. The thesis: simple interface > simple implementation

This is the sentence to remember. The reasoning is accounting: interface complexity is paid by every user; implementation complexity is paid once, by the developer. Chapter 4 said a deep module has a small interface and a lot of functionality; this chapter adds the move — when you find complexity you can't avoid, deliberately pull it below the interface, and the module gets deeper. The author's conclusion frames it as an attitude: when developing a module, look for chances to take a little extra suffering on yourself so your users suffer less.

2. Example: the editor's text class

The author returns to the text class of the GUI editor from Chapter 6. A line-oriented interface (get a line, put a line) is easy to implement but pushes complexity up: when the user inserts or deletes text in the middle of a line or across lines, the UI code has to split and join lines itself. A character-oriented interface (insert text at any position, delete a range) makes the text class map positions to lines and split and merge internally — but all that splitting and joining disappears from the UI code. The complexity didn't vanish; it moved from many call sites into one place.

3. Example: configuration parameters push complexity up

The author says configuration parameters are an example of moving complexity upward instead of down. He grants they have legitimate uses: developers of low-level infrastructure can't foresee every deployment, so a knob for tuning to a workload is reasonable. But configuration parameters also give developers an easy excuse to dodge important issues and pass them on to someone else — and the administrator often has no better idea of the right value than the developer.

His example is the retry interval of a network protocol. As a configuration parameter, someone has to guess "how long without a response means it's lost." Too short, and a bit of congestion triggers a flood of needless resends that makes it worse; too long, and real losses mean waiting around. The better design is for the protocol to measure the response time of successful requests and use a multiple of it as the retry interval. The complexity moves into the protocol and users no longer need to understand it; and since the interval is computed dynamically, it adjusts when conditions change — whereas a hand-set parameter easily goes out of date. A value tuned years ago for a 1 ms data-center RTT is simply wrong on a transoceanic link, where RTTs of 150 ms or more are common.

He gives two working rules. First, before adding a parameter, ask: "Will users (or higher-level modules) be able to determine a better value than we can determine here?" The answer is often no. Second, if you do add one, compute a reasonable default automatically, so users only supply a value in exceptional cases. His ideal: each module should solve its problem completely; a configuration parameter signals an incomplete solution, and that adds to system complexity.

4. Don't overdo it: three tests

The author immediately adds: pull complexity down with discretion. The extreme — pulling all of an application's functionality into a single class — is obviously absurd. The counterexample from Chapter 6 crosses the line: giving the text class methods specifically for the backspace and delete keys drags UI logic into the text class; the interface gets no simpler, and knowledge about the UI leaks in. Pulling down makes the most sense when all three hold:

  • Related: the complexity is closely related to the class's existing functionality;
  • Simplifies elsewhere: pulling it down lets many other parts of the application get simpler;
  • Simpler interface: pulling it down makes the class's interface itself simpler.

All three serve one goal: minimize the complexity of the whole system, not make one module look feature-rich.

5. Throwing exceptions: the other upward push

The chapter opens by putting "throw an exception and let the caller handle it" next to configuration parameters as a way of punting. Just a pointer here: every new exception is one more rule every caller has to handle. How to make such exceptions disappear semantically is the subject of Chapter 10.

Why it matters / in real systems

The best real-world footnote to this chapter is TCP. TCP makes its retransmission timeout adaptive: per RFC 6298, the sender keeps a smoothed estimate of round-trip time, SRTT, and of its variation, RTTVAR, and sets the timeout to SRTT + 4×RTTVAR — in plain words, "the usual time, plus room for four times the usual wobble," starting from 1 second. Nobody who writes a networked program has to set a retransmission timeout by hand; that is what pulling complexity into the protocol looks like.

Evidence and sources · publicly verifiable

  • Go's garbage collector: deliberately just two knobs. In his 2018 ISMM keynote, Rick Hudson of the Go team said Go's GC has two knobs (GCPercent, default 100, and a heap limit then still under internal evaluation), and stated: "We've had almost a decade now and we have two knobs and that feels about right. There is not an application that is important enough for us to add a new flag." That is an explicit choice to pull tuning complexity into the runtime.Source: The Go Blog · Getting to Go (ISMM 2018 keynote)
  • TCP retransmission timeout: standardized "measure it, compute it." RFC 6298 has the sender compute the RTO from measured round-trip times rather than having applications configure a fixed value — the industrial version of the chapter's retry-interval example.Source: IETF RFC 6298 (2011), Computing TCP's Retransmission Timer
  • The flip side: configuration pushing complexity up. The author's judgment is that configuration parameters often serve as an excuse to dodge hard problems, that administrators usually don't know the right value any better than developers, and that hand-set values go stale as environments change.Source: Ousterhout, A Philosophy of Software Design, Ch. 8

In everyday review: when you see a new config option or a new exception type, ask the chapter's question — does the caller have information I don't? And when an interview asks "how would you design an SDK," "good defaults out of the box, adapt internally, expose few knobs" is an answer you can now justify.

Pitfalls and debates

  • "Configurable = flexible = good." Every parameter is more interface for users to learn, and parameters combine into untested corners. Flexibility counts only if someone actually needs it.
  • "Pull down = cram everything in." All three tests must hold; putting UI logic in the text class or business rules in a general library crosses the line and leaks information.
  • "Adaptive always beats fixed." Adaptive behavior is harder to predict and harder to reproduce in debugging. The mature pattern is usually adaptive by default with an override — TCP implementations commonly put a floor under the RTO and let it be adjusted at the system level.
  • Debate: separating mechanism from policy. An old operating-systems principle says the lower layer provides mechanism and leaves policy to the layer above. It doesn't contradict this chapter — the key is still who holds the information. Business meaning the lower layer can't see belongs above; signals it can see (like round-trip time) shouldn't be pushed out.
  • Limitation: a direction, not a formula. "Can the user decide better?" takes experience to answer, and newcomers err both ways.

Key takeaways

① Thesis: it matters more for a module to have a simple interface than a simple implementation.

② The accounting: users usually outnumber developers, so complexity outside the interface gets copied N times.

③ Two common punts: throw an exception for the caller, or add configuration parameters for the admin to guess.

④ Text class: a character-oriented interface is harder inside, but the UI's line splitting and joining disappears.

⑤ Configuration parameters are the classic upward push; a retry interval should be derived from measured response times and adapt on its own.

⑥ Before adding a parameter, ask whether users can pick a better value than you; if you add one, compute a sensible default.

⑦ Three tests for pulling down: related to existing function, simplifies other code, simplifies the interface.

⑧ Real footnotes: TCP computes its own RTO; Go's GC deliberately keeps just two knobs.

⑨ Don't overdo it: pulling in unrelated logic crosses the line; the goal is always minimal complexity for the whole system.
