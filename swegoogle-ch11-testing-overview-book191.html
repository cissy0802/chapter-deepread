这一章讲什么？

你每天用的 Google 搜索，背后的程序几乎每天都在更新，可你很少遇到它突然坏掉。这一章讲的就是秘诀之一：让机器替人反复检查软件，也就是「自动化测试」——以及 Google 怎么把这件事变成全公司的习惯。

先说个怪事

你以为写测试是为了抓 bug，这一章说，更重要的是让人敢改代码。2005 年，负责 Google 搜索网页服务的团队，一度八成以上的上线版本都带着影响用户的毛病、只能撤回。大家改代码时提心吊胆，越改越慢。后来团队定了一条规矩：每次改代码都必须附上自动检查。一年后，紧急救火的次数少了一半——而那一年他们改动得比以往任何时候都多。

旧世界为什么难

过去靠一屋子测试员手动点一遍。可今天的搜索要查航班、电影场次、图片，还要乘上每种语言、每个国家、每种设备，人根本点不过来。更糟的是，就算每个工程师都很厉害、一个月只犯一个错，一百人的团队每个工作日仍会冒出五个新错。只靠「人聪明」挡不住规模。

核心机制直觉

  • 写一次，天天用：测试就像给房子装的烟雾报警器。装一次之后，谁在厨房做饭忘了关火，它都会响——不用每个人都学会闻烟味。
  • 按「占多大地方」分大小：小测试只在一个房间里做实验，中测试可以用整套房子，大测试才允许跑到别的楼。房间越小，干扰越少，结果越快越稳。
  • 小的多、大的少：像金字塔：底下大量又快又稳的小检查，顶上少量模拟真实用户走完全程的大检查。倒过来像蛋筒冰淇淋，又慢又容易塌。
  • 报警器要靠谱：如果报警器动不动乱响，大家很快就会把电池拔掉。时灵时不灵的测试，比没有测试还伤人。
  • 你在乎什么，就给它装报警器：Google 管这叫「碧昂丝法则」。别人改了公共设施把你的功能弄坏，如果你没装检查，那是你的责任。

带来了什么 / 该怎么选

Google 没有下命令逼人写测试，而是靠新员工培训、厕所隔间里每周一张的测试小贴士、给团队评等级的榜单，慢慢把「写测试是每个人的事」变成默认文化。诚实的代价是：写测试本身要花时间，测试多了还要专人照料，而且有些事——比如搜索结果「好不好」——机器判断不了，仍要靠人。

一句话记住

测试不只是抓错，是让很多人能放心地、天天改同一份代码。

一句话

你以为测试是为了抓 bug；本章说，测试首先是为了支撑改动——代码要在几十年、几万人手里不停地变，只有快、稳、自动化的测试，才能让人放心地变。Google 的做法是：按资源（大小）而不是按名字给测试分类，偏向又小又窄的测试，死磕不稳定，再用文化而非命令把测试变成每个人的工作。

Glossary · 术语表

  • 自动化测试（automated test）：一小段代码，给被测程序一个已知输入，检查输出是否符合预期，由机器反复运行。
  • 测试套件（test suite）：一个项目所有测试的集合。
  • 单元 / 集成 / 端到端测试：分别检查一个函数或类、几个组件之间的配合、整个系统从入口到出口的行为。
  • 进程（process）与线程（thread）：进程是操作系统里一个独立运行的程序；线程是进程内部并行执行的一条线。
  • I/O 与阻塞调用：读写磁盘、网络等外部设备；阻塞调用指程序停下来等结果回来。
  • 测试替身（test double）：用假的轻量实现顶替真依赖，比如用内存里的假数据库代替真数据库（第 13 章详述）。
  • 持续集成（CI）：每次提交代码都自动构建并跑测试的系统（第 23 章详述）。
  • 单体仓（monorepo）：全公司绝大部分代码放在同一个代码仓库里。
  • 回滚（rollback）：发现新版本有问题，退回上一个版本。

这章要解决什么

本章开篇给了一个 Google 自己的痛：Google Web Server（GWS），负责响应 Google 搜索请求的网页服务器，原书比作「机场的空中交通管制」。2005 年项目膨胀，发布越来越慢、越来越多 bug，工程师改代码没信心，常常到生产环境功能挂了才知道；一度超过 80% 的上线都带有影响用户的 bug、需要回滚。

GWS 的技术负责人于是规定：所有新改动必须附带测试，测试持续运行。一年内，紧急上线（emergency push）次数减半，而同期每季度的改动量还在创新高。如今 GWS 有数万个测试，几乎每天发布。

本章从这个故事提炼出一条关键洞见：不能只靠程序员的能力来避免缺陷。原书算了笔账：一个 100 人团队，每人每月只写一个 bug，合起来每个工作日仍是 5 个新 bug；而且在复杂系统里修一个 bug 常引出另一个。测试把个人的智慧变成团队的公共资产——一个人写的测试，所有人都在受益；而调试是每次出 bug 都由某个人重新付一遍代价。不解决会怎样？代码规模和发布频率一涨，手工验证必然跟不上，团队要么变慢，要么把 bug 发给用户。

核心内容，讲透

一、写、跑、响应：测试的价值在第三步

自动化测试由三件事构成：写测试、跑测试、对失败作出响应。测试写成代码而不是手工步骤，就能在每次改动时运行，一天跑上千次，换个浏览器、换个界面语言也只是换配置。但本章强调，真正决定测试有没有用的是第三步：让失败的测试堆积，很快就会抵消它的全部价值；能在失败几分钟内修好的团队，才能保持信心、快速定位问题。

原书列的收益不止「少调试」：改动更有信心、重构不必改测试；测试是可执行的文档，需求变了它会第一个变红；评审者看测试就知道边界情况是否覆盖；难测的代码往往是设计有问题（职责太多、依赖难管）；最后才是快速、高质量的发布。

二、两个维度：大小（size）≠ 范围（scope）

Google 早年发现，工程师偏爱写大型系统级测试，但这些测试又慢、又不稳、又难调试，于是大家越写越小。随之而来的争论是：「小」到底指什么？本章的答案是把它拆成两个独立维度：

  • 大小指跑这个测试需要的资源：内存、进程、时间、能不能碰网络。
  • 范围指这个测试在验证多少代码——注意是「验证」，不是「执行」。一个类的单测会顺带执行它的依赖，但只验证这个类。

为什么不直接用「单元 / 集成」？因为 Google 最想要的两种品质是速度与确定性，而这两者主要由资源决定，与范围无关。按资源分类，还能让基础设施强制执行：原书举例，Google 的 Java 测试跑在定制的安全管理器下，标为 small 的测试一旦尝试建立网络连接就直接失败。

三、三种大小的边界

小测试：必须在单个进程内运行（很多语言进一步限制为单线程），不许 sleep、不许 I/O、不许任何阻塞调用，因而不能碰网络和磁盘（例外：内存里的密闭文件系统）；要连数据库，就用测试替身。这些限制把最大的两个慢与不稳的来源挡在门外，能跑多快只取决于 CPU。

中测试：可以多进程、多线程、阻塞调用，可以起一个真数据库、或用 WebDriver 遥控真浏览器，唯一限制是网络只许连本机。原书说跨机器的网络「是绝大多数系统里最大的慢与不确定性来源」，挡住它，中测试还算有点保护——但「保险已经打开」，要更小心。

大测试：去掉本机限制，可跨多台机器。Google 主要把它留给验证配置多于验证代码的全系统端到端测试，以及无法用替身的遗留组件，并常把它和中小测试隔开，只在构建发布流程里跑，不拖慢日常开发。（脚注：Google 内部其实有四档，还有 enormous。）

所有大小共同的要求：密闭（hermetic）——自带搭建、执行、清理环境所需的一切，不依赖运行顺序或共享数据库；一眼看懂——测试本身没有测试来测，只能靠人读，所以强烈不鼓励在测试里写条件和循环。

四、不稳定的测试：千分之一就很贵

不稳定（flaky）指测试在代码没变的情况下时过时不过。本章的算术很直白：每个测试只有 0.1% 的误报率，一天跑 1 万个，就要排查 10 次假失败。自动重跑可以缓解，本质是拿 CPU 换工程师时间，只是推迟了修根因。更致命的是信任：原书的经验是，不稳定率接近 1% 时，测试就开始失去价值——工程师不再理会失败，整个套件形同虚设。Google 自己约 0.15%，按其规模意味着每天数千次假失败，所以要专门投入工程时间去修。根源多在测试本身的不确定性：时钟、线程调度、网络延迟。

System Design · Day 50 把 Code Review 当信号检测系统 — 和不稳定测试同一个道理：误报预算一超，人就不再看信号，工具随之死亡

五、配比：80 / 15 / 5 的金字塔

Google 同样鼓励窄范围。粗略目标是按测试数量 约 80% 单元、15% 集成、5% 端到端——Google 版的 Mike Cohn 测试金字塔（每个团队会略有不同）。单测是好地基：快、稳，失败定位几乎零成本；大测试是产品成形过程中的健全性检查，不应被当成抓 bug 的主手段。

六、碧昂丝法则与「为失败而测」

该测什么？凡是你不想被弄坏的，都要测——性能、正确性、无障碍、安全，也包括系统如何处理失败。Google 管这叫碧昂丝法则（Beyoncé Rule）：「你喜欢它，就该给它加个测试。」它常由负责全仓改动的基础设施团队援引：无关的基础设施改动通过了你所有的测试、却弄坏了你的产品，修复和补测试的责任在你。为失败而测，则是在单测里模拟异常、在集成和端到端测试里注入 RPC 错误与延迟，再大一级就是混沌工程（Chaos Engineering）。

System Design · Day 44 混沌工程 — 「为失败而测」推到生产环境：稳态假设、爆炸半径与故障注入实验怎么设计

七、覆盖率：度量会变成天花板

代码覆盖率（code coverage）只衡量某行代码被执行过，不衡量结果有没有被检查；少数测试就能刷出很高的数字。本章建议只用小测试计算覆盖率，避免大测试注水。更隐蔽的问题是：定下 80% 的线，工程师会把地板当成天花板，改动刚好卡在 80%。更好的问法是：客户期望的行为都有把握吗？依赖的破坏性变化抓得住吗？测试稳吗？

八、文化：没有下命令

2005 年前，Google 的测试「更像好奇心而非纪律」。GWS 之后，一群志愿者（Testing Grouplet）用三招改变了文化：新人培训里加一小时测试课，让新人把它当默认做法带回团队；Test Certified 五级认证，每级一个季度可达，内部看板公开各团队等级，到 2015 年被自动化的 Project Health（pH）取代时已帮助 1500 多个项目；Testing on the Toilet，2006 年 4 月起在厕所隔间张贴一页纸的测试小贴士，至今几乎每周一期。他们考虑过请高层下令，但认为强制与 Google 文化相悖，选择靠成功案例传播。如今每个改动都应同时包含功能代码和测试，缺测试的改动被评审拦下完全合理。

为什么重要 / 落到真实系统

这一章的分类已经开源成了工具：Bazel（Google 内部 Blaze 的开源版）的测试规则带 size 属性（small / medium / large / enormous），不写超时就按大小给默认值 60 / 300 / 900 / 3600 秒——「大小按资源定义」变成了构建系统里的约束。规模背景也决定了这些规则的必要性：原书称 Google 单体仓超过 20 亿行代码、每周约 2500 万行改动，其中约一半来自自动化系统；几乎不用分支、构建总基于最新的已验证提交。面试被问「怎么设计测试策略」，好答案不是「写够 80% 覆盖率」，而是「按资源分大小、偏向小而窄、盯住不稳定率、关键行为都有测试」。

易错点与争议

  • 「测试是为了抓 bug」——只对一半。本章把支撑改动放在同等重要的位置：没有测试，重构和大规模变更就没人敢做。
  • 「小测试 = 单元测试」——错。大小看资源，范围看验证多少代码；用替身包住依赖的接口级测试可以是小测试，验证一个日期选择器却可能要起整个浏览器、成为中测试。
  • 「单元测试就要把依赖全 mock 掉」——Google 反对。原书说可行时更倾向保留真实依赖；mock 滥用曾严重到有工程师喊出「别再用 mock 了」。
  • 「不稳定就自动重跑」——只是缓兵之计。它推迟了修根因；不稳定率涨到 1% 附近，信任就崩了。
  • 「覆盖率越高越好」——指标会变成目标。执行不等于验证，固定门槛会变成天花板。
  • 争议：金字塔并非唯一答案。业界有人主张更偏集成测试的「奖杯」「蜂窝」形状，尤其是逻辑多在服务交互的微服务场景；本章其实留了口子——配比应匹配本地架构，80/15/5 只是 Google 的粗略目标。
  • 局限：自动化不是全部。搜索结果质量要靠人工评估员，音视频质量、复杂安全漏洞也是人更擅长；探索式测试（exploratory testing）发现问题后，应立刻补一条自动化测试防回归。

要点

① 测试的首要价值是支撑改动；GWS 从八成上线需回滚，到一年内紧急上线减半。

② 不能只靠个人能力：100 人每人每月一个 bug，就是每天 5 个；测试把个人智慧变成团队资产。

③ 写、跑、响应——让失败堆积会抵消测试的全部价值。

④ 大小（资源）与范围（验证多少代码）是两个独立维度；小 = 单进程、中 = 单机、大 = 多机，且由基础设施强制。

⑤ 尽量写最小、最窄的测试；粗略配比 80% 单元 / 15% 集成 / 5% 端到端，警惕冰淇淋筒和沙漏。

⑥ 不稳定很贵：0.1% × 1 万次 = 每天 10 次假失败；接近 1% 时信任崩塌，Google 约 0.15%。

⑦ 测试要密闭、一眼看懂，不写条件和循环。

⑧ 碧昂丝法则：在乎的就加测试，没加测试被别人弄坏，责任在你。

⑨ 覆盖率只说明「执行过」；用行为和信心来衡量套件。

⑩ 文化靠培训、认证、厕所贴士和成功示范，而不是命令；判断类、创造类测试仍要靠人。
