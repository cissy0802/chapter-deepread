Build and Deployment Scripting

Continuous Delivery · Ch 6 · Jez Humble & David Farley · 2010

中文 →

What is this chapter about?

The app on your phone updates every week or so. Between the code an engineer finished and the working version on your device sits a chain of actions: compile, package, copy to servers, adjust configuration, restart. Chapter 6 of Continuous Delivery is about how that chain should be written as scripts — not a few commands typed from memory, but something written the way you write real product code.

An analogy first

Think of a release as cooking. Manual deployment is a chef improvising: an extra spoon of salt today, a burner left on tomorrow. Scripting it means writing the recipe down and letting a machine follow it. But this chapter goes further: the recipe should not live on a sticky note on the fridge — scribbled ad hoc, one per kitchen, messier with every edit. It should be maintained like a published work: versioned, reviewed, and traceable back to the edition that went wrong.

A true story first

In August 2012 the US brokerage Knight Capital rolled out new code by hand to eight production servers and missed one. Dormant old code on that machine was woken up by a repurposed switch, fired off bad orders, and in roughly 45 minutes burned more than $460 million — effectively ending the firm. The root cause is not exotic: deployment was done by a person, machine by machine, with nothing guaranteeing the eight were identical.

Three words that carry the chapter

One, the same script. Development, test, production — all run the same deployment script, and the differences between environments live only in an external configuration file. Once each environment gets its own script, they drift apart, and the thing you rehearsed twenty times in test is not the code that runs in production.

Two, run it as often as you like. A good script does not say "do these 12 steps"; it says "make sure it ends up looking like this" — skip what is already installed, fix what is installed wrong. So when it dies halfway, you just run it again instead of cleaning up by hand first.

Three, layers. Split "install the OS and middleware", "place the application", "apply configuration" and "migrate data" into four separate scripts, because they change at wildly different rates: configuration might change three times a day, the OS once a year. Fused together, changing one config line means reinstalling middleware.

Where to start

Don't try to script everything at once. The chapter's advice is practical: start with the step that hurts most — whatever part of every release you dread and keep getting wrong — script that, then grow outward from it.

And the cost is real: scripting is not free. These scripts have their own bugs and need their own maintenance; you are now carrying another codebase. It still pays, because errors in manual deployment never show up in the test environment — only in production.

One thing to remember

Writing deployment down as a script is not enough. Every environment must share the same script (differences live in configuration), running it twice must change nothing, and it must be treated like production code: in version control, reviewed, refactorable.

In one sentence

Chapter 6 handles the pipeline's manual labour: how to write build and deployment as scripts. Its core claim is a single line — build and deployment scripts are production code, not a pile of one-off commands: they belong in version control, they get layered, refactored and tested. Three hard rules follow: every environment shares one deployment script (differences only in external configuration), deployment must be idempotent, and deployment is layered by rate of change.

Glossary

  • Build: turning source code into something runnable (compile, package). The output is an artifact — a jar, an installer, an image.
  • Deployment: putting an artifact and its configuration onto a machine and making it run. Distinct from release, which means exposing it to users.
  • Build tool: Make, Ant, Maven, Rake, Gradle — programs whose job is to execute a build process.
  • Dependency graph / DAG: a directed acyclic graph of "what must finish before what". Traversing it is essentially all a build tool does.
  • Target: an individually callable unit in a build script, such as compile or test.
  • Idempotent: running the operation once and running it many times produce the same result.
  • Declarative vs imperative: the former describes what the end state should be; the latter describes which steps to perform in order.
  • Smoke test: a tiny set of checks run right after deployment, verifying only "is it alive, can it reach its dependencies", not business detail.
  • Environment: a complete set of machines, middleware and configuration capable of running the app — development, staging, production.
  • Native OS package: RPM / deb on Linux, MSI on Windows — installed, removed and queried by the system's own package manager.

Where it sits

This chapter belongs to Part II, "The Deployment Pipeline", and follows directly from Ch5: Ch5 draws the shape of the gates; this chapter answers what actually executes inside each box. It leans on Ch2 "Configuration Management" (the "same script plus external configuration" rule needs Ch2 to be real) and leads into Ch7 "The Commit Stage" and Ch11 "Managing Infrastructure". The real-world problem it maps to: why nobody on the team dares touch build.xml, the Makefile or deploy.sh after three years of evolution.

What problem it solves

Anyone can draw the pipeline diagram. What actually drags teams down is the pile of scripts that executes it. Their usual fate: a three-thousand-line build.xml only its author understands; deploy-dev.sh / deploy-uat.sh / deploy-prod.sh, each separately patched until they no longer resemble one another; and a wiki line saying "before running this, stop service A by hand."

What happens if you don't fix it? The chronic cost: nobody dares restructure the script, so every new requirement arrives as another if; build time climbs from 3 minutes to 25, blowing past the ten-minute budget Ch7 sets for the commit stage — developers stop waiting for the result, and continuous integration is dead in all but name. The acute cost: the Knight Capital 45 minutes from the plain version. The SEC's 2013 enforcement document faulted the firm's deployment process for lacking automation and verification of consistency. "One of eight machines is different" is exactly what scripting plus idempotence exists to eliminate.

The core content, properly

1. A build tool is a dependency graph — the split is over what the nodes are

Every build tool does the same thing: break the build into targets with dependencies, topologically sort them, execute in order. The disagreement is over what a node is.

Product-oriented, exemplified by Make: a node is a file to be produced. app depends on a.o, a.o depends on a.c; Make compares file timestamps and rebuilds only when the source is newer. Incremental builds come for free — but the test is fragile. Timestamps are one-second resolution on many filesystems, so edits within the same second are silently missed, and a fresh checkout stamps every file with "now". Teams end up in the habit of "when in doubt, clean build", handing back everything incrementality bought them.

Task-oriented, exemplified by Ant / NAnt: a node is a thing to do. You can express whatever you want without forcing it to map onto a file; the cost is that the tool has no idea whether work can be skipped, so the skip logic is yours to write inside each target and the default behaviour is to run everything.

The chapter names a third route: convention over configuration, exemplified by Maven. It fixes the directory layout and lifecycle (src/main/java; compile → test → package → install) so you configure rather than script. The authors' verdict is honestly two-sided: new projects work out of the box and teams share one shape; the moment you need to deviate from the convention, cost rises steeply — usually into writing a plugin, which is harder to read than the script it replaced.

And a fourth: just use a real programming language — Rake (Ruby), Psake (PowerShell), later Gradle. Once build logic needs conditionals, loops and abstraction, expressing it in XML is self-harm. The cost is that an unconstrained language lets the build script grow into a second application — which is why this route requires the discipline in the next section.

2. Build scripts are production code, so govern them like production code

This is the soul of the chapter and the part most often skipped. Build and deployment scripts go into version control, in the same repository and branch as the code they serve, through the same review. The reasoning is direct: a given version of the code can only be built and deployed correctly by the matching version of the scripts. Keep them elsewhere — in a CI server's "build configuration" screen, in someone's home directory — and you have permanently lost the ability to go back to the version from three months ago and reproduce it exactly.

The same rule yields concrete discipline: layer and de-duplicate, factoring shared logic into reusable modules instead of copy-paste; always use relative paths, because a script with /opt/app hard-coded runs only on its author's machine; write build output outside the source tree, or "clean" depends on .gitignore and luck; bind artifacts to the revision, putting the commit id in the filename or metadata so a production incident can be traced back to a line of code.

And one that is commonly done backwards: a failing test must fail the build, but must not abort it immediately. Record "something failed" as a flag, let this round of tests finish, and fail at the end — so one build shows you every failure instead of one, then the next, then another ten-minute wait.

3. The same script deploys to every environment

This is the most actionable rule in the chapter: developer machines, CI, staging and production all run the same deployment script, and differences between environments exist only as external configuration (per Ch2: configuration is version-controlled too, just managed separately from code).

Why so absolute? Because the deployment script is itself a thing under test. You rehearsed the deployment twenty times in staging; if production runs a different script, those twenty runs never touched the code that actually matters. "Code that executes for the first time on release day" is the risk — and a script per environment is a machine for manufacturing exactly that code.

The cost is real: the script must be parameterised, and parameters breed complexity of their own, so you need a configuration management approach (a config repository, template rendering, secret storage) to carry it. The principle is let environments differ in configuration, never in behaviour — the moment one environment needs "one extra step", ask whether that step could be done in all of them.

4. Idempotence: a script describes state, not steps

Idempotence means: whatever state the target machine is in now, after the script runs it is in the correct state; run it again and nothing changes.

The difference from "record the manual steps as shell" is fundamental. An imperative script says "unpack, create directory, write config, start service"; when step three dies, the machine sits in an intermediate state — re-running fails because the directory already exists, and you go in by hand. A convergent script says "this directory should exist, this config file should have these contents, this service should be running", reading current state first and changing only what disagrees. The result is that "just run it again" becomes a permanently safe action — and that property is the precondition for automation anyone dares leave unattended.

This is the shared design of the Puppet / Chef generation around 2010 (and Ansible shortly after). The chapter pairs it with a related discipline: layer deployment by rate of change — OS and middleware, application binary, configuration, data and schema each get their own script and their own cadence. Fused together, changing one config line means reinstalling the middleware.

5. Prefer native packaging; always end with a smoke test

The chapter offers an engineer's-taste suggestion that pays off: if RPM / deb / MSI will do, don't invent your own packaging format. They come with dependency declarations, standard install / remove / upgrade actions, and a queryable database of what versions are on a machine — all of which you would otherwise rebuild in scripts, probably worse. The cost is that cross-platform means maintaining several packages, and the package manager's abstraction gets in the way when you need fine control.

Finally, the integrated smoke test: the last step of a deployment script should be a short "is it actually alive" check — process up, port reachable, database connectable. It takes seconds, and it separates two things routinely conflated: "the script exited 0" is not "the service works".

Why it matters / in real systems

The chapter's three rules are industry default today, only renamed: "build scripts in version control" became CI configuration as code (Jenkinsfile, workflow YAML, sitting in the application repository); "the same script to every environment" became one container image plus per-environment parameters; "idempotence" became the founding property of declarative infrastructure — Terraform's plan / apply and Kubernetes' reconciliation loop are both the loop on the right of Fig 3.

The interview question about why one artifact should travel all the way through rather than be rebuilt per environment has a second half — the script travels all the way through too — and that half is this chapter.

Common mistakes and open arguments

  • Reading "scripting" as "record the manual steps". Recorded shell only hardens human error into machine error: not re-runnable, not readable, not testable. The chapter asks for layering, idempotence and version control, not merely "there is a script".
  • Using the build tool to deploy. The book explicitly discourages it: Ant and Maven were designed to build, and bending them into ssh-ing to twenty machines to rewrite configuration is awkward and drags build-time dependencies onto production hosts. Deploy with deployment tools.
  • Idempotence is not universal; data is the exception. "Run it again" does not hold for database migrations — adding a column or changing a value is inherently not repeatable, so you need versioned migration scripts plus a migrations table (Ch12 covers this). Treating idempotence as a universal slogan is the fastest way to come unstuck at the data layer.
  • "Don't check binaries into version control" needs a footnote. What the book opposes is mixing jars with source in one repository, not keeping artifacts at all — artifacts belong in an artifact repository (Nexus, Artifactory, a container registry): addressable, traceable, prunable.
  • Period limits. Written in 2010, the tool list stops at Ant / Maven / Rake / Psake, with Puppet and Chef newly arrived. Today Gradle and Bazel own the build, and containers plus orchestration own deployment. More interestingly, idempotence has been partly routed around: immutable infrastructure does not "change the machine into the correct state", it "never changes the machine, it replaces it" — stronger than idempotence, since it also eliminates the risk that the convergence logic itself is wrong. That does not overturn the chapter; it substitutes a more thorough implementation of the same goal: one script, one artifact, all the way to production — those three are untouched.
  • The open argument: is convention over configuration worth it? The fair statement is that it turned "building a simple project" from a problem into a non-problem, and turned "building a complex project" from hard into painful. The question to ask before choosing it is not "is it good" but "will this project likely need to deviate from the convention".

Takeaways

1. In one line: build and deployment scripts are production code — version-controlled, layered, refactorable, testable. Every other rule in the chapter grows from this one.

2. A build tool is a dependency-graph traversal; the split is whether nodes are files (Make: timestamps, a fragile test) or tasks (Ant: runs everything by default).

3. Convention-first (Maven) gives standard projects a working build for free, at the price of a steep cost once you deviate; a general-purpose DSL is expressive, at the price of growing into a second application.

4. The hardest rule: every environment shares one deployment script, differences only in external configuration — otherwise the code running in production has never been tested.

5. Idempotence: the script describes a target state, not steps; N runs equal one run. This is the precondition for unattended automation.

6. Layer deployment by rate of change: OS and middleware, application, configuration, data — one script and one cadence each.

7. Engineering discipline: relative paths, output outside the source tree, artifacts bound to a revision, failing tests fail the build but only after the round finishes, native packages over homemade ones.

8. The last step of deployment is a smoke test — "exited 0" and "the service works" are different claims.

9. Data is the exception to idempotence: schema migration is inherently non-repeatable and needs versioned migration scripts (Ch12).

10. In today's terms: CI configuration as code, one image across environments, and the declarative reconciliation of Terraform and Kubernetes are all direct descendants of this chapter.
