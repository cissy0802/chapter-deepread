构建系统与构建哲学

Software Engineering at Google · Ch 18 · Build Systems and Build Philosophy · Erik Kuefler · 2020

EN →

这一章讲什么？

程序员写的是人能读的文字，电脑要跑的是另一种机器才懂的文件。中间那道「翻译 + 组装」的工序，就叫构建。你手机上每个 App、每次更新，背后都走过这道工序。这一章讲 Google 怎么把这道工序做得又快又可靠——快到改一行几秒出结果，可靠到全公司几万人谁来做，结果都一模一样。

先说个怪事

问 Google 工程师最喜欢公司的什么，除了免费餐食，很多人会说：构建系统。内部调查里，它的满意度在 19 个工具里排第四。更怪的是，它之所以好用，恰恰是因为它不让工程师随心所欲——它收走了大家的自由。

旧世界为什么难

老办法像一张手写的做菜清单，每一步写什么都行。问题是厨房总管看不懂每一步到底干了什么，于是不敢让两个厨师同时开工，怕他们抢同一口锅；也不敢省掉任何一步，怕哪步偷偷用了过期的食材。结果每次都从头做到尾，越做越慢。更糟的是，清单常常只在写它的人的厨房里管用——换一台电脑，缺个工具、版本不对，就做不出来了。

核心机制直觉

  • 只说要什么，不说怎么做：工程师不再写步骤，只写「我要这道菜，它用到这几样原料和那几道半成品」。怎么做、按什么顺序，交给系统。
  • 同样的原料，必出同样的菜：每一步只许用声明过的原料，像在只放了这几样东西的小隔间里做。于是原料没变，上次的成品直接用；不相干的几道，放心同时做。
  • 全公司共用一个成品柜：既然同样原料必出同样成品，别人做过的，你直接从柜子里取，不用再做一遍。柜子里没有的，就派给机房里成千上万台机器一起做。
  • 外面买来的原料要验货、只认一个版本：每样外购原料都记下它的「指纹」，送来的货指纹对不上就拒收；同一样东西全公司只用一个版本，免得两道菜各要一个版本、凑不到一盘里。

带来了什么 / 该怎么选

换来的是：改一点只重做受影响的那一点，几乎从不需要「清空重来」；新人第一天就能构建任何代码，自动测试和上线都能放心地搭在上面。诚实的代价是：你不能再随手写一段脚本让它干任何事，得按它的规矩来；已经用老办法的大项目，搬过来也不便宜。

一句话记住

把构建从「执行一串步骤」改成「声明要什么成品」：收走一点自由，系统就敢并行、敢复用、敢分给成千上万台机器，还保证结果处处一致。

一句话

你以为好的构建系统是「给工程师最大的灵活性」，本章说恰恰相反：把权力从工程师手里收回给系统，让构建从「执行任务」变成「产出制品（artifact）」，系统才知道每一步做了什么，才敢并行、敢复用、敢分布式——快与正确从此不必二选一。

Glossary · 术语表

  • 构建（build）：把源代码编译、链接、打包成可运行文件的过程。
  • 编译器（compiler）：把一种语言的源码翻译成机器可执行格式的程序，如 javac、gcc。
  • 二进制 / 制品（binary / artifact）：构建产出的文件——可执行程序、库、JAR 包等。
  • 依赖（dependency）：「我要先有那个，才能做这个」；可以是另一段代码、一个第三方库，或一个工具。
  • 传递依赖（transitive dependency）：依赖的依赖；A 依赖 B、B 依赖 C，C 就是 A 的传递依赖。
  • 有向无环图（DAG）：节点之间用单向箭头相连、且绕不回起点的图；依赖关系天然是一张 DAG。
  • 增量构建（incremental build）：只重建因改动而受影响的部分，其余沿用上次结果。
  • 哈希（hash）：把任意内容压成一串固定长度「指纹」的函数，内容改一点指纹就全变。
  • 语义化版本（semver）：形如 1.1.4 的版本号约定，主版本号变意味着可能不兼容。

这章要解决什么

构建系统的目标只有两个：快（敲一条命令，常常几秒出结果）和正确（任何人在任何机器上，输入相同，结果必须相同）。老一代工具常拿正确换速度——走捷径做增量，换来时好时坏的构建。

本章用一个项目的成长讲规模问题：一开始 javac *.java 就够；跨语言、引第三方 JAR 后得手动排顺序、往 lib 目录塞包；改用 shell 脚本，为防用到过期产物只好每次全量重编；硬盘一坏，下载的库和环境变量找不回；新人入职、夜间 cron 构建，都在反复排查「我机器上能跑」。对一个人写几百行、干一两周，编译器就够了；一旦要跨多人、多台机器协作，再完美的脚本也挡不住机器之间的细微差异。

而在 Google，这件事被放大到极致：代码超过 20 亿行，一个简单二进制常依赖数万个构建目标；而且绝大多数构建是机器自动触发的——评审时自动测、合入前再测、底层库改动跨全仓数百万个测试验证。构建不可信，这一切无从谈起。

核心内容，讲透

一、任务式构建：给人的权力太多，给系统的太少

Ant、Maven、Gradle、Grunt、Rake 都是任务式（task-based）：基本单位是「任务」，每个任务是一段能做任何事的脚本，并声明依赖哪些别的任务，合成一张 DAG。ant dist 顺着 dist → compile → init 找下去再倒着执行——剥掉语法，和 shell 脚本区别不大。

病根：系统不知道脚本在干什么，只能极度保守。

  • 难并行：A 依赖 B 和 C，B、C 彼此无依赖，能同时跑吗？也许它们写同一个状态文件。系统无从判断，要么冒险（换来罕见又极难查的错），要么全程单线程——多核机器白白闲着，分布式更不用想。
  • 难增量：任务可能下载了会变的文件、写了每次不同的时间戳，系统无法确认「做过了」，只好每次重跑。让人手写「何时需要重跑」又很难写对——C++ 的 include 不解析源码就不知道该盯哪些文件。捷径出错几次，大家就养成每次先 clean 的习惯，增量彻底作废。
  • 难维护：构建脚本也是代码，却很少被审。典型 bug：B 换了输出路径，A 到运行时才挂；B 删掉对 C 的依赖，靠 C 输出的 A 莫名坏掉；任务偷偷假设工具路径或环境变量；B、C 写同一个文件，A 的结果取决于谁先跑完。

结论很直接：只要允许构建期运行任意代码，系统就永远拿不到足够信息去又快又对。

二、制品式构建：只声明「要什么」，「怎么做」归系统

Blaze 及其后代（Bazel、Pants、Buck）是制品式（artifact-based）：BUILD 文件不再是图灵完备的命令序列，而是一份声明式清单——要产出哪些目标（target）、各自的源文件 srcs、依赖 deps，外加少量受限选项。java_library 产出库，java_binary 产出可执行文件，deps 可以指同包（:mylib）、同仓别的包（//java/com/example/common）或第三方（@…guava//jar）。

作者用函数式编程作类比：只写「要算什么」，何时、怎么算交给编译器。构建整体就是一个以源文件和工具为输入、以二进制为输出的函数。于是：

  • 可并行：Bazel 知道这一步只是跑 Java 编译器，不是任意脚本，就敢把互不依赖的目标同时编——多核机器上能快一个数量级。
  • 可复用：编译器输出只取决于输入，输入没变就复用。什么都不改再跑一遍，不到 1 秒就报「已是最新」；改了 common，只重建 common → mylib → MyBinary，otherlib 原样沿用，且保证不会产出过期结果。

三、把「环境」也变成声明过的依赖

并行和复用还不够，前面那些「我机器上能跑」的坑要逐个堵上：

  • 工具即依赖：每个 java_library 隐式依赖一个 Java 编译器，缺了就下载，编译器一变就重建。跨平台靠工具链（toolchain）：按宿主和目标平台挑具体那一套工具。
  • 可扩展但收口：自定义规则（rule）生成若干动作（action）——最底层的可组合单元，只要只用声明过的输入输出，想做什么都行，调度和缓存归 Bazel。
  • 沙箱（sandbox）：每个动作只能看到它声明的输入和自己的输出，书中说 Linux 上靠 LXC（Docker 背后的同类技术）隔离；没声明的文件读不到，写了没声明的会被丢弃，还能禁止联网。两个动作抢同一个文件这件事，从此不可能发生。
  • 外部依赖确定化：工作区级清单为每个外部依赖记一个加密哈希。哈希对不上就构建失败，更新只能改清单并提交评审——每次升级都有记录，检出上周的提交就拿到上周的依赖。为防供货方宕机，作者建议非玩具项目都把依赖镜像到自己的服务器。

四、分布式构建：远程缓存 → 远程执行

数万个目标单机跑不完；把工作切小、摊到任意多台机器，就能「愿意付多少钱，就有多快」——这才是制品式设计追求的圣杯。

远程缓存最简单：开发机和 CI 共用一个缓存服务，要构建某制品先查缓存，有就下载、没有就自己建再上传。前提是构建完全可复现，且缓存键 = 目标 + 输入的哈希，这样多人同时改同一个目标也互不冲突。另一个前提是下载比构建快，要先实测网络延迟。

远程执行才是真分布式：改了底层库要全量重建时，光有缓存仍得在本机跑。做法是主控把请求拆成动作、分发给可伸缩的 worker 池，worker 经由缓存交换中间产物。它要求环境完全自描述、步骤完全自包含、输出完全确定——任务式系统几乎不可能做到。

Google 的实现：远程缓存 ObjFS 把产物存在 Bigtable 里，开发机上的 FUSE 守护进程 objfsd 让产物像本地文件、打开时才下载——比全存本地盘快一倍。远程执行 Forge：Distributor 把动作发给 Scheduler，命中动作缓存直接返回，否则入队，由大批 Executor 执行并把结果写进 ObjFS。规模是每天数百万次构建、数百万个测试用例、PB 级产物。

五、模块与依赖：细粒度、可见性、严格传递依赖

粒度在「整个项目一个目标」与「每个文件一个目标」之间取舍（见表 2）。Google 偏向比任务式系统里常见的小得多的目标：一个典型生产二进制依赖数万个目标，中等团队就拥有几百个。Java 通常一个目录一个包、一个目标、一个 BUILD——Pants 称之为 1:1:1 规则。小目标让分布式构建更快、重建更少，还能只跑受改动影响的那一小撮测试；维护负担靠工具自动管理 BUILD 文件抵消。

可见性（visibility）是依赖的反面：A 想依赖 B，B 得对 A 可见。尽量收窄：只有全公司通用的库才公开，内部实现只对本团队目录可见，多数 BUILD 文件只有一个非私有目标。

严格传递依赖：A 依赖 B、B 依赖 C，A 能不能直接用 C 的类？链接上没问题，Blaze 也允许了很多年。可一旦 B 重构不再需要 C、删掉这条依赖，所有「借道 B 用 C」的目标全挂——依赖变成了公共契约，永远不敢删，于是越积越多、构建越来越慢。Google 推出严格模式：引用了没直接声明的符号就报错，并附上一条能自动补依赖的命令。把数百万个目标改成显式声明花了好几年，作者认为非常值：显式加依赖是一次性成本，隐式传递依赖是只要目标还在就持续发作的成本。Bazel 对 Java 默认开启这一模式。

六、外部依赖：手动定版本、一个版本、不自动拉传递依赖

内部依赖从源码构建、和使用者处在同一个提交，没有「版本」的概念；外部依赖有版本，且独立于你的代码演进，难点都在这里。三条立场：

  • 手动定版本：Gradle 允许写 1.+（主版本为 1 的最新版），多人项目里这是「灾难配方」——对方即便声称遵守语义化版本也可能发破坏性更新，今天能过的构建明天就挂、无从回滚。手动定版本的每次变化都在版本控制里，可发现、可回滚。Bazel 要求全部手动定版本。
  • 一个版本规则（One-Version Rule）：理论上不同版本可以起不同名字并存，但会导致上图的菱形依赖。Google 对全部第三方依赖强制一个版本，新加依赖时现有依赖必然已是同一版本，可以和平共存。
  • 不自动下载传递依赖：Maven、Gradle 默认递归下载，加一个依赖可能拉进几十个制品，必然违反一个版本规则。Bazel 的替代是一份全局文件，列出每个外部依赖及其唯一版本，可由工具从 Maven 制品自动生成初版。作者承认这没有银弹，是方便与可扩展的取舍。

另两个判断：把自家代码预编成制品来提速，会让系统各部分来自仓里不同时刻、难调试——更好的解法是远程缓存。第三方供货的风险，可用镜像 + 哈希挡住，或干脆引入仓内（vendor）：Google 把所有第三方库检入根目录的 third_party，但这依赖它专为超大单体仓定制的版本控制。

关键权衡与选型

全章的灵魂一句话：灵活性换规模。每升一级，你交出一部分自由，换系统多一层保证。

为什么重要 / 落到真实系统

开发者一天要构建几十上百次，构建常常就是生产率的限速步骤。评审「要不要换 Bazel」时，本章的判据是：项目越大、换构建系统越贵，新项目一开始就上制品式最划算；已有任务式大项目，先看它是否已在速度或正确性上出问题。面试谈 CI 加速或供应链安全，能讲清「缓存键 = 目标 + 输入哈希」「可复现是远程缓存的前提」，就比「加机器、加缓存」深一层。

易错点与争议

  • 「构建工具越灵活越好」——本章结论正相反。限制工程师的权力反而提高了生产率，因为增量构建「就是能用」。
  • 「上了远程缓存就会快」——不一定。缓存离得远可能更慢；没有可复现性，缓存给的可能是错的结果。
  • 「沙箱保证了万无一失」——作者自己说不防呆。动作里仍可能有不确定步骤，只是被压到了动作这一层。Buck2 也明说仅在远程执行时保证密封。
  • 时代局限：本书 2020 年出版。书中的 WORKSPACE 文件在 Bazel 后续版本中逐步被 Bzlmod（MODULE.bazel）取代，后者会按最小版本选择自动解析模块间的传递依赖，与书中「不自动拉传递依赖」的描述已不完全一致；沙箱的具体实现也随版本演进。反方观点：Bazel 学习曲线陡，生态外的工具要自己写规则——作者也承认任务式系统对多数项目已够用。

要点

① 快与正确要兼得；一旦多人多机，再好的脚本也挡不住机器差异。

② 任务式的病根是系统看不懂任意脚本：难并行、难可靠增量、脚本难维护。

③ 制品式只声明目标、源文件、依赖，「怎么做」归系统；像函数式，输入不变就复用，多核并行快一个数量级，空跑不到 1 秒。

④ 把环境也声明化：工具即依赖、工具链、沙箱、外部依赖记哈希。

⑤ 远程缓存的前提是可复现，键 = 目标 + 输入哈希；Google 的 Forge + ObjFS 自 2008 年起支撑每天数百万次构建。

⑥ 模块偏细（1:1:1），可见性尽量收窄；严格传递依赖花了数年推行，因为隐式依赖是持续成本。

⑦ 外部依赖：手动定版本、一个版本规则防菱形冲突、不自动拉传递依赖。

⑧ 越大越难换：新项目一开始就上制品式。
