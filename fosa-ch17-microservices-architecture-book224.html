微服务架构：宁可重复，也不要耦合

Fundamentals of Software Architecture · Ch 17 · Mark Richards & Neal Ford · 2020

EN →

这一章讲什么？

你打开一个购物 App，下单、付款、查物流，背后很可能是几十上百个各自独立的小程序在接力，这种做法叫「微服务」。它是近十年最火的架构词，也是被误用最多的一个。这一章讲清楚它到底是什么、该切多细、以及它最难的那几件事。

打个比方：一条街的小店，而不是一座百货大楼

老式系统像一座百货大楼：所有柜台共用一个仓库、一本总账，改一个柜台的货架，全楼都得停业盘点。微服务像一条街上的独立小店：面包店、药店、书店各有自己的库房和账本，谁装修都不影响隔壁开门。

上一代为什么改不动

上一章讲过，老一代做法追求「全公司共用一套零件」，结果每个零件都被所有部门绑住。微服务反过来想：与其共用，不如各备一份。两家店都要记顾客地址？那就各记各的，哪怕重复。

它是怎么做到的

每家小店只管一件业务，从柜台到库房一手包办，别人不许直接进它的库房翻账本，有事只能在门口问。店里雇的保安、记账员这类杂事，交给统一的物业公司派人驻店，这样每家店的「店规」一致，生意却各做各的。

最难的是需要几家店同时办成的事，比如「下单」要同时扣库存、收钱、派送。大楼里一张总账一笔勾掉；一条街上只能一家一家去办，中途有一家失败，前面办好的就得一家家上门撤回。

带来了什么 / 该怎么选

好处是改得快、扛得住：一家店出问题，整条街照常营业；哪家生意火，就单独给哪家加人。代价也实在：店与店之间来回跑腿，比在一座楼里喊一声慢得多，管理一整条街也比管一座楼累得多。

一句话记住

微服务 = 一条街的独立小店：每家只做一件事、自带库房、互不翻账；用「重复」换「互不牵连」，代价是跑腿慢、管理难。

一句话

你以为微服务的关键在「微」，其实书引用 Martin Fowler 的话说得很直白：「微服务」是个标签，不是描述。微服务架构（microservices architecture）真正的驱动理念来自领域驱动设计的边界上下文：每个服务完整拥有一块业务和它的数据，宁可重复，也不要耦合。FoSA 第 17 章讲它的拓扑、粒度怎么定、数据和运维怎么隔离，以及分布式事务这道最难的坎。

Glossary · 术语表

  • 服务（service）：一个独立运行、通过网络被调用的程序，对外只暴露接口。
  • 耦合（coupling）：两部分互相依赖的程度；耦合越高，改一处越容易牵动另一处。
  • 领域驱动设计（DDD，domain-driven design）：Eric Evans 提出的方法，按业务领域而不是技术层来组织软件。
  • 事务（transaction）：一组操作要么全成功、要么全撤销；ACID 是单个数据库提供的这种强保证。
  • 同步 / 异步调用：同步是发出请求后原地等结果；异步是发出去就继续干别的，结果稍后再来。
  • 架构量子（architecture quantum）：能独立部署、独立运行的最小单元（第 7 章）。
  • 容器（container）：把程序和它的运行环境打包在一起的轻量隔离单位，如 Docker。
  • 延迟（latency）：一个请求从发出到拿到结果所花的时间。

坐标

Part II「架构风格」第 8 种，承接编排驱动的 SOA（第 16 章），下启「如何选择架构风格」（第 18 章）。它是书里领域分区 + 分布式走得最远的风格；现实对应：Amazon、Netflix 这类拆成成百上千个服务的互联网系统。

这章要解决什么

上一章的 SOA 用「企业级复用」换来了全局耦合：一个共享的 Customer 服务要装下所有事业部的需求，改一个字段，几个部门一起测、一起上线。规模一大，最贵的不再是机器，而是协调。

微服务要解决的就是这件事：怎样让一个上百人的工程组织里，每个小团队都能独立修改、独立测试、独立上线自己那一块，并且某一块出故障、某一块流量暴涨时，不拖累其他部分。不解决的后果很具体：发布要排「火车」，一次大版本几周一发，任何一个模块的 bug 都能把整列车拦下。

书也指出它出现的时机：2014 年 Lewis 与 Fowler 发文为它命名时，DevOps、自动化部署和容器已经成熟，运维成本降下来，才让「拆成很多份」变得负担得起。

核心内容，讲透

① 拓扑：每个服务连同它的数据库，自成一体

微服务的拓扑很简单：一组单一用途的服务，各自运行在独立进程里（通常是独立容器），前面可选一层 API 层。关键在每个方框里面，服务带着自己的数据库，别人不许直接访问。

② 边界上下文：宁可重复，也不要耦合

边界上下文（bounded context）是 DDD 的概念：每个服务围绕一块业务或一个工作流建模，它需要的一切都放在里面，包括类、子组件和数据库表结构。上下文之外的东西，它不依赖。

这直接和复用冲突。书的例子：好几个服务都需要一个 Address 地址类。传统做法是抽成公共库，大家继承或组合它；在微服务里，架构师通常宁可让每个服务各写一份。因为一旦共享，改地址类就要所有服务一起重新测试和部署，又回到了上一章的 Customer 服务。书的原则是：重复好过耦合（prefer duplication to coupling）。

这一条也带来了异构（heterogeneity）：既然服务互不依赖实现，每个团队可以挑最合适的语言或数据库，比如一个服务用图数据库，另一个用关系库。

③ 粒度：最难做对的事，三条判据

书说架构师最常犯的错就是把服务切得太细，然后只能在服务之间搭大量通信链路才能把事办成。名字里的「微」误导了很多人。书给出三条判断边界的判据：

  • 用途（purpose）：最理想的服务在功能上高度内聚，对整个应用贡献一种重要行为。
  • 事务（transactions）：边界上下文本就是业务工作流。如果几个实体必须在同一个事务里协作，这就是它们该放进同一个服务的信号；避免跨服务事务，是选粒度时最好的指引之一。
  • 协同（choreography）：如果一组服务为了完成工作要频繁互相通信，就把它们合回一个更大的服务，省掉通信开销。

书还补了一句很实在的话：迭代是保证服务设计好的唯一办法。很少有人第一次就切对，要边跑边合、边拆。

④ 数据隔离：每个服务只认自己的库

边界上下文要求数据也隔离：不允许多个服务共享一个「集成数据库」，否则改一张表又会牵动所有服务。每个服务自有数据，挑适合自己的存储。同一份信息在全系统里要有唯一的真实来源（single source of truth），别的服务需要时通过接口去问它，或者用复制、缓存拿一份副本。

代价是：以前一条 SQL join 能拿到的数据，现在可能要调好几个服务再拼起来；以前数据库替你守的一致性，现在得自己设计。

System Design · Day 3 数据库选型 — 每个服务挑自己的库时，按访问模式和一致性需求怎么选

⑤ API 层与运维复用：sidecar 和服务网格

服务前面可以放一个 API 层（如 API 网关），但书提醒它只能做代理、路由和命名，绝不能变成上一章那种塞满业务逻辑的编排中心，否则就把 ESB 请回来了。

那监控、日志、熔断（circuit breaker，下游连续失败时暂时切断调用，避免雪崩）这些每个服务都要的东西怎么办？书的答案是把运维关切和领域关切分开：运维能力放进挂在每个服务旁边的 sidecar 组件，由一个共享基础设施团队维护；各个 sidecar 再连成服务网格（service mesh），从一个控制面统一管理。业务不复用，运维可以复用，这是对「重复好过耦合」的一个精确修正。

System Design · Day 49 容器与编排 — 容器、sidecar 与声明式控制面怎样让成百上千个服务可运维

⑥ 通信：协同还是编排

服务之间可以同步调用，也可以异步发消息。跨服务的业务流程有两种协调方式：协同（choreography，像舞者各自按节拍动，没有指挥）和编排（orchestration，有一个指挥决定谁先谁后）。微服务偏好协同，因为没有中心节点、耦合最小；但这不是绝对的。

书的例子是一个需要多个服务协作的客户请求。纯协同下，第一个被调用的服务（如客户服务）只好兼任协调者，它和其他服务的耦合变重、职责变杂；另一种做法是专门建一个只协调这一流程的局部服务。两种做法都有耦合，只是放在不同地方，这正是本书反复强调的：没有免费的选择，只有权衡。

⑦ 事务与 Saga：别在微服务里做事务

书在这里给了一句很重的建议：别在微服务里做事务，去修粒度。架构师常常想把单体时代的事务原样搬过来，可是一旦一个业务动作横跨多个服务，就失去了数据库的 ACID。

实在需要时，最常用的模式是 Saga：由一个服务充当协调者，依次调用各个服务；某一步失败，就对已经完成的步骤逐个发起补偿事务（compensating transaction，一个反向操作，把前面的改动撤回去）。期间数据处在「待定」状态，别的请求可能读到中间态。

书的态度是：偶尔几个 Saga 可以接受；如果跨服务事务成了常态，说明粒度切错了，该把总在一起改的东西合回一个服务。

强项中等弱项
伸缩性、弹性、可演进性、模块化 5 星；可部署性、可测试性、容错、可靠性 4 星架构量子：1 到多个，通常每个服务一个性能 2 星；简单性、总体成本 1 星

怎么读这张表：微服务把可独立改、可独立伸缩推到了极致，代价算在性能和成本上。性能差的原因很具体：原来一次进程内调用约几纳秒到微秒，变成网络调用通常是毫秒级，而且每个端点还要做一次安全校验；一个请求串起五六个服务，延迟就叠上去。书的建议是通过合理粒度减少调用链、用缓存和复制减少跨服务读。

所以适合它的场景是：领域边界清楚、团队多、各部分负载差异大（比如商品浏览是下单流量的几十倍）、需要高频独立发布。不适合的是：小团队、领域还没想清楚、强一致事务多、对延迟极敏感的系统，这些情况下第 13 章「基于服务的架构」往往更务实。

为什么重要 / 落到真实系统

它是近十年面试和架构评审里被问得最多的风格，也是被误用最多的一个。书这一章的价值在于给出判据，而不是口号。公开资料里正反两面的经验都很清楚：

大厂实证 · 以下为公开资料中的做法与主张（转述，仅文字出处）
  • Amazon（2006）：CTO Werner Vogels 回顾亚马逊的服务化时说，服务之间只能通过接口通信，不允许从外部直接访问某个服务的数据库。这就是本章「数据隔离」的早期实践。ACM Queue，《A Conversation with Werner Vogels》，2006（转述）
  • Lewis & Fowler（2014）：为微服务命名的文章把「去中心化的数据管理」（每个服务管理自己的数据库）和「聪明端点、笨管道」列为核心特征，后者明确与 ESB 对照。James Lewis & Martin Fowler，《Microservices》，martinfowler.com，2014（转述）
  • Segment（2018，反例）：其工程博客《Goodbye Microservices》回顾，为每个数据目的地各建一个服务后，服务数涨到上百个，共享库版本分化、运维负担剧增，最终合并回单一服务。Segment 工程博客，Alexandra Noonan，2018（转述）
  • Amazon Prime Video（2023，反例）：其技术博客称，音视频质量监控工具原本由多个分布式组件拼成，改为单进程实现后基础设施成本下降约 90%。这正是书里「切太细、通信太多就合回去」的实例。Prime Video Tech 博客，2023（转述）

落到评审，可以直接问：这几个服务是不是总在一起改？有没有两个服务读同一张表？一个用户请求要串几个服务、P99 延迟预算够不够？落到面试，被问「微服务怎么拆」，可以答：「按边界上下文拆，看用途、事务和通信量三条判据；数据各自隔离，运维能力放 sidecar；跨服务事务尽量通过调粒度避免，必要时用 Saga 加补偿。」

易错点与争议

  • 「越小越好」是误解：书明说太细是最常见的错误；「微」只是个标签。
  • 「共享数据库的微服务」不是微服务：几个服务共用一个库，改表要全体协调，它们其实是一个分布式单体，同时承担了两边的缺点。
  • 「重复好过耦合」不是说什么都不复用：运维能力（日志、监控、熔断）通过 sidecar 和服务网格复用正是书推荐的；不复用的是领域逻辑。
  • API 网关别长成 ESB：一旦把路由之外的业务规则放进网关，就回到了第 16 章。
  • Saga 不是免费的 ACID：中间态对外可见，补偿操作本身也可能失败，需要可重试、幂等。
  • 时代背景：书写于 2020 年。此后「模块化单体」（一个部署单元、内部严格按领域分模块）重新受到重视，Prime Video 等案例常被引作论据；更公允的说法是，它和微服务是同一条「按领域分区」思路在部署粒度上的不同选择。

要点

① 驱动理念是 DDD 的边界上下文：一个服务完整拥有一块业务及其数据；「微」是标签不是描述。

② 核心原则：重复好过耦合，连 Address 这样的类也宁可各写一份。

③ 粒度三判据：用途、事务、通信量；太细是最常见错误，迭代是唯一保证。

④ 数据隔离：不共享集成数据库，每个信息只有一个真实来源。

⑤ API 层只做代理路由，不放业务逻辑；运维复用交给 sidecar 和服务网格。

⑥ 协调偏好协同，复杂流程可用局部编排；两者都有耦合，只是位置不同。

⑦ 别在微服务里做事务：Saga 加补偿可用，但常态化说明粒度错了。

⑧ 评分：伸缩、弹性、演进、模块化 5 星；性能 2 星；简单性与成本 1 星。

⑨ 面试复述：「按边界上下文拆、数据各自隔离、运维放 sidecar、跨服务事务靠调粒度避免。」
