信息隐藏与泄漏

A Philosophy of Software Design · Ch 5 · Information Hiding (and Leakage) · Ousterhout · 2nd ed 2021

EN →

这一章讲什么？

上一章说，好的零件要「深」：用起来简单，背后干很多活。这一章回答紧接着的问题：怎么才能做出深零件？答案是一个半世纪软件工程里最经典的点子——把「怎么做」的秘密锁在一个地方，别让它到处散落。你在网页上填完表单点「提交」，服务器那头的程序一行代码就能拿到你填的名字，至于它是怎么从一长串字节里抠出来的，写业务的人完全不用知道。

先说个怪事

一个程序要做三件事：读一个文件、改几处、再写回去。最顺手的拆法是照着步骤拆成三个零件：「读的」「改的」「写的」。看起来清清楚楚，可有一天文件格式变了——你发现「读的」和「写的」得一起改，漏改一个就出错。按步骤拆，反而把同一个秘密拆成了两份。

旧世界为什么难

人写程序时，脑子里最先浮现的是「先干啥、后干啥」。于是很多系统是照着流程图切开的。问题是，流程里的每一步往往要懂同一份知识：同一种文件格式、同一种网络消息的样子。知识被抄进好几个零件，就像一份菜谱被抄给三个厨师，改一次配方要通知三个人，而且没人提醒你漏了谁。

核心机制直觉

  • 每个零件守一个秘密。就像保险柜：秘密锁在里面，外面只留一个投币口和一个取货口。
  • 秘密只有一个人知道，就只用改一个地方。换了更好的做法，外面的人毫无感觉。
  • 泄漏 = 同一个秘密出现在两个零件里。最糟的是「后门」泄漏：两个零件明面上互不相识，私下却都背着同一本菜谱。
  • 按「要懂什么」拆，别按「先后顺序」拆。读和写都要懂文件格式，那就让同一个零件负责读写。
  • 最好的功能是你不知道它存在。好零件会自动做对的事，比如回复时自动用对方说话的那种「方言」，不用你吩咐。

带来了什么 / 该怎么选

它给了一个拆系统的新问题：不是「这件事分几步」，而是「这里有哪个以后可能会变的决定，该由谁一个人守着」。照这个问题拆，改动只落在一处，新人也只需看懂入口。一句诚实的代价：藏得太狠也会出事——真正需要被外面知道的东西藏起来了，用的人只能干着急。

一句话记住

一个秘密只住在一个零件里。按「谁要懂什么」拆，别按「先干啥后干啥」拆。

一句话

你以为模块的边界该沿着「先做什么、后做什么」去划，Ousterhout 说该沿着知识去划：每个模块封装几个设计决策，别人看不见、也不必知道——这就是信息隐藏（information hiding），造深模块最重要的手艺。它的反面是信息泄漏（information leakage）：同一个设计决策出现在多个模块里，改它就得一起改。

Glossary · 术语表

  • 模块 / 接口 / 实现：第 4 章的概念——模块是有接口的代码单元；接口是使用者必须知道的一切，实现是完成承诺的代码。
  • 设计决策（design decision）：实现时做出的选择，比如数据用什么结构存、文件长什么格式、用什么算法。
  • 依赖（dependency）：一段代码改了，另一段代码也得跟着看、跟着改。
  • 私有字段（private field）：类内部的变量，语法上外部不能直接访问；常配 getter / setter（取值 / 赋值方法）对外开放。
  • HTTP 请求：浏览器发给服务器的一段文本，开头几行是请求行和头部（header），后面可能跟着正文（body）。
  • 查询字符串（query string）：网址里 ? 后面的部分，如 ?q=book&page=2，常用来传参数。
  • URL 编码：网址里不能直接写空格等字符，于是写成 %20 或 +，服务器要先「解码」还原。
  • Content-Length：HTTP 头部里的一项，写明正文有多少字节，接收方靠它知道该读到哪里停。
  • 默认值（default）：使用者不指定时模块自动采用的选择。

坐标

全书第 5 章，紧接第 4 章「模块要深」：上一章定下目标，这一章给出最主要的手段。它直接继承 David Parnas 1972 年的经典论文，并用 Ousterhout 在斯坦福软件设计课（CS 190）上批改学生 HTTP 服务器项目时见到的真实错误来讲。下一章「通用模块更深」接着讲接口该做多通用。现实里对应每一次「这个类要不要拆成读和写两个」的评审。

这章要解决什么

第 2 章说复杂度的一大症状是变更放大（change amplification）：一个看似简单的改动，要在很多地方动手。它的根源常常不是代码写得乱，而是同一份知识被多个模块各持一份。比如一个文件格式，读取模块懂它、写出模块也懂它；格式加一个字段，两处都得改，漏一处，程序可能照样编译通过，只在运行时读出错数据。

更糟的是，这种依赖经常不显形：两个类的接口里谁也没提对方，看代码结构看不出它们绑在一起。本章要回答：模块到底该藏什么？什么情况算泄漏？为什么最自然的「按步骤拆」恰恰最容易泄漏？

核心内容，讲透

一、信息隐藏：每个模块守住几个设计决策

Ousterhout 列的典型「秘密」：怎么在 B-tree 里存数据并高效访问；怎么找到文件每个逻辑块对应的物理磁盘块；怎么实现 TCP 协议；怎么在多核上调度线程；怎么解析 JSON。秘密可以是数据结构和算法，也可以是更底层的细节（如页大小），甚至更高层的假设（如「大多数文件都很小」）。

信息隐藏从两个方向压复杂度：

  • 接口变简单：接口只反映功能的抽象视图，不暴露细节，使用者的认知负担就小——这正是第 4 章「深」的来源。
  • 系统更好演化：一个决策只在一个模块里，改它就只动这个模块。

一个常见误会要当场拆掉：把字段声明成 private 不等于信息隐藏。如果再配一组 getter / setter，把内部数据的样子原样交出去，外面照样依赖它的结构。判据是使用者需不需要知道这个决策，而不是语法上能不能碰到它。

隐藏也可以是部分的：某个功能只有少数人用，又是通过单独的方法拿到的，那它对大多数使用者来说就是看不见的——部分隐藏也有价值。

论文精读 · 如何把系统拆成模块（Parnas 1972） — 本章的源头：同一个 KWIC 索引程序的两种拆法，按处理步骤拆 vs 按「易变的设计决策」拆

二、信息泄漏：同一个决策出现在两个地方

泄漏是信息隐藏的反面：一个设计决策反映在多个模块里，它们之间就有了依赖，改这个决策就得同时改所有相关模块。泄漏有两种：

  • 经由接口泄漏：某条信息写进了模块的接口，按定义它就泄漏出去了。这有时不可避免，但越少越好，接口越简单越好。
  • 后门泄漏（back-door leakage）：信息不在任何接口里，却被两个模块各自知道。书里的例子：两个类都懂同一种文件格式，一个负责读、一个负责写。接口互不相干，格式一改两边都得改。作者说它比接口泄漏更阴险，因为从代码上看不出来。

修法有两种：如果受影响的类都不大、和这条信息关系紧密，把它们合并成一个类；否则把这条信息抽出来，放进一个新类，由它唯一掌握，对外只给一个把细节抽象掉的简单接口——把后门换成正门。作者把「信息泄漏」列为红旗：同一份知识被多个类使用。

三、时序分解：最自然、最常见的陷阱

时序分解（temporal decomposition）是按操作发生的先后来拆系统。还是那个例子：程序读文件、改内容、写回去，于是拆成「读取类」「修改类」「写出类」。读和写都必须懂文件格式，于是格式这条知识就漏进了两个类。

为什么它这么常见？因为写代码时脑子里最先出现的就是执行顺序，而流程图天然是按步骤画的。Parnas 1972 年批评的「第一种拆法」正是这种。作者给的原则是：设计模块时，关注完成每项任务需要什么知识，而不是任务发生的顺序。顺序当然重要，它应当体现在某个调用者的代码里，但不该决定模块边界。红旗：时序分解。

四、案例：学生写的 HTTP 服务器

CS 190 的作业是实现一个简化的 HTTP 服务器：收请求、交给应用处理、发回响应。Ousterhout 把学生最常犯的错归成几类，正好演示本章原理。

错误一：读和解析拆成两个类。很多小组用一个类从网络把请求读成字符串，再用另一个类解析字符串——典型的时序分解。问题是：不解析就不知道该读到哪里停，读的一方得先找到头部结束的位置、再读出 Content-Length 才知道正文多长。于是两个类都得懂 HTTP 请求的结构，格式知识泄漏了；调用方还得按固定顺序调两个方法。合并成一个类后，代码更短、接口更简单。作者由此给出一个反直觉结论：信息隐藏往往可以通过把类稍微做大一点来改进——这与上一章批判的「类越小越好」遥相呼应。

做得好的：参数接口。最好的设计提供 getParameter(name)，返回已经解码好的字符串。它藏起了两件事：参数可能来自请求行里的查询字符串，也可能来自正文；值要经过 URL 解码（如 + 还原成空格）。应用开发者两件都不用知道。反例是有的小组直接返回内部的 Map<String, String>：它浅，而且把内部表示暴露出去，以后想换存储方式就会波及所有调用方。更好的是再加一个 getIntParameter(name)，把转整数和错误检查也藏进去。

错误二：不给默认值。一些小组要求调用方在构造响应时指定 HTTP 协议版本。其实响应版本应与请求一致，类自己就能做对。作者的原则是：默认值是部分信息隐藏，应当让常见情况最简单；类应当在不被要求的情况下「做对的事」，最好的功能是你根本不知道它存在。红旗过度暴露（overexposure）：常用功能的 API 逼使用者去学那些很少用的功能。

System Design · Day 9 API 设计 — 把 getParameter 与默认值的思路放大到服务边界：一旦公开，接口里的每个字段都是你要长期维护的承诺

五、类内部的信息隐藏，与「藏过头」

信息隐藏不止在类与类之间。类内部同样适用：把私有方法设计成各自封装一点信息或能力，并尽量减少每个实例变量被用到的地方——变量被访问的地方越少，类内部的依赖越少。

但也会藏过头。只有在外部不需要这条信息时，隐藏才有意义。如果一个配置参数会显著影响性能，而使用者确实需要根据场景调它，就得暴露出来。作者的理想是模块能自己算出最佳配置（不暴露最好）；做不到时，要诚实地认出哪些信息外面需要，并尽量少暴露。这与第 4 章「假抽象」是同一条线：藏住不重要的，露出重要的。

为什么重要 / 落到真实系统

面试和评审里，「信息隐藏」比「封装」好用，因为它能被检验：假设格式 / 协议 / 存储方式明天要变，要改几个文件？答案大于 1，就说明有泄漏。把这个问题放大到服务层面同样成立（这一点是延伸，不是原书内容）：两个微服务直接读写同一张数据库表，就是跨服务的后门泄漏——接口里谁也没提谁，表结构一改两边一起坏。

实证与出处 · 公开可查

  • Parnas：按「易变的决策」拆。1972 年 Parnas 用同一个 KWIC 索引程序比较两种拆法：按处理步骤（流程图）拆，和按设计决策拆；他的结论是应当从一组困难的、或可能变化的设计决策出发，每个模块对其他模块隐藏一个这样的决策。本章的「时序分解」就是他批评的第一种拆法。出处：D. L. Parnas，On the Criteria To Be Used in Decomposing Systems into Modules，CACM 1972
  • Go 标准库的 FormValue：参数来源藏在一个调用后面。Go 文档写明 Request.FormValue 返回指定名字的第一个值，并按固定优先级合并三处来源：URL 编码的表单正文（仅 POST / PUT / PATCH）、查询参数、multipart 表单正文——调用方只写一行。出处：pkg.go.dev · net/http（Request.FormValue）
  • 同一个库的默认值。同一份文档写明：Write 之前若没调用 WriteHeader，会自动补 WriteHeader(http.StatusOK)；头部没有 Content-Type 时，用前 512 字节自动推断；Date 等响应头自动添加，想去掉才需显式置空——正是「不被要求也做对的事」。出处：pkg.go.dev · net/http（ResponseWriter）

易错点与争议

  • 「字段 private 了就是信息隐藏」。不是。getter / setter 原样交出内部结构，外面照样依赖它；要问的是使用者需不需要知道。
  • 「单一职责就是一个类只做一步」。把「读」和「解析」当成两份职责，恰好造成时序分解。职责应按知识划分，而不是按步骤。
  • 「泄漏只看接口」。最危险的是后门泄漏：接口完全干净，两边却共享同一个格式假设。代码评审时要问「谁还懂这件事」。
  • 「信息隐藏 = 什么都藏」。外部真需要的信息（性能参数、何时落盘）藏起来就是假抽象。
  • 「合并类违反小类原则」。作者明确主张信息隐藏常能通过把类稍微做大来改进；判据是知识是否集中，而非行数。
  • 争议：顺序有时就是知识。流水线、编译器的分阶段（词法、语法、代码生成）看起来是时序分解，却很成功——因为每个阶段之间的中间表示本身就是精心设计的接口，各阶段懂的知识确实不同。时序本身不是罪，知识跨阶段泄漏才是。这一点原书没展开，评审时要分清。

要点

① 信息隐藏是造深模块最重要的手段：每个模块封装几个设计决策，别人看不见。

② 它从两头压复杂度：接口更简单，系统更好演化（改一个决策只动一个模块）。

③ private 字段 ≠ 信息隐藏；getter / setter 把内部结构原样交出去照样是泄漏。

④ 信息泄漏 = 同一个决策出现在多个模块；后门泄漏（接口里看不出）最阴险。

⑤ 修法：小类就合并，大类就把知识抽进一个新类，用简单接口把后门换成正门。

⑥ 时序分解是最常见的陷阱：按任务需要的知识拆，不按任务发生的顺序拆。

⑦ HTTP 案例：读和解析应合并；getParameter 藏起参数来源与 URL 解码；返回内部 Map 是反例。

⑧ 默认值是部分信息隐藏：让常见情况零配置，类应不被要求也做对的事；过度暴露是红旗。

⑨ 别藏过头：外部真需要的信息要露出来，能自动调优最好。
