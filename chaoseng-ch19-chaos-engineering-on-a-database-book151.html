在数据库上做混沌

Chaos Engineering: System Resiliency in Practice · Ch 19 · Chaos Engineering on a Database · 2020

EN →

这一章讲什么？

你在手机银行里转账，钱从一个账户扣掉、在另一个账户出现——背后那套数据库，绝不能「扣了钱却没到账」。现在的大型数据库往往不是一台机器，而是几十上百台机器一起干活。这一章由一家做分布式数据库的公司（PingCAP，产品叫 TiDB）现身说法：他们怎样故意把自己的数据库往死里折腾，来确认它在出事时依然不丢数据、不算错账。

先说个怪事

你会以为：数据库的测试都写好了、全部通过，就可以放心上线。但分布式数据库最要命的毛病，偏偏藏在「测试从来不会走到的那条路」上——比如一台机器刚好在写到一半时断电，同时另外两台之间的网线又抖了一下。每一种故障单独测都没问题，凑到一起才出事。而这种巧合，在成百上千台机器、每天运行的生产环境里，迟早会碰上。

旧世界为什么难

  • 数据库的错是「安静的错」。网页挂了大家立刻知道；数据库悄悄少记了一笔账，可能几个月后对账才发现。
  • 故障种类太多。机器死机、硬盘变慢、网络断成两半、某台机器的钟走快了……排列组合起来数不清。
  • 靠人想不全。工程师只能测自己想得到的情况，真正伤人的往往是没想到的那种。

核心机制直觉

  • 像飞行员练模拟舱。在专门的测试环境里，反复给数据库制造各种「事故」：拔掉一台机器、把网络剪成两半、让硬盘假装坏掉、把某台机器的表拨快几分钟。
  • 一边折腾，一边对账。最经典的检查叫「银行测试」：开一堆账户，让程序不停地在账户之间互相转账。不管怎么转，所有账户加起来的总钱数必须一分不差。只要总数一变，就说明数据库在故障中出了错。
  • 让机器自己天天跑。他们搭了一个自动化的「事故模拟器」：每天拿最新的代码搭起一套数据库，随机组合各种故障去折腾，发现问题自动报告。人只需要看结果、修毛病。
  • 把工具分享出去。这套模拟器后来被整理成开源工具，别的团队也能拿去「摇」自己的系统。

带来了什么 / 该怎么选

好处是：那些「千年一遇」的巧合故障，在测试环境里一天就能被撞上好几次，问题在用户碰到之前就被抓住。一句诚实的代价：这套折腾只能证明「找到了错」，永远不能证明「已经没有错」，而且搭建和维护这样一个日夜运转的模拟器，本身就要花不少人力和机器。

一句话记住

数据库的错是安静的——所以要一边主动制造事故，一边用「总账不能变」这类铁律去对账。

一句话

你以为数据库靠测试用例保证正确，其实分布式数据库最致命的 bug 藏在多种故障恰好叠加的路径上，而且它们是「安静」的——不崩溃，只是悄悄算错。本章是 PingCAP 团队在 TiDB 上的实战记录：在应用、CPU / 内存、网络、文件系统四个层面系统性注入故障，用「不变量」（如转账总额守恒）判定正确性，再把整个过程交给自动化平台日夜运行——这套平台的经验后来沉淀为开源的 Chaos Mesh。

Glossary · 术语表

  • 分布式数据库（distributed database）：数据分散存在多台机器上、对外却像一个数据库那样提供读写。
  • 副本（replica）：同一份数据在不同机器上的拷贝，一台坏了其他还能顶上。
  • Raft：一种共识（consensus）算法，让几台机器对「数据按什么顺序写入」达成一致；只要过半数机器活着就能继续工作。
  • Leader / 主副本：Raft 组里负责接收写入、再复制给其他副本的那一个。
  • 网络分区（network partition）：机器都活着，但彼此之间的网络断开，被分成互相联系不上的几群。
  • 时钟漂移（clock skew）：不同机器的系统时间不一致，或某台机器的时间突然跳变。
  • 事务（transaction）：一组读写要么全部成功、要么全部不生效，比如转账的「扣款 + 入账」。
  • 不变量（invariant）：无论系统怎么运行都必须成立的性质，比如「所有账户余额之和不变」。
  • Kubernetes：管理容器化应用的平台，负责把程序部署到一群机器上并维持其运行。

坐标

这章要解决什么

TiDB 是一个兼容 MySQL 协议的分布式数据库，生产集群动辄几十到上百个节点，每天承接海量事务。对这种系统，「不丢数据、不出错账」是不可谈判的底线——Web 服务挂了五分钟可以道歉，数据库少记一笔转账可能要停业对账。

难点有三：其一，故障是常态——磁盘慢、进程崩、网络断、时钟跳，规模一大必然天天发生；其二，故障会叠加——单个故障的处理路径通常有单元测试覆盖，但「Leader 切换进行到一半时又遇到网络分区」这种组合，人很难事先写出用例；其三，数据库的错是安静的——它不报警，只是给了一个错误的结果，等发现时可能已经扩散。本章要回答：怎样把「故障下依然正确」从口头承诺变成每天被验证的事实。

核心内容，讲透

一、先看清靶子：TiDB 的三层架构

要摇一个系统，先得知道它的骨架。TiDB 拆成三部分：

  • TiDB server：无状态的 SQL 层，负责解析 SQL、生成执行计划，自己不存数据，可随意增减。
  • TiKV：分布式事务型 KV 存储。数据按 key 范围切成一个个 Region（区域），每个 Region 默认 3 个副本，组成一个 Raft 组。
  • PD（Placement Driver）：集群的「大脑」，记录每个 Region 在哪、负责调度和负载均衡，并发放全局递增的事务时间戳（TSO，timestamp oracle）。

这张图决定了实验的问题清单：杀掉 TiKV 的一个副本，Raft 能否选出新 Leader 且不丢已提交的写？PD Leader 挂了，时间戳还单调吗？SQL 层和存储层之间网络断了，事务是回滚还是卡死？

二、四个层面注入故障

本章把注入手段按「打在哪一层」分成四类，从最精细到最贴近真实：

① 应用层：failpoint。在代码里预埋「故障开关」，平时是空操作，测试时打开就让某一行返回错误、睡几秒或直接 panic。PingCAP 为 Go 写了 pingcap/failpoint、为 Rust 写了 fail-rs，思路来自 FreeBSD 的 failpoint。它的价值是精准：能让「Raft 快照发送到一半失败」这种极窄的时间窗被稳定复现。

② CPU 与内存。用压测工具抢占 CPU、吃掉内存，模拟「邻居进程把机器打满」。数据库在资源饥饿下会出现心跳超时、Leader 频繁切换等连锁反应，这些在空闲机器上永远测不到。

③ 网络。用 Linux 的流量控制（tc）注入延迟、丢包、乱序，用防火墙规则（iptables）切断特定节点之间的连通，制造网络分区。这是分布式数据库最该摇的一层，因为共识协议的所有精妙之处都在「消息丢了 / 晚到了怎么办」。

④ 文件系统。拦截 I/O 调用，让读写变慢或返回错误（如磁盘满、读出坏数据），检验存储引擎会不会把半截写入当成功、会不会在错误后带病继续运行。

另外两类贯穿始终：直接杀进程 / 重启节点，以及时钟偏移——把某个节点的时间拨快或拨慢。TiDB 的事务时间戳由 PD 统一发放，节点本地时钟不直接决定事务顺序，但依赖超时与租约的逻辑仍然可能被时钟跳变干扰，所以照样要摇。

三、网络分区下 Raft 该怎样表现

以最典型的实验为例：3 副本的 Region，把 Leader 所在节点 A 和 B、C 隔开。稳态假设是——少数派那侧（A）不能再提交写入，多数派那侧（B、C）在选举超时后选出新 Leader 继续服务，已提交的数据一条不丢；网络恢复后旧 Leader 退位、追上日志。任何一条不成立都是 bug：比如 A 仍以为自己是 Leader 并返回了旧数据（违反线性一致读），或两边都接受了写入（脑裂）。

CS Papers · Raft — 选举超时、日志复制与「过半数」规则，正是这类分区实验要验证的那套机制

四、怎么判定「出错了」：指标 + 不变量

注入故障只是一半，另一半是检测。本章给出两类信号：

  • 系统指标：通过 Prometheus 等监控看 QPS、延迟、Leader 切换次数、错误率。故障注入后 QPS 掉一下是预期，但长时间不恢复、延迟持续飙高，就是可用性问题。
  • 正确性不变量：这是数据库特有、也更关键的一层。最经典的是银行测试（bank test）：建若干账户，多个客户端并发地随机互转，同时不断读取全部余额求和。转账是事务，总额必须恒定；任何一次读到的总和变了，说明出现了丢失更新、读到中间状态等隔离性 / 一致性错误。类似的还有「只追加的日志不能丢条目、不能乱序」等。

不变量的妙处在于：你不需要预知 bug 长什么样，只需要说清「什么永远不该发生」。这和 Jepsen 的思路一脉相承——记录操作历史，再检查它是否符合声称的一致性模型。

关键权衡与选型

核心取舍：注入越精细，越好复现、越好定位，但离真实故障越远；越贴近真实，越能发现想不到的问题，但越难复现。

各层故障注入手段对比

手段擅长发现可复现性代价 / 局限
代码 failpoint极窄时间窗的竞态、错误处理分支高，可精确到某行要改代码预埋；只能测想到的点
杀进程 / 重启崩溃恢复、Leader 选举、日志回放中粗粒度，测不出「慢而不死」

验证「故障下仍正确」的几条路线

路线代表强项代价
单元 / 集成测试 + failpoint开发者日常快、可定位只覆盖预想路径
黑盒历史检查Jepsen对照一致性模型，找出隔离级别漏洞单次分析投入大，非持续
持续混沌平台Schrodinger / Chaos Mesh真实二进制、真实环境、日夜运行集群与人力成本；难复现
确定性模拟FoundationDB任何失败都可按种子完全重放须从第一天按可模拟方式设计系统

判据：一个分布式数据库至少要有「不变量检查 + 持续注入」这一组合；只有注入、没有对账，等于只测了可用性没测正确性。

为什么重要 / 落到真实系统

面试或架构评审里被问「你怎么证明这个存储在故障下不丢数据」，空谈「我们用了 Raft」不够——共识算法是对的，实现不一定对。可信的回答是：列出要验证的不变量（已提交写不丢、总额守恒、单调读），说明在哪些层注入哪些故障，以及这些实验是否在每次发版前自动跑。本章给出了一个可抄的完整模板。

大厂实证

  • PingCAP：把内部混沌平台开源为 Chaos Mesh。项目自述为「面向 Kubernetes 的开源、云原生混沌工程平台」，用 Kubernetes 自定义资源来定义、编排和观察受控的故障注入，覆盖 Pod、网络、I/O、时间、压力、内核等故障类型；现为 CNCF 孵化项目。出处：chaos-mesh/chaos-mesh README，GitHub
  • PingCAP：failpoint 作为代码级注入工具。其 Go 实现自述「failpoint 用于在代码中加入可由用户控制注入错误的位置」，并强调不启用时没有额外开销，设计沿袭 FreeBSD 的 failpoint。出处：pingcap/failpoint README，GitHub
  • Jepsen 对 TiDB 的独立检验（2019）。Kyle Kingsbury 对 TiDB 2.1.7 的分析发现，默认开启的事务自动重试会在冲突时导致丢失更新等异常；PingCAP 随后在 3.0 中把自动重试改为默认关闭。它说明厂商自建的混沌测试与外部黑盒检验是互补的。文字出处：Jepsen，「TiDB 2.1.7」分析报告，2019
  • FoundationDB：确定性模拟作为另一条路。官方文档称确定性「使模拟运行可以完美重复」，便于针对问题做受控实验；每晚运行数以万计的模拟，每次模拟大量组件故障，并估计累计已运行约相当于一万亿 CPU 小时的模拟。出处：FoundationDB 文档「Simulation and Testing」，GitHub

易错点与争议

  • 「用了 Raft / Paxos 就一致了」。算法证明的是协议，不是你的实现；快照、成员变更、Leader 租约等边角最容易出错，正是混沌实验该瞄准的地方。
  • 「服务没挂 = 实验通过」。数据库要验的是正确性。没有不变量检查的混沌实验，只能发现崩溃，发现不了「安静的错」。
  • 「随机注入足够了」。纯随机在组合空间里效率很低；要结合对架构的理解，有针对性地打在 Leader 切换、Region 分裂、快照传输这些窗口上（呼应 Ch12 实验选择问题）。
  • 「找到 bug 却复现不了」。真实环境注入的最大痛点。保留现场（日志、操作历史、注入时间线）和用 failpoint 把问题收窄成可复现用例，同样重要。
  • 测试环境 ≠ 生产。本章的实践主要在专门的测试集群上做，与 Netflix 式「在生产里实验」不同——对数据库而言，拿真实用户数据冒险的代价太高，这是一个合理但需要正视的取舍。
  • 时代局限与后续发展。原书写于 2020 年，Chaos Mesh 当时刚开源不久；此后它扩展到 HTTP、JVM、云厂商等更多故障类型。业界也在把混沌测试与确定性模拟、形式化方法（如 TLA+）结合使用，各补一块盲区。

要点

① 分布式数据库最危险的 bug 藏在多种故障叠加的路径上，而且是不崩溃的「安静的错」。

② 先看清架构：TiDB = 无状态 SQL 层 + Raft 复制的 TiKV + 负责调度与时间戳的 PD；每个节点和连线都是注入点。

③ 四层注入：应用（failpoint）、CPU / 内存、网络（tc / iptables）、文件系统；外加杀进程与时钟偏移。

④ 网络分区实验的稳态：多数派选出新 Leader、少数派停写、已提交数据不丢、无脑裂。

⑤ 检测靠两条腿：指标看可用性，不变量（银行测试总额守恒）看正确性。

⑥ 不变量不需要预知 bug 长什么样，只需定义「什么永远不该发生」。

⑦ 自动化是关键：Schrodinger 每天对新代码构建、部署、注入、校验，经验沉淀为开源 Chaos Mesh。

⑧ 权衡：越精细越好复现、越真实越能发现意外；持续混沌、Jepsen、确定性模拟互为补充。

⑨ 易错：「用了 Raft 就一致」「没挂就通过」都是误解；找到 bug 后能否复现同样决定成败。
