Choosing Names

A Philosophy of Software Design · Ch 14 · Choosing Names · Ousterhout · 2nd ed 2021

中文 →

What is this chapter about?

Every variable and every function in a program needs a name. This chapter is about one thing: how to choose those names. It sounds minor, yet the author gives it a whole chapter, because names are the first and most frequent thing a reader of code sees, like room numbers in a building. Mix up the numbers and people walk into the wrong room.

A strange story first

Years ago the author helped build an operating system. For a while, files on disk were mysteriously being overwritten by other data, and the team spent a long time hunting the cause. It turned out the code had one name, "block", that sometimes meant "which block of the file" and sometimes "which block on the disk". Two meanings shared one name, and somewhere one was used as the other. One fuzzy name, one very hard bug.

Why the old way is hard

The person naming things knows exactly what they mean, so "data", "result" or "status" feels good enough. But readers aren't inside the writer's head; they can only guess from the name. Guess wrong, and they use it wrong. These small fuzzy spots don't break anything right away; they pile up until the whole program is hard to read and hard to change.

How it works, intuitively

  • A name should paint a picture. Looking at the name alone, could a reader guess what it refers to? "Cursor visible" is obvious; "blink status" sends you digging through code.
  • Be precise. A "count" of what? Say so. But don't be too narrow either: if a feature can delete any stretch of text, don't call its input "the selected text", because it isn't always selected.
  • Be consistent. The same thing always gets the same name, and that name is never used for anything else. Like a family where no two kids share a name.
  • Can't find a good name? That's an alarm. If you rack your brain and still can't find a name that is short and accurate, the thing is probably doing several jobs at once and should be split.

What you get / how to choose

With good names, readers guess less, dig less and make fewer mistakes, and since one name gets read hundreds of times, a few extra minutes choosing it pays off. One honest cost: there's no single right length for a name; some teams prefer short ones, and the author admits that in the end the reader has to be the judge.

One line to remember

A name is the smallest piece of documentation: make it precise and consistent; if you can't name something well, you probably haven't thought it through.

One line

You think naming is polish you apply after the code works; Ousterhout says a name is the smallest unit of abstraction, and good names have just two properties: precision and consistency. And when you cannot find a name that is both accurate and short, the problem usually isn't your vocabulary, it's the design.

Glossary

  • Identifier: the name given to a variable, method, class and so on.
  • Abstraction: a simplified view that keeps only what users need and hides the rest.
  • Scope: the stretch of code where a name is valid; a local variable's scope is usually one function or one loop.
  • Boolean: a variable with only two values, true or false.
  • Block: a fixed-size unit of storage in a file system; "block N of a file" and "block N of the disk" are two different numbering schemes.
  • Red flag: the book's recurring warning signs; when you see one, stop and think about the design.
  • Complexity: the book's central concept, anything that makes a system hard to understand and modify.

Where it sits

Chapter 14 sits in the middle of the book's run on comments: Chapters 12 and 13 cover why to comment and what to write, this chapter covers naming, and Chapter 15 covers writing comments first. Names and comments both use words to supply what code can't say; a name is the shortest and most frequently read piece. It is also the most direct remedy for obscurity, one of the two sources of complexity from Chapter 2. In practice it maps to the naming rules in every style guide and to the "what does this name mean?" comments in code review.

The problem this chapter solves

A medium-sized codebase holds tens of thousands of names, and each one is read far more often than it is written. A single bad name almost never brings a system down, so people shrug it off. But as Chapter 2 argued, complexity accumulates from hundreds or thousands of small problems, and naming is the most common of them. A vague name sends readers to the declaration, the call sites and the comments, raising cognitive load; worse, readers often don't realize they guessed wrong, and that leads straight to bugs.

The chapter offers criteria that turn "is this a good name?" from gut feel into something you can discuss, and reframes "naming is hard" as a design signal.

Core ideas, in depth

1. Bad names cause bugs: Sprite's "block"

The author tells a real story from the Sprite operating system, which he worked on: the file system would occasionally corrupt data, with a file's block overwritten by other data. The bug was rare and hard to reproduce, and finding it took a long time. In the end, the code used many variables named block; sometimes they held a logical block number within a file, sometimes a physical block number on disk, and in one place a logical number was used as a physical one.

Because the two things shared a name, anyone reading block assumed it was the kind they expected, and the name hid the error perfectly. Had the variables been called fileBlock and diskBlock, the mistake would have been very unlikely to happen, and obvious if it did.

2. A name should create an image

When choosing a name, the author says, picture what will form in the reader's mind. A name is an abstraction: a few words standing in for something far more complex, so you can think about it without the details. A good name conveys what the thing is and, just as important, what it is not.

The book gives a test you can use directly: if someone sees this name in isolation, without its declaration, documentation or any code that uses it, how closely can they guess what it refers to? If they can't, change it. The author also notes that good names are usually two or three words; squeezing into one word rarely says enough, and five or six becomes a burden.

3. Be precise: too vague and too specific are both problems

Too vague is the common failure. Examples from the book:

  • getCount(): a count of what? Active connections or all connections?
  • A text editor using x and y for the cursor position: readers assume screen pixels, but they are actually character and line positions; charIndex and lineIndex remove the confusion.
  • A boolean called blinkStatus: what values does a "status" take? Does true mean on or off? Renamed cursorVisible, the meaning of true and false is self-evident. The author's advice: a boolean's name should read as a predicate.

Words like data, info, result, value and status fit almost anything, so they say almost nothing. The exception is idiomatic names with tiny scopes: i and j are fine in a loop that spans only a few lines, because the reader can see every use at once.

Too specific is the other side: a method that deletes any range of text shouldn't name its parameter selection, because it can delete any range, not just what the user selected; range fits. A name that is too narrow makes readers underestimate what something can do, or read in constraints that don't exist.

That gives the chapter's first red flag: Vague Name. A name broad enough to refer to many different things tells the reader little and invites misuse.

4. Be consistent: same thing, same name, always

Most programs have variables that recur again and again, such as block numbers in a file system. Consistent naming lowers cognitive load: once readers learn what a name means in one place, they can reuse that understanding everywhere. The author's three rules:

  • Always use the same name for a given purpose;
  • never use that name for anything else;
  • make the purpose narrow enough that every variable with that name behaves the same way.

Sprite's block broke the third rule: its purpose was so broad that same-named variables did not behave alike. When code needs two variables of the same kind, distinguish them with a common name plus a prefix, such as srcFileBlock and dstFileBlock, so readers still see they are the same kind of thing. Loop variables too: always i for the outer loop and j for the inner, a habit the team can rely on.

5. A name you can't pick is the design sounding an alarm

The chapter's second red flag: Hard to Pick Name. If you can't find a name that is precise, intuitive and not too long, that is a signal that the variable or method may lack a clear definition or a single purpose. It may be doing several things, or its boundaries may be fuzzy. The fix isn't a thesaurus; it's going back to split or redefine the thing.

This ties naming to the book's main thread: something that can be described by a simple name usually has a simple abstraction; something that needs a tongue-twister of a name is usually a shallow module or a muddle of responsibilities.

A rule of thumb: the smaller and more local the scope, the shorter a name can be; the more public and the farther it travels, the more precise it must be. Names in a public interface are hard to change once set, so they deserve the extra time.

Why it matters / in real systems

Naming is one of the most common kinds of code review comment, and one of the most often dropped as "just preference". This chapter's value is criteria both sides can cite: can you guess it from the name alone, does one name carry several meanings, what design problem hides behind a hard-to-pick name. Mainstream style guides broadly agree on these points, with some disagreement:

Evidence and sources · publicly verifiable (original sites unreachable from this run; text citations only)

  • Go Code Review Comments (official Go wiki) · Variable Names: variable names in Go should be short rather than long, especially local ones; the basic rule is that the farther from its declaration a name is used, the more descriptive it must be. This is the stance the book's "different opinion" section discusses, and the distance rule is the part the author accepts. Source: Go project wiki · CodeReviewComments (Variable Names)
  • Andrew Gerrand, "What's in a name?" (Go team talk, 2014): argues a name's length should match its scope and that long names obscure the code's logic; Ousterhout cites this talk in the chapter as the opposing view and says he is not fully convinced. Source: official Go talks archive, 2014
  • Google C++ Style Guide · General Naming Rules: names should describe the object's purpose or intent, readability matters more than saving horizontal space, and abbreviations should be minimized, in line with this chapter's "precision first". Source: google/styleguide · cppguide, "General Naming Rules"

In daily work: when review turns up handleData, tmp2 or flag, ask "could you guess what this is from the name alone?"; when one concept is uid, userId and accountId in different files, unify it under the consistency rules; when a class simply won't take a name, discuss its responsibilities before arguing over English words.

Pitfalls and debates

  • "Longer names are clearer." No. The author wants precision, not length; good names are usually two or three words, and i is a good name in a short loop.
  • "Names are style, they don't affect correctness." The Sprite bug says otherwise: one name with two meanings can corrupt data directly and make the bug very hard to find.
  • "If you can't think of a name, pick anything and rename later." Difficulty naming is a design signal; picking anything silences it. And once a name spreads to callers, renaming gets expensive fast.
  • "Good names replace comments." A name holds two or three words; units, bounds and what null means still need the comments from Chapter 13. Names and comments divide the work; neither replaces the other.
  • The short-name debate is unsettled. Go's short-name tradition is influential, and the author says plainly he is not fully on board, but he grants that the reader's experience is the final judge. A team's own convention often matters more than which camp wins, which foreshadows Chapter 17 on consistency.

Key takeaways

① A name is the smallest abstraction and is read far more than it is written; bad names are the most common of complexity's thousand cuts.

② Sprite file system bug: block meant two things (file block number / disk block number), a mix-up corrupted data; fileBlock / diskBlock would have prevented it.

③ The test: from the name alone, with no context, can a reader guess what it refers to?

④ Precision: getCount, x/y, blinkStatus are too vague; name booleans as predicates, like cursorVisible.

⑤ Not too specific either: a parameter that can be any range is range, not selection.

⑥ Consistency: one purpose, one name; never reuse it for something else; keep the purpose narrow enough that same-named variables behave alike; prefixes for siblings.

⑦ Two red flags: Vague Name, and Hard to Pick Name; the latter usually means unclear responsibilities, so fix the design first.

⑧ The length debate: Go leans short, the author leans precise; both accept that names used farther from their declaration need more description, and readers decide what is readable.
