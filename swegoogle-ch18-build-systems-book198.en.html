Build Systems and Build Philosophy

Software Engineering at Google · Ch 18 · Build Systems and Build Philosophy · Erik Kuefler · 2020

中文 →

What is this chapter about?

Programmers write text that people can read; computers run a different kind of file that only machines understand. The "translate and assemble" step in between is called the build. Every app on your phone, every update, has gone through it. This chapter is about how Google made that step both fast and dependable — fast enough that a one-line change comes back in seconds, dependable enough that whichever of tens of thousands of engineers runs it, the result is identical.

A surprising fact first

Ask Google engineers what they like best about the company, free food aside, and many will say: the build system. In an internal survey it ranked fourth out of 19 tools. Stranger still, it works so well precisely because it does not let engineers do whatever they want — it takes some of their freedom away.

Why the old way was hard

The old way was like a handwritten recipe where each step could say anything at all. The head chef could not tell what any step really did, so they never dared let two cooks work at once, in case both grabbed the same pan; nor dared skip a step, in case it quietly used stale ingredients. So every meal was cooked from scratch, slower and slower. Worse, the recipe often only worked in the kitchen of whoever wrote it — on another computer, a missing tool or the wrong version and the dish failed.

How it works, intuitively

  • Say what you want, not how to make it: engineers stop writing steps and just write "I want this dish; it uses these ingredients and those prepared parts." How, and in what order, is up to the system.
  • Same ingredients, same dish, every time: each step may only use the ingredients it named, as if cooking in a little booth holding nothing else. So if the ingredients haven't changed, last time's dish is reused; unrelated dishes can safely be cooked at once.
  • One shared pantry for the whole company: since the same ingredients always make the same dish, if someone already made it you just take it off the shelf. Whatever isn't there gets handed out to thousands of machines in the data center to make together.
  • Bought ingredients are checked and come in one version: each purchased ingredient has its "fingerprint" written down, and a delivery that doesn't match is refused; the whole company uses one version of each, so two dishes never demand two versions that can't share a plate.

What it brings / how to choose

What you get: change a little and only that little is redone; you almost never need to "wipe and start over"; a new hire can build any code on day one, and automated testing and releases can safely sit on top. The honest cost: you can no longer toss off a script that does anything you like — you play by its rules — and moving a big project already built the old way is not cheap.

One line to remember

Turn the build from "run a list of steps" into "declare the products you want": give up a little freedom, and the system can run in parallel, reuse results and spread work over thousands of machines — while guaranteeing the same result everywhere.

The one-liner

You'd think a good build system gives engineers maximum flexibility; this chapter argues the opposite: take power away from engineers and give it to the system. Once a build means "producing artifacts" rather than "running tasks", the system knows what every step does, so it can parallelize, reuse and distribute — and fast versus correct stops being a choice.

Glossary

  • Build: the process of compiling, linking and packaging source code into something runnable.
  • Compiler: a program that translates source in one language into a machine-executable form, such as javac or gcc.
  • Binary / artifact: a file the build produces — an executable, a library, a JAR.
  • Dependency: "I need that before I can have this"; another piece of code, a third-party library, or a tool.
  • Transitive dependency: a dependency of a dependency; if A depends on B and B on C, C is a transitive dependency of A.
  • DAG (directed acyclic graph): nodes joined by one-way arrows with no way back to where you started; dependencies naturally form one.
  • Incremental build: rebuilding only what a change affects and reusing everything else.
  • Hash: a function that squeezes any content into a short fixed-length "fingerprint"; change one byte and the fingerprint changes completely.
  • Semantic versioning (semver): version numbers like 1.1.4, where a new major number signals a possibly incompatible change.

What problem this chapter solves

A build system has exactly two goals: be fast (one command, often a result in seconds) and correct (anyone, on any machine, with the same inputs, gets the same output). Older tools often trade correctness for speed — shortcuts for incrementality that yield builds which sometimes work and sometimes don't.

The chapter tells the scaling story through a growing project: at first javac *.java is enough; with several languages and third-party JARs you are ordering steps by hand and stuffing downloads into a lib folder; move to shell scripts and, to avoid stale outputs, you rebuild everything every time; a disk dies and the downloaded libraries and environment variables are gone; every new hire and every nightly cron build means another round of "works on my machine". For one person writing a few hundred lines over a week or two, a compiler is all you need; once many people and many machines are involved, even a perfect script can't absorb the small differences between machines.

At Google this is pushed to the extreme: more than two billion lines of code, and even simple binaries often depend on tens of thousands of build targets. Most builds are triggered by machines, not people — changes are tested automatically in review, again before merging, and low-level library changes are verified across millions of tests. None of that works without a build you can trust.

The core ideas, in depth

1. Task-based builds: too much power to people, too little to the system

Ant, Maven, Gradle, Grunt and Rake are task-based: the unit of work is a task, a script that can do anything, which declares the other tasks it depends on; together they form a DAG. ant dist walks dist → compile → init and then runs them in reverse — strip the syntax and it's not far from a shell script.

The root problem: the system has no idea what the scripts do, so it must be extremely conservative.

  • Hard to parallelize: A depends on B and C, which don't depend on each other — can they run at once? Maybe both write the same status file. The system can't know, so it either takes the risk (rare, very hard-to-debug failures) or runs everything single-threaded — wasting a multicore machine and ruling out distribution entirely.
  • Hard to make incremental: a task might download a file that changed or write a fresh timestamp, so the system can't confirm it's "already done" and reruns it. Letting people hand-write "when to rerun" is hard to get right — with C++ includes you can't know which files to watch without parsing the sources. After a few bad shortcuts, everyone runs clean before every build and incrementality is dead.
  • Hard to maintain: build scripts are code that rarely gets reviewed. Classic bugs: B changes its output path and A only fails when it runs; B drops its dependency on C and A, which relied on C's output, mysteriously breaks; a task silently assumes a tool path or environment variable; B and C write the same file and A's result depends on which finished first.

The conclusion is blunt: as long as arbitrary code can run during the build, the system can never have enough information to be both fast and correct.

2. Artifact-based builds: declare what, leave how to the system

Blaze and its descendants (Bazel, Pants, Buck) are artifact-based: a BUILD file is no longer a Turing-complete list of commands but a declarative manifest — which targets to produce, their sources (srcs), their dependencies (deps), plus a few constrained options. java_library produces a library, java_binary an executable, and deps can point within the package (:mylib), to another package in the repo (//java/com/example/common) or to a third party (@…guava//jar).

The author's analogy is functional programming: you state what to compute and leave when and how to the compiler. A build as a whole is a function from source files and tools to binaries. So:

  • Parallel: Bazel knows a step just runs the Java compiler, not an arbitrary script, so it can compile independent targets at once — up to an order of magnitude faster on a multicore machine.
  • Reusable: a compiler's output depends only on its inputs, so unchanged inputs mean reuse. Run the build again with no changes and it reports "up to date" in under a second; change common and only common → mylib → MyBinary rebuild while otherlib is reused — with a guarantee of no stale output.

3. Turn the environment into declared dependencies too

Parallelism and reuse aren't enough; each "works on my machine" hole has to be plugged:

  • Tools as dependencies: every java_library implicitly depends on a Java compiler, downloaded if missing; change the compiler and dependents rebuild. Cross-platform builds use toolchains: the concrete set of tools is picked by host and target platform.
  • Extensible, but fenced: custom rules generate actions — the lowest-level composable unit, free to do anything as long as they use only their declared inputs and outputs, while Bazel handles scheduling and caching.
  • Sandboxing: each action sees only its declared inputs and its own outputs; the book says this is enforced on Linux with LXC, the same kind of technology behind Docker. Undeclared files can't be read, undeclared outputs are thrown away, and network access can be blocked. Two actions clobbering the same file becomes impossible.
  • Deterministic external dependencies: a workspace-wide manifest records a cryptographic hash for each external dependency. A mismatch fails the build, and updating means changing the manifest and getting it reviewed — so every upgrade is on record, and checking out last week's commit gives you last week's dependencies. To guard against the supplier going down, the author recommends any nontrivial project mirror its dependencies on servers it controls.

4. Distributed builds: remote caching, then remote execution

Tens of thousands of targets won't fit on one machine; cut the work small enough and spread it over any number of machines and a build gets "as fast as you're willing to pay for" — the holy grail the artifact-based design was aiming at.

Remote caching is the simple form: workstations and CI share one cache service; before building an artifact you check the cache, download it if present, otherwise build it and upload it. The precondition is fully reproducible builds, with the cache keyed on the target plus a hash of its inputs, so several people editing the same target at once don't collide. The other precondition is that downloading beats building — measure your network latency first.

Remote execution is the real distributed build: when a low-level change forces a full rebuild, a cache alone still leaves the work on your machine. A master splits requests into actions and schedules them on a scalable worker pool; workers exchange intermediate outputs through the cache. It requires a fully self-describing environment, fully self-contained steps and fully deterministic outputs — nearly impossible for a task-based system.

Google's implementation: the remote cache ObjFS stores outputs in Bigtable, and a FUSE daemon on each workstation, objfsd, makes them look like local files, downloading content only when opened — twice as fast as keeping all outputs on local disk. Remote execution is Forge: the Distributor sends actions to the Scheduler, which returns immediately on an action-cache hit and otherwise queues the action for a large pool of Executors, which write results into ObjFS. The scale: millions of builds, millions of test cases and petabytes of output every day.

5. Modules and dependencies: fine grain, visibility, strict transitive deps

Granularity is a trade-off between "one target for the whole project" and "one target per file" (see Table 2). Google favors targets much smaller than is typical in task-based systems: a typical production binary depends on tens of thousands of targets, and a moderate team owns several hundred. In Java, a directory usually holds one package, one target and one BUILD file — what Pants calls the 1:1:1 rule. Small targets mean faster distributed builds, fewer rebuilds, and running only the handful of tests a change could affect; the maintenance burden is offset by tools that manage BUILD files automatically.

Visibility is the mirror image of a dependency: for A to depend on B, B must be visible to A. Keep it narrow: only libraries meant for everyone are public, internal implementations are visible only to the team's own directories, and most BUILD files have only one non-private target.

Strict transitive dependencies: A depends on B, B depends on C — may A use C's classes directly? The linker doesn't mind, and Blaze allowed it for years. But once B is refactored and drops C, every target that "used C through B" breaks — dependencies became part of the public contract and could never be removed, so they piled up and builds slowed. Google introduced a strict mode: referencing a symbol without depending on it directly is an error, with a shell command that adds the dependency automatically. Making millions of targets declare their dependencies explicitly took years, and the author says it was well worth it: adding a dependency is a one-time cost, while implicit transitive ones keep costing for as long as the target exists. Bazel enables this mode for Java by default.

6. External dependencies: pin by hand, one version, no automatic transitive downloads

Internal dependencies are built from source at the same commit as their users, so they have no notion of "version"; external ones have versions that evolve independently of your code, and that's where the trouble lives. Three positions:

  • Pin versions manually: Gradle lets you write 1.+ (latest with major version 1); on a multi-person project that's "a recipe for disaster" — even suppliers that claim semantic versioning can ship breaking updates, so a build that worked today breaks tomorrow with no easy rollback. With manual pins every change lives in version control and can be found and rolled back. Bazel requires all versions to be specified manually.
  • One-Version Rule: in theory different versions could coexist under different names, but that produces the diamond above. Google enforces one version for every third-party dependency, so a newly added dependency is always already on the same version as existing ones and they coexist happily.
  • No automatic transitive downloads: Maven and Gradle download recursively by default, so one dependency can pull in dozens of artifacts — necessarily violating the One-Version Rule. Bazel instead requires a global file listing every external dependency and its single version, which tools can generate initially from Maven artifacts. The author admits there's no silver bullet: it's convenience versus scalability.

Two further judgments: prebuilding your own code into artifacts to speed things up leaves parts of the system built from different points in the repo and hard to debug — remote caching is the better fix. Supplier risk can be handled by mirroring plus hashes, or by vendoring: Google checks every third-party library into a third_party directory at the root, but that relies on version control custom-built for an enormous monorepo.

Key trade-offs and choices

The chapter's soul in one line: trade flexibility for scale. At each level you give up some freedom and the system gives you one more guarantee.

Why it matters / in real systems

Developers build dozens or hundreds of times a day, and the build is often the rate-limiting step of their productivity. When a review asks "should we move to Bazel?", the chapter's rule is: the bigger the project, the more expensive it is to change build systems, so new projects get the best deal by starting artifact-based; for an existing large task-based project, first check whether it already has speed or correctness problems. In an interview on CI speed-ups or supply-chain security, being able to explain "cache key = target + input hash" and "reproducibility is the precondition for remote caching" goes a level deeper than "add machines, add a cache".

Pitfalls and debates

  • "The more flexible the build tool, the better" — the chapter concludes the opposite. Limiting engineers' power raised their productivity, because incremental builds "just work".
  • "A remote cache always makes things faster" — not necessarily. A distant cache can be slower than building; without reproducibility, it may hand you the wrong result.
  • "Sandboxes make it foolproof" — the author says it isn't. An action can still contain a nondeterministic step; the risk is just pushed down to the action level. Buck2 likewise only guarantees hermeticity under remote execution.
  • Dated details: the book is from 2020. Later Bazel versions are replacing the WORKSPACE file with Bzlmod (MODULE.bazel), which resolves transitive dependencies between modules automatically using minimal version selection — no longer quite the book's "no automatic transitive dependencies"; the sandbox implementation has also evolved. A counterpoint: Bazel's learning curve is steep and tools outside its ecosystem need hand-written rules — and the author grants that task-based systems are enough for most projects.

Takeaways

① Be fast and correct at once; once many people and machines are involved, no script can absorb the differences between machines.

② The root flaw of task-based builds is that the system can't see into arbitrary scripts: hard to parallelize, unreliable incrementality, hard-to-maintain scripts.

③ Artifact-based builds declare only targets, sources and deps and leave "how" to the system; like functional code, unchanged inputs are reused, multicore parallelism gives up to 10x, and a no-op build takes under a second.

④ Make the environment declarative too: tools as dependencies, toolchains, sandboxes, hashed external dependencies.

⑤ Remote caching requires reproducibility, keyed on target + input hash; Google's Forge + ObjFS have carried millions of builds a day since 2008.

⑥ Favor fine-grained modules (1:1:1) and narrow visibility; strict transitive deps took years to roll out because implicit dependencies are an ongoing cost.

⑦ External dependencies: pin manually, enforce one version against diamond conflicts, don't pull transitive deps automatically.

⑧ The bigger it gets, the harder it is to switch: start new projects artifact-based.
