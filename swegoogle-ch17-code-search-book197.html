代码搜索

Software Engineering at Google · Ch 17 · Code Search · Alexander Neubeck & Ben St. John · 2020

EN →

这一章讲什么？

你在手机通讯录里找人，敲两个字就跳出来，从不需要一页页翻。可如果通讯录里有几十亿条记录，还每分钟都在变呢？Google 的程序员每天面对的就是这种局面：全公司的代码放在一起，大到任何一台电脑都装不下。这一章讲的是 Google 内部那个「代码搜索」网站——它为什么是工程师打开最多的工具，以及它怎么做到一敲就出结果。

先说个怪事

你可能以为程序员整天在写代码。其实他们花大量时间在读代码：这个功能在哪？别人是怎么用它的？这行为什么这么写、是谁加的？Google 统计过，大约三分之一的搜索是在找「别人是怎么做这件事的」范例。所以一个专门用来读的工具，比一个更好的编辑器还管用——很多人写代码时，旁边常开着好几个代码搜索的页面。

旧世界为什么难

普通做法是把代码下载到自己电脑上，用编辑器自带的搜索。可当代码大到装不下，这条路就断了；就算装得下，每个人的电脑都得各自从头整理一遍目录，开机要等很久。不整理直接硬搜，又像在图书馆里一本本翻书找一句话，慢得让人走神。

核心机制直觉

  • 全公司只编一份目录：与其让几万人各自整理，不如由一个中心统一编好。有人改了几个文件，就只把那几页目录重写一下，几秒钟后所有人都能搜到。
  • 目录按「三个字一组」来编：像给书做索引时，把每段话拆成一个个三字小片段，记下它们出现在哪几页。你要找一句话，先看这几个小片段同时出现在哪些页，再去那几页确认，不用翻整座图书馆。
  • 结果按「名气」排队：就像网页搜索把被引用最多的网页排在前面，被很多人打开、被很多代码用到的文件排前面；而你搜的词如果正好是某个功能的名字，它也会往前排。
  • 点哪就答哪：页面上几乎每个词都能点，点一下就告诉你它在哪定义、被谁用、谁什么时候加的，像一本处处是超链接的百科。

带来了什么 / 该怎么选

好处是新人第一天不用任何准备，就能翻遍全公司的代码、找到能抄的好例子；日志、报错、文档里提到的代码位置，也都直接链到这里，它成了全公司指认代码的「门牌号」。诚实的代价是：「点哪答哪」那部分要把全公司代码整个分析一遍，太费电脑，一天才更新一次，偶尔会和刚改完的代码对不上。

一句话记住

代码主要是被读的：给全公司编一份随改随新的目录，搜得快、排得准、搜得全，大家才会真的信它、用它。

一句话

你以为代码搜索是「大号 grep」，本章说它其实是一套为「读代码」而生的搜索引擎：规模逼着 Google 把索引集中到云端，交互性要求每个操作都低于 200 毫秒，而决定它成败的不是快，是信任——索引全部代码、能返回全部结果、又把想要的排在最前。

Glossary · 术语表

  • 单体仓（monorepo）：全公司代码放在同一个仓库；Google 的叫 Piper（见上一章）。
  • 索引（index）：提前整理好的「词 → 出现位置」目录，查询时不必扫全部内容。
  • 倒排索引（inverted index）：对每个词记一张「出现在哪些文件」的清单（posting list），网页搜索的标准结构。
  • grep：Unix 下逐字扫描文件找匹配文本的命令，没有索引，纯暴力。
  • 正则表达式（regex）：描述文本模式的小语言，如「以 get 开头、以 Id 结尾的词」。
  • IDE：集成开发环境，写代码的编辑器加编译、调试、跳转等功能。
  • 交叉引用（cross-reference）：「这个符号在哪定义、在哪被用」的关系；要靠编译器级分析才能分清同名符号。
  • 符号（symbol）：代码里有名字的东西——函数、类、变量。
  • 延迟（latency）：从发出请求到拿到结果的时间；「中位数」指一半请求比它快。

这章要解决什么

工程师的大量时间花在理解代码上。本章引用 Google 的一项研究（Sadowski 等，FSE 2015），把搜索意图分成五类：约三分之一是「How」——看别人怎么用某个 API；约四分之一是「What」——浏览、读懂某块代码在干什么；约 16% 是「Where」——某个定义或配置在哪；约 16% 是「Why」——这段为什么加、为什么这么表现，常发生在排查线上问题时；约 8% 是「Who / When」——谁、何时引入。

在 Google 的体量下，这些问题用本地工具答不了：整仓连一台机器都装不下；就算装得下，每人启动 IDE 都要重建一遍索引，不建索引则 grep 慢到让人走神。而 Google 每天有远超 100 万次代码搜索——问题不在要不要建，而在怎么在 TB 级语料上做到又快、又全、又准。

核心内容，讲透

一、为什么要一个独立的网页工具，而不是更好的 IDE

作者给了四个理由。规模：集中索引只建一次、全员共享。脚注里的算账很精彩：若每个开发者都在自己的 IDE 里建索引，代码库随时间线性增长、开发者人数也线性，总成本大致是平方级；集中且增量地索引，成本是线性的。零配置的全局视图：IDE 为了启动快、自动补全不被噪声淹没，会逼你把可见范围缩小；网页工具不用配项目、不用构建环境，随时翻遍全仓，改 API 时也不会漏掉依赖方。专精：恰恰因为它不是 IDE——没有文本光标，每一次点击都可以有意义（跳定义、列用法），而不是用来挪光标。

第四是平台效应。Code Search 的链接成了源文件的标准「地址」：日志查看器把「文件名:行号」链回代码；崩溃报告的调用栈因为知道二进制是从哪个快照构建的，能链到那个版本，代码后来被重构或删除也不失效；文档可以嵌入主干上最新的代码片段。反过来，全仓分析（如标出没人调用的「死代码」）直接把结果显示在这里，工具作者不用自己做界面。它也通过 RPC 接口和 vim、emacs、IntelliJ 插件把搜索与跳转送回编辑器。

二、两种索引，两种新鲜度

作者把它和网页搜索类比：热点新闻变得快、百科条目变得慢，可以分别增量更新。文本搜索索引正是增量的——一次提交只重建被改动的那几个文件，彼此独立、可并行，提交到可搜的中位延迟不到 10 秒。

交叉引用索引做不到。它来自 Kythe：在构建过程中抽取每条构建规则的局部语义图，再合并成全局图并为「跳定义、查用法」优化。任何改动都可能影响整个代码库，实际上常常牵动成千上万个文件，几乎所有二进制都得构建或分析一遍；抽取和后处理每一阶段都约等于一次完整构建（脚注举例：Chromium 在分布式环境下要约六小时）。所以它每天只建一次，且只保留一个版本。两套索引的时差是用户「罕见但反复出现」的困惑来源；事故排查时索引与线上运行的代码对不上，更可能掩盖真因、或引入无关的干扰。

三、延迟：用人的注意力算账

低延迟不是免费的，作者用工程师的时间来算它值不值：每天 100 万次查询，每次多 1 秒，约等于每天 35 名全职工程师在干等（100 万秒 ≈ 278 小时）；而搜索后端大约只需这个数的十分之一的人来建和维护。所以每天约 10 万次查询（对应不到 5,000 名开发者）时，单凭「快 1 秒」就已接近盈亏平衡。

而且损失不是线性的：低于 200 ms 界面才算「跟手」；超过 1 秒，注意力开始飘；再过 10 秒，人多半就切去干别的了，上下文切换代价很高。所以目标是所有高频操作端到端低于 200 毫秒。这也解释了为什么在大仓里，搜文件名常比点目录树快：带上当前文件作为上下文，后端会偏向邻近目录，敲几个字母就到。

四、索引：从三字片段到稀疏 n-gram

先看暴力搜索的账（书中估算）：当时索引约 1.5 TB，约 200 QPS，服务端中位延迟 <50 ms。RE2 正则库在内存里约 100 MB/秒，要在 50 毫秒内扫完 1.5 TB 需要约 30 万个核；换成约 1 GB/秒的专用子串搜索能降到十分之一，可 200 QPS 意味着同一 50 毫秒窗口里有约 10 个查询同时在跑——又回到 30 万核。

出路是索引。最早用的是三元组（trigram）索引：把每个文件切成所有连续三字符片段，为每个片段记一张「出现在哪些文件」的清单。查 Point 时取出 Poi、oin、int 三张清单求交集，得到候选文件，再在候选上真正跑匹配确认。正则也能这样做：把正则自动机改写成一组「必须同时出现的子串」，用索引先筛一遍。Russ Cox 后来开源了它的简化版。

此后它经历了自研后缀数组（suffix array）方案，再到现在基于 token 的稀疏 n-gram方案——比暴力搜索高效 500 倍以上，仍能飞快地答正则。换方案的两个理由很有工程味：其一，n-gram 能跑在 Google 主搜索栈的标准倒排索引上，白拿核心搜索团队在构建、编码、服务和「即时索引」上的全部积累，而自研后缀数组光是构建和分发就是个难题——这是用实现简单换一部分性能，检索与打分仍高度定制；其二，索引从内存搬到闪存，闪存比内存便宜至少一个数量级、访问延迟却高至少两个数量级。三元组要从闪存读取又多又大的清单；n-gram 用更大的索引换来更少、更小的清单。另一个细节：给完整提交历史建索引，靠自研压缩只让资源消耗涨到 2.5 倍。

五、排序：检索与打分要一起设计

小仓不需要排序；在 Google，任何短子串都出现成千上万甚至上百万次，不排序就只能逐条看或不停加条件。打分函数把文件的特征（信号）映射成一个分数，分两类。与查询无关的信号可离线算：文件被查看的次数（基础库的工具函数天然高），以及被引用的次数——把网页链接换成 include / import 语句，就是 PageRank 的翻版，可向上扩到构建依赖、向下到函数和类，合称文件的「优先级」。浏览量的坑是自我强化（排得高 → 看的人多 → 排得更高）和新文件冷启动；作者认为略微多展示高分项在实践中危害不大。引用的坑在大规模迁移：文件挪了位置，中间层会稀释它的「PageRank」、浏览量也丢了，最简单的办法是迁移期人工加权。

与查询相关的信号必须每次现算，只能用查询本身和索引里马上能取到的信息：干净的词边界匹配加分并考虑大小写（搜 Point 时 Point *p 胜过 appointed），符号名、文件名命中胜过普通内容命中，查询词出现在路径里（如带上项目名）再加分。

CS Papers · The Anatomy of a Search Engine — PageRank 的原始设计：用链接结构算全局重要度，正是这里「按被引用次数给文件定优先级」的源头

打分之前还有召回（retrieval）：不可能给所有文件打分，只能给召回来的候选打分。典型陷阱是搜一个类名——它可能有几千处用法、只有一处定义，召回固定条数时，可能在碰到那个定义之前就停了。解法叫补充召回（supplemental retrieval）：把原查询改写出更专门的子查询（只查定义和文件名），把结果并进候选池，再用部分打分只对最有希望的候选做完整评估。最后还要照顾结果多样性：一个函数名在 Java 和 Python 里都有，别让首屏全被一种语言占满。作者坦言这点做得不如网页搜索。

关键权衡与选型

本章的权衡几乎都绕着「完整性」打转。作者的立场很鲜明：宁可索引太多。

为什么重要 / 落到真实系统

评审「要不要投资内部开发者工具」时，本章给了一个可复用的算法：查询量 × 每次省下的秒数 ÷ 一个工程师一天的秒数，对比建设与维护的人力。面试里设计「代码搜索」或「日志搜索」，能讲清三元组索引 + 候选验证、增量与全量两种新鲜度、召回与打分的配合、「全部结果」模式，就比只说「上 Elasticsearch」高出一截。

易错点与争议

  • 「代码搜索 = 大号 grep」——不对。Google 的推动力来自 Kythe 的交叉引用，重心从「搜」转向「浏览与理解」，设计原则是「一次点击回答关于代码的下一个问题」。
  • 「全文搜索引擎直接套上就行」——按词切分对代码不准。符号、空格、括号、大小写在代码里都有意义。
  • 「为省资源少索引一点无妨」——信任一旦破，工具就没人用。被丢掉的文件连「结果不全」的提示都给不了。
  • 「排序准就够了」——召回漏掉的，打分救不回。那唯一的定义可能根本没进候选池。
  • 「两套索引一样新」——文本索引秒级、交叉引用按天。刚提交的新符号能搜到却跳不过去，事故排查时尤其要警惕版本错位。
  • 局限：作者自认结果多样性不如网页搜索、新文件冷启动尚未用时效信号修正；生成文件目前没被索引；机器生成的提交太多，朴素的「blame」价值打折。1.5 TB、200 QPS 等是 2020 年前后的数字。作者也提醒：小项目在 IDE 里装得下，这章对你帮助不大；早期能力较弱的版本只要局限被说清，同样有用、有人用。

要点

① 代码主要是被读的：约 1/3 搜索在找用法范例、1/4 在读懂代码、16% 找位置、16% 问为什么、8% 问谁何时。

② 独立网页工具的四个理由：规模（集中索引线性、人人建索引近似平方）、零配置全局视图、专为阅读优化、成为全公司的代码「门牌号」平台。

③ 延迟按人算：100 万次 × 1 秒 ≈ 每天 35 名工程师；高频操作目标端到端 <200 ms。

④ 文本索引可增量（中位 <10 秒可见），交叉引用要构建几乎全部二进制，只能每天一建，时差会造成困惑。

⑤ 暴力扫 1.5 TB 要约 30 万核；三元组 → 后缀数组 → 稀疏 n-gram，高效 500 倍以上，还能答正则。

⑥ 用标准搜索栈换实现简单；搬到闪存后要更少、更小的清单——介质决定索引形状。

⑦ 排序 = 离线信号（浏览量、引用数 ≈ PageRank）+ 现算信号（词边界、符号、路径）；召回要配补充查询。

⑧ 完整性三问：宁可多索引；按优先级分片同时支持「最相关」与「全部」；索引全部历史与工作区。

⑨ 判据：只有索引全部代码、给出全部结果、又把想要的排前面，工具才被信任、才被用。
