废弃

Software Engineering at Google · Ch 15 · Deprecation · Hyrum Wright · 2020

EN →

这一章讲什么？

你大概收到过这种通知：「旧版 App 将于下月停止服务，请升级。」大公司内部也天天发生同样的事，只是对象换成了程序：一套老系统被新系统取代了，可还有几百个别的程序在用它。这一章讲的就是：怎么把一个人人都在用的老东西体面地关掉，而不把大家一起拖下水。

打个比方

城里建好了一座新桥，旧桥年久失修，每年还得花钱养护。市政在旧桥头挂了块牌子：「请改走新桥。」结果呢？新来的司机大多走了新桥，老司机照旧走老路——习惯了，导航里存的也是旧路线。旧桥就这么一年年地「快要拆了」，却永远拆不掉。

旧世界为什么难

拆东西比建东西还难。用的人越多，就越有人用一种你想不到的方式依赖它：某家货运公司的卡车专挑旧桥，因为新桥限高。新桥再好也不是一模一样，每个老用户都得重新核对一遍。还有人舍不得——这桥是我当年亲手修的。更要命的是，拆桥要花看得见的钱，放着不管的代价却看不见，于是没人愿意出这笔钱。

核心机制直觉

  • 光挂牌子不够：提醒只能挡住新人，挪不动老用户。真要拆，得定一个截止日期，并且说到做到。
  • 派专门的搬家队：别让每家自己搬，那样谁都拖着。由负责拆桥的那支队伍上门帮大家改路线，他们搬得多了，工具和经验也越来越顺手。
  • 先试着封几次桥：拆之前，先封半天、再封一天、再封一周，看谁跳出来喊「我还要用」——这样才能找出那些连自己都不知道在走旧桥的人。
  • 堵住通往旧桥的新路：不许再修通往旧桥的新路，否则这边刚搬走一家，那边又搬来一家，永远拆不完。

带来了什么 / 该怎么选

拆掉一座多余的桥，养护钱省了，新桥也不必再迁就旧桥的规格，能放开手脚升级。但别同时封全城的路——一次只拆几座，拆一座就拆到底。诚实的代价是：这活儿要专门的人、要持续好几个月，而且常常没人记你的功，因为拆干净那天已经没人在用它了。

一句话记住

代码是负债不是资产：关掉一个老系统要有主人、有截止日期、有搬家队，光靠「请改用新的」永远关不掉。

一句话

你以为废弃（deprecation）就是给老 API 打个 @deprecated、等用户自己走，本章说那几乎从不奏效：代码是负债，功能才是资产；关掉一个被广泛依赖的系统是一项需要主人、截止日期、专职迁移团队和工具链的工程项目，而它最好在系统设计之初就被考虑。

Glossary · 术语表

  • 废弃（deprecation）：有序地让用户迁出一个过时系统、并最终把它删除的整个过程；不只是贴个「已过时」标签。
  • 下线（turndown / removal）：废弃的终点，真正关掉服务或删掉代码。
  • 依赖（dependency）与传递依赖：A 用到 B 就是依赖 B；A 用 B、B 用 C，则 A 间接依赖 C。
  • 符号（symbol）：代码里有名字的东西，如函数、类、常量。
  • 单体仓（monorepo）：全公司代码放在同一个仓库，谁依赖谁可以全局查到（见第 16 章）。
  • 海勒姆定律（Hyrum's Law）：用户足够多时，系统一切可观察行为都会被某人依赖，不管文档有没有承诺。
  • 大规模变更（large-scale change, LSC）：用工具一次性改动全仓成千上万处调用的流程（见第 22 章）。
  • 静态分析（static analysis）：不运行程序、只读代码就找出问题的工具；Google 的平台叫 Tricorder。
  • 构建可见性（visibility）：构建系统里声明「哪些目标允许依赖我」的白名单，不在名单上的依赖直接编译失败。

坐标

Part III「流程」的最后一章。上接 Ch11–14 测试四连章——全局测试集正是本章判断「旧符号删干净没有」的依据；下启 Part IV 工具，其中代码搜索、静态分析、大规模变更都是本章的执行手段。现实对应：API 下线、库升级、平台迁移、老服务关停。

这章要解决什么

所有系统都会老。比特本身不会坏，但周边的语言、库、技术一变，老系统就和生态越走越远：要专人维护、要偏门知识、工作量只增不减。年龄本身不是废弃的理由——LaTeX 改进了几十年依然好用；该废弃的是那些已被证明过时、且已有功能相当的替代品的系统。

新旧并存的代价比看上去大：两套系统要互通就得写复杂的转换代码；二者互相依赖后，哪个都更难删；最隐蔽的是，新系统被迫一直兼容旧系统，演进被拖慢。本章是 Google 废弃大型内部系统攒下的经验——作者坦白，这是全书少有的「Google 仍在学习」的话题。

核心内容，讲透

一、代码是负债，功能才是资产

本章的前提一句话：代码是负债（liability），不是资产（asset）。有价值的是代码提供的功能；同样的功能，一行好懂的代码胜过一万行意大利面条。所以该最大化的不是代码量，而是单位代码交付的功能，而最便宜的办法往往不是多写，是删掉不再需要的代码和系统。

但废弃也有容量上限。原书的比喻：人人都爱新铺的路，可若市政同时封掉所有道路去铺，谁都哪也去不了。组织能同时承受的废弃工作有限——既限于做废弃的团队，也限于被迫迁移的客户。所以要慎选废弃项目，选了就做完。

二、为什么废弃这么难

  • 海勒姆定律的终极版：删除系统是「最彻底的变更」——不是改行为，而是把行为整个拿走。用户越多，越多用法只是「碰巧能用」而非「保证能用」，删除会把这些意料之外的依赖全部震出来。
  • 新旧不会一一对应：新系统若和旧的一模一样，迁过去就没好处；既然不同，每一处旧用法都得在新系统语境下重新评估。
  • 情感依恋：Google 系统性删旧代码时真遇到过「可我喜欢这段代码！」。对策之一是让代码库可按历史搜索——删掉的代码也找得回来，删除就不再像毁灭。
  • 政治与资金：废弃要花真金白银，而「放着不管」的成本分散、看不见，很难说服相关方让它挤占新功能。可用第 7 章的工程效率研究方法拿出证据。

由此得出一条反直觉的结论：就地演进往往比整体替换便宜。Google 观察到迁移到全新系统极其昂贵、成本经常被低估；增量的就地重构不能免掉废弃，但能把它切成能各自交付价值的小块。

三、为废弃而设计

在别的工程学科里这并不激进：核电站设计时就要考虑数十年后的退役，甚至预先拨出经费（原书引 IAEA 1997 年的技术报告）。软件很少这样想：工程师偏爱造新东西，公司文化（包括 Google）奖励快速发布。Google 鼓励团队设计时问两个问题：用户从我这里迁到潜在替代品有多容易？我的系统能不能逐部分替换？

更根本的一句：要不要长期支持，在决定立项那一刻就定了。系统一旦存在，只剩三条路：继续支持、小心废弃、或者等某个外部事件把它弄坏。所以别启动组织不打算在其预期寿命内支持的项目。

四、建议式 vs 强制式

废弃是一条连续谱，从「我们希望有天能关掉」到「明天就没了，请做好准备」。原书切成两段。

建议式废弃（advisory）没有截止日期、组织不愿投入资源，也可叫「愿望式」废弃。它适合宣传新系统、吸引早期用户——前提是新系统已能扛生产负载、准备无限期支持，不能还在 beta。只有当新系统带来脱胎换骨而非增量的好处时，通知加自助迁移工具才会自发推动迁移；即便如此也到不了全量。Google 的经验是：贴一个废弃警告然后走开，只会让新用法略微变少，很少让团队真正迁走。原因是一种「引力」：旧系统现有用法越多，新代码越会照着抄。正如 SRE 的朋友常说的：「希望不是策略。」

强制式废弃（compulsory）带一个删除日期，过了日期还依赖它的系统就会坏。三个要件：

  • 专家集中（反直觉）：扩展性最好的做法不是让每个用户团队各自学怎么迁，而是把迁移专长集中在一支专家团队里——通常就是负责删除旧系统的团队。他们有动力帮人迁，经验和工具可复用。
  • 执行机制：日程可以调，但废弃团队必须有权在充分警告、努力帮忙迁移之后弄坏不合规的用户；否则客户总会把它排在新功能后面。
  • 配足人力：没人干活的强制废弃在客户眼里是刻薄的无经费指令（unfunded mandate）。所以 Google 强烈主张强制废弃由专门团队配足人手、一直做到完成。

即便有政策撑腰也有政治阻力：如果最后一个用户是全公司都依赖的关键基础设施，你真敢为一个日期把它弄坏吗？若那个团队能否决进度，废弃就算不上真强制。

揪出隐藏依赖：单体仓和依赖图让 Google 能看清系统怎么被使用，但有些团队根本不知道自己依赖旧系统，静态分析也难发现。办法是动态的：下线前的几个月到几周，宣布时长递增的计划停机，看谁坏——类似 Google 的灾难恢复演练 DiRT，常能挖出系统间未知的依赖，让依赖方提前规划或协商时间线。代码层面，Google 偶尔会给仅供内部实现的符号改名，看谁在不知情地依赖它。

五、废弃警告：可操作 + 相关

警告能挡新用法，很少带来存量迁移；而且会堆积：A 依赖 B、B 依赖 C，C 的警告在构建 A 时冒出来，多了用户就全部无视——医疗界叫警报疲劳（alert fatigue）。所以每条警告要满足两个条件：

  • 可操作（actionable）：普通工程师看完就知道下一步怎么做，如「把这个函数调用换成它的新版本」，或一封写明数据迁移步骤的邮件。
  • 相关（relevant）：在用户正要做那件事的时候出现。函数废弃最好在工程师正写调用代码时提示，而不是提交几周后；数据迁移邮件要提前几个月发，而不是删除前的周末。

Google 的做法是大方地标记、克制地展示：旧函数尽管标 deprecated，但借 ErrorProne、clang-tidy 等工具只在新改动的行上提示；对依赖图里已废弃目标那种侵入性强的警告，只在强制废弃、团队正主动迁移时才加。

六、把废弃当项目管

要有明确的主人。没有主人，警告再多也没进展。替代方案更糟：永不废弃，或交给用户自己迁——后者就是永远完不成的建议式废弃。最麻烦的是无主项目：原主人去做继任项目了，旧系统在「地下室」里吭哧运转，还是关键项目的依赖，大家盼它自己消失——它不会。负责团队要把删除当主要目标而非副业，否则排期上永远输；这类重要不紧急的清理也很适合拿 20% 时间来做。

要有中间里程碑。造新系统时每个功能上线都是一场胜利；废弃却容易让人觉得唯一里程碑是「关灯回家」——而那一刻，如果活儿干得好，外人几乎察觉不到，因为已经没人在用了，何况有的废弃根本走不到那一步。所以要设可度量、对用户有价值的增量里程碑，比如删掉一个关键子组件，并像庆祝新功能一样庆祝它。

七、三类工具：发现、迁移、防回流

发现贯穿全程：用代码搜索和 Kythe 静态找出谁用了某个库，并抽样看用户意外依赖了哪些行为；动态依赖靠生产日志和运行时采样。新信息可能让你重新审视废弃决定本身。最后，全局测试集是判官：判断旧符号的引用是否已全部移除——而用户有责任写足测试，保证旧系统被删时自己不受伤。迁移主要靠大规模变更流程与代码生成、评审工具。防回流最常被忽视：没有它，用户会照着熟悉的写法或仓库里的旧例子不断新增用法，废弃团队沦为打地鼠，既徒劳又打击士气。微观上，系统主人给旧符号加编译器注解（如 Java 的 @deprecated），Tricorder 在评审时提示新用法，个别情况还给一键修复；宏观上，用构建系统的可见性白名单禁止新依赖，工具定期修剪名单，迁走一个删一个。

易错点与争议

  • 「打上 @deprecated 就算废弃了」——那只是建议式的起点。它挡一部分新用法，存量不会自己消失。
  • 「老的就该废弃」——年龄不是理由。标准是「已证明过时 + 有功能相当的替代品」。
  • 「让每个用户团队自己迁最公平」——恰恰扩展不了。专长分散在几百个团队、人人排在新功能后面；集中在一支专家团队才能复用工具、推得动。
  • 「重写比修补干净」——算上下线成本常常不成立。原书 TL;DR 明说：计入下线成本后，就地演进通常比替换便宜。
  • 局限：本章只谈系统主人能看到用法的内部技术系统，单体仓和全局依赖图是大前提；面对看不见调用方的公开 API 或终端产品，发现与执行都难得多。作者也承认 Google 仍在学，有时奏效、有时不。

要点

① 代码是负债、功能是资产：要最大化单位代码交付的功能，删掉多余系统是最便宜的手段。

② 废弃对象是「已证明过时且有替代品」的系统，不是「老」系统；新旧并存会拖慢新系统演进。

③ 难在：海勒姆定律（删除是最彻底的变更）、新旧不一一对应、情感依恋、成本看不见。

④ 计入下线成本，就地演进通常比整体替换便宜；要不要长期支持，立项时就定了。

⑤ 建议式没截止日、只能推一把；强制式要截止日、执行权和配足人力的专家团队，否则成了无经费指令。

⑥ 用时长递增的计划停机、给内部符号改名，把不知情的依赖逼出来。
