专业书籍精读 · A Philosophy of Software Design · 第 4 章

模块要「深」

A Philosophy of Software Design · Ch 4 · Modules Should Be Deep · Ousterhout · 2nd ed 2021

EN →

这一章讲什么？

前三章说，软件最大的敌人是「复杂」。这一章给出全书第一件、也是最重要的一件武器：把系统拆成一个个「深」的零件——用起来特别简单，背后却替你干了一大堆活。你每天在手机上点一下「保存」，背后有几十万行代码在替你找磁盘、排队、防断电，你一行都不用知道。这就是「深」。

打个比方

开车只要一个方向盘、两个踏板。发动机、变速箱、刹车油路有多复杂，司机完全不用管——操作面很小，背后的活很多，这就是一个好零件。反过来想象一台车：油门要分别控制喷油和点火，换挡要自己去拨三根杆子。每个杆子本身都很简单，可你得把它们全学会、按对顺序操作，少拨一根车就趴窝。

旧世界为什么难

很多程序员从小被教导「零件越小越好」：一段代码别太长，一个模块只干一件小事。听起来很整洁，结果是系统被拆成一大堆小零件，每个零件都有自己的说明书。零件本身不难懂，难的是使用者要把几十份说明书都读一遍，还要知道该怎么把它们拼起来。复杂度没有消失，只是从零件内部挪到了使用者头上。

核心机制直觉

  • 每个零件都有两面。朝外的那一面是「说明书」，告诉别人怎么用它；朝里的那一面是「干活的部分」，别人看不见。
  • 说明书是成本，干的活是收益。别人每用一次，都要先读懂说明书；零件替他省下的活，才是它存在的理由。
  • 深零件 = 说明书短、干的活多。像电灯开关，一按就亮，电线怎么走不用管。
  • 浅零件 = 说明书和干的活差不多长。读说明书的工夫，都够你自己动手了，那它几乎没帮上忙。
  • 最常见的用法要「默认就对」。好零件让九成人什么都不用设置就能用好，少数特殊需求再去找额外的按钮。

带来了什么 / 该怎么选

它给了一把随手能用的尺子：评价一个模块，不看它多短多小，而看它替使用者藏起了多少麻烦。拆不拆、合不合，都拿这把尺子量。一句诚实的代价：深零件的内部会更厚、更难写，写它的人要多吃苦，好让用它的人省事。

一句话记住

好零件像方向盘：用起来简单，背后干的活很多。说明书和干的活一样长的零件，等于没帮忙。

一句话

你以为好模块的标志是「小」，Ousterhout 说标志是「深」：接口（interface）尽量简单，背后的功能尽量强大。接口是使用者要付的成本，功能是模块给出的收益——浅模块（shallow module）的接口和实现差不多复杂，几乎不帮人减负，把系统拆成一堆浅模块，正是复杂度的主要来源之一。

Glossary · 术语表

  • 模块（module）：任何有接口、有实现的代码单元——一个类、一个子系统、一个服务，甚至一个函数。
  • 接口（interface）：使用者为了用好这个模块必须知道的一切；实现（implementation）：完成承诺的那部分代码。
  • 函数签名（signature）：函数名、参数类型、返回值类型——编译器能检查的那部分接口。
  • 抽象（abstraction）：对某个东西的简化视图，略去不重要的细节。
  • 认知负担（cognitive load）：第 2 章的概念——开发者为完成一个改动必须记在脑子里的东西有多少。
  • 依赖（dependency）：一段代码不能脱离另一段代码被理解或修改。
  • 系统调用（system call）：程序向操作系统请求服务的入口，如打开、读写文件。
  • 缓冲（buffering）：先把数据攒在内存里成批读写，减少对磁盘的慢速访问。
  • 垃圾回收（garbage collection, GC）：语言运行时自动回收不再使用的内存，程序员无需手动释放。

坐标

全书第 4 章，是从「心态」（第 3 章战略编程）转到「具体手艺」的第一章，也是整本书的轴心：后面的信息隐藏（第 5 章）、通用模块（第 6 章）、把复杂度往下沉（第 8 章）、合还是分（第 9 章），都是在回答「怎么让模块更深」。现实里对应每一次「这个类要不要再拆一下」的代码评审。

这章要解决什么

第 2 章说复杂度来自依赖和晦涩。依赖不可能消灭——模块之间总要协作——所以真正的问题是：怎么拆，才能让每个开发者在任何时刻只需面对系统的一小部分？模块化（modular design）是标准答案，但拆错了反而更糟：模块越多，接口越多，使用者要学的东西越多。

书中的场景锚：在 Java 里想从文件读出序列化的对象，你得先建一个 FileInputStream，再包一层 BufferedInputStream，最后再包一层 ObjectInputStream——三个类、三次构造，只为做一件事。忘了中间那层，程序照样能跑，只是没有缓冲、慢得多，而且没有任何报错提醒你。每个类都「小而单一」，合起来却把负担全推给了调用方。本章要给出一个判据，区分这种拆法和好的拆法。

核心内容，讲透

一、模块 = 接口 + 实现：一笔成本—收益账

理想的模块化是让模块彼此完全独立，开发者改一个模块不用懂其他模块。现实做不到，但目标是把依赖压到最少。为此每个模块分两部分：接口描述它做什么，实现负责怎么做。在一个模块里干活的人，需要懂它的接口和实现，外加它所用模块的接口——但不需要懂别人的实现。

由此得出一条看问题的角度：接口是模块施加给系统其余部分的成本（每个使用者都要学），功能是它带来的收益。好模块就是收益远大于成本的模块。这也是为什么「好接口」的标准不是「方法少」本身，而是使用者要知道的东西少。

二、接口里有什么：写在签名里的，和写不进签名的

接口分两层。形式部分（formal）是代码里显式写出的：方法名、参数类型、返回值、可能抛的异常，编译器能检查。非形式部分（informal）是签名表达不了的：它的高层行为（比如「删除以参数命名的文件」）、调用约束（比如「必须先调 A 再调 B」）、副作用。非形式部分通常比形式部分大得多、也复杂得多，只能靠注释写清楚，而且编译器不会替你检查。

评估一个接口的成本，必须把非形式部分算进去：一个只有两个参数、却要求「先初始化、不可并发、调用后要手动清理」的方法，它的接口其实很重。

三、抽象：两种方向相反的错误

抽象就是对实体的简化视图，忽略不重要的细节。模块的接口就是它对外的抽象。抽象可能在两个方向上出错：

  • 塞进了不重要的细节：接口变得臃肿，增加使用者的认知负担。
  • 漏掉了真正重要的细节：使用者以为不用管，其实非管不可——作者称之为假抽象（false abstraction），它带来晦涩：看起来简单，实际藏着坑。

书里的例子是文件系统：它把「数据放在磁盘哪个块上」这种细节完全藏起来，这是对的；但对数据库这类应用来说，数据何时真正落盘是重要细节，所以文件系统要提供强制刷盘的手段（如 fsync）。设计抽象的关键，就是分清什么重要、什么不重要，并且尽量让「重要的东西」少。

四、深模块：小接口，厚实现

作者用一个矩形来画模块：面积是功能，上边的宽度是接口。最好的模块又窄又高——接口小，功能多；最差的模块又宽又扁——接口几乎和功能一样大。

标杆案例：Unix 文件读写。基础接口只有五个系统调用：open 打开、read 读、write 写、lseek 移动读写位置、close 关闭，签名都很简单。而作者指出，现代的实现需要几十万行代码，藏起了：磁盘上的文件怎么表示、目录怎么组织成层级、权限怎么检查、并发访问怎么调度、读写怎么缓存、不同的存储设备怎么驱动。几十年来实现被重写了无数遍，这五个调用基本没变——深模块的另一个红利是：实现可以大改，使用者毫无感觉。

另一个例子：垃圾回收。Go、Java 这类语言的垃圾回收器几乎没有接口——你什么都不用调，内存自动被回收。它藏起了大量复杂机制，还反而缩小了系统的整体接口（不再需要手动释放内存）。这是深模块的极致。

五、浅模块与「类越小越好」病

浅模块是接口相对其功能而言很复杂的模块。书里的极端例子：

private void addNullValueForAttribute(String attribute) { data.put(attribute, null); }

从管理复杂度的角度看，这个方法让事情更糟：它没有任何抽象，所有功能都写在接口上了——读懂它的名字和参数，并不比直接读 data.put(attribute, null) 省事；它还多了一个要学的名字、多了一行代码。作者把它列为一个红旗（red flag）：「接口相对于它提供的功能过于复杂」。书里也承认浅模块有时难以避免（比如链表这种类），也不是一无是处，但它们在对抗复杂度上帮不了多少忙。

浅模块为什么那么多？作者点名一种流行观念，他叫它 classitis（类炎）：「类是好东西，所以类越多越好」，以及「类应该小」「方法超过 N 行就该拆」。照这种建议，开发者把功能切得尽可能碎，结果是大量浅类，每个都单独简单，合起来整个系统更复杂：接口总量暴增，而且要用某个功能得同时理解好几个类怎么配合。

六、让常见情况尽量简单

Java 例子背后的教训是一条接口设计原则：接口应当让最常见的用法尽可能简单。几乎每个读文件的人都想要缓冲，那它就该是默认行为；真有人不要缓冲，可以提供一个关掉的办法。Unix 正是这样：大多数程序顺序读写，所以顺序访问是默认；少数需要随机访问的，额外调一次 lseek。如果一个接口有很多功能，但大多数使用者只需要知道其中几个，那它的有效复杂度就只是常用那几个的复杂度。

表 2 · 「要不要再拆一个类 / 方法？」的判据

常见理由Ousterhout 的看法该问的问题
「这个方法超过 N 行了」长度本身不是问题；拆出浅方法反而增加接口拆出来的部分，接口是否比实现简单得多？

一句判据：新增一个模块，应当让系统的接口总量变少（藏起了东西），而不是变多。拆分后若使用者要知道的东西反而多了，就是拆错了方向。

为什么重要 / 落到真实系统

面试和架构评审里，「深模块」给了一个比「高内聚低耦合」更能落地的问法：这个接口替调用方藏起了什么？一个好的存储引擎、一个好的 SDK、一个好的内部服务，都是把常见路径做成一两个调用、把重试 / 缓存 / 分片这些麻烦藏在里面。反过来，如果调用方必须按特定顺序调用五个方法、自己组装配置才能用对，这个模块再「单一职责」也是浅的。

实证与出处 · 公开可查

  • Unix：五个调用用了半个世纪。Ritchie 与 Thompson 在 1974 年的论文里，把普通文件、目录和设备统一成同一套读写接口；本章以它为深模块的头号例子。出处：Ritchie & Thompson，The UNIX Time-Sharing System，CACM 1974；Ousterhout 原书第 4 章
  • Java 后来补了「常见情况的捷径」。Java 7（2011）新增的 java.nio.file.Files 提供了一次调用读完整个文件的静态方法（如 readAllLines）和直接返回带缓冲读取器的 newBufferedReader——正是本章「让常见情况简单、缓冲默认开启」的方向。出处：Java SE 7 API 文档，java.nio.file.Files
  • 与《Clean Code》作者的公开论战。2024 年 9 月至 2025 年 2 月，Ousterhout 与 Robert C. Martin 把一场讨论整理成公开文档。Ousterhout 的核心论点就是本章：最好的方法用很简单的接口提供大量功能；分解可能过度，拆到最后，用某个方法的人必须理解它实现的每个细节。Martin 坚持短函数，但承认过度分解存在、而原书对何时算过度给的指导很少。出处：johnousterhout/aposd-vs-clean-code（GitHub）

易错点与争议

  • 「深 = 代码多」。不对。深是功能相对接口的比值；一个实现很长但接口同样复杂的模块，依然是浅的。
  • 「接口小 = 方法少、参数少」。不完全。非形式部分（调用顺序、副作用、并发约束）也是接口；签名很短、约束很多的接口其实很重。
  • 「深模块就是什么都藏」。漏掉重要细节是假抽象。文件系统必须把刷盘控制交给数据库，这是「重要的细节就该露出来」的例子。
  • 「本章反对小函数」。作者反对的是为小而小：拆分的判据是拆出来的东西够不够深，而不是行数。面试复述时要讲清这个区别。
  • 争议：深模块对实现者不友好。几十万行的实现本身需要内部再分层、再做深模块；作者的回答是复杂度应当集中在少数人维护的地方（第 8 章「往下沉」会展开），但这确实把压力转给了模块作者。
  • 争议：可组合性。Java 的分层流设计换来了自由组合（加密、压缩、缓冲任意叠加），Unix 管道哲学也偏爱小工具组合。作者并不否认组合的价值，他的批评点在于常见情况被迫承担组合的成本——默认值缺失才是病根。

要点

① 模块 = 接口 + 实现；接口是使用者付的成本，功能是模块给的收益。

② 好模块的标志不是「小」，是「深」：接口简单、功能强大。

③ 接口包括写不进签名的非形式部分：行为、调用顺序、副作用，只能靠注释写清。

④ 抽象有两种错：塞进不重要的细节（臃肿），漏掉重要的细节（假抽象）。

⑤ 标杆：Unix 五个文件调用背后是几十万行实现；垃圾回收几乎没有接口。

⑥ 浅模块红旗：接口相对功能过于复杂，如 addNullValueForAttribute。

⑦ 「类炎」：类越多越小越好的信条，产生一堆浅类，让系统整体更复杂。

⑧ 让常见情况最简单：缓冲该是默认，Java 三层流是反例，Unix 是正例。

⑨ 判据：新模块应让使用者要知道的东西变少；拆分看深度，不看行数。
