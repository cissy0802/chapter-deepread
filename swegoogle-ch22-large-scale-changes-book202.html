大规模变更

Software Engineering at Google · Ch 22 · Large-Scale Changes · Hyrum Wright · 2020

EN →

这一章讲什么？

一家大公司的程序，是几万名工程师一起写的一大堆文件。假如其中一个人人都在用的「老零件」要换成新的——它在几十万个地方被用到——怎么换？这一章讲的就是：怎么在一个永远有人在改的超大代码库里，安全地做一次「全场大换装」。

先说个怪事

你会以为，公司越大、工具越强，一次能改的东西就越多。Google 的经验正好相反：代码库越大、人越多，你能「一口气改完、一次交上去」的改动反而越小。所以他们干脆放弃了「一次改完」，改成「拆成成千上万份小改动，慢慢送进去」。

旧世界为什么难

想象给一栋住了几千户的大楼换水管。办法一：贴个通知，让每户自己换——没人愿意自掏腰包，总有人拖着不换，而且每户都得从头学一遍怎么换。办法二：选一个周末全楼同时停水、一次换完——可这栋楼从来没有「没人在用水」的时刻；换到一半出了漏水，你也很难在几千户里找到是哪一户的接口没拧紧。

核心机制直觉

  • 谁造的水管谁来换：由懂这套零件的团队集中负责，而不是摊派给每家每户。
  • 先装转接头：先让新旧两种接口能同时用，再一户一户慢慢换，最后拆掉转接头。整栋楼一刻也不用停水。
  • 让机器干体力活：改动由程序批量生成，再自动切成按「楼层」打包的小包，每包单独检查、单独签收、单独交付；哪包出问题，只退那一包。
  • 检查拼车：小改动彼此很少打架，就把一批拼成一趟「车」一起检查，只有出了问题才拆开逐个排查。
  • 装门禁防回潮：换完之后，谁再装老水管，检查时就被拦下。

带来了什么 / 该怎么选

有了这套本事，很多过去「一旦定下就再也改不动」的决定——一个函数叫什么名字、一个零件放在哪——都变成了可以后悔的。改几十处，手动改就好；改几百上千处，就该学会用工具批量改。诚实的代价是：这一切都建立在充分的自动检查和统一的工具环境之上，没有好测试的老代码，谁也不敢动。

一句话记住

大改动别指望一次做完：拆成许多能各自检查、各自交付、各自撤回的小改动，让机器干重活、让懂行的人集中负责。

一句话

你以为全库改动最稳的做法是「一次原子提交」，本章说代码库和人越多，可行的最大原子提交反而越小。Google 的答案是把一次逻辑上的大变更（LSC）拆成成千上万片可独立测试、评审、提交、回滚的小改动，由懂行的基础设施团队用工具集中推进——于是许多「定了就改不动」的技术决定变得可以重来。

Glossary · 术语表

  • 提交（commit）/ 原子提交（atomic commit）：把一组修改存进代码仓库的一次操作；「原子」指要么全部生效、要么全不生效。
  • 单体仓库（monorepo）：全公司代码放在一个仓库里，几乎人人可见（见第 16 章）。
  • 重构（refactoring）：不改变程序行为、只改代码写法与结构的修改。
  • 合并冲突（merge conflict）：你改的文件在你提交前已被别人改过，需要重新合并。
  • presubmit / 提交前检查：提交前自动跑的测试与规则检查。
  • CI / TAP：持续集成，每次改动自动构建与测试；TAP 是 Google 的 CI 平台（见第 23 章）。
  • 传递闭包（transitive closure）：直接或间接依赖某文件的所有目标——改它可能影响到的全部测试。
  • AST（抽象语法树）：编译器把代码解析成的树状结构，按结构而非文本改代码就靠它。
  • flaky 测试：同样的代码有时过、有时不过的不稳定测试。
  • 类型别名（type alias）：给同一个类型起第二个名字，新旧两个名字可以混用。

这章要解决什么

LSC 的定义：一组逻辑上相关、但实际上无法作为一个原子单元提交的改动。原因可能是文件太多、工具一次提交不了，可能是改动大到总会撞上合并冲突，也可能只是仓库拓扑决定的——多仓库之间本来就做不到原子提交。动机大致四类：用全库分析清理常见反模式、替换已废弃的库用法、支撑编译器升级这类底层改进、把用户从旧系统迁到新系统。

量级：基础设施团队常常要改几十万处引用，最大的一次触及几百万处；如今一个项目里 10%–20% 的改动来自 LSC，作者都不是这个项目的人。规模最大的一批 LSC 在三天内从仓库删掉了超过 10 亿行代码。没有这种能力，代码库会被自身重量压垮。

为什么不「发个新类，让大家自己迁」？其一，懂行的人在基础设施团队：让每个团队各自重学一遍，全局极其浪费；集中处理时错误只有几类，可以有一本处置手册。其二，没人喜欢「无资金的强制令」（unfunded mandate）：新系统的好处分散在全组织，单个团队没动力迁，有机迁移几乎做不完——新代码还会照抄旧用法。由想删掉旧系统的团队出钱出人，是把外部成本内部化，还吃到规模经济。

核心内容，讲透

一、原子提交为什么输给规模

理想中每个逻辑改动都是一次可测试、可评审、可提交的原子提交。但仓库和人越多，这个理想越不现实，书里列了六道障碍：

  • 技术极限：版本控制的操作随改动大小线性增长，几千个文件可能内存都不够，集中式系统里还会阻塞他人。
  • 合并冲突：文件越多、仓库里的人越多，提交前撞上冲突的概率越高。小公司可以周末偷偷改全库，Google 这种全球公司永远有人在提交。
  • 闹鬼的墓地（haunted graveyard，借自 Google SRE 的口号）：古老、难懂、无人敢碰却在收入关键路径上的代码，会卡住整条迁移与编译器升级。解药是老派的测试：测得充分，再老的代码也敢改。
  • 异构：LSC 要靠机器干主要工作，机器需要一致的环境；各项目各有版本控制、CI、格式与特殊检查，批量改动就寸步难行。
  • 测试：25 个文件的改动挂了，找原因不难；1 万个文件里找 1 个失败，是大海捞针。代价是小改动会把同一批测试重复跑很多次——Google 的判断是工程师排查的时间远比机器时间贵，但作者也提醒，这个权衡不一定适用于每个组织。
  • 评审：所有改动都要评审，LSC 也不例外；拆成小片，人才审得过来。

反过来，能力一旦就位，填坑也变得划算：Google 早年两个头文件 stl_util.h 与 map-util.h 分隔符不一致，工程师常记错、白等一轮编译；借助 LSC 工具，修这一个字符只花了几周的后台工作量。

二、四件基础设施：洞察、切片、测试、语言

代码库洞察：既要文本级搜索，也要语义级分析。Kythe 语义索引能回答「这个函数有哪些调用方」「哪些类继承它」；ClangMR、JavacFlume、Refaster 基于编译器索引，在 AST 上做可高度并行的变换；小改动用 sed、正则甚至 shell 脚本也行。硬指标是人力投入要随代码库亚线性增长：不管仓库多大，生成全部改动花的人力应该差不多。经验法则：超过 500 处编辑，学用生成工具通常比手改划算；老练的「代码清洁工」门槛更低。

变更管理（Rosie）：作者认为这可能是最重要的一件——把主改动按项目边界和所有权规则切成可原子提交的小片，每片走独立的「测试—发评审—提交」流水线。Rosie 是共享基础设施的重度用户，所以它限制每个 LSC 同时在途的片数、以低优先级运行，并和测试平台协商可以施加多少负载。

测试：每片可能包含任意文件，所以不用项目自己的 presubmit，而是对每片跑它可能影响的传递闭包里的全部测试。

语言支持：类型别名、转发函数这类特性能让新旧系统共存、非原子地迁移用户；缺这些特性的语言很难增量迁移。静态类型语言远比 Python、Ruby、JavaScript 这类动态语言好做自动化改动——编译器能在测试前就拒掉无效变换。最后，自动格式化器（clang-format、google-java-format）另跑一遍，机器改的代码才像人写的——作者说没有它，大规模自动改动不会成为 Google 的常态。

三、流程：授权 → 生成 → 切片提交 → 清理

授权：作者写一份短文档，说明动机、预计会切成多少片、给外人看的 FAQ，并取得被重构 API 所有者的「领域评审」。提案发到一个约十几人的监督邮件组。委员会最常见的修改是：把评审统一交给一位全局审批者。它批得很宽，直接否掉的只有危险的（把全部 NULL 换成 nullptr）或价值极低的（英式拼写改美式）。

生成：尽量全自动，这样用户「回潮」写回旧用法、或出现文本冲突时，父改动可以随时重新生成。工具做不到时也可以把生成工作分给人——见 §6 的 RoseHub。

切片与提交：Rosie 切片后，每片跑测试；通过后按 OWNERS 挑最可能看懂这片的评审人，不回应就自动加人。项目自定义的描述格式检查之类会被选择性关掉，改动之前就已经失败的检查一律忽略——保持本项目没有既有失败，是本地所有者对基础设施团队的社会契约。

清理：「完成」的定义因 LSC 而异，可能是彻底删掉旧系统，也可能只迁高价值引用。但几乎都需要防回潮：Google 用 Tricorder 在代码评审时标出新增的已废弃用法。

四、测试：TAP「火车」与对 flaky 的态度

核心洞察：LSC 之间很少相互影响，而且绝大多数受影响的测试都会通过——所以可以多个改动一起测。前提有两条：LSC 多是语义保持的窄重构；单个改动简单、被仔细审过，多半是对的。

切片提交阶段同理：多数片影响的测试不到一千个（全库有几百万个）；更多的就分组，先跑并集，再对每片只重跑第一轮失败的那些——并集常已接近全库，多加几片几乎免费。

规模一大，小概率事件成了必然：flaky 测试会严重拖慢 LSC 的吞吐。Google 的结论很大胆：对于语义保持、机器生成的改动，他们更相信改动本身，而不是一个最近 flaky 过的测试——于是自动化提交时直接忽略近期 flaky 的测试。理论上会漏掉「从 flaky 变成真失败」的回归，实际罕见到靠人沟通处理就够了。

五、迁移手法：scoped_ptr → std::unique_ptr

Google 的 C++ 早年有一个自毁型智能指针 scoped_ptr；C++11 引入了严格更好的 std::unique_ptr，而代码库里有超过 50 万处 scoped_ptr 引用，散在几百万个源文件里——这是当时 Google 最大的一次 LSC。几位工程师并行干了几个月，高峰期每天生成、测试、提交 700 多个独立改动、触及 1.5 万多个文件；作者说如今有时能做到这个吞吐的 10 倍。

难点在于它被用作一些广泛使用的 API 的参数类型，没法拆成互不相关的小改动。他们考虑过写调用图分析、把 API 及其调用方传递地一次改完，又担心这个改动本身大到无法原子提交。最终的解法是三步：先把 scoped_ptr 变成 std::unique_ptr 的类型别名 → 再做旧别名到新名字的文本替换 → 最后删掉别名。它也有 LSC 典型的长尾：Hyrum 定律式的行为依赖、与他人的竞态、工具看不见的生成代码，都靠测试暴露后手工处理。

六、社会面：牛 vs 宠物，与全局审批者

普通改动像宠物：工程师花几天几周精心打磨，被拒会难受。LSC 的改动要当牛：无名无姓，随时可能因为合并冲突或测试没覆盖的问题被回滚、被拒，只要整群没事就无所谓——工具改一改，几乎零成本重新生成。

评审上有个反直觉的发现：本地所有者太信任 LSC 作者，常常只是草草看一眼。所以 Google 只把需要本地上下文的片发给本地所有者，其余交给全局审批者——一个有全仓批准权、懂这门语言和这个库的人。他用基于模式的工具自动批准符合预期的改动，只人工看因合并冲突或工具故障而异常的那一小部分。文化上，本地所有者可以提问、作者照常回应，但所有者对整个 LSC 没有否决权；好的 FAQ 和长期可靠的记录，才换来全公司的认可。

为什么重要 / 落到真实系统

本章最深的影响在设计期：既然能低成本改全库，很多决定就不必一次定死——符号名、类的位置、语言版本都可以后悔。所以 Google 设计继任系统时，会预先想好从旧系统的迁移路径。面试被问「怎么换掉一个被几千处调用的接口」，答案就是三段式：引入可互换的新接口 → 逐步迁移调用方 → 删除旧接口，外加测试、切片与防回潮门禁。

易错点与争议

  • 「大改动就该原子提交，才不会出现半新半旧」——规模下恰恰相反。半新半旧的过渡期是要被设计出来的，不是要被避免的；避免它的代价是一个永远提交不进去的巨型改动。
  • 「发个通知让大家自己迁就行」——无资金强制令几乎从来做不完，而且新代码还会照抄旧用法。
  • 忽略 flaky 测试是有意识的冒险，前提是改动语义保持、机器生成；照搬到手写的功能改动上就不成立。
  • 局限：整套做法依赖单体仓库、统一工具链、普遍测试和充足算力；作者自己也说动态语言的维护者「格外辛苦」，多仓库、测试稀薄的组织很难直接复制。

要点

① LSC = 逻辑上相关、却无法作为一个原子单元提交的一组改动；仓库和人越多，可行的最大原子提交越小。

② 障碍有六道：版本控制极限、合并冲突、闹鬼的墓地、异构环境、测试定位、评审负担。

③ 由拥有旧系统的基础设施团队集中迁移，把无资金强制令的成本内部化。

④ 生成靠工具：超过约 500 处就别手改；人力要随代码库亚线性增长，自动格式化让机器改动像人写的。

⑤ Rosie 按项目与所有权切片，每片独立测试、评审、提交，失败只退一片——改动是牛，不是宠物。

⑥ TAP 火车：样本筛选、拼车跑并集、失败才拆；近期 flaky 的测试直接忽略。

⑦ 迁移三段式：引入可互换的新接口（类型别名）→ 迁移 → 删除旧接口；scoped_ptr 的 50 万处引用就是这么换掉的。

⑧ 机械改动交全局审批者，本地所有者无否决权；完成后用静态分析防回潮。

⑨ 最大的回报在设计期：技术决定不必一次定死。
