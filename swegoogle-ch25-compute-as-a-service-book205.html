计算即服务

Software Engineering at Google · Ch 25 · Compute as a Service · Onufry Wojtaszczyk · 2020

EN →

这一章讲什么？

代码写完了，总得找台电脑把它跑起来。这一章讲的就是这件看似简单的事：「给我点机器，让我的程序跑起来」，在一家有几万工程师、几百万台机器的公司里，会长成什么样。Google 内部管这件事的系统叫 Borg，你今天常听到的 Kubernetes 就是它的「开源后代」。

先说个怪事

Google 的工程师通常不知道、也不关心自己的程序跑在哪台机器上。系统可能随时把它停掉、搬到另一台机器重新启动——而这被当成好事，不是事故。

旧世界为什么难

最早的做法像手工作坊：把程序拷到一台台机器上，一台台登录启动，再一台台盯着。2002 年，Jeff Dean 抱怨跑一个数据任务是「后勤噩梦」：要找 50 多台机器、挨个启动、挨个盯；某台机器坏了没人自动接手；大家抢机器，还得靠一份手工「报名表」排队。机器越多，人越累。

核心机制直觉

  • 牛群，不是宠物：宠物病了，你要亲自守着、想办法治好；牛群里的牛只有编号，一头倒下，自动补一头新的。程序也该这样——随时能被「复制一份新的」顶上，不靠人去救。
  • 一个总调度：像一家酒店的前台，知道每个房间空不空，客人来了自动分房，房间坏了自动换房，不用客人自己去找。
  • 合租但有隔断：一台大机器上住好几个程序，像合租公寓，每间屋有门有锁、水电各自计量，邻居再吵也吵不到你。这就是「容器」。
  • 白天的空座给夜班用：网站服务要预留很多空位应付突发高峰，平时大半空着；不着急的计算任务就坐进这些空位，高峰一来立刻让座。于是这些计算几乎是「免费」跑的。

带来了什么 / 该怎么选

好处是规模再大，管机器的人也不用跟着翻倍。但它要求程序换个写法：自己的数据不能只存在本机上，因为随时可能被搬走。至于选哪种平台——自己管机器、租虚拟机、用容器平台，还是连服务器都不管的「无服务器」——没有标准答案：越省心，能自己动手调的地方就越少，而且一旦选定，很难再换。

一句话记住

把机器当成随时可替换的牛群：交给一个统一的调度系统去管，程序写成「被搬走也不怕」——规模越大，这笔账越划算。

一句话

你以为「计算即服务」只是「租台机器」，本章说它真正改变的是你写软件的方式：把机器和进程当牛群（cattle）而不是宠物（pets），交给一个统一的调度池去装箱、自愈、搬迁；软件则要把本地状态当成随时会消失的东西。而一旦选定计算平台，Hyrum 定律会让你被它锁住很多年。

Glossary · 术语表

  • 计算即服务（CaaS, Compute as a Service）：工程师只描述「要跑什么、要多少资源」，由平台决定跑在哪台机器上。
  • 调度器（scheduler）：知道所有机器空闲情况、负责把程序分配到机器上的中央服务。
  • 副本（replica）：同一个程序同时运行的多份实例，任何一份都能干同样的活。
  • 虚拟机（VM）：在一台物理机上模拟出一整台带完整操作系统的电脑，隔离强但启动慢、开销大。
  • 容器（container）：共享宿主操作系统内核、只把进程的资源与文件视图隔开的轻量运行单元。
  • cgroups / namespace：Linux 内核功能，前者限制一个进程组能用多少 CPU 与内存，后者让进程只看到自己的一份进程号、网络等视图。
  • 装箱（bin-packing）：把大小不一的任务尽量紧凑地塞进有限的机器里。
  • 批处理（batch）/ 在线服务（serving）：前者跑完就结束、看吞吐；后者长期运行、处理请求、看单次延迟。
  • 幂等（idempotency）：同一个请求发两次和发一次结果相同。
  • Hyrum 定律（Hyrum's Law）：用户够多时，系统每一个可观察到的行为都会被某人依赖——无论你是否承诺过。

这章要解决什么

起点是一个朴素愿望：写完代码，给我硬件让它跑。单机时代 SFTP 上传、SSH 登录、手动启动就够了；问题在于这套做法会随规模线性甚至超线性地吃掉人力。Jeff Dean 2002 年为「Global WorkQueue」写的设计文档列出了全部症状：要找 50 多台机器、逐台启动和监控；机器挂了不会自动迁移；进程互相干扰，只能靠一份人工维护的「报名」文件限流，调度既低效又抢资源。

组织长大时，三条轴会同时增长：应用的种类、每个应用的副本数、最大应用的体量。不自动化，组织会被运维负担压垮。

核心内容，讲透

一、从手工到 Borg：一步步消灭苦差（toil）

演进路线很清晰，每一步都把一类人工交给机器：

  • 简单自动化：脚本并行部署；导出「还活着吗」等指标做看板；代理发现「5 分钟没报活」就杀掉重启（云上叫自动修复，autohealing）。
  • 自动调度：第一个真正的「服务」出现了——一个知道全部机器清单的中央调度器，按需挑空闲机器部署，手工报名表从此消失。再结合坏机检测（扫日志里的大量磁盘读错误等），坏机器不再被分配任务，任务所在机器坏了就换一台重启，旧的直接放弃。
  • 容器与多租户：一机一程序太浪费——任务种类远多于机型；采购新机要几个月，只能按未来需求买大；新旧机器混杂。解法是每个程序声明 CPU、内存、磁盘需求，让调度器把副本装箱进机器池。

合租带来新问题，书里起了个好标题：「邻居家的狗在我的内存里叫」。某个副本说好用 1 个 CPU、200 MB 内存，因为 bug 或自然增长用超了，邻居在线服务就会出现延迟毛刺，或者被内核 OOM 杀掉（Google 早就决定：swap 带来的延迟太可怕，宁可直接 OOM 杀掉再迁移）。还有依赖版本冲突、抢 /tmp、敏感数据隔离。虚拟机隔离够强，但启动慢、开销大，不适合短命的批任务。于是 2003 年设计 Borg 时选了容器：基于 cgroups（Google 工程师 2007 年贡献进 Linux 内核）加 chroot、bind mount、overlay 文件系统做隔离。

最后一块是自动定规格（rightsizing）。让人填资源数本身有缺陷：程序在长、配置不跟着改，余量被一版版蚕食，直到某次高峰时不够用——事故。自动化出奇地难：Google 直到最近，全机群才有一半以上的资源用量由自动定规格决定；但按配置数算占比更高，多数工程师已不必操心——「简单的事要简单，复杂的事要可能」。

二、为失败而设计：牛群要「随时可复制」

调度器可以单方面杀掉你的任务、搬到别处（升级内核、换坏盘、重新装箱），而作为软件作者，我既不该知道、也不该关心为什么。所以每个实例都要能无人工介入地「再印一份」：宠物坏了要人慌着去救；牛群编号 replica001 到 replica100，倒下一头自动补一头。

但「是牛群」不等于「平稳扛住失败」。书里的算例：校验 100 万份文档、每份 1 秒，单机要约 12 天；分到 200 台机器约 100 分钟。若静态均分，每被杀一个 worker 总时长就多约 50 分钟，而 200 台里被杀不止一次几乎必然。改成把文档切成 1000 块、每块 1000 份，worker 做完一块汇报再领下一块——一次失败最多丢一块。

在线服务天然更适合：请求本身就是小块、靠负载均衡动态派发。Borg 计划搬迁容器时会提前通知，容器拒收新请求、做完在途请求，负载均衡器也得听懂「我不收了」。不天然适合的三类要警惕：持有状态的「leader」、静态分片（100 台各存 1%，挂一台就暂时丢一片数据）、以及靠主机名被别人找到的服务。

CS Papers · MapReduce — 本章点名的批处理标准框架：任务切小块、动态派给 worker、失败就重跑那一块

三、托管计算下怎么写软件

状态是牛群化的头号障碍：实例被换掉，进程内状态和本地盘全丢。所以要活过一次请求的东西都放进外部持久存储；存储自己也是牛群，靠多副本复制（通常 3 到 5 份），做对很难（写入需要共识），于是 Google 造了 GFS、Bigtable、Spanner。本地只放可重建的数据：缓存、预热、批量写，长计算定期打检查点。缓存有一条硬经验：按延迟目标配缓存，按总负载配核心服务——缓存层整体丢失时，不走缓存的路径虽慢但扛得住；代价是要为这份冗余付钱。

连接服务：主机名写死（哪怕是启动参数）就不是牛群。解法是加一层间接：别人用一个跨重启不变的标识找你，调度器放置实例时写入解析系统——即服务发现，通常附带负载均衡。随之而来的是重试：对方可能还没回答就被调走。修改类请求重试要幂等，好工具是客户端分配的 ID（订单号已存在就直接回成功）。还有个怪事：调度器与某机失联、在别处重启任务，那台机器又回来了——出现两个都自认是 replica072 的实例，这又是需要幂等的理由。

System Design · Day 23 可靠性 — 重试、退避、抖动与级联故障：本章脚注要求「重试要做对」，那篇讲怎么做

一次性代码：扫 1 TB 日志单机要一天，几百核几分钟就出结果。一千核时远不及一天工程师工资，为省算力设审批得不偿失；但算力容易一不小心拿太多（有新人调试时没发现后台拉起了 8000 个整机 worker）。Google 的解法：低优先级批处理本就近乎免费，于是给工程师几乎无限的低优先级配额。

四、一个池管所有：批处理白吃在线服务的冗余

WorkQueue 时代，批任务共享一个池，在线服务各自有专属机器池。2003 年启动的 Borg 把它们并成每个数据中心唯一的一个池，收益有二。其一，服务机器也成了牛群（Borg 设计文档原话：机器是匿名的，程序不关心跑在哪台上），不再有 n 个团队各自养一套、做法慢慢分叉。其二更微妙：在线服务必须为高峰和故障超额预留，申请量已经占满整机、真实利用率可能只有 30%；对在线服务超卖等于让余量失效，但剩下的 70% 可以塞批任务——在线服务要资源时，CPU 冻结、内存直接杀批任务收回。批任务看总吞吐、本身就是牛群，乐于吸收这些碎片。书里结论：Google 大多数时候相当于免费跑批处理。

在线服务进共享池要额外条件：服务发现；限速重调度（批任务重启一半副本只是吞吐抖一下，在线服务重启一半，剩下的扛不住流量）；以及提前几秒预警再杀。

五、容器是抽象，抽象就逃不过 Hyrum 定律

容器起初是为隔离，后来更重要的角色是把软件和机器隔开的抽象边界：机器在变，只需容器层（一个团队）去适配，各团队的应用不必改。文件系统抽象让外来软件带着自己的目录布局与依赖上车；端口也该归容器管——Google 早期没把端口放进容器，程序只能自己找空闲端口，结果 PickUnusedPortOrDie 在 C++ 代码库里有 2 万多处调用；Docker 借 namespace 给容器虚拟网卡，Kubernetes 更进一步让每个 pod 有自己的 IP。

反面教材是 2011 年的 PID 耗尽。Linux 默认 PID_MAX 约 32000，改个配置就能调大——但按 Hyrum 定律，「PID 不超过五位数」已成隐式 API：日志存储把 PID 写进记录名，六位数就超长出错。修复变成长期工程：先限制单容器 PID 数，再把线程与进程的 PID 空间分开（几乎没人依赖线程 PID）；第三步引入 PID namespace 时，又发现大量系统假设 {主机名, 时间戳, PID} 唯一标识一个进程——八年后仍在清理。教训不是「要用 PID namespace」，而是：机器上总有隔离不够的资源，所以优先选社区广泛使用的容器系统，别人踩过的坑已经填好。

关键权衡与选型

本章的判据：先决定管牛群还是宠物，再选抽象层级。每个团队在每个数据中心养一台宠物，成本随团队数 × 数据中心数超线性增长。

为什么重要 / 落到真实系统

面试被问「Kubernetes 为什么这样设计」，本章给出能复述的根：pod 有独立 IP、用 label 分组、声明式配置、无状态副本 + 外置存储，几乎每一条都对应 Borg 踩过的坑。选型评审时则提醒：平台锁定度极高——代码会用上它的一切特性，周边还会长出一整圈日志、监控、配置工具。

易错点与争议

  • 「上了容器就是牛群」是误解：能重建只是恢复，平稳还要动态分块、优雅下线与幂等重试。
  • 无服务器的比较对象选错了。多数讨论拿它和「虚拟机当宠物」比，所以显得革命；本章认为该和持久容器比，差别主要只剩「缩到 0」与控制权。
  • 「免费跑批」有前提：在线服务有大量预留余量、批任务容忍被杀；负载形态不同未必成立。
  • 别把「while true; do 程序; done」当自愈。书里明确说它在 Borg 下有害：把失败藏了起来，平台的故障处理机制无从介入。
  • 定制是慢性病。每个「就为这一个用户加个开关」都扩大显式或隐式 API；Kubernetes 起点更干净，但书里也承认它普及后开始遇到同样问题。
  • 时代局限：写于 2020 年，GPU / TPU 调度只点到为止，AI 时代的加速器调度未覆盖。

要点

① 规模需要统一的计算基础设施：应用种类、副本数、单应用体量三轴同时增长，手工 SFTP + SSH 会让运维随规模超线性膨胀。

② 演进路线：简单自动化 → 中央调度 + 坏机隔离 → 容器装箱多租户 → 自动定规格；Google 全机群仅一半多资源由自动定规格决定，但已覆盖多数配置。

③ 牛群而非宠物：实例可无人工复制替换；调度器可单方面杀任务，作者不该关心原因。

④ 牛群只保证恢复，平稳还要动态分块（100 万文档切 1000 块）、优雅下线、避开静态分片与写死主机名。

⑤ 状态外置到多副本存储；本地只放可重建数据；按延迟配缓存、按总负载配核心；重试必须幂等，客户端分配 ID 是利器。

⑥ 一个池管所有：批处理吸收在线服务的预留余量，Borg 论文测得拆池要多 20–30% 机器。

⑦ 容器是抽象边界，也是 Hyrum 定律的重灾区：五位数 PID、端口自找、ash 替换 Bash 都成了事故；优先选社区广用的系统。

⑧ 选平台就是选锁定：持久容器 vs 无服务器取决于状态与规模；集中 vs 定制、公有云 / 多云 / 混合云各有代价，留好逃生通道。
