开放心态、开放科学与开放混沌

Chaos Engineering: System Resiliency in Practice · Ch 14 · Open Minds, Open Science, and Open Chaos · 2020

EN →

这一章讲什么？

你每天刷的购物、视频、打车软件，背后都有一群工程师在「故意把系统弄坏一点」，好提前找到隐患。这一章问的是：他们找到的那些坑，该不该告诉别人？作者的答案很干脆：该，而且要像科学家发表实验那样讲清楚。

先说个怪事

同一家公司里，三个团队可能在三个月里踩进同一个坑：都忘了给某个慢服务设「等多久就放弃」。每个团队都很努力，各自修好，各自写了份没人看的总结。坑本身不难，难的是消息没流动。

旧世界为什么难

  • 怕丢脸。承认「我们的系统扛不住」，像是在承认自己没做好，于是发现被悄悄关在团队里。
  • 写得没法重来。就算分享了，也常是一句「我们测了断网，没事」——别人不知道你断的是哪、断了多久、看的是什么指标，没法照着再做一遍。
  • 工具各造各的。每家都从零写一套「搞破坏」的工具，重复劳动，还没人帮着挑错。

核心机制直觉：把演练当成科学实验来发表

作者借了科学界的老规矩：一篇好论文要写清你猜会发生什么、你做了什么、实际发生了什么，让别人能照着重做一遍、挑你的错。搬到故障演练上就是三件事：

  • 心态开放：把「系统没扛住」当成大家的学习材料，而不是某个人的错。
  • 工具开放：像共享菜谱一样共享「搞破坏」的工具，大家一起改，一起看它到底做了什么。
  • 实验和结果开放：每次演练写成一张卡片——猜想、怎么弄坏的、弄坏多大范围、什么情况立刻喊停、结果如何、后来改了什么。别人拿到卡片，就能在自己那儿再做一遍。

带来了什么 / 该怎么选

一个团队花一周踩出来的坑，别的团队读五分钟就能绕开；被很多人重做过的结论，也比一家之言可信得多。起步不用一步到位：先在公司内部把卡片共享起来，再考虑对外讲。

一句诚实的代价：公开要花写作的功夫，有些细节（比如安全漏洞）也确实不能马上说。

一句话记住

坑踩一次就够了：把故障演练写成别人能照着重做的实验卡片，把结果像科学发现一样分享出去。

一句话

你以为混沌工程的产出是「修好了几个漏洞」，其实最值钱的产出是知识——而知识只有在流动、能被别人复现和挑错时才会增值。本章主张把科学界的开放规范搬进混沌工程：协作的心态、开源的工具、可复现的实验设计、可分享的结果。

Glossary · 术语表

  • 混沌实验（chaos experiment）：在受控范围内向系统注入故障（宕机、延迟、断网），观察系统是否仍维持正常。
  • 稳态（steady state）：系统正常时某个可量化的业务指标，如每秒下单数，用来判断「有没有出事」。
  • 假设（hypothesis）：实验前写下的预测，如「推荐服务变慢时下单成功率不变」，实验就是去尝试推翻它。
  • 爆炸半径（blast radius）：一次实验最多会影响多少用户或机器，如 1% 流量。
  • 中止条件（abort condition）：指标偏离到什么程度就立即停止注入、恢复原状。
  • 可复现（reproducibility）：别人按你描述的步骤和条件重做一遍，能得到同样结论。
  • 同行评议（peer review）：结论发表前后由同行检查方法和推理是否站得住。
  • 开源（open source）：源代码公开、任何人可阅读、修改和贡献的软件。
  • 复盘（postmortem）：事故或演练后写下发生了什么、为什么、改什么的文档。

坐标

全书第 14 章，属于 Part IV「商业因素」，由当时在 Gremlin 任首席 SRE 的 Tammy Bütow 执笔。上一章 Ch13 讲怎么证明混沌工程值钱，这章讲怎么让这份价值溢出单个团队；下接 Ch15 成熟度模型，其中「采用度」那一维正是这里讲的扩散。

这章要解决什么

前面十几章讲的都是「怎么做好一次实验」。可一个中等规模的公司，可能有几十个团队、上百个服务，各自做实验。如果每个团队的发现只留在自己的周报里，会出现三种浪费：

  • 重复踩坑：缺超时、重试风暴、单可用区依赖这类问题，在不同团队里反复出现，每次都要花一次实验（甚至一次真实事故）才重新被发现。
  • 结论不可信：「我们测过断网，没问题」——测的哪条链路？断多久？看什么指标？无法复现的结论，别人既不敢依赖，也无从反驳。
  • 工具重复造：每家都自研一套注入框架，没人审查它对生产到底做了什么，也没人贡献改进。

不解决的后果是：混沌工程停留在「少数英雄团队的手艺」，组织层面的韧性并没有随实验次数线性增长。

核心内容，讲透

一、协作心态：发现不是某个人的失败

本章起手是心态问题。一个团队发现「我们的服务扛不住依赖超时」，第一反应常是藏——怕被看成工作没做好，或者觉得是内部家务事。作者把这种封闭心态和协作心态对比：后者把每个被推翻的假设当作组织的共同资产，主动邀请其他团队来看、来问、来挑错。

这和全书反复强调的「不追责（blameless）」一脉相承：如果暴露弱点会被惩罚，人们就会停止暴露弱点，混沌实验就只剩下表演。开放的前提是安全——先保证说出「我们错了」不会受罚，分享才会发生。

二、开放科学：为什么要借科学界的规矩

混沌工程从一开始就自称「实验的学科」：定义稳态、提出假设、注入真实世界的事件、尝试推翻假设。作者顺着这个自我定位往前推一步——既然是科学方法，就该接受科学的开放规范：方法要公开、条件要写清、结果要能被别人复现和评议。

科学界的开放科学运动主张公开方法、数据和结果，理由很朴素：一个结论被独立重做过，才算真正立住；封闭的结论，错了也没人能发现。混沌实验面临一模一样的问题——一次实验只是一个样本，换个时间、换个流量形态、换个依赖版本，结论可能就变了。

三、开源：工具开放，信任才有地基

第二层开放是工具。混沌工程的工具本身就有一个特殊的信任难题：你要允许它在生产环境里搞破坏。闭源的注入工具，你不知道它到底改了什么网络规则、杀了哪些进程、失败时会不会残留；开源让这些行为可审查。再加上社区贡献，各种注入方式（实例、网络、容器、云服务 API）不必每家重写一遍。

这条路的起点很具体：Netflix 在 2012 年把 Chaos Monkey 开源，之后注入工具陆续以开源形式出现。开源也把「实验格式」标准化的可能性带了进来——当实验能写成声明式文件，它就成了可以分享、版本管理、代码评审的东西。

四、开放混沌实验：把设计写成别人能重做的卡片

第三层，也是本章最可操作的一层：实验本身要写成可分享的形态。一句「我们测了断网」没有信息量；能被复现的实验描述，至少要回答下面这些问题：

这张卡片的上半部分是设计：别人拿去就能在自己的系统上重做。最常被漏掉的是环境与版本——同样的注入，换一个依赖版本或一个流量高峰时段，结论可能相反。没有这一行，「复现失败」时你分不清是系统变了还是实验变了。

五、实验发现与可分享的结果

卡片的下半部分是结果。作者强调结果要写成别人读得懂、用得上的形态：原本的假设是什么、是否被推翻、看到的现象、推断的原因、做了什么改进、改进后有没有复验。尤其要分享失败的实验——「假设成立、一切正常」的结果同样有价值，它告诉别人这条路径已经验证过。

分享的受众可以分层：先是团队内，再是全公司（例如一个可搜索的实验库、定期的分享会），最后是对外（技术博客、会议演讲、开源的实验模板）。每往外一层，被挑错的机会就多一层，结论也就更硬一分。

关键权衡与选型

开放不是越多越好，权衡在于复用和评议的收益对比写作成本和暴露风险。

开放到哪一层：收益与代价

开放层级收益代价 / 风险适用
仅团队内零额外成本，可以畅所欲言知识困在边界内，别的团队重复踩坑刚起步、实验还不稳定时
公司内共享库跨团队复用，同类问题一次修全要统一卡片格式、要有人维护索引；依赖不追责文化多数组织的主战场
开源工具与实验模板行为可审查，社区贡献注入能力维护负担；项目会老化甚至停更工具成熟、有通用性时
对外公开结果行业级同行评议，招聘与声誉可能暴露架构与安全细节，需审核与脱敏结论已复验、细节可脱敏时

工具怎么选：开源、商业还是自研

路线优势代价
开源工具代码可审查，实验格式可分享，免授权费运维与安全护栏要自己补；社区活跃度不稳定
商业平台开箱即用，中止、权限与审计通常现成费用；实验格式可能绑定厂商，难以与外部分享
自研贴合内部架构，可做到请求级注入成本最高；没有外部评议，最容易变成封闭孤岛

判据：先把公司内的卡片格式和共享库做起来，这一层投入小、复用收益最大；工具尽量选格式开放的，以后才能和外部交换实验；对外公开留给已复验、可脱敏的结论。

为什么重要 / 落到真实系统

这章看似是「文化篇」，落到工程上却很具体：实验即代码。当实验写成声明式文件，它就能进版本库、走代码评审、在流水线里重放——这正是 Ch16「持续验证」的前提。面试被问「怎么在组织里推广混沌工程」，好的回答不是「多做实验」，而是「统一实验格式、建共享库、复盘不追责、结论可复现」。

数据库领域有一个开放科学的标杆：Jepsen 项目（开源仓库自述「Breaking distributed systems so you don't have to」）对分布式数据库做故障注入测试，并公开发布测试代码与分析报告，不少厂商据此修复缺陷、改写文档里的一致性承诺——这正是「可复现 + 公开评议」能产生的外部压力。（Ch19 讲数据库混沌时会再遇到这类方法。）

大厂实证

  • Netflix 开源 Chaos Monkey，并把价值写成行为改变。其仓库开头：「Exposing engineers to failures more frequently incentivizes them to build resilient services.」——让工程师更频繁地面对故障，促使他们把服务做得更有韧性。Netflix · Chaos Monkey README（github.com/Netflix/chaosmonkey）
  • 反面：开源项目也会老化。Netflix 的 Simian Army 仓库现在写明「The Simian Army project is no longer actively maintained」，Chaos Monkey 改为独立服务。开放工具不等于永久可用，选型要看维护者。Netflix · SimianArmy README（github.com/Netflix/SimianArmy）
  • Shopify 把开源的网络故障代理用进日常开发。Toxiproxy 自述：「We've been successfully using it in all development and test environments at Shopify since October, 2014.」——说明开放工具不只用于生产演练，也能下沉到每个开发者的测试里。Shopify · Toxiproxy README（github.com/Shopify/toxiproxy）
  • 「共享实验」已经被做成基础设施。CNCF 项目 LitmusChaos 的 ChaosHub 被描述为「a central hub where the application developers or vendors share their chaos experiments」，即一个集中分享实验定义的地方。LitmusChaos README（github.com/litmuschaos/litmus）
  • 实验格式的开放化。Chaos Toolkit 把使命写成「provide an open API to chaos engineering in all its forms」，实验以 JSON / YAML 声明式文件描述，可直接分享与重放。Chaos Toolkit README（github.com/chaostoolkit/chaostoolkit）

易错点与争议

  • 「开放 = 把一切公开到外网」。本章的重心其实在组织内部；对外公开是最后一层，且需要脱敏审核。
  • 「分享工具就够了」。工具开源只解决了一层，真正稀缺的是可复现的实验设计与结果。大家用同一个工具，各自写不可复现的结论，仍是孤岛。
  • 「复现失败说明原实验错了」。未必：系统、版本、流量都可能变了。这正是要写清环境与版本的原因——没有它，复现失败无法解读。
  • 安全与开放的张力。某些实验结果本身就是漏洞信息，公开前必须修复并评估风险；这一点本章着墨不多。
  • 没有不追责文化，开放会变成表演。只分享「成功」的实验、掩盖被推翻的假设，比不分享更误导。
  • 本章偏倡议、少数据。它没有给出「开放程度与韧性提升」的量化证据，作者本人也来自混沌工程厂商，读时可留意立场。

要点

① 混沌实验最值钱的产出是知识，知识只有流动起来才增值。

② 封闭的代价：重复踩坑、结论不可复现、工具重复造。

③ 开放的前提是不追责：说「我们错了」不受罚，分享才会发生。

④ 混沌工程自称科学方法，就该接受科学的开放规范：方法公开、可复现、可评议。

⑤ 工具开源让「在生产里搞破坏」的行为可审查，并让实验格式有机会标准化。

⑥ 一张可复现的实验卡片：稳态、假设、注入强度、爆炸半径、中止条件、环境版本、结果、改进。

⑦ 「环境与版本」最常漏写，却决定复现失败能否被解读。

⑧ 开放分层推进：团队内 → 公司共享库 → 开源 → 对外公开，主战场在公司内。

⑨ 实验即代码，是走向持续验证（Ch16）的前提。
