基于服务的架构：几个粗粒度服务 + 一个共享库，微服务的务实折中

Fundamentals of Software Architecture · Ch 13 · Mark Richards & Neal Ford · 2020

EN →

这一章讲什么？

一家中等规模的公司，订单、库存、发货、记账都在一套软件里。软件越长越大，改一行记账代码，整个系统都得停下来重新上线。大家听说「微服务」很时髦——拆成几百个小程序——可团队只有二三十人，真拆了根本管不过来。这一章讲的就是中间那条路：只拆成几块大的，书里叫基于服务的架构。

打个比方：把一家大饭馆分成几个档口

原来一个大厨房什么都做，一个灶台出问题全店停火。现在分成凉菜、热菜、面点、甜品四五个档口，各有各的师傅、各自开工收工，面点间装修，热菜照常出菜。但大家仍然共用一个大冷库，食材放在一处，不用每个档口各建一个冷库、再派人来回调货。

旧世界为什么难

只有一个大厨房时，任何改动都牵一发动全身。可如果走到另一个极端，每道菜一个小厨房、各有冷库，那光是协调「这块肉现在在谁那儿」就要累死人：顾客点一桌菜，十几个厨房要互相确认，一个环节失手，账就对不上。

核心机制：大块分工 + 共用仓库

它就三样东西。几个大档口：按业务分，通常四到十来个，每个能单独开工、单独升级。一个前台：顾客只跟前台打交道，前台再把单子派给对应档口。一个共用冷库：所有档口从同一处取货，所以一张订单的事在一个档口里就能从头办到尾，要么全办成、要么全退回，不会出现「钱扣了、货没出」的半截事。

冷库也会划分区域：人人要用的公共货架谁都不能乱动，各档口专用的货架自己管。

带来了什么 / 该怎么选

它拿到了微服务的大部分好处：改一块只上线一块，一块出事其他照常；又躲开了微服务最贵的那部分。很多公司最后停在这里就挺好。代价是：档口大，改一处要把整个档口都检查一遍；共用冷库的格局一动，好几个档口都要跟着调整。

一句话记住

基于服务的架构 = 几个按业务切的大服务 + 一个共享数据库：拿到独立上线和故障隔离，留住「一件事一次办完」的简单。

一句话

你以为从单体出发只能一路拆到微服务，其实大多数团队需要的是中间那一站：4 到 12 个粗粒度领域服务，各自独立部署，前面一个界面、后面共享一个数据库。FoSA 第 13 章称它是最务实的架构风格之一——拿到分布式的可部署性与故障隔离，却因为服务够粗而保住了服务内的 ACID 事务，不必上来就和分布式事务较劲。

Glossary · 术语表

  • 粒度（granularity）：一个服务管多大一块业务；粗粒度 = 管一整个领域，细粒度 = 只管一件小事。
  • 领域（domain）：业务里一块相对独立的职责，比如「下单」「发货」「记账」。
  • ACID 事务：数据库保证一组操作要么全成功、要么全回滚，中途失败不会留下半截数据。
  • Saga / 最终一致：跨多个服务时没有统一事务，只能一步步做、失败了再逐个「补偿」撤销，数据会短暂不一致。
  • 共享库（shared library）：多个服务共同引用的一份代码包，例如映射数据库表的实体类。
  • API 网关 / 反向代理：挡在服务前的一层，统一处理路由、鉴权、限流，对外暴露接口。
  • REST / RPC / 消息：三种跨进程调用方式：发 HTTP 请求、像调本地函数那样调远端、或把消息丢进队列异步处理。
  • 架构量子（architecture quantum）：能独立部署、带完整功能的最小单元（第 7 章）；共享数据库会把多个服务绑成同一个量子。
  • 星级评分：书中每种风格按 1–5 星给各项架构特征打分，便于横向对比。

坐标

Part II「架构风格」中，紧接三种单体风格（分层、管道、微内核），是书里第一个分布式风格，也是后面事件驱动、空间、SOA、微服务（第 14–17 章）的参照原点。现实对应：中型企业的业务系统、从单体往外拆的第一步。

这章要解决什么

单体的痛第 10–12 章已经讲透：一个部署单元，改一处就要全量测试、全量上线，一处内存泄漏拖垮全部，伸缩只能整块加机器。第 9 章又提醒了分布式的价格：八个谬误、网络延迟、分布式事务。

微服务把这两头的取舍推到极端：几十上百个细服务、每个独占数据库。对一个 20 人的团队、一个读写比不算极端的企业系统，这意味着要先搭好服务发现、链路追踪、容器编排、Saga 补偿，才能开始写业务——基础设施的复杂度先于业务价值到来。

本章回答的问题是：有没有一种分布式形态，让你只为真正需要的那部分分布式买单？书的答案是把应用切成少数几个按领域划分、独立部署的大服务，但数据库先不拆。

核心内容，讲透

① 基本拓扑：独立 UI + 粗粒度服务 + 单一数据库

书中的基本形态是一种分布式宏分层结构：一个单独部署的用户界面、若干远程的粗粒度服务、一个单体数据库。服务数量通常在 4 到 12 个，平均约 7 个。每个服务是应用里一块独立部署的部分，书把它们叫领域服务。

UI 通过 REST、消息、RPC 或 SOAP 远程调用服务。通常每个服务只部署一个实例；若某个服务要扩容或容错，可以多跑几个实例，但这时 UI 与服务之间就要加负载均衡。

这个拓扑有三个常见变体，书逐一画出：UI 拆分（按领域拆成多个界面，如客户端与内部后台）、数据库拆分（服务数据足够独立时，按领域拆成几个库）、加一层 API（UI 与服务之间放反向代理或网关，适合要把服务暴露给外部系统，或要统一处理鉴权、指标这类横切关注点）。

② 服务设计：粗粒度，内部再分层或分领域

因为每个服务都管一整个领域，它内部本身就是个小应用。书给了两种组织方式：技术分层——API 门面层、业务层、持久化层；或领域分区——按子领域拆内部组件，比如订单服务里再分下单、支付、库存扣减。

API 门面层负责编排来自 UI 的业务请求：UI 只发一个「下单」，门面在服务内部依次调用下单、扣款、扣库存。对比微服务：同样的请求，往往要由 UI 或某个协调者去编排三个独立部署的服务。

这带来本章最重要的好处：服务内仍能用 ACID 事务。下单时扣款失败，一个数据库事务回滚即可；微服务里则要写补偿逻辑，按书的说法，在高度分布式的风格里只能依赖 BASE（基本可用、软状态、最终一致）。代价是反过来的：服务越粗，改一处要测的范围越大，部署风险也越高——改了支付逻辑，整个订单服务都要回归测试、重新上线。

③ 数据库：共享库的颗粒度决定改表的爆炸半径

共享数据库最大的麻烦是改表。书的做法是：服务通过一份共享库里的实体对象访问数据库。若只有一个大共享库，任何一张表的结构变化都会让所有服务跟着改代码、重新测试、重新部署——哪怕大多数服务根本不碰那张表。

书推荐的解法是先把数据库按领域逻辑分区，再配一组联邦式共享库：一个公共实体库（书中名为 common_entities_lib）放所有服务都用的表，每个领域再有自己的实体库（如客户、发票、订单各一份）。改领域表只影响用到该库的服务；公共表的改动被锁住，要经数据库团队审批，因为它会波及所有服务。书的建议是：逻辑分区在保持数据领域清晰的前提下越细越好。

④ 书中示例：电子设备回收

书沿用第 12 章的电子设备回收业务。顾客端服务有报价（顾客询价）和物品状态（查进度）；内部服务有接收、评估、回收、会计、报表等。两类服务配两套 UI、两个物理分开的数据库，内部那一侧放在独立的网络区域里。

每个服务按自己的需要取舍：面向顾客的服务要扛流量、要可伸缩；评估规则常改，单独成服务后改它不必重新部署其他部分；某个内部服务宕了，顾客照样能报价。这正说明了本章的要点：服务的切分和数据库的切分，可以各自按特征需要来做。

⑤ 书中的特征评分

基于服务的架构是领域分区的风格；架构量子通常为 1（共享 UI 与数据库把服务绑在一起），UI 和数据库也按领域拆开时可以多于 1。评分：可部署性、可测试性、可靠性、容错性、模块化 4 星；整体成本 4 星；简单性、可伸缩性、可演进性、性能 3 星；弹性 2 星。理由：

  • 可靠与容错 4 星：服务独立部署，一个挂掉不连坐；服务数少、彼此调用少，网络往返和分布式事务也少。
  • 可部署、可测试 4 星：改动只落在一个领域服务上，但服务粗，测试范围仍比微服务大。
  • 弹性只有 2 星、伸缩 3 星：服务太粗，突发流量时只能整块复制一个大服务，扩起来慢且浪费。

判据一句话：你需要独立部署和故障隔离，但不需要极致弹性，也付不起分布式数据的代价？那就停在这里。书还特别指出它和领域驱动设计（DDD）天然契合：一个领域服务对应一块业务领域，切分时不必纠结细粒度边界。反过来，若某个领域确实有秒级突发流量要扛，把它单独拆细就好，不必全盘微服务化。

为什么重要 / 落到真实系统

大厂实证 · 以下为公开资料中的做法与主张（转述）
  • Segment（2018）：工程博客《Goodbye Microservices》回顾，他们为每个数据投递目标各建一个服务，增长到上百个后，共享库版本漂移、逐个部署和运维负担压垮了小团队，最终把这些服务合并回一个服务。这是「拆得太细」的典型反例，也是本章主张的实证。Segment Engineering Blog，Alexandra Noonan，2018（转述）
  • Amazon Prime Video（2023）：技术博客介绍，其音视频质量监控工具原本由多个分布式组件串起来，组件间传数据的开销和编排成本很高；改为单进程部署后，基础设施成本降低了 90% 以上。说明粒度该按通信与数据流来定，而不是越细越好。Prime Video Tech Blog，2023（转述）

这两个案例都不是「基于服务的架构」字面上的落地，但讲的是同一件事：每多一条服务边界，就多一次网络调用和一份运维，这个账要先算。落到架构评审，可以问三件事：一次典型请求要跨几个服务？共享库改一张表要重新部署几个服务？哪个服务真的需要单独弹性伸缩？落到面试，被问「为什么不直接上微服务」，可以答：「先切 4–12 个领域服务、共享数据库，保住服务内 ACID；等某个领域真的有伸缩或团队独立性的需求，再把它单独拆细。」

易错点与争议

  • ≠「小一点的微服务」：两者的本质差别在数据——基于服务默认共享数据库，微服务要求数据隔离；只看服务数量会认错。
  • 共享数据库是双刃剑：它换来 ACID 和简单，也让服务在数据层面耦合；一个大共享实体库会把「独立部署」变成空话。
  • 服务间互相调用要克制：领域服务之间若频繁同步调用，就在重造分布式单体，既有网络开销，又没换来独立性。
  • 粗粒度的测试成本：改一个小功能也要回归整个服务，这是换取事务简单的直接代价，别假装它不存在。
  • 不是必然的过渡态：常被说成「通往微服务的中转站」，但书把它当作可以长期停留的独立风格；很多系统根本不需要再往前走。
  • 时代局限：书写于 2020 年；此后「模块化单体」和「宏服务」的讨论升温，Prime Video 一类案例让「别拆太细」成了更主流的共识。

要点

① 基于服务 = 独立 UI + 4–12 个（平均约 7 个）粗粒度领域服务 + 通常共享的单体数据库；书中第一个分布式风格。

② 三个变体：按领域拆 UI、按领域拆库、在 UI 与服务间加 API 层 / 反向代理。

③ 服务内部按技术分层（API 门面 / 业务 / 持久化）或按子领域分区，门面负责编排请求。

④ 最大好处：服务够粗，服务内保住 ACID，不必上来就写 Saga 补偿。

⑤ 最大代价：改一处要测整个服务；共享表改动会波及多个服务。

⑥ 数据库按领域逻辑分区 + 联邦共享库，公共实体库改动需审批，分区越细越好。

⑦ 评分：可部署、可测试、可靠、容错、模块化、成本 4 星；伸缩、性能、简单性、演进 3 星；弹性 2 星。

⑧ 与 DDD 天然契合；量子通常为 1，UI 与库按领域拆开时可多于 1。

⑨ 实证：Segment 把上百个细服务合并回一个；Prime Video 改单进程后成本降九成以上。

⑩ 面试复述：「先切几个领域大服务、共享库保 ACID；哪块真要弹性，再单独拆细。」
