这一章讲什么？

你在手机上点一下「确认支付」，这条消息要跨过基站、光纤、好几台机房里的机器，最后落到某个数据库上。前七章讲的都是一台机器内部怎么存怎么找。从这一章起，故事换了一个场地：多台机器之间，只能靠互相喊话来合作。这一章不教任何具体做法，它先告诉你：在这种场地上，有哪些事从原理上就办不到。

先说个怪事

你给朋友发消息问「今晚八点行吗」，等了十分钟没回。可能是消息没送到；可能是他回了、但回复丢在路上；也可能他正低头打字。这三种情况，你从外面看完全一样。分布式系统里最硌人的就是这个「看起来一样」——超时了，你并不知道对方是死了、是慢了，还是回话丢了。

旧世界为什么难

在一台机器上写程序，有三件事是白送的：调用一个函数，它一定会返回；读一个变量，读到的就是最新值；看一眼表，时间总是往前走。跨到两台机器，这三条一条不剩：函数调用变成了「寄一封信出去，可能永远没有回音」，「最新值」变成了「我上次听说的值」，两块表还可能一快一慢差出好几秒。

它怎么做到的

这一章的做法不是给解药，而是先把话说死——把含糊的「网络不太靠谱」变成三张写明白的假设表，后面所有算法都照着这三张表设计：

  • 这条线路有多可靠。最底下那层是「信可能丢、可能重、可能次序颠倒」；往上垫一层「不停重寄，直到收到回执」；再往上垫一层「收件人记住已经收过的单号，重复的直接扔掉」。到这一层，才敢说这条线「可靠」。关键在于：可靠不是线路本身的性质，是你用重寄和记账垒出来的。
  • 时间有多可信。是「对方必须在十秒内回话」，还是「没有任何时限」，还是「平时都挺准、偶尔抽一次风」？这一条决定了你敢不敢把「超时」当成「对方挂了」。
  • 对方会怎么坏。是直接断电、从此不吭声；还是活着但时不时漏听一句；还是干脆胡说八道、给不同的人报不同的数。假设越离谱，防起来越贵。

所以该怎么选

承诺越强，代价越大。最典型的是「不多不少、正好送到一次」——这件事在线路层面做不到：发信人收到失败时，永远分不清是「没送到」还是「送到了但回执丢了」。真正能做的，是多寄几次，让收件人按单号去重。支付的幂等键、消息队列的去重表，都是这一条的实例。

诚实的代价：这三张假设表买来的是「能讲清楚为什么对」，而不是可靠本身——假设定得太宽松，算法根本跑不动；定得太乐观，真实世界抽一次风就全盘崩。

一句话记住

分布式难的不是机器多，而是没有任何人能看见「现在」。每台机器手里只有一份过期的传闻。工程上唯一能做的，是先把「线路多可靠、时钟多可信、节点会怎么坏」写死成假设，再在上面盖楼。

一句话

你以为分布式的难点是「机器多了不好管」，其实是没有任何观察者能看见「现在」。这一章不给一行算法，它给的是 Part II 全部算法共用的那张假设表——链路（link）有多可靠、时间有多可信、节点会怎么坏。把这三格填错，后面的共识、复制、反熵全都建在流沙上。

Glossary · 术语表

  • 节点（node）/ 进程（process）：参与协作的一台机器上的一个程序实例。本章里两者常混用。
  • 链路（link）：两个节点之间传消息的那条通道——不是物理网线，而是「发消息 / 收消息」这组能力的抽象。
  • 消息传递（message passing）：节点之间唯一的沟通方式：发一条、等一条。没有共享内存，没有共享变量。
  • 副本（replica）：同一份数据在多台机器上的多个拷贝。
  • 超时（timeout）：等了一段时间还没收到回音，就主动放弃等待。注意它只说明「这段时间内没收到」，不说明对方死活。
  • RTT（round-trip time，往返时延）：一来一回所花的时间。同机房约 0.1–0.5 毫秒，跨大洲常在 100–200 毫秒。
  • 幂等（idempotent）：同一个操作执行一次和执行十次，结果一样。重试安全与否，全看它。
  • quorum（法定人数）：一组节点中必须有多少个点头，这件事才算数，通常取「过半」。
  • 共识（consensus）：一群节点对「某个值是什么」达成所有人都认的一致结论。Part II 的终点。
  • 时钟漂移（clock drift）：两台机器的石英钟走速不同，时间会越走越偏，必须定期对表（NTP）。

坐标

Part I 讲的是一台机器里的存储引擎（B-tree、LSM-tree、事务恢复）；Part II 从这一章起跨出机器。它上承第 7 章、下启第 9 章故障检测、第 10 章领导者选举、第 11 章复制与一致性、第 12 章反熵与传播，直到第 13–14 章的共识。对应现实里的哪一类系统？所有多副本的东西——etcd / ZooKeeper、Cassandra / DynamoDB、Kafka、Spanner / CockroachDB，它们的分歧全在这一章画出的坐标系里。

这章要解决什么

单机程序员有三条白送的假设：调用必返回、读到即最新、时钟单调向前。跨机之后三条全废，而废掉的方式很隐蔽——不是立刻报错，是平时都对、压力一大就错。书里借 Peter Deutsch 的「分布式计算八大谬误」点名前几条：网络可靠、延迟为零、带宽无限、拓扑不变。

不解决会怎样？三种典型翻车：拿墙上时钟给事件排序——两台机器各自的 now() 在 NTP 校准之间可能差出几毫秒到几十毫秒，于是「后发生」的写被判成先发生，数据被静默覆盖；把超时当死亡——旧主只是 GC 停顿了 8 秒，新主已经选出来了，两个主同时接受写入（脑裂）；网络错误就无脑重试——第一次其实成功了，于是用户被扣了两次款。三种错误都不是「代码写错了」，而是假设表填错了。

核心内容，讲透

一、共享状态：系统里没有「快照」这回事

书里给的定义很朴素：分布式系统就是一组各自独立执行、只靠消息互通的进程。由此推出一个后果——系统里不存在「当前全局状态」这个东西。每个节点手上只有两样：自己的局部状态，和若干条已经到达的消息。没有上帝视角，没有可以一口气拍下来的快照。

所以任何「系统现在是什么样」的说法，都只是某个节点在某个时刻的猜测，而且天生落后——落后的下限就是一次单程网络时延。跨大洲部署时「最新」至少陈旧 50 毫秒，这不是实现不好，是光速。

二、链路阶梯：不可靠是底座，可靠是垒出来的

本章最实用的一节。它把「网络」拆成三层抽象，层层加码：

  • 公平损失链路（fair-loss link）：消息可能丢、可能重复、可能乱序，但保证一件事——只要你无限次重发，就有无限次送达。它不保证任何一条消息，只保证不会「永远针对性地吞掉你」。
  • 固执链路（stubborn link）：在公平损失之上加一条「发出去就不停重发，永不停止」。于是得到最终必达，代价是收件方会收到大量重复、而且顺序乱。
  • 完美链路（perfect link）：固执链路 + 按消息 ID 去重。它给三条保证：有效性（发出去的终会送达）、无重复（同一条不会交付两次）、无凭空创造（没发过的不会冒出来）。

要带走的一句：「可靠链路」不是网络的性质，是你用重试和记账在不可靠网络上盖出来的一层楼。而且盖得并不彻底——现实里「无限重发」永远是「重试 N 次 + 超时放弃」，所以完美链路是理想模型，不是你能买到的产品。

三、消息顺序，与「恰好一次」的真相

顺序保证也是阶梯，四档由弱到强：无序（到达顺序任意）→ FIFO 序（同一个发送者发出的消息，按发送顺序交付）→ 因果序（causal order）（有因果关系的消息不会颠倒，互不相干的可任意）→ 全序（total order）（所有节点看到完全相同的一串顺序）。越往上越贵：FIFO 只需每条链路一个递增序号；因果序要带上因果元数据（向量时钟）；全序基本等价于要过一次共识，这就是第 13–14 章的活。

投递语义同样三档：至多一次（发了就不管，可能丢）、至少一次（重试到确认，可能重）、恰好一次。第三档是全章最该记住的结论：在链路层面，恰好一次不可能。发送方收到一个失败或超时时，它无法区分「消息没到」和「消息到了、处理了、但回执丢了」——唯一可信的状态是成功。工程上所说的「恰好一次」，实际上永远是至少一次 + 接收方幂等去重：消息带唯一 ID，接收方维护一张已处理 ID 表。

论文精读 · Time, Clocks, and the Ordering of Events — Lamport 怎么用「happened-before」把因果序定义出来，以及逻辑时钟为什么能取代墙上时钟给事件排序

四、两将军与 FLP：两条不可能结论

两将军问题（Two Generals' Problem）：两支军队分处山谷两侧，只能派信使穿越敌营商定同时进攻，信使可能被截。结论是：无论交换多少轮确认，最后一条消息的发送方永远无法确定它送到了没有。在可能丢消息的链路上，两方无法就「同时行动」达成确定的一致。

FLP 不可能性（Fischer–Lynch–Paterson，1985）：在异步系统里，哪怕只有一个进程可能崩溃，也不存在既保证终止又保证一致的确定性共识算法。根子还是那句老话——异步系统里分不清「崩了」和「只是很慢」。

关键不是「所以共识做不了」，而是它告诉你必须松开哪个螺丝：加时间假设（用超时把系统当成部分同步——Raft、Paxos 的路线）、放弃确定性（随机化共识）、或放弃「一定终止」的承诺（永不出错，但极端调度下可能一直选不出主）。真实系统几乎都选第一条：用超时换活性，并接受超时偶尔骗你。

System Design · Day 46 分布式共识与协调 — Paxos 与 Raft 怎么在这些不可能结论之下仍然把「让 5 台机器对一件事达成一致」做出来，以及 lease、fencing token 怎么防脑裂

五、系统同步性：三档时间假设

同一个算法，在不同的时间假设下结论完全不同，所以这一格必须先填：

  • 同步系统：消息传递与处理时间都有已知上界。超时于是成了可靠的故障判据，算法写起来最舒服——但真实网络给不出这个上界。
  • 异步系统：没有任何时间上界，时钟不可用。最贴近真实，但 FLP 堵在门口。
  • 部分同步（partially synchronous）：大多数时候有界，偶尔超出。这是现实系统的落脚点——Raft 的选举超时、第 9 章的 φ-accrual 故障检测器，都是在这一档里做工程。

六、故障模型：假设对方会怎么坏

最后一格是「坏」的形状，从便宜到昂贵：

  • 崩溃停止（crash-stop）：一旦挂掉就永远不回来。最好分析，也最不现实。
  • 崩溃恢复（crash-recovery）：挂了还会回来，而且带着一份可能已经过期的状态。于是必须有持久化日志 + 重新追平机制。
  • 遗漏故障（omission fault）：进程活着，但漏发或漏收若干消息——过载丢包、长 GC 停顿都属此类。最阴险的一种，因为它看起来还活着。
  • 拜占庭故障（Byzantine fault）：任意行为，包括撒谎、给不同节点报不同的值。容忍它的代价是硬性的：容忍 f 个崩溃需要 2f+1 个节点，容忍 f 个拜占庭需要 3f+1。

数据库系统默认不做拜占庭假设——机器都在同一个组织的机房里，不值得为撒谎付三倍的账；把这一格打开的是区块链那一类互不信任的场景。

为什么重要 / 落到真实系统

这一章的价值在于：它把「分布式很难」这句废话，换成了三个能在设计评审上直接开口问的问题——我们假设的是哪一档链路？哪一档时间模型？哪一档故障模型？面试里同理：被问「怎么保证消息不重不漏」，答「用 MQ 的 exactly-once」是没分的，答「链路层做不到恰好一次，所以做至少一次投递 + 接收端幂等去重，去重表按业务 ID 建、保留 7 天」才是懂行的回答。

  • etcd 用一张表把「多数派」的代价钉死：集群 3 台容 1 台故障、4 台仍然只容 1 台、5 台容 2 台，并直言「把集群补成偶数台买不到额外的容错能力」；选奇数还有一条理由——「奇数个成员保证网络分裂时总会存在一个多数派分区，可以继续工作，并在分区结束后成为真相来源」。etcd FAQ · Failure tolerance ↗
  • Google（Eric Brewer 谈 Spanner 与 CAP）给「分区到底多常见」提供了罕见的实测口径：「对跨广域的分布式系统而言，普遍认为分区是不可避免的，尽管未必常见」；Spanner「可用性超过 5 个 9（故障率低于 10⁻⁵）」，而且「我们发现网络造成的故障，在 Spanner 本就罕见的故障中占比不到 10%」——换句话说，真实世界里咬人的多半不是网络分区，而是本章说的那些遗漏与崩溃恢复。Google Cloud Blog · Inside Cloud Spanner and the CAP Theorem ↗

易错点与争议

  • 「超时了就是挂了」——错。超时只说明「这段时间内我没收到回音」。把它当死亡判据，就得接受偶尔的误判；真正的防线不是把超时调得更准，而是让误判无害（fencing token、lease 过期后主动退位）。
  • 「重试总是安全的」——只有幂等时才安全。非幂等操作上加重试，等于给自己装了一个概率性的重复执行器。
  • 「机器越多越容错」——偶数不买账。4 节点和 3 节点的容错能力一样，都是 1 台；多出的那台只增加协调成本和分区时形成僵局的机会。
  • 「CAP 说你必须在 C 和 A 里二选一」——被过度传播了。Brewer 自己的表述是：只有在真正发生分区时才需要放弃一致性或可用性，平时两者可以兼得。
  • 「这些都是理论，工程上不重要」——反例就在上面。Dataflow 那句「Deadline Exceeded 是有歧义的」，就是两将军问题在一行 RPC 错误码上的显形。
  • 本章自身的局限。它是一张「术语与模型的地图」，干净但也干燥：真正把部分同步落地的工程手段（lease、混合逻辑时钟 HLC、fencing token）基本没展开，要等后面几章甚至别的书来补。

要点

① 分布式系统＝一组独立进程只靠消息协作；没有全局状态、没有快照、没有上帝视角——每个节点手里只有一份过期的传闻。

② 单机三条白送的假设（调用必返回、读到即最新、时钟向前）跨机后全废，而且是压力大了才发作。

③ 链路阶梯：公平损失（会丢会重会乱序）→ 固执（无限重发 ⇒ 最终必达）→ 完美（去重 ⇒ 有效性 / 无重复 / 无凭空创造）。可靠是垒出来的，不是网络给的。

④ 顺序阶梯：无序 → FIFO → 因果序 → 全序；全序基本等价于一次共识，最贵。

⑤ 恰好一次在链路层不可能。工程上的「恰好一次」永远是至少一次 + 唯一 ID + 接收方去重表。

⑥ 两将军：可能丢消息的链路上，最后一条消息的发送方永远无法确认它送到了。

⑦ FLP：异步系统里，哪怕只有一个进程可能崩溃，也没有既终止又一致的确定性共识——因为分不清「崩了」和「很慢」。

⑧ 出路是松开某个螺丝：加时间假设（部分同步）是现实系统的普遍选择——用超时换活性，但安全性绝不建立在时钟上。

⑨ 故障模型：崩溃停止 / 崩溃恢复 / 遗漏 / 拜占庭。容 f 个崩溃要 2f+1 台，容 f 个拜占庭要 3f+1；数据库默认不付拜占庭这笔钱。

⑩ 评审时的三问：我们假设的是哪一档链路、哪一档时间模型、哪一档故障模型？答不上来，后面的复制与共识都是空中楼阁。
