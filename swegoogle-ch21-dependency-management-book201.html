依赖管理

Software Engineering at Google · Ch 21 · Dependency Management · Titus Winters · 2020

EN →

这一章讲什么？

你手机上的任何一个 App，都不是从零写出来的：它用了别人写好的「零件」，那些零件又用了更多别人的零件，一层套一层。这些借来的零件就叫「依赖」。这一章讲的是：零件的主人随时会改它，而你管不着他们——怎么让整台机器长期不散架？

先说个怪事

你会以为，零件的版本号能告诉你「升级安不安全」：大版本变了要小心，小版本随便升。Google 的经验是，版本号只是零件作者的一句猜测。他觉得「只是修了个小毛病」，可总有用户偷偷依赖了那个「毛病」；他觉得「这次改动很大」，可你根本没用到改动的那部分，却被拦着不让升级。

旧世界为什么难

想象一个家装工程：你请了木工和电工，两人都要用同一家厂的螺丝。厂家出了新款螺丝，螺纹和旧款不一样。木工换了新款，电工还在用旧款——而你的房子里只能装一种螺丝。两位师傅都没做错，可你的房子装不起来了。更麻烦的是，发现问题的是你，而你既不懂木工也不懂电工。零件网越大，这种「两头都对、合起来不行」的局面就越常见。

核心机制直觉

  • 能自己管的，别当外人管：Google 把几乎所有代码放进同一个大仓库。同一家公司的零件，改之前能看到谁在用、能先跑一遍大家的检查——这比跟陌生人约定版本号省事得多。
  • 引进外人的零件，要当成「领养」而不是「借用」：今天图省事拿进来，几年后它有了安全漏洞，得有人懂它、能升级它。
  • 与其听作者猜，不如做实验：零件作者要改东西，就先把所有用它的人的检查都跑一遍——全过了就是安全的，不用争「这算大改还是小改」。
  • 升级每次只迈小步：别一口气跳到最新，只升到刚好够用的那一版，因为那一版最可能被作者亲手试过。

带来了什么 / 该怎么选

小项目、零件少、都是靠谱作者维护的，看版本号就够用；零件网大到几千个、项目要活几十年，就该把检查的责任压到零件作者身上：要改，先证明没把别人弄坏。诚实的代价是：这要求人人有自动检查、还要海量机器去跑，目前只有 Google 这种规模的公司在自家围墙内做得到。

一句话记住

依赖不是一次性的借用，而是一份长期合约；版本号只是对方的一句猜测，真正可靠的答案来自「把用它的人的检查都跑一遍」。

一句话

你以为依赖管理的核心是「挑对版本号」，本章说版本号只是提供者对兼容性的有损估计：规模一大，SemVer 加求解器会同时「管太严」又「保太松」。Google 的答案是能变成源码管理问题就别留成依赖管理问题，长远看让提供者用下游测试拿出证据——Live at Head。

Glossary · 术语表

  • 依赖（dependency）：你的代码要用到的别人的库或包；它自己用到的库叫传递依赖（transitive dependency）。
  • 依赖网络 / 依赖图：所有依赖及其相互需求连成的图，节点是库，边是「谁需要谁的哪些版本」。
  • API / ABI：API 是源码层面的接口约定；ABI 是编译好的二进制之间的约定，ABI 兼容意味着旧二进制不用重编就能接新库。
  • 源码管理 / 主干开发（trunk-based development）：大家都往同一条主线上提交，不长期维护分支（见第 16 章）。
  • 单体仓库（monorepo）：全公司代码放在一个仓库里。
  • CI（持续集成）：每次改动自动构建并跑测试（见第 23 章）。
  • Hyrum 定律（Hyrum's Law）：用户够多时，系统任何可观察的行为都会被某个人依赖（见第 1 章）。
  • pin（钉版本）：把依赖固定在某个确切版本上，不随上游变化。
  • CVE：公开登记的安全漏洞编号。

坐标

Part IV「工具」第六章，接在 Ch16 版本控制之后：Ch16 管自己能控制的代码，本章管管不着的代码；也为 Ch22「大规模变更」铺垫。现实对应：npm、pip、Maven、Cargo、Go modules 这些包管理器。

这章要解决什么

依赖管理管的是一张我们控制不了的库与包的网络：怎么在版本间升级、怎么描述版本、依赖允许做哪些改动、什么时候该依赖别的组织的代码。它和源码管理的分界只有一句话：这个子项目的开发和更新，是不是我们组织说了算？

源码管理里，你改一行就能跑测试、看到谁在用；依赖管理里，上游在你看不见的地方改动，更容易弄坏你的构建。规模一大，你依赖的是一整张网，总有某一刻两个依赖无法同时满足。作者坦承：Google 没有跨组织大规模验证过的好方案，本章很大程度上是在总结「什么不管用」。

核心内容，讲透

一、菱形依赖：一切冲突需求的原型

核心难题是冲突需求（conflicting requirements）：网络里两个节点对同一样东西有互斥的要求，而你同时依赖它们俩。最典型的形态是菱形依赖（diamond dependency），至少需要三层：

libbase 做了不兼容改动，liba 和 libb 分属不同组织、不会同时升级——一个要 v1、一个要 v2，libuser 就没有通用办法把它们拼起来。菱形可以出现在网络的任何深度。它比看上去更普遍：操作系统、语言版本、编译器版本这类要求，都同构于图里的一个隐藏节点。

Java 可以用 shading（把依赖的符号改名后各带一份）缓冲；C++ 几乎零容忍，两份定义违反单一定义规则（One Definition Rule），触发未定义行为。但改名只是半个解：一旦类型要跨依赖传递——v1 的 map 传给 v2 的 API——就无法语义一致。

撞上之后，只能前后挪版本找一组兼容的，不行就本地打补丁；而发现问题的人往往最不懂问题——只有同时拉进两者的你会撞上。若升级本就是安全漏洞逼的，降级也走不通。所以作者把整个领域归结为一个问题：怎么在互不协调的群体持续改动的前提下，避免冲突需求？

二、引入依赖：「能跑」和「被支持地跑」是两回事

复用当然比重写好——没人该自己写 JSON 解析器。但一旦把时间算进来，引入依赖就不是免费的：即使你无意升级，安全漏洞、平台变化、依赖网的演化也会逼你升级。那一天要花多少钱？取决于提供者的兼容性承诺。书里对比了四种：

  • C++ 标准库：几乎无限期向后兼容，连 ABI 都尽量保；gcc on Linux 上大部分代码约十年都能跑。
  • Go：多数版本之间承诺源码兼容，不承诺二进制兼容。
  • Abseil（Google 开源的 C++ 基础库）：不承诺 ABI；API 只做有限承诺——不会在不附带自动重构工具的情况下做破坏性 API 改动。Google 内部约 2.5 亿行 C++ 依赖它，最坏的升级成本应当只是「跑一下工具」。
  • Boost：不承诺版本间兼容，定位是试验场——与水平无关，只关乎承诺。

这里的关键区分是编程任务 vs 软件工程任务：只要今天能跑、永不升级，随便拿多少依赖、怎么违反约定都行；项目一旦要活很久，依赖就变贵。Google 鼓励引入前先问：有没有能过的测试、谁提供的、承诺什么兼容、要依赖多久、多久破坏一次，以及谁来升级、升级多难。作者承认：何时该引入、何时该自己写，没有公式，Google 自己也常常判断错。

Google 怎么做？答案是「本可以更好」。绝大多数依赖都是内部开发的，所以内部的依赖管理根本就是源码管理——这是刻意设计的。外部代码放进单体仓库的 third_party 目录，门槛很低：能编过、没有重复版本、至少两名 OWNERS。书里的 Alice 为休假前的演示引入一个包，拉同事 Bob 签了名；之后 Charlie 从搜索基础设施深处依赖了它，它悄悄成了关键依赖。某天爆出安全漏洞：Bob 转了管理岗，Alice 换了组，几千个项目间接依赖它，没人懂它，升级还要一口气跨过所有积压的版本。结论：提高所有权门槛，让定期升级更容易，让「无人维护却很重要」更难发生。

三、四种依赖模型：版本由谁来选

一个好方案要能在动态生态里（任何节点随时可能加入新依赖）避免冲突需求；如果还不假设版本稳定、组织间可见与协调、或海量算力，就是很好的方案。作者列出已知的四种：

  • 什么都不变（静态依赖模型）：不改 API、不改行为。每个组织都从这里起步，对新组织也合适；但时间够长它必然是假的，且没人知道还能假装多久。
  • 语义化版本（SemVer）：主.次.补丁三段号，主版本变代表可能破坏现有用法，次版本只加功能，补丁版只改实现细节。依赖写成「libbase ≥ 1.5」，由包管理器里的求解器选出一组满足所有约束的版本。找不到解，就是俗称的依赖地狱（dependency hell）。
  • 打包发行（bundled distribution）：像 Linux 发行版那样，由发行方挑出一组相互兼容的版本、打补丁、测试后整体发布。用户从「依赖 72 个库的这些版本」变成「依赖 Red Hat 第 N 版」。
  • Live at Head：主干开发在依赖管理上的延伸——取消 pin、放弃 SemVer，永远依赖所有东西的最新版；提供者提交前，先用下游的测试和 CI 实验性地验证改动安不安全。

四、SemVer 的局限：一份有损压缩

本章最尖锐的论点：版本号是提供者对「这个改动对旧用户有多兼容」的估计，而求解器把它当成 SAT 问题里非真即假的绝对值来用——我们在一块摇晃的地基上搭了整套版本求解逻辑。于是它会在两个方向上出错：

管太严：库里几乎总有彼此独立的接口。设想 libbase 只有 Foo、Bar 两个函数，liba 和 libb 只用 Foo。维护者改坏了 Bar，按规矩必须升主版本；求解器只认 1.x，于是拒绝 2.0——而实际上它们完全能一起工作。「破坏了就升主版本」这条压缩，只有在单个 API 的粒度上才准。

保太松：SemVer 假设改动只有三类——破坏、纯增加、不影响 API。那么给时间敏感的 API 加 1 毫秒延迟算哪类？改日志格式、改导入依赖的顺序、改「无序」流的返回顺序呢？按 Hyrum 定律，规模一大，这些都必然打破某个消费者的假设。所以「破坏性改动」一词本身有误导：删掉没人用的 API 理论上破坏、实际安全；Hyrum 式改动理论上安全、实际破坏。一个改动孤立地看无所谓破坏不破坏，只能放在「被怎么使用」里评估——而这正是 SemVer 公式里缺的信息。

还有激励问题：维护者升主版本只承担后果的一小部分。作者欣赏 Go 和 Clojure：主版本升级就该是一个全新的包。再加上人为失误——语义改动无法用工具判定，升哪一位终归靠人拍板。

五、最小版本选择：迈最小的那一步

2018 年 Google 的 Russ Cox 在为 Go 设计包管理时提出最小版本选择（Minimum Version Selection, MVS）。大多数求解器在需要升级下游时选最新版；MVS 反过来：liba 写着需要 libbase ≥ 1.7，就直接用 1.7，哪怕已有 1.8。道理是：写下「≥ 1.7」的人当时装的多半就是 1.7，只要他发布前做过最基本的测试，这一对组合至少被人试过。就像提交一小时的工作比一次倒进一年的安全，依赖也该每次只走到刚好够用。作者评价克制：这是对 SemVer 用法的明显改进，但能否让它「够用」尚无实证。

六、无限资源思想实验：证据取代估计

业界用 SemVer，是因为它只需要本地信息、不假设有测试和算力。可依赖网络只长在同一组织内或源码可见的开源生态里——下游怎么用你，信息本来就在。如果算力不是约束，「这个改动安全吗」的真相就来自跑一遍受影响的下游测试：都过了就是好改动，不需要分类、不需要估计。资源有限时，就优先跑使用量大、信号可靠的下游，目标放宽为「风险缓解」。

开源生态离这一步还差很多：并非所有依赖都有单元测试；包管理器大多看不到谁依赖它（反向边）；多数开发者没有测试集群；依赖普遍被 pin 住，没法拿改动去跑下游测试。再问「拿每个依赖的哪个版本来测」？测所有历史组合连 Google 也烧不起，最自然的简化是只测当前稳定版——于是无限资源下的最优解，恰好就是 Live at Head。剩下的问题是：资源有限时它是否仍然有效，提供者是否愿意担起测试责任。

七、导出依赖：开源一个库不是免费的善举

反过来，你的代码成为别人的依赖时同样有代价：维护不好伤声誉；内外版本不同步，任何分叉迟早都变贵。两个案例：

  • gflags：约 2006 年 Google 开源了 C++ 命令行参数库。当时做不了大规模重构，内部无法改用开源版，外部补丁也有法律问题合不回来；原作者离开后它逐渐腐烂，被外部另起分叉。约 2008–2017 年少数项目依赖了内外两版的公共子集；后来内部实现调整了「可观察但未文档化」的部分，这些项目全面报错，一项能省全集群累计几千颗 CPU 的优化被大幅推迟。
  • AppEngine：2014 年 Python 运行时升级与 C++ 编译器升级绑在一起推进，但付费客户不能或不愿迁移（包括负担不起 32 位到 64 位的资源变化）。于是 AppEngine 依赖到的所有 C++ 代码必须同时兼容新旧编译器，持续了将近三年。

结论：外部用户的 API 比内部用户贵得多。不是说别发布，而是别在没有长期支持计划和授权的情况下发布。

为什么重要 / 落到真实系统

作者认为依赖管理可能正在成为软件工程政策里最重要的问题。架构评审讨论「要不要引入这个包」「要不要拆多仓库」时，本章的判断是：同等条件下，宁要源码管理问题，不要依赖管理问题——把「组织」边界画大一点往往划算。面试里被问「SemVer 够不够」时，可以复述三个前提：提供者准确负责、依赖粒度细、所有用法都在预期之内；小规模能同时成立，大规模下很难长期都成立。

易错点与争议

  • 「补丁版本就是安全的」——不是。Hyrum 定律下，改顺序、改日志格式、改延迟都会打破某人；能写出精确到补丁号的约束，本身就说明补丁之间有可观察差异。
  • 「升了主版本就一定有破坏」——也不是。只改了你没用的接口，SemVer 会白白把你挡在依赖地狱里。
  • 「shading / 多版本共存能解决菱形依赖」——只解决一半。类型跨依赖传递时无解；C++ 里更是未定义行为。
  • 「签了 OWNERS 就有人维护」「开源是纯粹的善举」——Alice 与 gflags 说明都不是。
  • 争议与局限：Live at Head 作者自己承认「理论上成立、规模上未被证明」，严重依赖单体仓库、普遍测试与算力，难以直接搬到普通公司或开源生态；MVS 效果也未被实证。但「版本号是估计、测试才是证据」这一核心论点并未过时。

要点

① 依赖管理 = 管理我们控制不了的代码网络随时间的变化；与源码管理的分界是「这个子项目是否由我们组织说了算」。

② 同等条件下，宁要源码管理问题：Google 的内部依赖绝大多数本质上就是源码管理，这是刻意设计。

③ 菱形依赖是冲突需求的原型；shading 只是半个解，C++ 几乎零容忍。

④ 引入依赖对编程任务近乎免费，对软件工程任务不是：要看兼容承诺和谁来升级。

⑤ 四种模型：什么都不变、SemVer、打包发行、Live at Head——区别在于版本由谁来选。

⑥ SemVer 是人对风险的有损估计，求解器却把它当绝对值：既管太严（依赖地狱），又保太松（静默破坏）。

⑦ MVS 只往前走到刚好够用，最接近作者实际测过的组合；是改进，但未被实证。

⑧ 无限资源下，「安全与否」的真相来自下游测试——最优解恰好是 Live at Head，代价落在提供者身上。

⑨ 导出依赖同样昂贵：gflags 腐烂分叉、AppEngine 被锁近三年。
