Designing for Performance

A Philosophy of Software Design · Ch 20 · Designing for Performance · Ousterhout · 2nd ed 2021

中文 →

What is this chapter about?

You tap an app and it spins for three seconds — somewhere, a piece of code is "too slow." Many programmers believe that to be fast, code has to be twisted and hard to read. This chapter's author says the opposite: most of the time, clean and simple code is already the faster code.

A curious fact first

The author once tore down and rewrote a piece of his team's code that packs up messages, aiming to make it faster. The new version ran nearly twice as fast — and it was shorter. Here, fast and simple turned out to be the same thing.

Why it was hard before

Two common extremes both go wrong. Some people squeeze for speed from day one and turn the code into a tangle. Others ignore speed entirely, and when the system finally crawls they discover it is a little slow everywhere — with no single spot to fix.

How it works, intuitively

  • Know what is "expensive." Inside a computer, using what is close at hand is like pulling keys from your pocket; asking another machine over the network is like a long-distance phone call; reading an old spinning disk is like mailing a letter and waiting for a reply. The gaps are thousands of times.
  • Simple is fast in itself. Fewer detours and fewer "just in case" checks mean less work for the machine; convoluted code is often doing the same work twice.
  • If two roads are equally clean, take the faster one. It costs nothing extra — it is just a habit.
  • Measure before you change anything. Gut feelings about "where it's slow" are often wrong, like a surgeon operating without a blood test.
  • Speed up only the road most people take. Like a supermarket's "five items or fewer" express lane: most shoppers zip through, and the odd complicated cases go to a regular counter instead of making everyone wait in one long line.

What it buys you / how to choose

Day to day, write simply and pick the faster option when it costs nothing. When you truly need speed, measure where it's slow first, then make the most-traveled road short and straight. One honest cost: redesigning that main road often means tearing up existing structure, which is real work — so do it only after measuring shows it's worth it.

Remember it in one line

Simple is usually fast; to go faster, measure first, then straighten the road most traveled.

In one sentence

You think performance and clean code are enemies; this chapter's conclusion is that clean design and high performance are largely compatible, and complicated code tends to be slow — because it does extraneous or redundant work. The author's approach to performance compresses into three steps: develop a feel for what is expensive and pick the faster of equally clean options; measure before you modify; when you need a fundamental improvement, redesign around the critical path.

Glossary

  • Latency: how long one operation takes, measured in nanoseconds (ns), microseconds (µs), or milliseconds (ms); 1 ms = 1,000 µs = 1,000,000 ns.
  • Cache miss: the data the CPU needs isn't in its fast on-chip cache, so it must fetch it from slower main memory.
  • Dynamic memory allocation: asking the system for a block of memory while the program runs, e.g. malloc in C or new in C++.
  • Micro-benchmark: a small program that times one isolated operation.
  • Profiling: measuring how much time each part of a program takes, to find the "hot spots."
  • Critical path: the code that must run to complete a task in the most common case.
  • Special case: a situation that departs from the common case and needs an extra branch to handle.
  • Deep module: a Chapter 4 idea — a simple interface hiding a lot of functionality.
  • RPC (remote procedure call): asking another machine to run an operation and return the result, as if calling a local function.

Where it sits

Chapter 20. Right after Chapter 19 tests software fashions against complexity, this chapter tests another common excuse — "we had to make it complicated for performance." It leads into Chapter 21, "Decide What Matters." In practice it maps onto every review that asks "should we add a cache or a new structure to make this faster?"

The problem this chapter tackles

The first nineteen chapters urge you to write simple code. A fair question is: won't simple be slow? If the answer is yes, the book's advice collapses for performance-sensitive systems.

Real teams fail in two ways. One is optimizing everything: adding special branches, hand-rolled caches, and broken abstractions to save a few nanoseconds — the code becomes hard to read, and most of the savings land where they don't matter. The other is ignoring performance entirely: every module is "a bit slow," the system ends up several times slower, and there is no obvious hot spot to attack. The chapter offers a middle road: get most of the performance you need for the least complexity.

Core ideas, in depth

1. Performance thinking: an order-of-magnitude sense of what's expensive

The author does not recommend heavy performance work from day one, nor ignoring it. His approach: among several equally natural alternatives, pick the more efficient one — provided it is just as clean. To do that you need to know which operations are fundamentally expensive. The book names four:

  • Network communication: a round trip within a datacenter takes roughly 10–50 µs, tens of thousands of instruction times; a wide-area round trip takes 10–100 ms.
  • Secondary-storage I/O: a disk operation takes about 5–10 ms; flash, about 10–100 µs.
  • Dynamic memory allocation: malloc / new carry significant overhead for allocation, freeing, and garbage collection.
  • Cache misses: fetching from main memory costs a few hundred instruction times.

Knowing this gives everyday choices a basis. The author's examples: for a large table looked up by key, a hash table is typically several times faster than an ordered map; in C/C++, allocating an array of structures as one block usually beats allocating each separately and storing pointers. These choices are no more complicated — you just have to know. When unsure, write a micro-benchmark.

2. Simple and fast usually point the same way

This is the chapter's most counterintuitive line: simpler code tends to run faster. Three reasons. First, if you have defined special cases and exceptions out of existence (Chapter 10), no code is needed to check for them. Second, deep classes are more efficient than shallow ones: each call does more work and crosses fewer layers, and every layer crossing adds overhead. Third, complicated code often does extraneous or redundant work.

So what if the faster design really is more complex? The author weighs cost against payoff. If it adds only a little complexity and the gain is significant (say, adding a cache), it may be worth it. If it adds a lot of implementation complexity or complicates interfaces, start with the simpler approach and optimize later if performance becomes a problem. But if there is clear evidence that performance is the central goal, design for it from the start — the author's RAMCloud project aimed for the lowest possible remote-access latency, so it used networking that bypasses the operating-system kernel and talks to the network card directly, despite the extra complexity.

3. Measure before modifying

When a system really is too slow, "fixing it by intuition" is the most common mistake. Even experienced programmers' performance intuitions are unreliable, the author says; acting on them often spends effort where it doesn't matter while adding complexity. Measurement serves two purposes: finding the place where a change will have the biggest impact — knowing "what's slow" isn't enough; you want the point with the most leverage — and setting a baseline so you can re-measure afterward and confirm things actually improved. If a change makes no measurable difference, back it out — unless it also made the system simpler. Keeping it only keeps the complexity.

4. Design around the critical path

The best optimizations are often "fundamental": adding a cache, or switching algorithms (say, from a balanced tree to a hash table). When none is available, the author's method is to redesign around the critical path:

  • Ask what the ideal code looks like: in the most common case, what is the smallest amount of code that must run? Ignore the existing structure for now and imagine writing a new method that serves only the critical path. That ideal code is usually both simple and fast.
  • Evict special cases from the critical path: ideally, a single if at the start detects every special case, and everything else moves to a separate slow path. Reshape data structures if needed — for example, combining several scattered conditions into one value that can be tested once.
  • Then restructure the rest around it: add back all the functionality without disturbing the ideal critical path.

5. The example: RAMCloud's Buffer

RAMCloud is the all-in-memory key-value store built by the author's group; its Buffer class holds variable-length RPC request and response messages. A Buffer is made of memory chunks, whose storage either belongs to the Buffer (about 1KB inside the object, with more allocated as needed) or comes from outside (such as network packets).

In the old version, allocating new space — the most common operation — passed through several layers of method calls, each mostly forwarding arguments, with special-case checks along the way. The author rewrote it as a critical path: the common case needs just one test, "is there enough room at the end of the last chunk?" If so, carve the new region right there and return; every other situation — new chunks, insufficient space, external memory — goes to the slow path. The key operation got nearly twice as fast (the book measures about 8.8 ns down to 4.75 ns), and the new code was about 20% smaller. Performance and simplicity won together.

Rule of thumb: a performance change must clear two bars — does it measurably help? If not, back it out; is the complexity worth it? Changes that make the critical path shorter and straighter often win on both.

Why it matters / in real systems

The chapter's value is dismantling the "performance vs. readability" opposition: most of the time, deep modules with few special cases are exactly the fast code; the places that truly require sacrificing clarity are rare, and measurement should decide them.

Industry evidence · publicly verifiable

  • Google · Jeff Dean and Sanjay Ghemawat, "Performance Hints" (first published 2023, updated 2025) note that Knuth's "premature optimization is the root of all evil" is often quoted out of context; the full sentence continues, "Yet we should not pass up our opportunities in that critical 3%." They also push back on "write it as simply as possible and deal with performance later when we can profile": disregard performance while building a large system and you end up with "a flat profile where there are no obvious hotspots because performance is lost all over the place." Their advice: choose the faster alternative if it does not impact readability/complexity significantly — almost the same sentence as this chapter's first rule. Source: abseil/abseil.github.io · fast/hints.md
  • RAMCloud (Stanford) turned "performance is the core goal" into numbers: its README says data stays in DRAM at all times, so objects can be read remotely in as little as 5 µs, and writes take less than 15 µs. In its Buffer source, alloc() opens with exactly this chapter's fast-path test, commented "There is extra space at the end of the current last chunk, so we can just allocate the new region there." Source: PlatformLab/RAMCloud README · src/Buffer.cc

In daily work: when a review shows a complex change "for performance," ask for the measurements and the baseline; when choosing data structures, count network round trips, disk I/O, and allocations as the "expensive things"; when you inherit slow code, first ask "what is the least the common case must do?", then see what the existing code does beyond that. In an interview asked "how would you optimize this?", leading with measurement and then the critical path sounds far more experienced than reciting tricks.

Pitfalls and debates

  • "The author says don't care about performance." Wrong. He rejects both extremes and advocates a feel for costs plus picking the faster of equally clean options.
  • "Premature optimization is the root of all evil" is not a free pass. Knuth was talking about the ~97% of small efficiencies; Google's document warns that ignoring performance everywhere yields a flat profile. That agrees with the author's "pick the faster one day to day," but leans harder on early investment than his "if it's complex, start simple." The disagreement is over how much complexity is acceptable.
  • Critical-path redesign ≠ bolting on a fast path. Adding one more special branch to the old structure only adds complexity; the author first works out the ideal code, then reorganizes everything else around it.
  • Measurements can mislead. Micro-benchmarks time isolated operations and ignore cache state, concurrency, and more; re-measure changes under real load.
  • Numbers age. Specific costs shift with hardware (flash and networks keep getting faster), but the ladder of orders of magnitude is fairly stable — remember the ladder.
  • The examples lean toward systems software. RAMCloud is a microsecond-scale system; in business code where a request already takes tens of milliseconds, nanosecond-level critical-path gains may not justify a rewrite — measuring first still comes first.

Key takeaways

① Clean design and high performance are largely compatible; complicated code is often slow because it does extraneous or redundant work.

② Have an order-of-magnitude feel for what's expensive: network round trips, disk / flash I/O, dynamic memory allocation, cache misses.

③ Among equally clean options, pick the faster one — it costs almost nothing.

④ Small complexity for a big gain: do it. Big complexity: start simple. Performance as the core goal: design for it from day one.

⑤ Measure before modifying: find the point of greatest impact, keep a baseline; back out changes with no measurable gain.

⑥ Prefer fundamental fixes — a cache, a better algorithm; failing those, redesign around the critical path.

⑦ Critical path: write the ideal code for just the common case, guard every special case with one if, move the rest to a slow path.

⑧ Evidence: the RAMCloud Buffer rewrite ran nearly 2x faster with ~20% less code; Google's "Performance Hints" also says pick the faster option when readability doesn't suffer, and warns of the "flat profile."
