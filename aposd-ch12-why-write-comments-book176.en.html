Why Write Comments? The Four Excuses

A Philosophy of Software Design · Ch 12 · Why Write Comments? The Four Excuses · Ousterhout · 2nd ed 2021

中文 →

What is this chapter about?

You buy a new washing machine. The buttons say "Quick", "Heavy", "Delicate". From the buttons alone, can you tell whether "Quick" is fine for jeans, or whether detergent goes in first? The buttons tell you what exists; the manual tells you how to use it and why. Comments in a program are that manual. This chapter is about why many programmers skip them, and why each of their four reasons falls apart.

A strange thing first

Many programmers believe that "good code speaks for itself; it needs no comments." The author calls this a delicious myth, like a rumor that ice cream is good for your health: we would love to believe it, but it simply isn't true.

Why the old world was hard

Whoever writes code carries a lot in their head: why it was done this way, where the traps are, when not to use it. The code captures only part of that. If they don't write the rest down, it stays in their head; months later even they forget, and whoever comes next has to read the code line by line and guess. Guess wrong, and you get a bug.

How it works, intuitively

Four common excuses, and the author's answers:

  • "Good code needs no explanation." However clear a button is, it can't say "don't press me when the drum is full". Code can say what it does; it can't say why, or what to watch out for when using it.
  • "No time." Most of programming is thinking, trying and hunting bugs; actual typing is a small slice. A few extra lines of explanation cost a little now and save a lot later.
  • "Comments go stale and lie." They can, but fixing them is easy: the manual sits right next to the machine, so whoever changes the machine updates the sentence, and the colleague checking the change glances at it too.
  • "Every comment I've seen was useless." The most reasonable excuse: there really are a lot of empty comments. But that shows people never learned how to write them, not that they shouldn't. The next chapters teach how.

What it buys you / how to choose

Good comments move what's in the designer's head onto paper: the next person can use the code safely without reading all of it, and is less likely to hit traps they didn't know existed. One honest cost: comments do need to be maintained alongside the code, and left unattended they really do go stale.

One line to remember

Code says what it does; comments say what code can't. Without them, everyone else is guessing.

In one sentence

You think comments are a patch for code that isn't written well enough; Ousterhout says comments are part of the abstraction itself. Code can express only a small part of a design; the rest (what a method means, its edge cases, the rationale) can live only in comments. Not one of the four excuses for skipping them (good code is self-documenting, no time, they go stale, the ones I've seen are useless) holds up, and the act of writing comments improves the design.

Glossary

  • Comment: text in source code meant for people, not executed by the machine.
  • Interface: everything a user of a module must know; it includes parts that can be written in code and parts that can only be described in words.
  • Declaration / signature: a method's name, parameter types and return type; the small, formal part of the interface the code captures.
  • Abstraction: a simplified view of something that keeps what users need and hides the rest.
  • Shallow module: from Chapter 4, a module whose interface is complex relative to the little work it does.
  • Cognitive load and unknown unknowns: complexity symptoms from Chapter 2; the first is how much you must hold in mind to do a task, the second is not knowing what you need to know.
  • Code review: the process of colleagues checking a change before it is merged.

Where it sits

Chapter 12 opens the book's five-chapter run on comments: this one answers why write them; Chapter 13 covers what to write (things that aren't obvious from the code), 14 naming, 15 writing comments first, and 16 keeping them current when code changes. It builds on Chapter 2's diagnosis of complexity: comments are the main tool against obscurity. In practice it maps to API docs, docstrings, Javadoc and code-review norms.

What problem this chapter solves

The author observes that a significant fraction of commercial code, and an even larger fraction of open-source code, is poorly documented or not documented at all. Many developers sincerely believe that skipping comments is right, and their reasons sound respectable.

What happens if you don't fix this? The designer holds information the code cannot express, from a hardware quirk that explains a tricky stretch of code up to why a class exists at all. Unwritten, later developers must re-derive it or guess, which costs time and causes bugs when they guess wrong. And the "later developer" is often you: a few weeks away from a piece of code and you will have forgotten many of its details.

The core ideas, in depth

1. "Good code is self-documenting": the most tempting myth

The author calls it a delicious myth, like the rumor that ice cream is good for your health: we would like to believe it, but it isn't true. Good names and clear structure do reduce the need for comments, but a great deal of design information cannot be expressed in code:

  • Only a small part of an interface can be specified formally in code: the method signatures. What each method does and what its result means can only be described in words.
  • Rationale: why this approach and not another.
  • Conditions of use: when it makes sense to call this method.

The book's example: a method that extracts a substring takes two arguments, start and end. From the declaration alone you cannot tell whether the substring includes the character at end, or what happens when start > end. Those are exactly the things a caller most needs to know.

This leads to the chapter's central claim: comments are fundamental to abstraction. The point of an abstraction is to hide complexity; if users must read a method's code to use it, there is no abstraction, and all its complexity is exposed. Without comments, a method's only abstraction is its declaration, and the declaration is missing too much essential information.

Some say "if you want to know what a method does, read the code." Reading large methods is slow and painful; so some go further and make methods tiny, which produces lots of shallow methods (Chapter 4's anti-pattern) and still doesn't remove the need for comments. The author also stresses that comments are written in human language: less precise than code, but more expressive, so they can give simple, intuitive descriptions.

2. "I don't have time": the arithmetic is wrong

Something is always more urgent than comments, so they keep sliding down the list, and once documentation may be deprioritized, you end up with none. The author's rebuttal has two layers:

  • The investment mindset: Chapter 3 argues for spending roughly 10–20% of development time on design investment; good comments are part of that.
  • Do the sums: add up the time spent actually typing code (as opposed to designing, compiling, testing and so on) and the author doubts it exceeds 10% of total development time. Even if there is as much comment text as code, typing it probably adds no more than about 10% to the total.

More importantly, the most valuable comments are about abstractions: top-level documentation for classes and methods. Chapter 15 argues these should be written during design, where writing them is itself a design tool that exposes interface problems. Those comments pay for themselves immediately.

3. "Comments get out of date": a manageable maintenance problem

Comments do go stale, but the author argues this need not be a major problem in practice. Keeping them current doesn't take enormous effort: large documentation changes are only needed for large code changes, and the code changes will take far longer than the comment changes.

Two ways to keep the cost down (developed in Chapter 16): avoid duplicated documentation, so each fact lives in one place; and keep documentation close to the code it describes, so whoever changes the code sees it. On top of that, code review is a great mechanism for catching and fixing stale comments.

4. "All the comments I've seen are worthless": the one excuse with merit

The author concedes this one probably has the most merit of the four: every developer has seen comments that add nothing, and most existing documentation is mediocre at best. But the problem is solvable; writing solid documentation is not hard once you know how. The following chapters supply the method, whose core test is Chapter 13's: comments should describe what is not obvious from the code, not repeat it.

5. What good comments actually buy

The overall idea behind comments: capture information that was in the designer's mind but couldn't be represented in the code. Against Chapter 2's three symptoms of complexity (change amplification, cognitive load, unknown unknowns), good documentation helps mainly with the last two:

  • Lower cognitive load: give developers the information a change requires, and make it easy to ignore what's irrelevant, instead of reading large amounts of code to reconstruct what the designer was thinking.
  • Fewer unknown unknowns: clarify the system's structure so it's clear which information and code matter for a given change.

The author makes a larger claim too: written properly, comments improve the design; conversely, a good design loses much of its value if it is poorly documented.

Why it matters / in real systems

Major language communities all accept that comments are necessary, but stress different things about what to write: some warn against explaining implementation, others against stale comments, which map onto this chapter's first and third excuses.

Evidence and sources · publicly verifiable

  • The Ousterhout vs Robert Martin debate: Martin argues that every comment is a failure to use our languages to express intent, calls comments a "necessary evil", and says he doesn't trust them to be maintained; Ousterhout replies that comments are crucially important and that for him the cost of missing comments is easily 10–100x the cost of incorrect ones. Source: johnousterhout/aposd-vs-clean-code
  • Python PEP 8: its Comments section opens with "Comments that contradict the code are worse than no comments" and asks you to prioritize keeping comments up to date when code changes. It accepts the risk behind the third excuse, but the prescription is maintenance, not abstinence. Source: python/peps · pep-0008.rst
  • Linux kernel coding style: comments are good, but beware over-commenting; never explain HOW the code works in a comment, make the code obvious instead, since explaining badly written code is a waste of time. This points the same way as Chapter 13's "describe the non-obvious, don't repeat the code". Source: torvalds/linux · coding-style.rst

A line you can repeat in an interview or review: "The signature is the formal part of the interface, the comment is the informal part; together they make the abstraction." Today your code is also read by AI coding assistants, which likewise see only what has been written down.

Pitfalls and debates

  • "Commenting means explaining every line." No. The chapter wants information the code can't convey; comments that restate code are exactly where "all the comments I've seen are useless" comes from.
  • "Small enough methods need no comments." The author argues this just creates shallow methods whose signatures still lack information. This is his core disagreement with Clean Code, and the industry hasn't settled it.
  • "Comments go stale, so better not to write them." PEP 8 also says contradictory comments are worse than none, but concludes: maintain them, don't delete them. The author's accounting says missing beats wrong in cost by a wide margin.
  • "Lots of comments means a good job." Chapter 2 warned that a design needing extensive documentation to explain is often a sign the design itself isn't right. Comments are not a cover for a complicated interface.
  • "10%" is an estimate, not a measurement. The time accounting is the author's judgment and teams will vary, but the conclusion isn't sensitive to the exact figure.

Takeaways

① Designers hold much information the code can't express; comments get it out, or the next developer guesses, including you a few weeks later.

② Comments are fundamental to abstraction: a signature is a small part of the interface; meaning, boundaries, rationale and conditions of use need comments.

③ The substring example: the declaration doesn't say whether end is included or what happens when start is greater than end.

④ Forcing readers into the implementation means no abstraction; chopping into tiny methods only makes shallow ones.

⑤ No time: typing is under 10% of development time, comments add roughly 10% at most; once deprioritized, they go to zero.

⑥ Stale: upkeep follows code changes; avoid duplication, keep docs near code, use code review.

⑦ All useless: the excuse with most merit; the fix is learning to write the non-obvious.

⑧ Good comments mainly reduce cognitive load and unknown unknowns, and writing them improves the design.

⑨ The split with Clean Code is a public debate: whether missing or wrong comments cost more decides which side you're on.
