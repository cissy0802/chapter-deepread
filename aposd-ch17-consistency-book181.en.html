Consistency

A Philosophy of Software Design · Ch 17 · Consistency · Ousterhout · 2nd ed 2021

中文 →

What is this chapter about?

You can find the checkout and the exit in almost any supermarket within seconds, because supermarkets are laid out in much the same way. Software works the same. In a program with hundreds of thousands of lines, if the same kind of thing is always done the same way, a newcomer who learns it once can read it in a hundred places. This chapter is about that: consistency, and why "I have a better idea" is usually not a good enough reason to break it.

An analogy

Think of a city's traffic lights: red means stop and green means go, everywhere, so drivers never have to think about it. Now one engineer decides blue is more visible and makes blue mean stop at their intersection. Blue may really be more visible, but every driver in town will make mistakes at that corner. A good idea that differs from everything around it becomes a trap.

Why the old way is hard

Software is written by many people over many years. Everyone has habits, and each habit makes sense on its own. The result is three or four ways of doing the same thing. Readers must work out each spot from scratch. Worse, they guess based on what they learned elsewhere, guess wrong, and a bug slips in.

How it works, intuitively

  • Similar things are done the same way. Names, layout, how errors are handled: one pattern, learned once.
  • Different things should look different. Forcing two genuinely different things into the same shape misleads the reader.
  • When in Rome. Before changing someone's code, look at how the code around it is written, and write it the same way.
  • Write the rules down, then let a machine watch. People forget; automatic checks don't. And when reviewers point out small slips, everyone learns fast.
  • If you change the way, change it everywhere. Changing only half just adds one more way.

What it buys you / how to choose

Code becomes faster to read, mistakes become rarer, and people spend their energy on real problems instead of arguing about style. One honest cost: sticking to the rules sometimes means living with an old approach that is not the best.

One line to remember

Do similar things the same way; "I have a better idea" is not enough unless it is good enough to change every old place too.

In one sentence

You might think consistency is just a tidiness preference; Ousterhout treats it as a powerful tool for reducing complexity: when similar things are done in similar ways and dissimilar things in different ways, readers get leverage — learn once, apply everywhere. The price is discipline: having a "better idea" is not a sufficient excuse to introduce inconsistencies.

Glossary

  • Convention: a team's shared default for how a kind of thing is written, such as a naming format or a way of handling errors.
  • Coding style: rules about indentation, brace placement, declaration order, naming and comment format, usually collected into a style guide.
  • Interface: what a module promises to its users; one interface can have several implementations.
  • Design pattern: a well-known solution to a common kind of problem, such as model-view-controller in user interfaces.
  • Invariant: a property of a variable or data structure that is always true, for example "every line of text ends with a newline."
  • Cognitive load: from Chapter 2, how much a developer needs to know to complete a task.
  • Code review: colleagues read and comment on code before it is merged.
  • Pre-commit check: a script that runs before code enters the repository and rejects the commit if it fails.

Where it sits

Chapter 17, in the book's later group on making code obvious. It builds on Chapter 14, "Choosing Names" (consistent names are a special case), and Chapter 16, "Modifying Existing Code" (keep existing conventions when you change things), and leads into Chapter 18, "Code Should be Obvious" — consistency is one of the main sources of obviousness.

What problem this chapter tackles

Chapter 2 named three symptoms of complexity: change amplification, cognitive load and unknown unknowns. Inconsistency worsens the last two at once. Picture a service maintained by a 20-person team with three ways of handling errors: some functions return error codes, some throw exceptions, some return null. For every function a reader must first figure out which camp it belongs to. Worse, they guess based on the camp they know best, miss a call that never throws but quietly returns null, and the error is swallowed.

Such inconsistency rarely comes from laziness. It usually comes from good intentions: everyone believes their own way is better. The chapter answers three questions: what consistency buys; how to keep it in a codebase touched by many people over many years; and when and how it may be broken.

The core ideas, in depth

1. Consistency is leverage

The central claim: consistency creates cognitive leverage. Once you have learned how something is done in one place, you can immediately understand every other place that does it the same way. Without consistency, each place has to be learned separately.

It also reduces mistakes. In a consistent system, developers can safely assume that something that looks like X really is X, and the assumption holds. In an inconsistent one, the same assumption walks people into traps. That is why the author files consistency among the tools that make code obvious: readers can guess correctly without studying the details.

2. Five places consistency shows up

  • Names: covered in Chapter 14 — the same name always means the same kind of thing, and the same kind of thing always gets the same name.
  • Coding style: indentation, braces, declaration order, naming and comment format, plus restrictions on dangerous language features. Style guides make code easier to read and can prevent some errors.
  • Interfaces: an interface with several implementations is itself consistency — once you understand one implementation, the others are easier, because you already know what they must provide.
  • Design patterns: using a well-known pattern lets readers recognize what the code is doing at a glance; inventing a fresh approach to the same problem throws that benefit away.
  • Invariants: a property that always holds cuts the special cases a reader must consider. If every line of text is guaranteed to end with a newline, text-handling code never has to ask whether the last line does.

3. Four ways to keep it

Consistency is hard to maintain, especially on projects with many people over many years: one group doesn't know another's conventions, newcomers don't know the rules, and they introduce new, conflicting conventions. The author's remedies:

  • Document: list the most important overall conventions in a document, such as a style guide, somewhere developers will find it, and encourage newcomers to read it. More local conventions go into comments in the relevant code.
  • Enforce: the author's preferred approach is a tool that checks for violations, set up so that code cannot be committed unless it passes. People forget; tools don't.
  • When in Rome…: look around before writing. Adding a method? Check how existing methods order their parameters, name things and handle errors, and follow suit.
  • Code reviews: another checkpoint for enforcing conventions and teaching them to newcomers. As the author puts it, the more nit-picky the reviewers, the faster the team learns the conventions and the cleaner the code.

4. Don't change existing conventions lightly

The sharpest rule in the chapter: don't change existing conventions. You may think the old approach is flawed and have a better one in mind. But, the author argues, the value of consistency over inconsistency is almost always greater than the value of one approach over another. Use the new approach only in your new code, and the system now has two ways; every reader must remember both.

When is a change allowed? The bar is high: first ask whether the new approach is good enough to be worth the time to update all the old uses. If it is, update all of them. If you won't or can't update them all, don't introduce it. Afterwards, update the documentation and the checking tools as well, so the new convention is the only one.

5. Don't take it too far

The flip side matters just as much: dissimilar things should not be forced to look alike. Reusing a variable name for things that behave differently, or squeezing a problem into a design pattern that doesn't fit, creates false consistency — readers believe the things are the same when they are not, which is worse than obvious inconsistency. Consistency is only valuable because developers can trust that if something looks like X, it really is X.

6. Consistency is an investment

The author closes by placing consistency within the investment mindset of strategic programming: keeping things consistent takes extra effort — learning the conventions, writing checkers, nit-picking in review, migrating old code — but it pays back on every later read and change, which become faster and less error-prone.

Rule of thumb: hand every convention a tool can check to a tool, and spend review attention on the parts that need judgment. Local consistency matters more than global — two styles within one file or one set of related interfaces do the most direct damage.

Why it matters / in real systems

Almost every large engineering organization's style guide puts consistency above any specific rule, and formatters plus static checks have turned "enforce it with a tool" into everyday infrastructure.

Industry evidence · publicly verifiable

  • Google C++ Style Guide lists "be consistent with existing code" among its goals: one style across the codebase lets people focus on more important issues, and consistency is what lets automated tools work. It says many consistency rules boil down to "just pick one and stop worrying about it" — the value of flexibility is outweighed by the cost of people arguing. It also draws a boundary: consistency is a good tie breaker when there is no clear technical argument, applies more heavily locally (per file, or a tightly related set of interfaces), and should not be used to justify an old style without considering the benefits of the new one. Source: Google Style Guides · cppguide.html (Goals of the Style Guide)
  • Python PEP 8: "Consistency with this style guide is important. Consistency within a project is more important. Consistency within one module or function is the most important." But also "know when to be inconsistent" — for instance when following the rule makes code less readable, or to match surrounding code that also breaks it — and above all, don't break backwards compatibility just to comply with PEP 8. Source: PEP 8 · A Foolish Consistency is the Hobgoblin of Little Minds
  • Effective Go: formatting issues are "the most contentious but the least consequential," so Go lets the machine take care of most formatting — gofmt emits one standard style; if its answer doesn't seem right, rearrange the program or file a bug about gofmt, don't work around it. That is this chapter's "enforce" taken to its limit. Source: Effective Go · Formatting

In practice: spend half an hour learning an unfamiliar codebase's conventions before changing it; encode team conventions in formatters and lint rules wired into pre-commit and CI; in review, separate what tools can police from what needs a human; and when an AI assistant edits code, ask it to imitate the surrounding code rather than apply its own preferences.

Pitfalls and debates

  • "Consistency means uniform formatting." Formatting is the shallowest layer; consistent interfaces, patterns and invariants help understanding far more and are harder to enforce with tools.
  • "New code uses the new way; old code will fade out." By this chapter's standard, that is exactly how inconsistency is born: without a real migration, two styles coexist for years.
  • "Consistency trumps everything." No. Forcing dissimilar things to look alike is false consistency, and Google's guide warns that consistency shouldn't be an excuse to reject a better new style.
  • Tension with PEP 8. The chapter leaves almost no room for local exceptions; PEP 8 explicitly allows deviations when a rule hurts readability or to match surrounding code. Both agree that local consistency comes first.
  • "More nit-picky reviews are better" has limits. The author favors picky reviewers, but a flood of small comments drains both sides; handing mechanical checks to tools and leaving judgment to people is the more common engineering practice.
  • Migration cost is understated. In a very large codebase, "update every old use at once" may be impractical; industry relies on automated refactoring tools or staged migrations, which the book doesn't cover.
  • The evidence is experiential. As with the whole book, the conclusions come from the author's engineering and teaching experience, not controlled studies.

Key takeaways

① Consistency is a powerful tool against complexity: do similar things similarly and dissimilar things differently.

② It creates cognitive leverage — learn once, understand everywhere — and makes "looks like X, is X" a safe assumption, so fewer mistakes.

③ It shows up in five places: names, coding style, interfaces, design patterns, invariants.

④ Keep it by documenting, enforcing with tools (no commit unless it passes), following local custom, and nit-picky code review.

⑤ "I have a better idea" is not enough to introduce inconsistency: consistency is almost always worth more than one approach's edge over another.

⑥ To change a convention, it must be worth updating every old use — and you must actually update them all.

⑦ Don't overdo it: making different things look the same is false consistency that misleads readers.

⑧ Local consistency matters most; give every mechanically checkable convention to a tool.

⑨ Real-world echoes: Google's style guide, PEP 8, Go's gofmt; like strategic programming, consistency is an investment.
