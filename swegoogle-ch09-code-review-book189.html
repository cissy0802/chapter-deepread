代码评审

Software Engineering at Google · Ch 9 · Code Review · Tom Manshreck & Caitlin Sadowski · 2020

EN →

这一章讲什么？

你在 Google 搜索、YouTube 背后用到的每一行代码，在上线前都被至少另一个工程师读过并点头。这条规矩叫「代码评审」：写完代码不能直接放进公司的大仓库，要先交给同事看。这一章讲 Google 怎么做这件事，以及它真正换来了什么。

打个比方

像报社的稿件。记者写完稿，先给编辑看：编辑挑错别字、查事实，但更重要的是确认「读者看得懂」。同时，这个版面的主编要点头「这篇适合放我们版」；还有一位老编辑负责看文风合不合报社规范。三个人可以是同一个人，但三个问题都得有人回答。

先说个怪事

大多数人以为评审主要是为了抓 bug。可 Google 自己的研究发现，评审最大的收益反而是那些「看不见」的：让代码被至少两个人懂、让全公司的写法保持一致、让新人在一次次评审里学会门道。抓 bug 只是其中一项。

旧世界为什么难

一段代码写一次，却要被很多人读、改上好多年。如果只有作者自己懂，作者一换组，这段代码就成了没人敢碰的「黑箱」。几万人各写各的，整个代码库会越来越像一锅大杂烩。

核心机制直觉

  • 改动要小：一次只交一小份，像交一页作业而不是一整本，同事半小时就能认真看完，而不是硬着头皮扫一遍。
  • 回复要快：别让作者干等，最晚第二天早上就给答复；慢的评审比没有评审更伤人。
  • 三把钥匙：同事确认「看得懂、写得对」，这块代码的主人确认「放这里合适」，懂语言规范的人确认「写法合规」。
  • 对事不对人：代码不属于某个人，属于团队；评论针对代码，语气保持礼貌。
  • 机器先过一遍：格式、常见错误交给自动检查，人只看机器看不出来的东西。

带来了什么 / 该怎么选

你的团队要不要评审？只要代码要活好几年、不止一两个人维护，就值得做，关键是保持改动小、回复快。诚实的代价是：评审要花每个工程师每周好几个小时，做慢了会让人等得心烦。

一句话记住

评审不是在抓坏人，是在确保每一行代码，至少有两个人懂。

一句话

你以为代码评审是「上线前抓 bug 的关卡」；本章说，它首先是让代码被另一个人理解的机制——正确性只是收益之一，更大的回报是可理解、一致、知识扩散和团队文化；而让它在几万人规模下跑得动的，是小改动、快回复、三重批准各司其职、能自动化的全自动化。

Glossary · 术语表

  • 改动 / 变更列表（change / CL）：一次要合入代码库的修改，Google 内部叫 CL（changelist），相当于 GitHub 的 pull request。
  • 快照（snapshot）：作者上传给评审看的某一版代码；改了一轮就再传一版快照。
  • LGTM：「Looks Good To Me」，评审者表示「我看过了、没问题」的标准回复。
  • OWNERS 文件：目录里列出「谁对这块代码负责」的文本文件，所有者可以批准改动进入该目录。
  • 可读性认证（readability）：Google 内部的语言级认证，持有者能为某语言的写法与风格把关（见第 8 章）。
  • 单体仓（monorepo）：全公司代码放在同一个仓库，任何人都可能改到别人的代码。
  • 静态分析（static analysis）：不运行程序、只读源码就能找出可疑写法的自动工具。
  • 回滚（rollback）：把一次已合入的改动撤销，恢复到改之前的状态。

坐标

Part III「流程」第二章。上承 Ch8 风格指南（规则由谁来人工执行——就是评审），下启 Ch10 文档与 Ch11 起的测试；Ch19 再讲承载这套流程的工具 Critique。现实对应：任何 GitHub / GitLab 上的 pull request 流程。

这章要解决什么

Google 单一代码库里有数万名工程师同时改代码，工程师频繁换组。本章开宗明义一个反直觉的立场：代码是负债（code is a liability），不是资产。每多一行，就多一份未来要读、要改、要排错的成本；真正的资产是代码提供的功能。所以把一段代码放进库里，应该像做一笔长期投资一样慎重。

不评审会怎样？代码只有作者一人懂，作者离开就成了没人敢动的黑箱；写法各自为政，库越来越难读；危险写法、缺测试的改动静静地流进主干。可评审也有代价——Google 的研究里，工程师每周平均花约 3 小时在评审上；如果流程慢、改动大、评论粗暴，它会变成全公司的速度瓶颈。本章要回答：评审该检查什么、谁来批准、怎么做才不拖慢几万人。

核心内容，讲透

一、流程：一个改动怎么走到主干

Google 的评审流程本身很朴素，跟 pull request 大同小异：

  • 作者写改动，在自己的工作区里生成一份快照，上传到评审工具（Critique）。工具会先跑自动检查、给出评论，作者可以先自查一遍 diff。
  • 发给评审者（原书叫 mail out），评审者在 diff 上逐行留言。评论分两种：必须改的，和「可选 / nit」的小建议。
  • 作者修改，上传新快照、回复每条评论，循环直到大家满意。
  • 拿到批准：评审者给出 LGTM，并且所需的三类批准都齐。
  • 提交：所有评论都已解决（resolved）后，作者才能把改动提交进主干。

二、三重批准：把三个问题拆开问

本章最有辨识度的设计：一个改动要合入，需要回答三个不同的问题，每个问题对应一种批准：

  • LGTM——正确吗、看得懂吗？由另一位工程师给出，确认代码做了它声称的事，而且另一个人能读懂。这一位不必是专家，往往就是同组同事。
  • 所有者批准——放在这里合适吗？由该目录 OWNERS 文件里的人给出。所有者对这块代码的长期健康负责，判断这个改动是否符合该模块的方向。
  • 可读性批准——写法合规吗？由持有该语言可读性认证的人给出，确认符合 Ch8 的风格与最佳实践。

为什么拆开？因为三个问题需要的专长不同：读懂代码人人能做，判断模块方向需要所有者，语言惯用法需要专门训练的人。拆开之后，每个人只为自己那一个问题负责。但实际上大多数改动并不需要三个人——一个人同时具备三种资格就能一次给齐，常见改动通常只有一位评审者。这既保证了把关的完整性，又不让流程成本随问题数翻倍。

三、五大收益：抓 bug 只是其一

  • 正确性：在合入前截住缺陷——越早发现，修复越便宜。但本章提醒，大部分「正确性」工作应交给测试和自动检查，评审是补充。
  • 可理解性：作者永远觉得自己的代码好懂；评审者是第一位「未来读者」，他读不懂，以后的人也读不懂。本章把这点看得比挑 bug 还重。
  • 一致性：可读性批准让全库写法统一，让人员流动、工具改写都更容易（呼应 Ch8）。
  • 心理与文化收益：评审传达「代码属于团队，不属于个人」；它也是一种认可——有人认真看过你的工作；还能温和地纠正「闭门造车」。
  • 知识分享：评审是 Google 最主要的知识传播渠道之一——新人通过评论学到惯用法和系统细节，评审者也在读代码的过程中了解别处在发生什么。

四、五条最佳实践：让评审在几万人规模下不卡

  • 礼貌与专业：评论针对代码不针对人；评审者若对方案没有实质异议，应尊重作者的做法，而不是强推自己偏好的写法；作者则把评论当成改进而非攻击，每条都回应。
  • 写小改动：这是最重要的一条。小改动容易读、容易回滚、评审者能认真看。Google 的工程实践指南给的量级是：约 100 行通常合适，1000 行通常太大。
  • 写好改动描述：第一行一句话说清改了什么，正文说清为什么——它会成为版本历史里长期留存的记录。
  • 评审者越少越好：多数改动一位评审者足矣；多拉一个人，收益递减，等待时间却叠加。
  • 能自动化的全自动化：格式、静态分析、presubmit 测试在人看之前就跑完，人只看需要判断的部分。

五、四类评审，打法不同

  • 全新代码（greenfield）：最需要严审。设计应在写代码前已评审过；代码评审确认 API 与设计一致、有测试、有合适的所有者——因为新代码一旦进库，就是一笔长期负债。
  • 行为变更、改进与优化：大多数改动属于此类，关注它是否真的必要、是否有对应测试，性能优化要有基准数据说话。
  • 修 bug 与回滚：修复要聚焦，别顺手夹带别的改动；应附上能复现 bug 的测试。回滚要快——它的目的就是止血。
  • 重构与大规模变更（LSC）：往往由工具自动生成、横跨成百上千个目录。评审者只需确认「这个改动在我这块代码上是安全的」，不必重新审议整体方案（Ch22 展开）。

为什么重要 / 落到真实系统

今天几乎所有公司都在用 pull request 做评审，本章给的是「为什么这样做」和「怎么做才不变成瓶颈」。GitHub 的 CODEOWNERS 文件、受保护分支上的「必须至少一个批准」，本质就是 OWNERS 与 LGTM 的翻版；Chromium 等 Google 开源项目至今沿用 OWNERS 文件。面试或架构评审被问「怎么保证代码质量」，好答案不是「严格评审」，而是「小改动 + 快评审 + 自动化前置 + 所有权明确」。

大厂实证 · 公开可查

  • Google · 评审的最高原则：Google 公开的工程实践指南写道，只要一个改动「明确改善了所在系统的整体代码健康，即使不完美」，评审者就应倾向批准，并称这是「所有评审准则中最高的原则」；同文还说「不存在『完美』代码，只有更好的代码」。google/eng-practices · The Standard of Code Review ↗
  • Google · 一个工作日：同一指南规定「回应一个评审请求最多一个工作日」，并提出「LGTM with comments」——剩下的只是小问题时先批准，免得作者为一句 LGTM 再等一天。google/eng-practices · Speed of Code Reviews ↗
  • Google · 小改动的量级：指南给出「约 100 行通常是合理的 CL 大小，1000 行通常太大」，并强调涉及的文件数也算「大小」。google/eng-practices · Small CLs ↗
  • Google · 评审的真实动机：Sadowski 等人的《Modern Code Review: A Case Study at Google》（ICSE SEIP 2018）调研了 Google 内部评审，发现工程师把教育、维护规范、把关和防止意外列为动机，而不只是找缺陷；Google 的改动普遍很小、多数只有一位评审者、周转很快。论文：ICSE SEIP 2018（文字出处）
  • 反方视角 · Microsoft：Bacchelli 与 Bird 的《Expectations, Outcomes, and Challenges of Modern Code Review》（ICSE 2013）发现，开发者期望评审主要用来找缺陷，但评审实际产出更多是知识传递、团队认知和替代方案——与本章「抓 bug 只是其一」的判断互相印证。论文：ICSE 2013（文字出处）

易错点与争议

  • 「评审主要是抓 bug」——误解。本章与 Google、Microsoft 的研究都指向同一结论：可理解性、一致性和知识扩散才是大头；指望评审代替测试，两头落空。
  • 「评审越严越好」——错。追求完美会让改动卡上好几天；Google 的尺度是「明确更好就批」，小问题用可选评论或 LGTM with comments 处理。
  • 「大改动一次评完更省事」——反了。大改动评审者只能扫读，问题反而更容易漏；也更难回滚。
  • 评审者把偏好当标准。作者的方案只要合理、合规，评审者就该放行；把「我会这么写」当成拒绝理由，是最常见的摩擦源。
  • 多拉人不等于更安全。多评审者会出现「别人会看的」心理，等待时间叠加，收益却递减。
  • 语境局限。三重批准依赖 Google 的单体仓、OWNERS 体系和可读性认证；小团队照搬会变成纯流程负担。开源项目里评审者是志愿者，「一个工作日」也难保证。

要点

① 代码是负债而非资产，所以每一行入库前都要被另一个人读懂并认可。

② 流程：快照 → 发出 → 评论 / 修改循环 → 批准 → 评论全解决 → 提交。

③ 三重批准：LGTM（正确且可懂）、所有者（放这里合适）、可读性（写法合规），可由一人兼任。

④ 五大收益：正确性、可理解性、一致性、心理与文化、知识分享——抓 bug 只是其一。

⑤ 五条实践：礼貌专业、写小改动、写好描述、评审者越少越好、能自动化就自动化。

⑥ 量级：约 100 行合适、1000 行太大；最晚一个工作日回复；多数改动一位评审者。

⑦ 尺度：明确改善代码健康即批准，不追求完美；尊重作者的合理方案。

⑧ 四类评审：新代码严审、行为变更看必要性和测试、修 bug 要聚焦带测试、大规模变更只确认局部安全。

⑨ 易错：评审不能代替测试；越严越多人不等于越好；Google 的三重批准带着规模前提。
