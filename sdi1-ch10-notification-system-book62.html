设计通知系统

System Design Interview Vol 1 · Ch 10 · Alex Xu · 2020

EN →

这一章讲什么？

手机屏幕上弹出的那一条「你的包裹已派送」「有人回复了你」，背后是一整套通知系统。这一章讲怎么把它造出来——听起来像件小事，其实是全书里最典型的一堂课：你要负责的事情，最关键的那一步却不在你手里。

打个比方：三个不听你指挥的邮差

把通知系统想成一个快递总站。信是你写的，但最后一公里必须交给三家外包邮差：给苹果手机送的（苹果家）、给安卓手机送的（谷歌家）、发短信的（运营商）。麻烦在于，这三家只认自己的规矩：

苹果家说：人不在家时，我只帮你留最新的那一封，之前的直接扔；谷歌家说：我最多帮你存 100 封，超了全扔，而且存四个星期没送出去也扔。它们还都不给你「本人已签收」的回执——只告诉你「信我收下了」。

旧办法为什么撑不住

最朴素的做法：下单成功后，代码顺手就去敲邮差的门，等他回话再往下走。三个坏处一个比一个疼：邮差回话慢一秒，你的下单接口也跟着卡一秒；负责跑腿的那台机器一挂，所有通知凭空蒸发；大促当天通知涨了几十倍，你想加人手都插不进去。

核心办法：中间加一条传送带

做法是在中间放一条传送带。业务那边只管把「要发什么、发给谁」丢上传送带就走人，几毫秒的事；传送带另一头站着一排工人，慢慢取、慢慢跑腿。这样邮差再慢也慢不到你的主流程上。

关键是传送带要按邮差分开：苹果一条、安卓一条、短信一条、邮件一条。短信那家今天堵了，只堵短信这一条，推送照跑；短信忙不过来，就只给短信那条加工人。一条堵死不牵连另外三条，这是整章最值钱的一句话。

还得管三件小事

光有传送带不够，还有三件必须自己管住的事：开关——发之前先查这个人愿不愿意收这类通知；编号——每封信贴一个唯一编号，工人送之前查一下「这个号送过没」，送过就扔掉（因为跑腿失败要重试，重试就一定会重复）；上限——每人每天最多几封。第三件最容易被忽略，代价却最狠：用户被烦到把通知权限一关，你以后连「支付成功」都送不到了，而且这扇门他多半不会再打开。

诚实的代价：加了传送带，通知就不再是「立刻」——正常几百毫秒到几秒，堵车时可能几分钟；而且你只能做到「至少送到一次」，重复得靠编号自己挡。

一句话记住

通知系统难的不是「怎么发出去」，是最后一公里在别人家：三方通道不保证送达、也不保证只送一次。你唯一能管住的是自己这一侧——用传送带把业务和跑腿隔开、按通道各走各的、每条信编个号防重复，以及别把用户烦到关掉开关。

一句话

这一章表面在教「怎么把一条消息推到用户手机上」，实际是一堂依赖不可控外部通道的可靠性课：最后一跳交给 APNs / FCM / 短信网关，你既不能保证送达、也不能保证只送一次，于是所有工程手段全部前移到你自己这一侧——用消息队列把业务与投递解耦、按通道隔离故障、用幂等键挡住重试带来的重复、用用户设置与频率上限守住「别把用户烦到关掉通知权限」这条不可逆的底线。

Glossary · 术语表

  • 推送通知（push notification）：由服务端主动送到用户设备、无需用户打开 app 的消息。
  • 设备令牌（device token）：苹果 / 谷歌发给某台设备上某个 app 的一串唯一地址；服务端拿着它才知道「推给谁」。换机、重装、卸载都会让它失效。
  • APNs（Apple Push Notification service）：苹果的推送通道，所有发往 iOS 设备的推送都必须过它。
  • FCM（Firebase Cloud Messaging）：谷歌的推送通道，对应 Android。
  • 短信网关 / 邮件服务商：Twilio、Nexmo（短信），SendGrid、Mailchimp（邮件）——按量收费的第三方。
  • 扇出（fan-out）：一条输入放大成多条输出。这里是「一条通知 → 一个用户的多台设备 → 多次调用」。
  • 消息队列（message queue）：生产者丢进去就返回、消费者（worker）另一头慢慢取的缓冲区；作用是解耦、削峰、缓冲。
  • 幂等（idempotency）：同一个操作做一次和做多次结果一样。做法通常是给每次操作一个唯一 ID，重复的直接丢弃。
  • 至少一次 / 恰好一次（at-least-once / exactly-once）：投递语义。前者允许重复但不丢，后者不重不丢——分布式下后者几乎做不到。
  • 死信队列（dead letter queue，DLQ）：重试若干次仍失败的消息被挪进来的「垃圾桶」，只供人工查证。
  • 指数退避（exponential backoff）：重试间隔按 1 秒、2 秒、4 秒……翻倍，避免一群客户端同时重试把下游打死。

坐标

本章是卷一 Part II「系统案例」的第 7 篇。它上承 Ch8 短网址、Ch9 爬虫那条「大规模读写与调度」的线，下启 Ch11 信息流——两章都是扇出问题，区别在于扇出的终点：本章扇到你控制不了的第三方通道，Ch11 扇到你自己的收件箱。现实里它对应的是几乎每个 To C 产品都会长出来的那套 notification platform（LinkedIn 的 ATC、Netflix 的 Pushy、各家的推送中台）。

这章要解决什么

先把规模摆出来。书里给的估算量级是：每天 iOS 推送 500 万、Android 推送 1000 万、短信 100 万、邮件 500 万，合计约 2100 万条 / 天，平均下来只有 243 条 / 秒——听起来毫无压力。

但均值在这里是最没用的数字。通知是典型的尖峰负载：一次面向 500 万人的营销推送，若要求 5 分钟内送完，瞬时就是 16,700 条 / 秒，是均值的 近 70 倍；一次线上故障告警要在 30 秒内触达所有值班人。系统必须按峰值设计，按均值付钱。

不做这套设计会坏在三处。拖垮主流程：下单后同步调 APNs，第三方正常 200ms、偶尔 5s，你的下单接口 p99 跟着被拽上去。静默丢失：通知只活在内存里，进程一重启，那条「支付成功」就永远不存在了，而且没有任何人会发现——通知丢失是所有故障里最安静的一种。把用户逼走：重试写得糙，同一条推送发 5 遍，用户顺手关掉通知权限——这是本章唯一不可逆的失败。

核心内容，讲透

收件人不是「用户」，是「设备」

第一步是把联系方式收上来：用户安装 app 或登录时，客户端向 APNs / FCM 换取本机的 device token，交给 API 服务器落库。数据模型是一对多——user 表（user_id、邮箱、手机号）配 device 表（device_id、user_id、device_token、最近登录时间）。

这里藏着一个常被跳过的关键点：推送的收件人粒度是设备，不是人。一个用户手机 + 平板 + 旧手机三台在线，一条通知就要扇出成三次第三方调用。于是设备数而非用户数才是真正的负载参数——按人估算容量会低估两三倍。

另一半是回收。token 会因卸载、换机而失效，APNs 会回 410 Unregistered、FCM 回 UNREGISTERED。必须拿这个回执把死 token 删掉，否则两件事同时恶化：白白消耗调用配额，以及送达率统计被稀释到失真——而送达率是你判断「某条通道是不是坏了」的唯一外部信号。

朴素版的三个死穴

最直接的做法是：各业务服务 → 一台通知服务器 → 直接调三方 → 设备。它死在三处：单点故障（那台机器挂了，全站通知停摆）、扩不动（模板渲染、图片附件、三方 SDK 全挤在一台机器上）、强耦合（第三方一慢，上游业务一起慢）。

这里有个反直觉的点值得算一笔：压垮朴素版的往往不是 QPS，是第三方的延迟方差。假设单机 200 个并发线程、三方平均耗时 200ms，理论吞吐 1000 条 / 秒；一旦短信网关抖动、耗时涨到 5s，同样 200 个线程的吞吐立刻掉到 40 条 / 秒——掉了 25 倍，而你的 CPU 还闲着。线程全被堵在等待上，这是同步直连架构的根本病灶。

骨架：用队列把「产生」和「投递」切开

改造分三刀。一：把数据库和缓存从通知服务器移出去，让服务器无状态——无状态才能水平扩容、才能自动伸缩。二：在服务器与第三方之间插入消息队列，写完队列就返回，主流程耗时从「等三方回话」压回一次入队的 1–5ms。三：每个通道一条独立队列，各配一组 worker 专职消费。

为什么是一通道一队列，而不是一条大队列加个 type 字段？两个理由，都很硬：

  • 故障隔离：短信网关挂了，SMS 队列开始堆积，而 APNs / FCM / 邮件三条照常流动。共用一条队列的话，堆在队首的短信会把后面所有类型的消息一起堵死（队头阻塞）。
  • 独立伸缩：四种通道的耗时差一个数量级（推送几十毫秒、短信几百毫秒、邮件可能几秒），需要的 worker 数完全不同。分开才能各扩各的。

队列还顺带给了可观测的抓手：书里点名队列积压长度是这套系统最该盯的指标。可操作的判据是 积压条数 ÷ 出队速率 = 预计清空时间——一旦超过你的通知时效目标（比如 60 秒），就该扩容或降级，而不是等用户来投诉。

System Design · Day 8 消息队列 — 队列到底提供了什么：削峰、解耦与投递语义，以及积压与消费者组该怎么监控和扩

可靠性三件套：不丢、不重、不烦

不丢，靠落库 + 重试。入队前先写一条通知日志（notification log）记下 event_id、收件人、通道、状态；worker 调用失败按指数退避重试（1s / 2s / 4s…），到上限后进死信队列并告警。诚实的代价：一条通知从 1 次网络调用变成「写库 + 调用 + 更新状态」，写放大 2–3 倍；换来的是事后能回答「这条到底发出去没有」——没有日志，你连追查的起点都没有。

不重，靠幂等，因为 exactly-once 根本做不到。网络超时时你分不清是「三方没收到」还是「三方收到了但回包丢了」，重试就必然产生重复。唯一的解法是把责任接到自己这边：每条通知带全局唯一 event_id，worker 发送前先做一次原子的「见过没」检查（Redis SET key NX EX，或数据库唯一索引），见过就丢弃。TTL 要覆盖整个重试窗口——重试窗口 24 小时，去重键就至少存 24 小时，存短了等于没做。

不烦，靠用户设置 + 频率上限。设置表很简单（user_id、channel、opt_in），关键是校验要前置到入队之前：否则队列里塞满根本不该发的东西白吃吞吐，而且用户中途关掉开关，队列里的旧消息照样会发出去。频率上限的理由书里说得很直白——用户被烦到会直接关掉系统级通知权限，那扇门关上就基本不会再开。折中做法是「入队前粗筛 + 发送前复查」，后者兜住那几秒内的设置变更。

System Design · Day 23 可靠性 — 重试、退避与抖动、熔断与降级怎么组合，才不会让一次下游抖动被重试放大成雪崩

模板、鉴权、追踪：最容易被面试漏掉的三件

模板：一条「订单已发货」要出中英日三语 × 推送 / 短信 / 邮件三通道 = 9 个变体；模板把不变的骨架与可变的参数分开，改一处全站生效。鉴权：调通知 API 要带 appKey / appSecret，否则任何拿到内网地址的人都能借你的通道向全体用户广播。追踪：送达率、打开率进分析系统——这不只是产品需求，三方返回 200 只说明它收下了，送达率骤降才是「通道坏了」的唯一外部信号。

关键权衡与选型

这一章的真正选型不在架构图上，而在两个地方：走哪条通道，以及你打算把「重复」的责任放在哪一侧。

还有一处常被追问：业务侧是同步调通知 API，还是直接写队列？直接写队列最快，但校验只能后移到 worker，发现参数错时消息已在队列里。多数团队选同步调一个极薄的通知 API——只做校验 + 入队、1–5ms 返回，把脏数据挡在门外，又不引入等待第三方的耗时。

为什么重要 / 落到真实系统

这套骨架不是教学模型，它就是真实公司里那个叫「消息中台 / notification platform」的东西。面试里被问到通知系统，能把这四点说清楚基本就过了：一通道一队列（故障隔离）、event_id 幂等（重复责任在自己）、用户设置前置校验、队列积压监控（唯一有效的健康信号）。真实系统在此之上还多长了一层——决定「这条到底该不该发」的智能层，那才是各家最花力气的地方。

大厂实证 · 这些主张不是书里说的，是公司自己公开说的
  • Apple 的 APNs 文档写明：apns-expiration 非零时，APNs 会存储该通知并至少尝试投递一次、按需重复直到过期；设为 0 则只尝试一次且不存储——说明「重试与丢弃的规则由第三方定，不由你定」。Apple Developer Documentation《Sending notification requests to APNs》↗
  • Google 的 FCM 文档给出了离线堆积的硬上限：设备离线时最多存 100 条不可折叠消息，超过就把已存的全部丢弃；消息默认最多保存 4 周——坐实了「推送通道不承诺送达」这一前提。Firebase Cloud Messaging 文档《Non-collapsible and collapsible messages》↗
  • LinkedIn 的 Air Traffic Controller（ATC）把通知做成一条 Samza 流处理管线，按「5 Rights」——对的人、对的内容、对的通道、对的时间、对的频率——逐条决策，并做重复合并与频率封顶——正面验证了本章「用户设置 + 限流」不是可选项，而是通知系统的核心逻辑。LinkedIn Engineering《Air Traffic Controller: Member-First Notifications》↗
  • Netflix 走了另一条路：自建 WebSocket 长连接网关 Pushy，绕开第三方通道直接推到设备，规模已达数亿级并发连接、常态每秒约 30 万条消息——说明「自建通道」在足够规模下是真实可行的替代方案，代价是你要自己扛住连接管理与运维。Netflix TechBlog《Pushy to the Limit》, 2024 ↗
System Design · Day 15 聊天系统 — 自建长连接那条路怎么走：接入层怎么维持千万级 WebSocket、消息怎么定序，以及离线时怎么退回推送通道

易错点与争议

  • 把「三方返回 200」当成「用户收到了」——最常见的误解。200 只表示 APNs / FCM 收下了请求；之后设备离线、被折叠、被丢弃、被关掉权限，你一概不知道。
  • 追求 exactly-once：最后一跳在别人家，端到端「恰好一次」不可得。正解永远是 at-least-once + 幂等键。
  • 不回收失效 token：既浪费配额，又让送达率统计失真——你会因此错判某条通道的健康度。
  • 用户设置只在 worker 侧查：队列里会塞满不该发的消息，且设置变更管不到存量。要「入队前粗筛 + 发送前复查」。
  • 书里没展开的两块，恰恰是真实系统最难的：一是该不该发的智能决策（相关性打分、合并、择时——LinkedIn ATC 那一层）；二是跨通道降级与去重（推送没点开就转短信，转完推送又被看到了怎么办）。本章给的是骨架，不是全部。
  • 时代局限：书成于 2020 年。此后 GDPR / 个人信息保护法对营销通知的明示同意要求，把「用户设置」从产品功能变成了合规红线；Web Push、RCS 也成了新通道。骨架依旧成立，但「该不该发」的约束比书里写的硬得多。

要点

① 核心命题：通知系统的难点不在「怎么发」，而在最后一公里不归你管——三方通道不保证送达、不保证不重复，所有工程手段只能前移到自己这一侧。

② 收件人粒度是设备不是用户：一人多机意味着一条通知扇出成 N 次调用，容量要按设备数估；失效 token 必须靠 410 之类的回执主动回收。

③ 朴素的同步直连死于三处：单点、扩不动、强耦合；压垮它的是第三方的延迟方差而非 QPS（三方从 200ms 抖到 5s，单机吞吐掉 25 倍）。

④ 骨架三刀：服务器无状态化、插入消息队列、一通道一队列——后者换来故障隔离与独立伸缩，短信挂了不牵连推送。

⑤ 最该盯的指标是队列积压长度：积压 ÷ 出队速率 > 时效目标，就该扩容或降级。

⑥ 可靠性三件套：不丢（落库 + 指数退避 + 死信队列，代价是写放大 2–3 倍）、不重（event_id 幂等，去重键 TTL 必须覆盖整个重试窗口）、不烦（用户设置前置 + 频率上限）。

⑦ 投递语义只能是 at-least-once + 幂等；exactly-once 端到端不可得，说得出这一点比画对架构图更能证明你懂。

⑧ 通道选型是确定性 / 成本 / 时效的三角：推送最便宜最不确定、短信最贵最及时、站内信是唯一你能完全掌控的兜底通道。最贵的失败是不可逆的那种——用户关掉通知权限后连验证码都送不到，所以频率上限不是产品洁癖，是可靠性设计。
