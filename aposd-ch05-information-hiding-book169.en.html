Information Hiding and Leakage

A Philosophy of Software Design · Ch 5 · Information Hiding (and Leakage) · Ousterhout · 2nd ed 2021

中文 →

What is this chapter about?

The previous chapter said good parts should be "deep": easy to use, doing lots of work behind the scenes. This chapter answers the obvious next question: how do you build a deep part? The answer is one of the oldest and best ideas in software: lock each "how it's done" secret in one place, and don't let it scatter. When you fill in a web form and hit "Submit," the program on the server gets your name with a single line of code. How it dug that name out of a long stream of bytes is something the app developer never has to know.

A strange thing first

A program has three jobs: read a file, change a few things, write it back. The obvious split follows the steps: a "reader" part, a "changer" part, a "writer" part. Looks tidy. Then one day the file format changes, and you discover the reader and the writer both have to change; miss one and things break. Splitting by steps quietly split one secret into two copies.

Why the old way is hard

When people write programs, the first thing that comes to mind is "what happens first, what happens next." So many systems get cut along the lines of a flowchart. The trouble is that several steps often need the same piece of knowledge: the same file format, the same shape of a network message. Once that knowledge is copied into several parts, it's like a recipe handed to three cooks: change the recipe and you must tell all three, and nobody warns you if you forget one.

How it works, intuitively

  • Each part guards one secret. Like a safe: the secret stays locked inside, with only a slot to put things in and a slot to take things out.
  • If only one part knows the secret, only one part changes. Swap in a better way of doing it and nobody outside notices.
  • Leakage = the same secret living in two parts. The worst kind is a "back door": two parts that seem to have nothing to do with each other, yet both secretly carry the same recipe.
  • Split by "what you need to know," not by "what happens first." If reading and writing both need the file format, let one part do both.
  • The best features are the ones you don't know exist. A good part does the right thing on its own, like answering in the same "dialect" the other side spoke, without being told.

What it buys you / how to choose

It gives you a new question for carving up a system: not "how many steps is this," but "which decision here might change later, and who alone should guard it?" Split that way, each change lands in one place, and newcomers only need to learn the front door. One honest cost: hide too much and it backfires; if something the outside really needs is locked away, users are left stuck.

Remember it in one line

One secret lives in one part. Split by who needs to know what, not by what happens first.

In one sentence

You'd think module boundaries should follow "what happens first, what happens next"; Ousterhout says they should follow knowledge: each module encapsulates a few design decisions that others can't see and don't need to know. That is information hiding, the single most important technique for building deep modules. Its opposite is information leakage: the same design decision shows up in several modules, so changing it means changing all of them.

Glossary

  • Module / interface / implementation: from Chapter 4. A module is a unit of code with an interface; the interface is everything a user must know, the implementation is the code that keeps the promise.
  • Design decision: a choice made while implementing something, such as which data structure to use, what a file format looks like, or which algorithm to run.
  • Dependency: when one piece of code changes, another piece must be re-read or changed too.
  • Private field: a variable inside a class that outside code can't touch directly; often paired with getters and setters that read or write it from outside.
  • HTTP request: the text a browser sends to a server: a request line and headers first, then possibly a body.
  • Query string: the part of a URL after the ?, like ?q=book&page=2, commonly used to pass parameters.
  • URL encoding: URLs can't contain raw spaces and some other characters, so they're written as %20 or +; the server must decode them back.
  • Content-Length: an HTTP header stating how many bytes the body has, so the receiver knows where to stop reading.
  • Default: the choice a module makes on its own when the caller doesn't specify one.

Where it sits

Chapter 5, right after Chapter 4's "Modules Should Be Deep": the previous chapter sets the goal, this one gives the main means. It inherits directly from David Parnas's classic 1972 paper and is taught through real mistakes Ousterhout saw grading student HTTP-server projects in his Stanford software design course (CS 190). Chapter 6 then asks how general-purpose an interface should be. In practice it maps to every review where someone asks, "should this class be split into a reader and a writer?"

What problem this chapter tackles

Chapter 2 named change amplification as a key symptom of complexity: a seemingly simple change requires edits in many places. The root cause is often not messy code but the same knowledge held separately by several modules. Take a file format: the reading module knows it, the writing module knows it too. Add one field to the format and both must change; miss one, and the program may still compile, only to read back wrong data at runtime.

Worse, such dependencies are often invisible: neither class mentions the other in its interface, and nothing in the code structure shows they're tied together. This chapter asks: what exactly should a module hide? What counts as leakage? And why is the most natural split, "by steps," the one most likely to leak?

The core ideas, in depth

1. Information hiding: each module guards a few design decisions

Ousterhout's typical "secrets": how to store data in a B-tree and access it efficiently; how to find the physical disk block for each logical block of a file; how to implement the TCP protocol; how to schedule threads on a multicore processor; how to parse JSON. A secret can be a data structure or algorithm, a lower-level detail (like a page size), or even a higher-level assumption (like "most files are small").

Information hiding cuts complexity from two directions:

  • Simpler interfaces: the interface reflects an abstract view of the functionality and exposes no details, so users carry less cognitive load. This is where Chapter 4's "depth" comes from.
  • Easier evolution: if a decision lives in one module, changing it touches only that module.

A common misconception, dismantled on the spot: declaring a field private is not information hiding. Add a set of getters and setters that hand out the internal data as-is, and outside code still depends on its shape. The test is whether users need to know the decision, not whether the syntax lets them touch it.

Hiding can also be partial: if a feature is needed by only a few users and reached through separate methods, it is invisible to most users. Partial hiding still has value.

2. Information leakage: one decision in two places

Leakage is the opposite of hiding: a design decision is reflected in more than one module, which creates a dependency between them; changing the decision means changing all of them. It comes in two forms:

  • Leakage through an interface: if a piece of information appears in a module's interface, it has by definition leaked. Sometimes unavoidable, but the less the better, and the simpler the interface the better.
  • Back-door leakage: the information appears in no interface, yet two modules each know it. The book's example: two classes both understand the same file format, one to read it, one to write it. Their interfaces are unrelated, yet a format change forces both to change. Ousterhout calls this more pernicious than interface leakage, because it isn't visible in the code.

Two fixes: if the affected classes are small and closely tied to the information, merge them into one class; otherwise pull the information out into a new class that alone owns it and exposes a simple interface that abstracts the details away. Replace the back door with a front door. "Information leakage" is one of the book's red flags: the same knowledge used in multiple classes.

3. Temporal decomposition: the most natural trap

Temporal decomposition splits a system by the order in which operations happen. Same example: a program reads a file, modifies it, writes it back, so it gets split into a reader class, a modifier class and a writer class. Reading and writing both need the file format, so that knowledge leaks into two classes.

Why is it so common? Because the order of execution is the first thing in your head when you write code, and flowcharts are naturally drawn as steps. The "first decomposition" Parnas criticized in 1972 is exactly this. Ousterhout's rule: when designing modules, focus on the knowledge needed to perform each task, not the order in which tasks occur. Order matters, and it should show up in some caller's code, but it should not decide module boundaries. Red flag: temporal decomposition.

4. Case study: student HTTP servers

The CS 190 assignment is a simplified HTTP server: receive requests, hand them to the application, send responses back. Ousterhout groups the students' most common mistakes, and they illustrate the chapter neatly.

Mistake one: reading and parsing as two classes. Many teams used one class to read a request off the network into a string and another to parse the string: textbook temporal decomposition. The catch: you can't know where to stop reading without parsing. The reader must find the end of the headers and read Content-Length to know how long the body is. So both classes must understand HTTP request structure; the format leaked, and callers must invoke two methods in a fixed order. Merged into one class, the code got shorter and the interface simpler. Hence a counterintuitive conclusion: information hiding can often be improved by making a class slightly larger, an echo of the previous chapter's attack on "smaller classes are always better."

Done well: the parameter interface. The best designs offered getParameter(name), returning an already-decoded string. It hides two things: a parameter may come from the query string in the request line or from the body, and its value must be URL-decoded (for example + becomes a space). The application developer needs to know neither. The counterexample: some teams returned their internal Map<String, String> directly. That's shallow and exposes the internal representation, so changing how parameters are stored would ripple into every caller. Better still to add getIntParameter(name), which also hides the integer conversion and its error checking.

Mistake two: no defaults. Some teams required callers to specify the HTTP protocol version when building a response. The response version should simply match the request's, and the class can do that by itself. Ousterhout's principle: defaults are partial information hiding and should make the common case as simple as possible; a class should "do the right thing" without being asked, and the best features are the ones you get without even knowing they exist. Red flag: overexposure, when the API for a commonly used feature forces users to learn about features that are rarely used.

5. Hiding within a class, and hiding too much

Information hiding isn't only between classes. It applies inside a class too: design private methods so that each encapsulates some piece of information or capability, and minimize the number of places where each instance variable is used. The fewer places touch a variable, the fewer dependencies inside the class.

But you can hide too much. Hiding only makes sense when the information isn't needed outside the module. If a configuration parameter strongly affects performance and users genuinely need to tune it for their situation, it must be exposed. Ousterhout's ideal is a module that computes the best setting itself (better not to expose it at all); when that's impossible, recognize honestly which information the outside needs, and expose as little as possible. This is the same line as Chapter 4's "false abstraction": hide what's unimportant, expose what's important.

One rule of thumb: before drawing boundaries, list the decisions likely to change, and give each exactly one owner. If any change request makes you say "this means editing both A and B," there's a leak between A and B.

Why it matters / in real systems

In interviews and design reviews, "information hiding" beats "encapsulation" because you can test it: if the format, protocol, or storage changed tomorrow, how many files would you touch? More than one means a leak. The same question scales up to services (an extension, not from the book): two microservices reading and writing the same database table is back-door leakage across services; neither API mentions the other, and a schema change breaks both.

Evidence and sources · publicly verifiable

  • Parnas: split by decisions likely to change. In 1972 Parnas compared two decompositions of the same KWIC index program: by processing steps (a flowchart) and by design decisions. His conclusion was to begin with a list of difficult design decisions, or decisions likely to change, and design each module to hide one such decision from the others. This chapter's "temporal decomposition" is exactly the first decomposition he criticized. Source: D. L. Parnas, On the Criteria To Be Used in Decomposing Systems into Modules, CACM 1972
  • Go's FormValue: the parameter source behind one call. The Go docs state that Request.FormValue returns the first value for the named component, merging three sources in a fixed precedence: a URL-encoded form body (POST, PUT, PATCH only), query parameters, and a multipart form body. The caller writes one line. Source: pkg.go.dev · net/http (Request.FormValue)
  • Defaults in the same library. The same docs state that if WriteHeader hasn't been called, Write calls WriteHeader(http.StatusOK) first; if there's no Content-Type header, it infers one from the first 512 bytes; and automatic headers such as Date are added unless you explicitly set them to nil. That's "do the right thing without being asked." Source: pkg.go.dev · net/http (ResponseWriter)

Pitfalls and debates

  • "Private fields mean information hiding." No. Getters and setters that hand out the internal structure as-is still create dependencies; the question is whether users need to know.
  • "Single responsibility means one class per step." Treating "read" and "parse" as two responsibilities is exactly what creates temporal decomposition. Divide responsibilities by knowledge, not by step.
  • "Leakage is only about interfaces." The most dangerous kind is back-door leakage: spotless interfaces, yet both sides share one format assumption. In review, ask "who else knows this?"
  • "Information hiding means hiding everything." Hiding what the outside truly needs (performance knobs, when data hits disk) is a false abstraction.
  • "Merging classes violates the small-class rule." Ousterhout explicitly argues that information hiding can often be improved by making a class slightly larger; the test is whether knowledge is concentrated, not line count.
  • Debate: sometimes order is the knowledge. Pipelines and compiler phases (lexing, parsing, code generation) look like temporal decomposition yet work well, because the intermediate representation between phases is itself a carefully designed interface and each phase really does know different things. Order itself isn't the sin; knowledge leaking across stages is. The book doesn't expand on this, so draw the distinction yourself in reviews.

Key takeaways

① Information hiding is the main way to build deep modules: each module encapsulates a few design decisions others can't see.

② It cuts complexity two ways: simpler interfaces, and easier evolution (a decision change touches one module).

③ Private fields ≠ information hiding; getters and setters that expose internal structure still leak.

④ Leakage = one decision reflected in several modules; back-door leakage (invisible in interfaces) is the most pernicious.

⑤ Fix: merge small classes, or extract the knowledge into a new class with a simple interface, turning the back door into a front door.

⑥ Temporal decomposition is the most common trap: split by the knowledge each task needs, not the order tasks occur.

⑦ HTTP case: merge reading and parsing; getParameter hides parameter source and URL decoding; returning the internal Map is the counterexample.

⑧ Defaults are partial hiding: make the common case zero-config, have classes do the right thing unasked; overexposure is a red flag.

⑨ Don't over-hide: expose what the outside truly needs, and auto-tune when you can.
