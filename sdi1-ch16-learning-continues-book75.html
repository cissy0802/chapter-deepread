学习的延续

System Design Interview Vol 1 · Ch 16 · Alex Xu · 2020

EN →

这一章讲什么？

你手上这本书，前面十五章教的都是同一件事：面试官说「设计一个微信」「设计一个 YouTube」，你怎么在白板前当场把它画出来。最后一章突然不教题了。它给了你一份清单——真实公司自己写下来的、「我们这套东西到底是怎么搭的」那类文章，外加几十家公司的技术博客地址。然后说了一句：接着读下去。

打个比方

你照着一本菜谱练了十二道菜，每道都练熟了。现在客人点了第十三道，菜谱上没有。你会不会做，取决于你学到的是十二套固定动作，还是「火候怎么看、下锅什么顺序、咸了怎么救」。这一章想把你送进的，是真实后厨：不是干净的菜谱，是有人手忙脚乱临时改方案的现场。

旧世界为什么难

自学搭系统，最难的不是找不到资料，是资料的形状不对。教科书给你干净的原理，练习题给你干净的题面——两边都把最值钱的东西删掉了：当时的限制。真实项目里选了甲没选乙，往往不是因为甲更好，而是因为当时只有三个人、机器就那么多、下个月必须上线。这些在题面上一个字都看不到。

它怎么做到的

办法说穿了很朴素：去看人家写下来的那一份。过去二十年里，大公司养成了一个习惯——把自己踩过的坑写出来公开。不全是因为慷慨：写出来能招到人、能让同行帮着挑毛病、能让自己的做法变成行业里的默认选项。于是有了两类东西。一类是一篇文章讲透一个系统的来龙去脉：我们当初怎么做的、做到多大就撑不住了、后来改成什么、改完付出了什么代价。另一类是公司博客，隔三差五更新一篇，让你不掉队。这一章做的事，就是把这两类东西的入口一次性列给你。

该怎么用

最有效的用法不是从头读到尾——那是读不完的，也不必读完。而是每练一道题，就去找同一个问题的真实版本对一遍：你刚自己设计完一套发通知的系统，就去读某家公司讲他们怎么发通知的那篇，看两边哪里不一样、为什么不一样。不一样的那几处，才是你真正学到的东西。

代价要说清楚：这些文章几乎只写成功了的那一版，中间失败的三次不会写；而且从写下的那天起就开始过时——五年前那份清单里，今天有些链接已经点不开了。

一句话记住

题会做完，清单不会。把「自己练一道题」和「读一个真实系统怎么做的」配成一对，一直重复下去，这一章就算读对了。

一句话

你以为这是全书的励志收尾，其实它是唯一一章在承认：前十五章的答案会过期，读真实系统的习惯不会。这一章没给新方法，给的是一份语料库——几十篇公司自己写下的架构文章（Amazon 的 Dynamo、Google 的 GFS 与 Bigtable、Facebook 的 TAO 与 Haystack、Twitter 的 Snowflake……）加几十家工程博客的入口，外带一句「熟能生巧」。提纯出来只有一条可操作的主张：把「做一道设计练习」和「读一个真实系统的公开资料」配成一对，用后者去校准前者里那些你根本不知道自己在瞎猜的地方。

Glossary · 术语表

  • 工程博客（engineering blog）：公司官方开的技术专栏，由自家工程师写自家系统，更新持续、时效最好。
  • 会议论文（paper）：投到 SOSP / OSDI / NSDI 这类学术会议、经过同行评议的正式文章，机制完整、有实验数据。
  • 事后复盘（postmortem）：一次线上故障之后写的公开报告——发生了什么、为什么、怎么防再犯。行业里少数专门写失败的文体。
  • QPS：每秒请求数，衡量系统负载最常用的那个数字。
  • 单体（monolith）与服务化：整个产品打成一个程序部署叫单体；拆成多个各自部署、互相调用的小程序叫服务化。
  • 分片（sharding）：一台数据库装不下或扛不住时，把数据按某个键切开放到多台机器上。
  • 幸存者偏差（survivorship bias）：你看到的都是活下来的样本，于是高估了那条路的成功率——公开架构文章的通病。
  • 链接腐烂（link rot）：一份清单里的网址随时间陆续失效，公司改名、迁站、删文都会造成。
  • 架构决策记录（ADR，architecture decision record）：把「为什么选了这个方案、放弃了什么」写成一条条留档，是把读来的东西沉淀成自己资产的常见形式。

坐标

卷一第 16 章，全书最后一章。Ch1–3 给方法（扩展阶梯、粗略估算、四步框架），Ch4–15 给十二道案例练习，Ch16 回答的是练习用完之后怎么办。它不对应任何一道题，对应的现实问题是：一个工程师在没人带的情况下，怎么把架构判断力养成长期能力。

这章要解决什么

读完前十五章的人会撞上一个很具体的坎：第十六道题。书给的题库是有限的，而且从写下那天起就在贬值——它成书于 2020 年，里面的容量数字、中间件选型、云服务报价，今天都得重算一遍。

不解决会怎样？两种失败都很常见。一种是把系统设计背成了模板：题面一改约束就塌——「如果只给你三台机器呢」「如果写比读多十倍呢」「如果这些数据受监管、不许出境呢」。面试官恰恰专挑这种追问，因为它一问就能分开「背过」和「懂了」。另一种失败更贵：面试过了，进了公司真要做架构决策时，手里只有十二个干净的参考答案，而真实项目从来不干净。这一章的回答不是再给十道题，是换语料。

核心内容，讲透

这一章的真身：一份两层的公开架构语料库

把这一章拆开，实质内容只有两类东西，分工相当明确。

第一层是点名的单篇：一篇文章或一篇论文，讲透一个系统。清单里点名的包括 Amazon 的 Dynamo、Google 的 GFS 与 Bigtable、Facebook 的 TAO（社交图数据存储）与 Haystack（照片存储）、Twitter 的 Snowflake 公告与「一亿五千万活跃用户的架构」、「A Brief History of Scaling LinkedIn」、「Scaling Pinterest」、Uber 实时撮合平台、Dropbox 的扩展历程、WhatsApp 的架构等等。共同点：一篇读完，你拿到的是一条完整的决策链。

第二层是几十家公司的工程博客入口（Airbnb、Dropbox、Etsy、Facebook、Google、LinkedIn、Netflix、Pinterest、Slack、Stripe、Uber、Yelp……）。单篇给深度，博客给增量与时效。

一句话概括这个分工：单篇是教材，博客是订阅。教材把一件事讲透一次，订阅让你别在三年后还在讲三年前的做法。

为什么公开资料比题库有营养：约束、拐点、代价都写在里面

练习题给你的是终局——「设计一个短网址服务」，然后是一张最终架构图。真实文章给你的是轨迹：我们一开始这么做 → 做到某个量级出问题 → 改成了什么 → 新代价是什么。差别不在信息量，在有没有那个「撑不住」的拐点。

而拐点几乎就是架构判断力的全部。知道一个设计怎么工作是入门；知道它在什么量级、因为什么原因失效才是能拿来做决策的知识。「读缓存命中率掉到 80% 以下时数据库就被打穿」「单表过一亿行之后这个查询的 p99 从 20 毫秒涨到 2 秒」——这种句子在教科书和题面里都不会出现，只在真人写的复盘里出现。LinkedIn 那篇讲的是从一个叫 Leo 的单体 Java 应用一路拆出去的过程，它的价值也不在最终架构长什么样，在于每一步是在什么压力下、什么时候做的。

可操作的判据：一篇读完，如果你说不出它放弃了什么，就等于没读。

清单的隐藏结构：把 Ch4–15 的每道题挂到一个真实系统上

原书这份清单是按公司排的，但它和前十五章其实能一一对上——对上之后才真正好用：

  • Ch6 设计键值存储 ↔ Dynamo：quorum、向量时钟、反熵这一整套，源头就是这篇论文。
  • Ch7 唯一 ID ↔ Twitter Snowflake：Ch7 从头到尾讲的就是它的结构。
  • Ch11 信息流 ↔ Facebook 的 TAO：扇出与社交图读放大的真实形态。
  • Ch12 聊天系统 ↔ WhatsApp 架构：长连接接入层在真实规模下的样子。
  • Ch14 YouTube ↔ YouTube 可扩展性的公开演讲。
  • Ch1 扩展阶梯 ↔ Scaling LinkedIn / Scaling Pinterest：书里那七级台阶，这两篇是它的实录。

这不是巧合：前十五章的题面本来就是从这类公开资料里提炼出来的。所以最高效的读法不是照清单顺序啃，而是做完哪道题就读哪一篇——你刚在白板上亲手做过一轮取舍，再去看真人当时怎么取舍，差异会自己跳出来；反过来先读文章再做题，你只会复述它。

怎么把一篇架构文章读成能复用的东西

原章只给了清单、没给读法——这是它最大的缺口。下面这套四问是本页的补充，不是书里的内容，但它补的正是「读完之后什么都没留下」这个真实问题。每读一篇，问一遍：

  • ① 约束是什么？当时多少用户、多少 QPS、几个人的团队、什么预算、什么截止日期？脱离约束的架构决策没法评价，也没法搬运。
  • ② 拐点在哪？哪个数字撑不住了才动手改的？「用户到五百万时主库的写入打满了」这种句子，通常是全文最值钱的一行。
  • ③ 放弃了什么？换来的代价是一致性、运维复杂度，还是成本？只写好处的那半篇可以跳过。
  • ④ 在你这儿成不成立？他们的量级和你差几个数量级？差两个数量级以上的方案，直接照抄通常是负收益。

产出物要具体：每篇读完写三行进你自己的一张表——问题、他们的选择、失效条件。二十篇之后，这张表就是你在面试和架构评审里真正能当场掏出来的东西；没有这张表，读过的一百篇和没读过区别不大。

为什么重要 / 落到真实系统

这一章的主张听着软，其实有很硬的证据：过去十五年行业的默认架构，有相当一部分就是某家公司把自己的内部系统写出来之后长出来的。你今天用的工具，很多就是别人「学习的延续」的产物。

大厂实证
  • Twitter · Snowflake（2010 公开并开源）：Twitter 给它的自我定义是「a network service for generating unique ID numbers at high scale with some simple guarantees」（高并发下生成唯一 ID 的网络服务，附带若干简单保证）。这个名字后来成了通用名词，本书 Ch7 整章讲的就是它。同一个仓库也把代价一并证明了：它已于 2021-09-18 被官方归档、转为只读——公开资料会停更，但它塑造的设计活了下来。来源：Twitter 官方仓库 README，github.com/twitter-archive/snowflake
  • Google · 从 Borg 到 Kubernetes：Kubernetes 官方仓库开篇自陈「Kubernetes builds upon a decade and a half of experience at Google running production workloads at scale using a system called Borg.」（Kubernetes 建立在 Google 用一套叫 Borg 的系统大规模运行生产负载的十五年经验之上。）内部系统的经验被写出来、再开源，直接变成了今天容器编排的行业默认。来源：Kubernetes 官方仓库 README，github.com/kubernetes/kubernetes
  • Netflix · Chaos Monkey：Netflix 把「在生产环境里随机杀实例」这件极反直觉的事连做法带工具一起公开，自陈它「randomly terminates virtual machine instances and containers that run inside of your production environment」（在你的生产环境里随机终止虚拟机实例与容器）。一家公司的内部实践，因为被写出来而长成了一整个工程分支——混沌工程。来源：Netflix 官方仓库 README，github.com/Netflix/chaosmonkey

面试里这一章怎么用：当面试官问「你平时怎么学系统设计」「最近读了什么」，有具体答案和没有具体答案，差别非常大。「我读了 X，它的拐点是数据量到了某个数之后写入打满，我们系统在这点上不一样，因为我们的读写比是反的」——这是少数几个能提前准备、且几乎必被问到的开放问题。

易错点与争议

  • 把清单当收藏夹：最常见的失败。它有几十条，读完既不可能也不必要——它是索引不是作业。唯一有效的进度条是那张三行表有没有变长。
  • 链接会腐烂：这一章成于 2020 年，五年多过去，公司改名（Twitter 变成 X）、博客整体迁站、文章被删，清单里相当一部分入口已经打不开。实际做法是拿标题去搜，别直接点链接；上面 Snowflake 仓库 2021 年被归档就是现成的例子。
  • 幸存者偏差与公关成分：公司写的几乎都是「我们后来做成了」的版本，中间失败的三次不会写，被裁掉的那条线也不会写。系统性的例外只有一个——事后复盘（postmortem），那是行业里唯一专门写失败的文体，含金量常常高于架构介绍文。
  • 规模错配是最贵的误读：Facebook 的 TAO 是为十亿量级的社交图建的；你的两百万用户系统照抄，拿到的是它的复杂度而不是它的收益。比你大两个数量级的方案，默认不适用，除非你能说清为什么这次是例外。
  • 这一章本身很薄：它只给来源，不给读法，也不给验收标准——读多少算够、怎么知道自己确实学到了，一个字没写。前面那四问就是为补这个缺口写的。把它当「书末附录」看待是公道的评价。
  • 有力的反方观点：不少工程师认为，对大多数人而言，读大厂架构的边际收益低于在自己系统上认真量一次真实负载——前者给你别人的约束，后者给你你自己的。这个批评是成立的。合理的读法是两者配着来：先量自己的，再去找同量级的公开资料对照，而不是反过来拿别人的结论套自己的系统。

要点

① 这一章表面是励志收尾，实质是全书唯一一次承认：题库会用完、会过期，读真实系统的习惯不会。

② 它的内容只有两层：点名的单篇（Dynamo、GFS、Bigtable、TAO、Haystack、Snowflake 等）和几十家公司工程博客的入口。单篇是教材，博客是订阅。

③ 公开资料比练习题有营养，是因为它写了约束、拐点和代价——「做到多大才撑不住」这件事，题面上永远不会有。

④ 清单按公司排，但该按题重排：Ch6↔Dynamo、Ch7↔Snowflake、Ch11↔TAO、Ch1↔Scaling LinkedIn。先做题，再读对应那篇；反过来你只会复述。

⑤ 读法（原章缺的部分）：每篇问四件事——约束、拐点、放弃了什么、在你这儿成不成立；产出是三行表（问题 / 选择 / 失效条件）。

⑥ 四类来源各有价格：论文最扎实但慢且滞后，工程博客最及时但有公关成分且链接最易烂，演讲最坦白但难检索，二手聚合最省时但会丢约束、传错误。

⑦ 三个最常见的坑：把清单当收藏夹、忽视幸存者偏差（只有 postmortem 专门写失败）、规模错配（大你两个数量级的方案默认不适用）。

⑧ 反方值得听：量一次自己系统的真实负载，可能比读十篇大厂文章更有用。正确姿势是先量自己的，再找同量级的公开资料对照。
