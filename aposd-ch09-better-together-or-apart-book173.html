合还是分

A Philosophy of Software Design · Ch 9 · Better Together or Better Apart? · Ousterhout · 2nd ed 2021

EN →

这一章讲什么？

写程序时有一个天天都要做的小决定：这两块功能，放在一起写，还是拆开写？很多人有个默认答案——「拆得越细越好，一段代码越短越好」。这一章说：不一定。拆开本身是有代价的，该合的时候就要合。

打个比方

想想厨房。把刀和砧板放在一起，切菜顺手；要是按「物品种类」严格分柜——刀在东边柜、砧板在西边柜——看上去很整齐，可每切一次菜都要跑两个地方。反过来，把洗洁精和面粉塞进同一个罐子，就是合错了。整理的标准不是「分得够不够细」，而是「用起来顺不顺」。

先说个怪事

有人把一段几十行的代码拆成了八个只有两三行的小段，每一段都很「干净」。结果别人读的时候，得在八个地方之间来回跳，才能拼出它到底在干什么——每一块都好懂，合起来反而看不懂了。

核心机制直觉

  • 拆开要付「过路费」。每多一块，就多一个要记住的名字、多一处交接；本来挨在一起的东西被分开，读的人还可能根本不知道另一半在哪。
  • 四种情况该合：两块要用到同一份内情；它们总是一起出场；它们其实在讲同一件事；不看这一块就看不懂那一块。
  • 一种情况该分：「谁都能用的通用部分」和「只为某个场景写的专用部分」，要分开放。好比做一个通用的「后悔药」：它只管记下每一步、按顺序撤回；至于每一步具体怎么撤回，由各个功能自己说明。
  • 长不是罪。一段代码长，但读起来一路顺下去，就没问题；该拆的信号是「拆出来的那块能独立看懂」。

带来了什么 / 该怎么选

遇到合还是分，问一句：哪种方式让读的人需要记住的东西更少？一句诚实的代价：这是个要靠经验的判断，没有一条「多少行就该拆」的简单规矩可套。

一句话记住

拆不拆，看的是整体好不好懂，不是每一块够不够短。

一句话

你以为拆得越细、函数越短，设计就越好；Ousterhout 说拆分本身有成本，合还是分的判据不是行数，而是整个系统的复杂度——选那种信息隐藏最好、依赖最少、接口最深的结构。

Glossary · 术语表

  • 模块（module）：有接口、有实现的代码单元，可以是类、方法、库或子系统。本章讨论的「合与分」对类和方法都适用。
  • 方法 / 函数（method / function）：一段有名字、可被调用的代码，是最小的模块。
  • 接口（interface）：使用者为用好模块必须知道的一切，包括签名与「什么时候会出错」这类约定。
  • 深模块 / 浅模块：第 4 章的概念。深 = 接口简单、背后功能多；浅 = 接口几乎和实现一样复杂，「隔层纸」却没省事。
  • 信息泄漏（information leakage）：第 5 章的概念，同一条设计知识（如某种格式）散落在多个模块里，改一处就得改多处。
  • 依赖（dependency）：一段代码不看另一段就没法理解或修改，两者便相互依赖。
  • 缓冲（buffering）：读文件时一次多读一大块放进内存，之后的小读取直接从内存拿，避免频繁访问磁盘。
  • 撤销（undo）：编辑器里把最近的操作一步步回退的功能。
  • goto：C 语言里直接跳到函数内某个标签处继续执行的语句。

坐标

全书第 9 章。第 4–8 章分别讲深模块、信息隐藏、通用接口、分层与把复杂度下沉；这一章把它们落成一个日常动作：两段功能放进同一个模块，还是分进两个模块。下一章转向异常处理。现实里对应每一次「抽个方法 / 拆个类 / 合并两个服务」的决定，以及代码评审里「这个函数太长了」的意见。

这章要解决什么

业界流行一种直觉：模块越小越好，拆分是免费的「整理」。作者说这是错的——拆分会带来复杂度，而这些代价常被忽略。他列了四条：

  • 组件多了：每多一个类或方法，就多一个名字、多一个接口要记住，组件越多越难追踪。
  • 要写胶水代码：拆开后往往需要额外的代码来管理它们，比如把数据在两个对象之间来回传递。
  • 相关代码被隔开：本该一起看的逻辑被分到两处，读者很难同时看到——甚至根本不知道另一半存在。
  • 可能产生重复：两边各自需要的那点共同逻辑，往往各写一遍。

反过来，作者给出该合并的四个信号：两段代码共享信息（都依赖同一种格式或知识）；它们总是一起被使用，而且是双向的（用 A 时必然要用 B，用 B 时也必然要用 A）；它们在概念上重叠，存在一个能把两者都包住的上位概念；不看其中一段，就看不懂另一段。不解决这件事，代码库会滑向一堆浅模块：每个都很短、很「干净」，组合起来却没人能一眼看懂。

核心内容，讲透

一、共享信息就合

作者回到第 5 章的 HTTP 服务器例子：学生把「从网络读入请求」和「解析请求」写成两个方法，可读入时就得懂请求格式才知道何时读完，解析时也要懂同一种格式——同一份知识出现在两处，就是信息泄漏。合进一个方法，格式知识只在一处，接口也更短。

二、合了能让接口变简单就合

两个模块各做一半时，调用方往往得亲手把它们拼起来；合并后，模块可以自动完成这件事。作者的例子是 Java I/O：要高效读文件，得先建 FileInputStream，再套一层 BufferedInputStream。几乎所有人都需要缓冲，但每个人都得记住多套这一层，忘了就悄悄变慢。若把缓冲并入文件流并默认开启，这一层知识就从所有调用方身上消失了。合并还能省掉在模块间来回传递信息的那部分接口。

三、能消除重复就合

同一段代码模式反复出现，就该想办法只留一份。最常见的做法是抽成一个方法——但作者提醒，只有当「调用这个方法」比原来那段代码更简单时才值得：如果原片段只有两三行，抽出来的方法签名又要传一堆参数，就等于没省事。另一个办法是调整结构让那段代码只在一处执行，书里举的就是 C 里用 goto 跳到函数末尾的统一清理处，而不是在每个出错的分支里各写一遍释放资源的代码。

四、通用与专用要分开

这是本章唯一一条明确「该拆」的规则：通用机制和专用代码混在一个模块里，就该拆开。理想的结构是下层提供通用机制，上层放只为某个场景写的专用代码；通用模块对专用部分一无所知。作者给这类问题起了个红旗名字：通用与专用混杂（Special-General Mixture）。

书中的长例子是编辑器的撤销。学生们常把撤销逻辑塞进文本类，于是文本类里混进了「记录历史」这件与文本无关的事，选区、光标等其他会变化的东西也没法撤销。作者的做法是拆成两层：一个通用的历史（History）模块，只负责保存一串「动作」，并支持插入栅栏（fence）把多个动作分组——一次撤销回退到上一道栅栏，比如一次「查找替换」改了十处，撤销时一起回退；每个专用模块（文本、选区、光标）各自定义自己的动作该如何撤销、如何重做。历史模块完全不知道动作的内容，因而可以服务任何新功能。

论文精读 · 如何把系统拆成模块（Parnas 1972） — 「按要隐藏的设计决策来切模块」这条判据的源头，以及为什么按处理步骤切会让同一份知识散落各处

五、两个反例：分错了的地方

作者也展示了「不该分」的情形。一是光标与选区：有学生项目把两者放进同一个对象，理由是光标总在选区一端；作者认为这并没有让接口更简单，反而处处要处理「有光标没选区」的特殊情况，分成两个对象更清楚——共享一点信息不等于该合，关键看合后接口是否真的变简单。二是单独的日志类：有一个类专门记录网络错误，每个方法只在一处被调用、只做一件小事。它没有隐藏任何东西，只是让读者在出错处与日志类之间来回翻；把日志直接写回出错的地方更好。

六、方法的拆与合：长不是罪

本章最常被引用的一节。作者认为长方法本身不是问题：一个上百行的方法，若由几个顺序执行、彼此独立的块组成，从上读到下也不难，拆开反而让读者在多处之间来回跳。深度比长度重要：先把方法做深，再看是否短到好读。

拆方法有两种形态。好的拆法是抽出子任务：子方法功能清晰、能独立看懂，读者不看它的实现也知道它做了什么，父方法也因此更好读。常见的坏拆法是把一个方法劈成前后两半，让调用方依次调用——两个新方法往往都是浅的，接口几乎和实现一样复杂，调用方还得知道调用顺序。判据只有一条：拆完后，每个方法能否不看别的方法就被理解？若不能，作者称之为红旗连体方法（Conjoined Methods）：两段代码看似分开，读懂一段必须去读另一段，说明它们本该是一体。反过来，合并方法也可以消掉浅接口、去掉重复、或者把散在多处的状态收回一处。

七、第 2 版新增：与《Clean Code》的分歧

第 2 版专门加了一节回应 Robert Martin 的《Clean Code》。Martin 主张「函数的第一条规则是要小，第二条规则是要更小」，书中的函数常只有几行。Ousterhout 的反驳是：这种建议把注意力放在长度上，鼓励出大量浅方法，每个方法的接口都几乎和实现一样复杂，读者还得在它们之间跳来跳去。他承认短方法通常更好读，但长度从来只是手段，深度和独立可理解才是目的。

为什么重要 / 落到真实系统

这一章是代码评审里最常用的一把尺子。「这个函数 300 行，拆一下吧」和「这几个小方法读起来要来回跳，合起来吧」，两种意见都会出现；本章给的不是立场，而是可以对着具体代码讨论的问题——拆出来的东西能独立看懂吗？它藏住了什么？架构层面同理：把一个服务拆成两个，若它们共享同一份数据格式、总是同步发布、谁也离不开谁，就只是换了一种连体方法，还多出网络调用和部署协调的成本。

实证与出处 · 公开可查

  • Ousterhout 与 Martin 的公开辩论（2024–2025）。两位作者在 GitHub 上留下了一份长对谈。Ousterhout 指出《Clean Code》里的 PrimeGenerator 示例被拆成 8 个很小的方法，彼此纠缠，需要一起读才能看懂，主张合并；Martin 坚持自己偏好拆分，认为若要犯错宁可拆过头，因为多余的方法之后可以内联回去。两人各自重写后，Martin 的一个中间版本把一个循环拆成两个，运行慢了 3–4 倍，后来又把循环合了回去。出处：GitHub · johnousterhout/aposd-vs-clean-code
  • Linux 内核：用 goto 把清理收到一处。内核编码规范专设「函数的集中退出」一节：函数从多处退出、又有共同的清理工作时用 goto，理由包括减少嵌套、避免改代码时漏改某个出口。同一份规范对长度的态度也接近本章：函数的最大长度与其复杂度和缩进层数成反比，概念简单的长 case 语句可以接受。出处：Linux kernel · Documentation/process/coding-style.rst
  • Java I/O：把缓冲留给调用方的反面教材。作者在第 4 章和本章都以此为例：缓冲几乎人人需要，却要调用方手动套一层；许多后来的语言标准库把缓冲做成文件读写的默认行为。出处：Ousterhout，A Philosophy of Software Design，第 4、9 章

易错点与争议

  • 「函数越短越好」。短是好读的常见结果，不是目标。把一个能顺着读完的方法拆成八段，读者要在八处间拼图，认知负担反而更重。
  • 「Ousterhout 反对拆分」。不对。他明确支持抽出能独立理解的子任务，也要求把通用与专用分开；他反对的是只为缩短长度而拆。
  • 「共享一点信息就该合」。光标与选区的例子说明，合并的最终检验是接口是否真的变简单，不是有没有交集。
  • 「抽方法总能消除重复」。如果调用新方法和原来那几行一样复杂，只是把重复从代码搬到了参数列表。
  • 争议仍在。Martin 一方认为小方法配上好名字就是文档，过度拆分的代价比看起来小；Ousterhout 一方认为纠缠的小方法是真实的认知成本。两人在辩论里都承认对方的部分观点，但没有达成一致——这本身说明判据需要结合具体代码讨论。

要点

① 合还是分的判据是整个系统的复杂度，不是行数或类的个数。

② 拆分有四种代价：组件变多、要写胶水代码、相关逻辑被隔开、容易产生重复。

③ 该合的四个信号：共享信息、总是一起用、概念重叠、不看一个就看不懂另一个。

④ 合并能让接口变简单时就合，例如把缓冲默认并入文件流。

⑤ 消除重复值得做，但抽出的方法必须比原片段更简单才算数。

⑥ 唯一明确该拆的：通用机制与专用代码分开，撤销功能拆成历史模块和各自的动作。

⑦ 长方法不是罪；好的拆法是抽出能独立看懂的子任务，坏的拆法是劈成要按顺序调用的两半。

⑧ 红旗：连体方法（读懂一个必须读另一个）、通用与专用混杂、重复。

⑨ 第 2 版点名反对《Clean Code》的「越小越好」；两位作者 2024–2025 年的公开辩论把分歧摆上了台面。
