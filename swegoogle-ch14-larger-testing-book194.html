更大范围的测试

Software Engineering at Google · Ch 14 · Larger Testing · Joseph Graves · 2020

EN →

这一章讲什么？

你用的地图、邮箱、搜索，背后是几十个程序互相打电话协作。工程师平时会把每个小零件单独检查一遍——可零件个个合格，拼起来照样可能出事。这一章讲的就是：怎么检查「拼起来的整体」，又不让这种检查把大家拖垮。

打个比方

造汽车，每颗螺丝、每个轮胎出厂前都验过，这是「零件检查」。但没人敢不试驾就交车：零件装配有没有错、配置单有没有填错、高速上会不会抖，只有整车上路才看得出来。试驾比验螺丝贵得多、慢得多，还可能被天气、路况干扰，所以不能每拧一颗螺丝就试驾一次。

旧世界为什么难

只验零件，会漏掉几类毛病：替身演的对手和真对手说法不一样；程序本身没错，配置文件写错了——Google 说这是它重大事故的头号原因；平时好好的，几百万人同时涌进来就垮；还有用户总能找到工程师没想到的用法。可整车测试又慢、又容易时好时坏、牵扯好几个团队，坏了不知道找谁修，久而久之就没人管了。

核心机制直觉

  • 先想清楚试驾场地：从「在车间原地发动」到「直接开上大街」，越像真实路况越可信，但越贵、越危险。挑一个够用的就行。
  • 把大考拆成几场小考：前端和后台之间、自家和外部公司之间，最好各考各的，再把上一场的结果当下一场的起点，像接力赛。
  • 新旧两辆车跑同一条路：不用事先写下所有标准答案，只看新车哪里和旧车不一样，再请人判断这个不一样是改进还是退步。
  • 上路后也要巡检：派人定时绕一圈确认还能开；新版本先只给一小部分人用，没问题再推开；甚至故意制造小故障，看系统扛不扛得住。

带来了什么 / 该怎么选

零件检查打底、整车测试补漏，各管一类风险。关键是每一场整车测试都要有明确的负责人、出错时说清楚坏在哪，否则大家只会跳过它。诚实的代价是：这些测试搭起来费钱费人，还得一直维护，越大越难养。

一句话记住

零件全合格不等于整车能开：大测试补的是「真实感」，但要拆小、要有人管，否则只是个昂贵的摆设。

一句话

你以为大测试只是「更大的单测」，本章说它是另一种东西：它存在的唯一理由是保真度——补单测按设计就看不见的风险。但它天生慢、不密封、不确定，所以本章的全部功夫都在一件事上：在够用的保真度下，把它做得尽可能小，并且有人管。

Glossary · 术语表

  • 被测系统（system under test, SUT）：这次测试要检查的那部分系统；大测试里通常是一个或多个独立进程。
  • 测试规模（size）与范围（scope）：规模看资源约束（小测试 = 单线程、单进程、单机）；范围看验证了多少代码（单元 < 集成 < 端到端）。
  • 测试替身（test double）：测试里顶替真依赖的对象，如 mock、fake（见第 13 章）。
  • 密封（hermetic）：测试需要的一切都由它自己掌控，不和别的测试或真实流量共享资源。
  • 不稳定（flaky）：代码没变，测试却时过时不过。
  • 预提交 / 提交后（presubmit / post-submit）：代码合入主干之前 / 之后自动跑的检查。
  • TAP：Google 的持续集成系统，只收密封、能在时限内跑完的测试。
  • 预发环境（staging）：上线前的共享环境，结构接近生产，但不服务真实用户。
  • 海勒姆定律（Hyrum's Law）：用户够多时，系统所有可观察的行为都会被人依赖，不管文档承诺没承诺。

坐标

Part III「流程」，测试四连章的收尾。上承 Ch13 测试替身（替身覆盖不到的风险，本章用真依赖补），下启 Ch15 废弃。现实对应：集成与端到端测试、预发环境、金丝雀、混沌工程——测试金字塔的塔尖。

这章要解决什么

回想你自己怎么确认程序能跑：写了单测，但多半还会亲手运行一次。依赖的 Google Maps API 出了新版本，单测也告诉不了你兼容不兼容。单测给的是「每个零件对」的信心，大测试给的是「整体按预期工作」的信心，而且自动化，能像手工测试做不到的那样规模化。

但大测试违反好测试的三条：可靠（用的基础设施多，就更 flaky）、快（Google 大测试默认超时 15 分钟或 1 小时，有的跑好几个小时甚至几天）、可扩展（吃资源，还互相干扰）。外加两个组织难题：归属——跨团队的测试坏了谁修？缺标准——Ads、搜索、Drive 的差异测试各用各的平台和框架，大规模改动时没人知道怎么跑，于是常被跳过。

核心内容，讲透

一、保真度：大测试为什么存在

保真度（fidelity）指测试多大程度上反映被测系统的真实行为。从环境看是一条光谱：单测把一小段代码和测试打包成一个可执行单元，离生产最远；生产本身保真度最高；中间有单进程、单机、多机、共享预发等过渡。保真度越高，成本越高，到了生产还要加上出故障的风险——所以要找的是恰好够用的那一档。

保真度还有第二个维度：测试数据像不像真的。手写数据覆盖窄、带着作者的偏见；生产数据更真，难的是上线前造出真实流量。

二、单测按设计就看不见的五类风险

  • 替身不忠实：mock 由写单测的人定义，他通常没写被 mock 的那个东西，可能理解错契约；真实现改了，mock 也不会收到任何信号而过期。由所有者提供 fake 能大体缓解。
  • 配置问题：二进制要配部署配置、启动脚本、配置库，单测验证不了二者兼容。原书直言配置变更是 Google 重大事故的头号原因，并举了 2013 年一次因未经测试的网络配置推送导致的全球故障；配置用专门的语言写、上线比二进制更快、更难测。
  • 负载下才出现的问题：Google 的量动辄每秒数千到数百万次查询（如广告实时竞价），塞不进单测的模型。
  • 预料之外的行为：单测只能测作者想到的输入，而用户碰到的问题大多是没想到的。按海勒姆定律，真实契约是全部可观察行为，不只是文档里写的那部分。
  • 真空效应：单测像放进真空的理论物理题，屏蔽了真实依赖、网络和数据的混乱——换来快和稳，也必然漏掉某些缺陷。

规模放大了这一点。原书算过：用户服务器和广告服务器都换成保真度 10% 的替身，出 bug 的概率是 1 − 0.1 × 0.1 = 99%——意思是每多一个低保真替身，「拼起来全对」的概率就再乘一次，服务越多越糟。可规模也让端到端场景数组合爆炸。结论是两头都要：用大测试，但要在规模下保持合理保真度的方式去做。

三、大测试的结构：SUT、数据、动作、验证

大测试几乎都是四步：拿到一个被测系统 → 灌入测试数据 → 对它执行操作 → 验证行为。每一步都有选择。

SUT 的形态按两个因素评判：密封性（离别的使用者多远，越密封越少并发与基础设施带来的抖动）和保真度（配置、基础设施、拓扑多像生产）。二者常常直接冲突。原书列了五种：单进程、单机、多机、共享环境（预发与生产）、混合——混合在 Google 不可避免，因为不可能把整个 Google 互联的服务都复制一份，通常是被测的那部分自己起、后端用共享的。

为什么要密封？在生产上测，代码必须先到达生产，测试就没法拦住发布，「SUT 来得太晚」；共享预发要排队「预约时段」，工程师和服务一多就撑不住。下一步就是云上隔离或单机密封的 SUT。原书还讲了 YouTube 的 Webdriver Torso：公开频道里自动上传的测试视频被媒体当成谜团追查——放进生产的测试数据，要做好被用户发现的准备。

在痛点边界上缩小 SUT：UI 测试出了名地脆（外观一改就红、异步行为难测），所以前端加后端的端到端测试维护成本是乘出来的——更好的做法是在 UI / API 边界切开，用公开 API 驱动端到端测试，浏览器、命令行、桌面、手机 App 都适用。第三方依赖也是天然切口：没有共享测试环境、发流量可能要花钱，不建议自动化测试直连。再把数据库换成内存库、移掉不关心的服务器，让 SUT 塞进一台机器——这样的集成测试最省心也最稳。

就算是集成测试，也是越小越好：几个大测试好过一个巨型测试。跨很多系统的用户旅程可做成链式测试（chained tests）：拆成两两之间的小集成测试，上一个的输出存下来当下一个的输入。

录制 / 回放代理（record/replay proxies）是 Google 最常用的办法，用来解决「整个服务的替身未必忠于真货」：跑大测试时录下发往外部服务的流量，跑小测试时回放。录制模式的大测试在提交后持续运行，主要为产出流量日志；回放模式的小测试用于开发和预提交。请求靠匹配器决定回放哪条响应，所以它很像 stub；客户端大改就匹配不上、得重录，因此录制必须容易、快、稳。Google 外部常见的是消费者驱动契约测试（consumer-driven contract tests），如 Pact：客户端写下「这个输入得到这个输出」，服务端拿同一对输入输出跑真实测试；Google 因重度依赖 protocol buffers 而内部不用。

数据分两种：预置数据（测试开始时 SUT 的状态）和测试流量（测试执行中发给它的请求）。预置往往比单测的准备复杂几个数量级：社交网络的大测试需要足够真实的用户和关系图才会被认可；直接写库又可能绕过真实写入路径上的校验。来源有三：手写、从生产复制、采样（用最少数据换最大覆盖）。验证也有三种：人工（按测试计划回归，或探索式）、断言（如搜 xyzzy，断言结果含「Colossal Cave」）、A/B 对比（跑两份 SUT、喂同样数据、比较输出，不写死预期，由人判断差异是否有意为之）。

四、把大测试接进开发者工作流

很多大测试不进 TAP：不密封、太 flaky 或太吃资源。Google 为它们另建提交后持续构建，并鼓励预提交也跑，因为反馈能直达作者；需要人工批准差异的 A/B 测试，可以把「在 UI 里批准差异」列为代码评审的前置条件，有个测试甚至会在带着未处理差异提交时自动开阻塞发布的 bug。实在太痛的只在提交后和发布时跑，代价是坏代码先进主干、要事后回滚。

提速：最好的办法是缩小范围，或把一个大测试拆成两个能并行的小测试。别用固定时长的 sleep 等异步动作，改成高频轮询（配超时）或订阅完成事件——靠 sleep 的测试会在机群过载时集体失败，重跑又加重负载，恶性循环。生产代码里写死的超时要做成可调，测试时调低。

治不稳定：从缩小范围开始——密封 SUT 没有多用户干扰，单机 SUT 没有网络和部署抖动。超时是双刃剑：调高内部超时减少 flaky，调低则可能制造 flaky，要在「用户可容忍」和「测试稳定」之间找平衡。更隐蔽的是优雅降级：广告超时就不展示、不返回 500，测试看来却像广告代码坏了——要让这类失败一眼可见。

看得懂的失败：最糟的报错是一句「Assertion failed」加堆栈。好的报错预设读者不熟代码，写成「某测试预期 10 条搜索结果，实际 1 条」；跨进程时堆栈没用，要产出跨链路追踪，如 Dapper 用一个请求 ID 串起整条 RPC 链的日志；还要写明负责人。

CS Papers · Dapper 精读 — 一个请求 ID 怎么串起跨几十个进程的调用链，正是大测试失败时替代堆栈的那件工具

归属：大测试必须有文档化的负责人，否则改不动、修得慢，最后腐烂。项目内的集成测试归项目负责人，跨服务的功能测试归「功能负责人」。负责人信息要结构化（沿用单体仓的 OWNERS，或逐测试注解），失败时自动找到人。

为什么重要 / 落到真实系统

被问「你们的测试策略」，好答案不是「单测覆盖率 90%」，而是按风险列清单：配置靠部署配置测试和金丝雀，负载靠隔离压测，迁移靠 A/B 差异，容错靠混沌演练，并说清谁负责、何时跑。时间维度也要考虑：原型期的手工测试若一直堆下去，就成了冰淇淋筒反模式，几天内造出只能端到端测试的「遗留代码」。

易错点与争议

  • 「大测试 = 端到端测试」——不止。规模和范围是两个维度；单机集成、配置冒烟、压测、A/B 差异、探针、混沌演练都算。
  • 「测生产最真实，就在生产测」——生产测试拦不住发布。代码到了生产才能测，发现问题时用户已受影响；写操作还会改生产状态。
  • 「A/B 差异测试是全自动的」——差异要人批准。它不定义预期，噪声大时人工核对会吞掉它省下的成本；所以要用 A-A 测试（自己比自己）先找出噪声。
  • 争议：录制回放 vs 契约测试。二者都在回答「替身怎么保真」。Google 因 protocol buffers 选了录制回放；业界多用 Pact 一类消费者驱动契约。录制回放依赖匹配器、本质近似 stub，客户端一大改就要重录；原书只说明了 Google 的选择，没有宣称它普适更优。

要点

① 大测试存在的唯一理由是保真度：从单进程到生产是一条光谱，越真越贵越险，挑恰好够用的一档。

② 单测的五个盲区：替身不忠实、配置、负载、未预料行为（海勒姆定律）、真空效应；配置变更是 Google 重大事故的头号原因。

③ 大测试的代价：慢、不密封、不确定，外加归属不清和缺标准两个组织难题。

④ 结构四步：SUT → 数据 → 动作 → 验证；SUT 按密封性与保真度权衡，二者常冲突。

⑤ 在痛点边界切小：UI / API 边界、第三方依赖；链式测试把长旅程拆成两两小测试。

⑥ 录制回放：大测试持续录流量，小测试回放；业界的对应物是 Pact 一类契约测试。

⑦ A/B 差异测试是 Google 最常见的大测试，挡未预料的副作用，代价是人工批准与去噪。

⑧ 接进工作流：另建提交后构建、尽量预提交；用轮询和事件替代 sleep；失败信息要可读、可追踪。

⑨ 每个大测试都要有结构化记录的负责人，否则必然腐烂。
