Testing for Reliability

Site Reliability Engineering · Ch 17 · Google · 2016

中文 →

What is this chapter about?

The apps on your phone update almost weekly, and the services behind them change dozens of times a day. The odd thing is how rarely an update takes everything down. Chapter 17 of Google's SRE book is about exactly that: change is unavoidable, so how do you keep change from breaking things? The answer is a whole discipline of tasting before serving.

An analogy first

Think of shipping a new version as a restaurant putting a new dish on the menu. You changed the recipe, so you don't send it straight to a full dining room. First you taste it yourself in the kitchen. Then you run the whole thing end to end — plating, timing, service. Then you serve it to one table by the window and watch how they react. Only then does it go out to everyone. And regardless of new dishes, every day you send someone in to order a plate pretending to be a customer, just to confirm the kitchen is still alive. Those steps map onto the kinds of checks this chapter describes.

Why the old way was hard

Not changing code is the safest thing you can do, and also the end of your business. The real difficulty is that things break not because someone got a line wrong, but because of the things that only exist in production — real user traffic, real configuration, the real number of machines. Everything tastes fine in the kitchen and falls apart in the dining room. Worse, many teams have exactly one move after shipping: stare at the dashboards and hope, letting users find the problem first.

The central idea: not catching bugs, but making bugs cheap

The most counterintuitive line here is this: the value of testing isn't finding a problem, it's deciding at which step the problem gets found. If a dish is too salty and the kitchen catches it, the cost is one remade plate. If the customer catches it, the cost is an apology, a refund, and your reputation. Software works the same way. A bug stopped by an automated check before release is nearly free to fix. A bug that leaks into production is a 3 a.m. page, an investigation, a rollback, and a postmortem — there goes your night.

So the lesson isn't "write more tests." It's put each gate where the cost is lowest, and be honest about what each gate misses — the kitchen can't taste the crowding in the dining room, and one table by the window doesn't speak for every customer.

So how do you choose?

A small system you can undo in a minute can afford looser gates and lean on "pull it back the moment it looks wrong." A large system that takes hours to recover has to move its gates earlier and stop bad changes before they ship. The honest cost: more gates means slower releases — and a check that passes sometimes and fails other times is worse than no check at all, because it teaches everyone to ignore red lights.

One thing to remember

Testing isn't about proving nothing is broken. It's about making sure breakage is discovered at the cheapest possible place. Taste before serving, serve one table first, and keep sending in a fake customer — three gates, each covering a different stretch, none of them optional.

In one sentence

You think testing exists to find bugs. This chapter makes a sharper claim: testing is how an SRE quantifies confidence, and what it really changes is not the number of bugs but the cost of fixing them. The chapter opens by saying that one key responsibility of Site Reliability Engineers is to quantify confidence in the systems they maintain — and that reliability is a function of mean time to failure (MTTF) and mean time to repair (MTTR). The economics of testing land squarely on the MTTR side: a bug blocked before it ships has a repair time of roughly zero.

Glossary

  • Binary / push: the compiled program you deploy; pushing is the act of sending it to production.
  • MTTF / MTTR / MTBF: mean time to failure (how long until it breaks), mean time to repair (how long to fix it), mean time between failures. Reliability is determined by these together.
  • Unit test: exercises one smallest unit — a function, a class — in milliseconds, touching no database and no network.
  • Dependency injection: handing a component its external dependencies from outside, so tests can swap in fakes (mocks).
  • Regression: an old, already-fixed bug coming back; the test written to prevent that is a regression test.
  • Canary: releasing a new version to a small slice of servers and users first, watching for a while, then widening. Named for the bird miners took underground.
  • Prober: a small program that continuously sends known requests at production and checks whether the responses match expectations — black-box monitoring.
  • Flaky test: a test that passes sometimes and fails other times on identical code, usually from a race condition or environmental noise.
  • Error budget: the amount of unreliability your SLO permits; when it runs out you stop shipping features and go fix things.

Where it sits

This chapter belongs to Part III, "Practices," right after the incident-handling cluster that includes Ch 15 on postmortem culture. It builds on Ch 3's error budgets and Ch 8's release engineering, and it sets up Ch 19–22 on load balancing and overload, and Ch 27 on launch coordination. In today's terms it maps onto one pipeline: CI → canary release → black-box probing, now marketed as progressive delivery and synthetic monitoring.

The problem this chapter attacks

SREs get asked one question every single day: "can this version go out?" Past reliability can be settled by looking at monitoring history; future reliability can only be predicted. And prediction requires that the system hasn't changed — but systems change constantly. The chapter's answer: testing is the mechanism you use to demonstrate specific areas of equivalence when changes occur. Every test that passes both before and after a change removes one piece of uncertainty.

What happens if you don't solve it? Both extremes are common. One is fear of shipping: every release pulls the whole team in for manual checks, cadence falls to once a month, features pile up into one enormous change, and failures get harder to localize. The other is shipping blind: push, watch dashboards, let users be your probes. A production bug costs you alert → diagnose → roll back → postmortem, easily hours; the same bug caught by CI costs one red build and one commit.

The core, explained

1. What testing really does: move the bug to the cell with the lowest MTTR

One formulation in the chapter is worth copying down: when a system-level test applied to a subsystem detects exactly the same problem that monitoring would detect, that test lets the push be blocked so the bug never reaches production — repairing such "zero MTTR" bugs by blocking a push is both quick and convenient.

That line redefines testing from a quality activity into an economic one. You are not eliminating bugs, which is impossible. You are choosing where they get discovered, and the location sets the price.

2. Traditional tests: unit → integration → system

The first family runs against an undeployed binary on constructed, known data. Three layers:

  • Unit tests exercise the smallest unit, run in milliseconds, are the most numerous, and form the base of the pyramid.
  • Integration tests run assembled components together, using dependency injection to replace the real database and the real downstream with fakes — collapsing cross-process logic into a few seconds.
  • System tests run against a complete but undeployed system, and come in three flavours: a smoke test checks the simplest yet most critical behaviour and runs first, so a failure spares you the rest; performance tests guard against latency and resource usage drifting version by version; regression tests freeze every bug you've fixed into a permanent case.

Regression testing carries one highly actionable rule: when you find a bug, first write a test that reproduces it reliably, then fix it. That rule also answers "where do I start on a legacy project with no tests?" — you don't backfill full coverage; you accumulate cases one fixed bug at a time.

3. Production tests: configuration, stress, canary

The second family runs against an already deployed system, because some things exist only in production.

  • Configuration test: compare the configuration actually in effect in production against what the version control system says should be in effect, and alert on divergence. It gets its own category because configuration is a leading source of incidents yet often isn't in CI at all — Terraform's plan and drift detection are today's version of the same idea.
  • Stress test: go find the limits. How full can the database get before writes start failing? How many QPS before overload? How little free disk before the alert fires? If you don't test it, you don't know where the edge is — and production's way of telling you is an outage.
  • Canary: send the new version to a small subset of servers first, let it bake under real traffic, then widen.

On canaries the book makes a point that is routinely missed: a canary test isn't really a test; rather, it's structured user acceptance. Configuration and stress tests confirm a specific condition over deterministic software; a canary is more ad hoc — it exposes the code under test only to less predictable live production traffic, so it isn't perfect and doesn't always catch newly introduced faults. Treat it as your last line of insurance, not as proof that the change is good.

4. Probers: the cell that neither testing nor monitoring reaches

Lay the pieces out on a two-by-two and one cell is conspicuously empty. Traditional testing = known input × undeployed binary. Monitoring = unknown real traffic × deployed binary. So who owns known input × deployed binary? Probers.

The chapter names the cause of the gap precisely: the release test probably wrapped the integrated server with a frontend and a fake backend, while the probe test wraps the release binary with a load-balancing frontend and a separate, genuinely scalable persistent backend. In other words, the configuration actually running in production is one that was never tested as a whole. Google fills that cell with a tool called Prober, which runs a protocol check against a target and reports success or failure; it can validate the response payload itself — the HTML contents of an HTTP response, say — and even extract values and export them as time series.

Probers have costs too. They issue real requests against production, so you must handle write side effects (usually dedicated test accounts and disposable data), quota consumption, and the question of who is at fault when the prober itself dies — its alerts have to distinguish "the service is broken" from "the prober is broken."

5. Three problems that only appear at scale

① The tools SREs write are software too. Draining traffic from a cluster, restarting in bulk, reclaiming data, adjusting quota — these have a larger blast radius than most product code and frequently have no tests at all. The chapter offers a crisp rule: how thoroughly a tool is tested determines how often it is appropriate to use that tool against production. An untested tool runs only in a window with a human watching; a well-tested one has earned automation.

② How do you test disaster recovery tooling? By nature it only runs on the worst day, so you can't wait for a real disaster to validate it. The chapter's move is elegant: many disaster recovery tools can be carefully designed to operate offline and compute a checkpoint state equivalent to cleanly stopping the service, then push that checkpoint to be loadable by existing non-disaster validation tools. Turn a disaster into a snapshot you can validate offline — the single most portable trick in the chapter.

③ Speed is availability. The longer tests take, the longer the lag between check-in and feedback, and the more engineers route around them. Flakiness is the subtler poison: what an engineer actually wants to know is whether their code has an unanticipated race condition, and a test that flips red and green on its own buries that signal in noise. An intermittently failing test is worse than no test — it trains the whole team to ignore red.

All three are tied together by one control loop: as MTBF rises in response to better testing, developers are encouraged to release features faster; new bugs push release velocity back down. In practice that loop is the error budget — keep shipping while the SLO has room, stop and reinvest in testing when the budget is spent.

These aren't alternatives; they're two sides of one equation. Reliability is a function of MTTF and MTTR, and you can buy it from either side. The actual mistake is funding neither and trusting luck.

Why it matters in real systems

Almost every modern delivery practice has its prototype in this chapter: layered CI tests map onto Bazel and GitHub Actions pipelines; configuration tests onto Terraform plan and drift detection; canaries onto Spinnaker, Argo Rollouts and Flagger; probers onto Prometheus blackbox_exporter, Datadog Synthetics and every synthetic-check product. Reading this chapter gives you the manual for why those tools look the way they do — and lets you answer "how do you make a release safe?" starting from MTTR rather than from a list of tool names.

Pitfalls and open questions

  • Treating the canary as a test. The most common misreading, and the book pre-empts it: a canary is structured user acceptance and does not catch all newly introduced faults.
  • Mistaking coverage for safety. Coverage measures that code was executed, not that behaviour was asserted — and configuration, dependency versions and deployment topology, the things that actually break, don't enter the coverage number at all.
  • Forgetting to test your own SRE tooling. The code with the largest blast radius is routinely the code with no tests. The rule stands: if it isn't tested enough, don't let it run unattended.
  • Tolerating flaky tests. The damage compounds — first the test gets re-run, then it joins an ignore list, and eventually nobody reads red at all.
  • Dated in places. Written in 2016, before mature automated canary judgment (Kayenta was open-sourced in 2018), before service-mesh-grade traffic splitting, and before OpenTelemetry unified the probing layer. Progressive delivery has since engineered the canary further than this chapter anticipated.
  • A strong counterargument that is really the same coin. The continuous-delivery camp says: rather than funding a longer test suite, drive MTTR down to minutes. That sounds like opposition but is exactly this chapter's own reasoning — reliability is a function of MTTF and MTTR, and both sides are purchasable. The real disagreement is only whether your system can roll back in seconds.

Takeaways

① In one line: testing is how SREs quantify confidence; it changes not the number of bugs but where they are found, and therefore what they cost.

② Core claim: reliability is a function of MTTF and MTTR; a bug blocked before release has near-zero MTTR, and fixing it by blocking a push is quick and convenient.

③ Traditional tests (undeployed + known data): unit → integration → system, with system splitting into smoke, performance and regression.

④ Production tests (deployed): configuration tests (live config vs. version control), stress tests (go find the limits), and canaries.

⑤ The book is explicit: a canary isn't a test, it's structured user acceptance — exposed only to a small slice of unpredictable real traffic, and not always catching new faults.

⑥ The missing cell is the prober: known requests against the deployed system, because the real production combination was never tested as a whole.

⑦ Three problems at scale: SRE tooling needs tests too (test depth decides how often it may touch production); disaster tooling is tested offline (compute a checkpoint equivalent to a clean stop, then validate it); speed is availability (a flaky test is worse than no test).

⑧ The control loop: better tests → higher MTBF → faster releases → new bugs → velocity pushed back. Its practical form is the error budget.

⑨ The judgment to keep: don't ask "are we testing enough?" — ask "which cell will this bug be caught in, and what is that cell's MTTR?"
