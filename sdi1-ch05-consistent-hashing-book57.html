设计一致性哈希

System Design Interview: An Insider's Guide · Vol 1 · Ch 5 · Alex Xu · 2020

EN →

这一章讲什么？

你网购的包裹要先进分拣中心：几个仓库排在那里，每个包裹按单号被分到其中一个。分拣规则要满足两件事——快（不用查册子，看一眼单号就知道去哪个仓库）、稳（下次找这个包裹，还得算到同一个仓库）。这一章讲的就是这条分拣规则，以及它在仓库数量变化时会出什么事。

先说个怪事

你大概觉得：本来 4 个仓库，新开第 5 个，那把大约五分之一的货挪过去就行了。可用最常见的那条规则，你得把差不多八成的货全部重新搬一遍——不是搬到新仓库，而是每个包裹都要换一个不同的旧仓库。开一个仓库，全城的货都得动。

旧世界为什么难

那条最常见的规则是：单号除以仓库数，看余数。4 个仓库，余数 0、1、2、3 各对应一个。简单又快。问题出在「仓库数」这三个字被写进了公式里：仓库从 4 变成 5，除数就从 4 变成 5，几乎每个包裹算出来的余数都变了——它们不是「大部分不动、少数搬去新仓库」，而是集体换了个位置。

后果很直接：分拣中心其实是缓存。平时几乎人人都能就近拿到东西；仓库一变，大家全找错地方，请求哗地一下全砸到后面那个又慢又金贵的总库上。压垮系统的不是新加的那台机器，是那次搬家本身。

核心机制：把仓库排成一圈

换个办法。把所有可能的单号想象成一条首尾相接的圆形跑道，每个包裹按单号落在跑道上某一点；仓库也按自己的名字落在跑道上某一点。规则改成一句话：包裹从自己的位置出发，顺着跑道往前走，遇到的第一个仓库就归它。

妙处在于：公式里再也没有「仓库数」这个东西了。新开一个仓库，就是往跑道上插一个新点——只有「从新点往回退到上一个仓库」的那一小段包裹需要挪，其余整条跑道上的包裹一个都不用动。关掉一个仓库同理：它那一段的包裹顺着跑道交给下一个仓库，别人不受影响。

还得打个补丁

光这样还不够均匀。仓库落在跑道上的位置是随机的，可能三个仓库挤在一起、留下一段特别长的空当归第四个——那个仓库就被撑爆了。补丁很土也很有效：让每个仓库在跑道上开几十上百个「分店」，名字带编号，各自算各自的落点。分店一多，长短弧被打散又摊平，每个仓库分到的总量自然就接近了——这就是「虚拟节点」。

诚实说一句代价：分店不是越多越好——一个仓库的货散在越多小段上，就跟越多的邻居搅在一起，某天两个仓库同时出事，波及面反而更大。

一句话记住

老办法把「仓库数」写进了公式，所以仓库一变，全城的货都要搬。一致性哈希把仓库排成一圈、只让每个包裹找顺时针方向最近的那一个，于是加减仓库只惊动一小段。再给每个仓库开一堆分店，把长短不一的弧摊匀。

一句话

你以为一致性哈希（consistent hashing）是「一种更好的哈希函数」，其实它根本没让数据分得更均匀——把数据摊平的是后来打的那个补丁（虚拟节点）。它真正买到的只有一样东西：把扩缩容时必须搬动的数据，从「几乎全部」压到「1/N」。这一章是全书最像纯算法的一章，值得记住的其实是那个思路：凡是把「机器数量」写进路由公式的方案，都会在加机器的那一刻自爆。

Glossary · 术语表

  • 哈希函数（hash function）：把任意输入（一个字符串、一个 key）压成一个固定长度数字的函数。同一输入永远得到同一输出，不同输入尽量散得开。
  • 键 / key：数据的名字，如 user:8613。系统靠它决定这条数据放在哪台机器上。
  • 分片 / 分区（sharding / partitioning）：一份数据装不下或扛不住，就切成若干块，每块放一台机器。「路由」就是决定某个 key 属于哪一块。
  • 取模（modulo）：除法取余数，写作 %。hash(key) % 4 就是「除以 4 看余数」，结果必是 0–3 之一。
  • 再哈希（rehashing）：机器数变了，重新计算每个 key 的归属并把数据搬过去的过程。
  • 缓存命中率（cache hit rate）：请求在缓存里直接拿到数据的比例。命中率一跌，压力就原样传给后面的数据库。
  • SHA-1：一种常用哈希函数，输出 160 位（0 到 2^160-1 之间的一个数）。本章只借用它「输出散得开」这一条性质。
  • 虚拟节点（virtual node）：一台物理机在环上占的多个「化身」位置，用来把它的份额打散成许多小段。Cassandra 里叫 token。
  • 标准差（standard deviation）：衡量一组数字彼此差多远。这里用它衡量「各台机器分到的数据量差得有多离谱」，越小越均匀。
  • 副本（replica）：同一份数据在多台机器上各存一份，任一台挂了还能读到。
  • 热点 key（hot key）：单独一个被疯狂访问的 key，如某个明星的主页。它再怎么分散也只有一份。

坐标

Part II「系统案例」的第二题，也是全书最短、最「零件」的一章：没有 API、没有数据模型，只有一个算法。它正好接住 Ch4 限流器留下的尾巴——几十台无状态的限流器，配额状态怎么分到多台缓存上；往后它是 Ch6「设计键值存储」的第一块砖，Dynamo 那一整套都盖在这个环上。对应现实：Dynamo 与 Cassandra 的数据分区、CDN 的边缘节点选择、Google 的 Maglev 负载均衡器，以及任何一个多节点缓存层。

这章要解决什么

问题只有一句：机器数量会变，而最直觉的路由公式受不了这个。

最直觉的公式是 serverIndex = hash(key) % N——N 台服务器，算个余数就知道去哪台。够快、够稳（不用维护任何路由表）、分布也够均匀。唯一的毛病是：N 出现在公式里。

严格算一下这毛病有多大。4 台缓存挂掉一台，N 从 4 变 3：只有约 1/4 的 key 还落在原机器上，其余 75% 全部换了归属；理想情况本该只搬走那台自己的份额，也就是 25%。加机器同样糟：4 台变 5 台约 80% 的 key 换位置，理想值 20%。

不解决会怎样？算一笔账：缓存层扛 100,000 QPS、命中率 99%，每秒只有 1,000 个请求穿透到数据库。一台缓存挂了，客户端按新的 N 重新取模，瞬间约 75% 的 key 找错机器，命中率跌到 25% 附近，穿透请求变成每秒 75,000 个，放大约 75 倍。连接池打满、响应变慢、超时重试再叠一层——缓存还没恢复，后端先塌了。原书把这个现象叫 cache miss 风暴：击垮系统的不是那台挂掉的机器，是紧接着的那次全局搬家。

核心内容，讲透

一、把 N 从公式里拿掉

这是全章唯一的核心思路，其余都是它的工程化：换一种不需要知道有几台机器的定位方式——机器和 key 都在同一个固定坐标系里安一个位置，归属由相对位置决定，不由总数决定。加减机器只是往坐标系里增删一个点，其他点纹丝不动。

二、哈希环：把「除法」换成「找邻居」

那个固定坐标系就是哈希环。取一个哈希函数（书里用 SHA-1），它的输出范围是 0 到 2^160-1；把这条线的首尾接起来，就成了一个环。然后三步：

  • 放服务器：用服务器的 IP 或主机名算哈希，落到环上一点。
  • 放 key：用 key 算哈希，也落到环上一点。注意这里不做取模——key 落在环上，不落在某台机器上。
  • 查归属：从 key 的位置顺时针走，遇到的第一台服务器就是它的家。

加一台服务器 s4：它插进环上某个位置，只有「从 s4 逆时针回退到上一台服务器」这一段区间里的 key 改换门庭，环上其余部分完全不受影响。删一台同理：它负责的那一段整体顺时针交给下一台。

这正是 Karger 等人 1997 年那篇原始论文给出的性质：哈希表大小变化时，平均只需重新映射 k/n 个键（k 是键总数、n 是槽位数）——人话就是「加一台机器，只搬 1/n 的数据」。

三、基本环的两个毛病

直接用上面的环，会撞上两个都跟「随机」有关的问题，原书把它们并列点出：

毛病一：分区大小不均。服务器在环上的落点是哈希算出来的，等于随机撒点，相邻两点的弧长天差地别。更糟的是它会因节点变动而恶化：移除一台服务器，它那一段并到邻居头上，邻居的负担可能一下变成别人的两倍。

毛病二：key 分布不均。就算弧长恰好均匀，key 本身也可能扎堆落在某一小段上。极端情况下有的机器管着一大片热闹区间，有的机器一个 key 都分不到。

注意这两条说的是同一件事的两面：基本的一致性哈希只保证「搬家便宜」，从来没保证「分得均匀」。很多人把这两件事混为一谈，是这一章最常见的误读。

四、虚拟节点：用数量把方差压下去

补丁是：一台物理服务器不再只在环上占一个点，而是占很多个点。服务器 s0 派出 s0_0、s0_1、s0_2…… 每个化身各自算哈希、各自落点，查询规则完全不变（顺时针找第一个虚拟节点），只是最后要把虚拟节点映射回它背后的物理机。

直觉一句话：一台机器不再拿整副身家赌一段弧的长短，而是赌两百段小弧的平均。赌一次方差极大，赌两百次就被大数定律摁下去了。原书引了一份实验的数字：虚拟节点取 100 个时，各机器负载的标准差约为均值的 10%；取 200 个时约为 5%。书里给出的代价是存储开销——环上的点多了，映射表更占内存、查找也更慢。（书没讲的那个更重要的代价，见「易错点」。）

虚拟节点还顺手解决了一个 Dynamo 论文专门强调、书里没展开的问题：异构。集群里的机器往往不一样强，而虚拟节点让「多分点活」变得极简单——给强的机器多派几个化身，权重直接落在数量上，路由逻辑一行不改。

五、算出受影响的键区间

原书为这件事单开一节，因为「知道要搬多少」和「知道要搬哪些」是两回事。规则很短：加节点，受影响区间是从新节点位置逆时针回退到上一个节点；删节点，受影响区间是从被删节点逆时针回退到上一个节点，这段 key 顺时针交给下一个节点。

为什么必须算准？真实系统搬数据靠的是按 token 区间做范围扫描并流式传输（Cassandra 的 bootstrap 就是这么干的）。区间算窄了会漏搬、数据永久丢失；算宽了等于全量扫描，一次扩容能把集群 I/O 打满几小时。

为什么重要 / 落到真实系统

这套算法是无中心分布式存储的入场券：只要你想做一个「客户端自己就能算出数据在哪、不用问任何协调者」的系统，就绕不开它。面试里它也是极高频的追问点——拉开差距的从来不是「环 + 虚拟节点」这六个字，是受影响区间怎么算、以及虚拟节点数为什么不是越大越好。

大厂实证 · 这些主张不是书里说的，是公司自己公开说的
  • Amazon 在 Dynamo 论文里明说基本一致性哈希有两个问题——节点在环上的随机落点导致数据与负载分布不均，以及算法对节点性能的差异视而不见；解法就是给每个节点在环上分配多个位置，也就是「虚拟节点」。论文还列出它带来的第三个好处：一个节点能负责多少虚拟节点，可以按它的容量来定。这正是本章两个「毛病」和那个补丁的原始出处。Dynamo: Amazon's Highly Available Key-value Store, SOSP 2007 ↗
  • Apache Cassandra 的官方生产建议给出了书里没有的那半句话：虚拟节点让扩容更平滑，「但更多 token 意味着与更多对端共享数据，结果是可用性下降」，两者必须按集群的读写特征来平衡。它当前的默认值是 num_tokens: 16，并直言 16 「不推荐用于超过 50 节点的集群」——这是对「虚拟节点越多越好」最直接的反驳。Apache Cassandra 官方文档「Production recommendations · Tokens」↗
  • Discord 公开了自家规模与痛点：2017 年 12 个 Cassandra 节点存数十亿条消息，2022 年初变成 177 个节点、数万亿条消息；最折磨他们的是热分区——大型公开服务器里一个特别活跃的频道压垮单个分区，延迟不可预测、on-call 被反复叫醒。一致性哈希摊匀了 key，却摊不匀一个 key 上的流量，这是活的反例。Discord Blog「How Discord Stores Trillions of Messages」↗
  • Google 的 Maglev（自 2008 年起承载 Google 对外流量的软件负载均衡器）走了另一条路：用一张固定大小的查找表实现一致性哈希，在「节点变动时尽量少扰动」之外，把均匀度做得比朴素哈希环更好。环不是唯一实现，「最小扰动」与「均匀」可以用别的结构配平。Eisenbud 等，「Maglev: A Fast and Reliable Software Network Load Balancer」，USENIX NSDI 2016

易错点与争议

  • 把「搬家便宜」当成「分得均匀」。基本环只保证前者。均匀是虚拟节点带来的，且只是概率意义上的——100 个化身时标准差仍有 10%，最忙的机器比平均多扛一成是常态。容量规划要按最忙那台算，不能按平均算。
  • 虚拟节点越多越好。原书只提到「存储开销变大」，漏了更贵的那条：化身越多，一台机器的数据就与越多对端交织，任意两台同时故障、命中同一份数据全部副本的概率就越高，可用性反而下降。Cassandra 把默认值从早年的 256 一路降到 16 正是因为这个。「越多越均匀」在纸上成立，在生产里是陷阱。
  • 以为一致性哈希能治热点。原书提到它能缓解热点 key 问题（举了明星账号的例子），这句要读细：它均匀的是大量 key 的分布；流量若集中在单独一个 key 上，那个 key 只有一份，落哪台哪台烧。真正的解法在别处——给热 key 加随机后缀拆成 N 份，或在客户端加一层本地缓存。
  • 纠结用哪个哈希函数。SHA-1 只是个例子，MD5、MurmurHash 都行且更快；这里不需要任何密码学性质，只需要输出散得开和所有客户端算出同一个值。但反过来有条铁律：换哈希函数 = 全量搬家，和取模换 N 一样惨，所以这是个近乎不可逆的决定。
  • 忘了副本。真实存储不是「顺时针第一台」，而是「顺时针前 N 台，且跳过同一物理机 / 同一机架」——Dynamo 的 preference list 就干这件事。缺了它，环只是个路由算法，不是能存数据的系统。
  • 忘了迁移期间。书讲清了「哪些 key 要搬」，没讲「搬的过程中读写去哪」：新节点还没同步完，读请求发给谁？Cassandra 用 pending ranges 让请求在迁移期同时打到新旧两处。从算法到系统之间那道最费工的坎，恰好在书的镜头之外。

要点

① 病根一句话：hash(key) % N 把机器数量写进了路由公式，所以 N 一变、几乎所有 key 都要换机器。4 台挂成 3 台，约 75% 的 key 搬家；理想值只有 25%。

② 代价是雪崩不是麻烦：缓存层 100,000 QPS、命中率 99% 时，一次全局再哈希能把穿透到数据库的请求从每秒 1,000 拉到 75,000，放大约 75 倍。

③ 解法只有一个思路：把 N 从公式里拿掉。哈希空间首尾相接成环，服务器和 key 各自落点，key 顺时针遇到的第一台就是归属。加减一台只搬 1/N——这正是 Karger 1997 年论文给出的 k/n 性质，也是理论最优。

④ 基本环有两个毛病，都源于随机落点：弧长不均（移除一台后邻居可能负担翻倍）与 key 扎堆。记住：环只保证搬家便宜，从没保证分得均匀。

⑤ 虚拟节点是那个补丁：一台机器在环上派出多个化身，用大数定律压方差。100 个化身标准差约 10%、200 个约 5%；顺带还能表达机器强弱——强的多派几个。

⑥ 环不是唯一答案：Redis Cluster 走的是 16384 个固定 slot + 一张映射表，多一个控制面，换来「哪块搬到哪」完全可控。

⑦ 但化身不是越多越好：Cassandra 官方说更多 token 会降低可用性，默认值是 16，且不推荐用于 50 节点以上的集群。生产上的答案是十几个，不是几百个。

⑧ 它没解决的：单个热 key（Discord 的热分区就是活例）、跨分片事务、副本放置、迁移期的读写路由。面试里能说清受影响区间怎么算和虚拟节点的可用性代价，才算真懂这一章。
