微内核架构：小核心守住主流程，变化都关进插件

Fundamentals of Software Architecture · Ch 12 · Mark Richards & Neal Ford · 2020

EN →

这一章讲什么？

你的浏览器装过广告拦截、翻译、密码管理这些扩展吧？浏览器本身没变，装一个扩展就多一样本事，卸掉也不影响上网。写代码用的编辑器也一样：装个插件就能写一门新语言。这一章讲的就是这种软件形状：一个小而稳的核心，外加一圈可插可拔的插件，书里叫微内核架构，也叫插件架构。

打个比方：一台带接口的厨师机

厨房里的多功能厨师机，主机只管一件事：转。想揉面就装面钩，想打蛋就装打蛋头，想绞肉就装绞肉配件。配件之间互不认识，每个配件只要能插进主机那个统一规格的接口就能用。厂家出新配件，你家的主机不用换。

旧世界为什么难

不这么做的话，所有特殊情况都写在主程序里：「如果是这款手机就这样估价，如果是那款就那样」。一年后这里有几百个「如果」，改一处怕牵连别处，加一款新手机就得把整个程序重新测一遍、重新上线。

核心机制：主机、配件、说明书、接口

这套结构就四样东西。主机：只做每次都要走的那条主流程。配件：每一种特殊情况一个，各管各的，互相不打交道。配件清单：主机手里有一本册子，记着有哪些配件、各自怎么找到。统一接口：每个配件都按同一个规格插进来，主机不用知道配件内部怎么做。

有的配件要关机才能换，有的开着机就能插拔——后者更方便，但需要更复杂的主机。

带来了什么 / 该怎么选

它最适合「核心固定、花样常变」的软件：浏览器、编辑器、报税软件、按地区规则不同的保险理赔。便宜、好懂、加新花样不碰老代码。代价是：它通常仍是一整台机器，某个配件特别忙时没法只给它加人手，主机一倒全部停摆。

一句话记住

微内核就是小核心 + 插件 + 一本配件清单 + 统一接口：把会变的东西关进插件，核心就能长期不动。

一句话

你以为微内核是操作系统内核才谈的东西，其实它是最常见的产品型软件形状：核心系统只留最小功能或「主干流程」，所有定制、特例、新功能都关进彼此独立的插件，靠注册表找到它们、靠契约和它们说话。FoSA 第 12 章说明，它是唯一既可按技术、也可按领域分区的风格；成本 5 星、简单性 4 星，但作为单体，伸缩、弹性、容错仍是 1 星。

Glossary · 术语表

  • 单体（monolith）：所有代码打成一个部署单元一起上线；微内核通常属于单体。
  • 插件（plug-in）：独立的小模块，按约定接入主程序，增加功能或处理特例。
  • 圈复杂度（cyclomatic complexity）：代码里分支路径有多少，if/else 越多越高，越难测。
  • 接口 / 契约（contract）：双方约定好的输入、输出和行为，只要守约，内部怎么实现都行。
  • JAR / DLL：Java 与 Windows 下打包好的代码库文件，可以被主程序加载调用。
  • REST / 消息队列：两种跨进程通信方式：前者发 HTTP 请求等回复，后者把消息丢进队列由对方异步取走。
  • OSGi：Java 世界的模块化运行时框架，允许程序运行中安装、卸载模块。
  • ZooKeeper / Consul：分布式协调与服务发现工具，常用来登记「某个服务在哪」。
  • 技术分区 / 领域分区 / 架构量子：按技术职责还是业务领域切组件（第 8 章）；能独立部署的最小单元（第 7 章）。

坐标

Part II「架构风格」第三章，接在分层（第 10 章）、管道（第 11 章）之后，是三种单体风格的最后一个；下一章基于服务的架构（第 13 章）开始走向分布式。现实对应：IDE、浏览器、CI 服务器这类产品，以及规则因客户、地区而异的业务系统。

这章要解决什么

书一开头就点出它的天然场景：产品型应用——打包好、下载、作为单个单体部署、装在客户那里跑的软件。这类软件有个共同难题：核心功能很稳定，但不同用户要的扩展千差万别，而且一直在变。

不解决会怎样？书里的例子是电子设备回收：每收一台旧手机，要按机型做一套不同的评估。若全写进核心，就是一个巨大的条件分支，每加一款机型都要改核心、重测全部、重新部署，改一款的规则还可能误伤另一款。业务应用也一样：保险理赔规则每个司法辖区都不同，书举例说有的州允许石子打裂挡风玻璃时免费更换、有的州不允许。把几千条规则堆进一个规则引擎，书形容它会变成规则的「大泥球」。

核心内容，讲透

① 拓扑：核心系统 + 插件

整个风格只有两类组件。核心系统的定义书给了两种：一是运行系统所需的最小功能——Eclipse 的核心只是个基础文本编辑器，装上插件才变成可定制的 IDE；二是主干流程（happy path）——几乎不含定制处理的通用流程。把圈复杂度从核心挪进插件，核心的可扩展性、可维护性、可测试性都会上升。

核心系统内部可以再用分层或模块化单体来组织；表现层可以嵌在核心里、单独拆出，甚至自己也是一个微内核。

② 插件：独立、无相互依赖、三种接法

插件是独立的组件，承载特化处理、附加功能和定制代码，用来增强或扩展核心。书强调：插件之间最好没有依赖，否则一个插件的改动会连锁影响另一个，插件化的意义就没了。

接法有三种。编译期插件：最简单，但增删改任何一个都要重新部署整个单体。运行期插件：不重新部署核心就能增删，书点名的管理框架有 Java 的 OSGi、Penrose、Jigsaw 和 .NET 的 Prism。这两种都是点对点：核心直接调用插件入口类的方法，插件以 JAR、DLL、Gem 等共享库或命名空间（如 app.plugin.<domain>.<context>）的形式存在。第三种是远程插件：每个插件是独立服务，核心通过 REST 或消息调用。

远程接法换来更好的解耦、伸缩与吞吐，不用 OSGi 也能运行期替换，还能异步调用插件。代价书也写明：整个架构从单体变成分布式，部署更难、更复杂、更贵；而且用 REST 同步调用时，一个插件无响应，请求就完成不了。书的结论是：点对点还是远程，按实际需求选，别为了时髦上远程。

数据方面：插件不应直接连中央共享数据库，由核心负责把需要的数据交给插件；插件可以有只属于自己的数据存储，比如某个评估插件自带规则库。

③ 注册表：核心怎么知道有哪些插件

核心需要知道有哪些插件、怎么找到它们，这就是注册表。每条记录含插件名、数据契约和远程访问协议细节（如果是远程插件）。最简单的注册表就是核心里的一张映射表，书中的示例把机型名映射到插件类名、消息队列名或 REST 地址；复杂的可以用 Apache ZooKeeper、Consul 这类发现工具。

④ 契约：插件与核心之间的那份约定

契约通常对一类插件统一，内容是行为、输入数据、输出数据，可以用 XML、JSON 或对象表达。书中设备回收的契约是一个评估接口：assess() 执行评估、register() / deregister() 增删注册；输出带评估报告、能否转售、估值与转售价。

当插件出自第三方、你控制不了它的契约时，书的建议是在两者之间加一层适配器，把第三方契约翻译成标准契约，让核心不必为每个插件写特殊代码。这条是整个风格的命门：核心一旦开始认识某个插件的私有细节，插件就不再「可插拔」。

System Design · Day 9 API 设计 — 插件契约就是一份对外 API：一旦公开，破坏它的代价由所有插件作者承担

⑤ 书中的特征评分

微内核是书里唯一既可技术分区、也可领域分区的风格：插件按领域划分（每个机型、每个辖区一个）时偏领域分区；核心内部常按技术分层。部署上通常是单体，架构量子数为 1。评分：整体成本 5 星；简单性 4 星；可部署性、可测试性、可靠性、模块化、可演进性、性能 3 星；可伸缩性、弹性、容错性 1 星。理由：

  • 可测、可部署、可靠略高于平均：功能隔离在独立插件里，改动的测试范围和部署风险都缩小，运行期插件尤甚。
  • 性能 3 星，比分层和管道的 2 星高：微内核应用通常不大，也较少陷入分层的污水池反模式；还能拔掉不需要的插件让应用更轻。
  • 伸缩、弹性、容错 1 星：根源仍是单体部署。

判据一句话：你的系统能不能分出「每次都走的主干」和「因人因地而异的特例」？能，而且特例在持续增长，微内核几乎是最便宜的答案。反过来，如果「特例」之间要互相调用、共享状态，或者主干本身就在剧烈变化，硬切插件只会造出一堆互相纠缠的模块。

为什么重要 / 落到真实系统

大厂实证 · 以下为公开资料中的做法与主张（转述）
  • Eclipse（2004）：Eclipse 3.0 把运行时重建在 OSGi 之上（即 Equinox），除一个很小的内核外，几乎所有功能都是插件——书里拿它当「核心 = 最小功能」的标准例子。Eclipse 3.0 发布说明 / Equinox 项目文档（转述）
  • Microsoft · VS Code：官方文档说明扩展运行在单独的「扩展宿主」进程里，目的是不让扩展拖慢编辑器启动与界面响应。这是给单体微内核补上的一道容错隔离。VS Code 扩展 API 文档 · Extension Host（转述）
  • Mozilla · Firefox 57（2017）：Mozilla 宣布 Firefox 57 起只支持 WebExtensions，停用旧式扩展。旧式扩展能直接触碰浏览器内部，导致核心改造（多进程等）处处受阻。这是契约过宽的反面教材：核心被插件「认识」得太深，就再也动不了。Mozilla Add-ons Blog，“The Road to Firefox 57”，2017（转述）
CS Papers · 如何把系统拆成模块 — Parnas 的信息隐藏：按「什么会变」来切模块，正是核心与插件的分界依据

落到架构评审，可以问三件事：核心里还剩多少 if/else 在区分特例？插件之间有没有偷偷互相调用？契约里有没有暴露核心内部结构？落到面试，被问「微内核的优缺点」，可以答：「小核心守主干、特例关进独立插件，靠注册表发现、靠契约通信；成本低、扩展性好、性能在单体里最好，但仍是单体，伸缩容错 1 星。」

易错点与争议

  • ≠ 操作系统的微内核：名字借自 OS，但本章说的是应用级结构风格，和 Mach、seL4 那套进程隔离不是一回事。
  • 插件互相依赖是头号坑：一旦插件 A 调插件 B，就回到了耦合的老路；书明确要求插件之间独立。
  • 核心偷偷长胖：为某个大客户在核心里加一个「特殊处理」很诱人，几次之后核心就又是大泥球。
  • 远程插件不是免费升级：换成 REST 后就要承担第 9 章分布式计算的八个谬误，特征评分整张表随之改写。
  • 第三方插件 = 信任边界：单体里插件与核心同进程，一个插件崩溃或作恶会拖垮整体；书着墨不多，这是现实产品（浏览器、IDE）要额外做沙箱与进程隔离的原因（本页补充）。
  • 时代局限：书把它当单体评点；如今很多 SaaS 平台用 webhook、低代码扩展把「插件」放到租户侧或云端，权衡要另算。

要点

① 微内核 = 核心系统 + 插件，也叫插件架构；天然适合产品型软件，也适合规则因客户、地区而异的业务系统。

② 核心的两种定义：运行所需最小功能（Eclipse），或主干流程；把圈复杂度挪进插件。

③ 插件独立、彼此无依赖；不直连中央数据库，可有私有数据存储。

④ 三种接法：编译期（简单但需整体重部署）、运行期（OSGi 等）、远程（REST / 消息，变成分布式）。

⑤ 注册表记录插件名、契约与访问方式，简单的是一张映射表，复杂的用 ZooKeeper、Consul。

⑥ 契约统一定义行为、输入、输出；第三方插件用适配器接入，核心不写特例代码。

⑦ 唯一可同时技术分区与领域分区的风格；量子数 1。

⑧ 成本 5 星、简单性 4 星，性能 3 星为单体之最；伸缩、弹性、容错 1 星。

⑨ 实证：Eclipse 建在 OSGi 上；VS Code 把扩展隔离进单独进程；Firefox 因旧扩展契约过宽而整体换代。

⑩ 面试复述：「小核心守主干、特例进插件，注册表发现、契约通信；便宜好扩展，但仍是单体。」
