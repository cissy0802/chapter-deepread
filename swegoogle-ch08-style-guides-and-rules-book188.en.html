Style Guides and Rules

Software Engineering at Google · Ch 8 · Style Guides and Rules · Shaindel Schwartz · 2020

中文 →

What is this chapter about?

Google has tens of thousands of engineers, nearly all writing code in one giant shared repository. Everyone has habits: how far to indent, how to name things, which fancy tricks to reach for. This chapter is about how Google sets the "house rules" for writing code — and who those rules actually serve.

An analogy

Think of a city's traffic code. "Drive on the right" is not smarter than "drive on the left" — the British manage fine. What matters is that everyone in the city does the same thing, so nobody crashes. Other rules really do prevent danger, like a lower speed limit outside schools. And some are just advice, like "turn on your headlights in the rain": no fine, but experienced drivers do it anyway.

A strange thing first

Many of Google's rules forbid a "cleverer" way of writing something, for one reason only: the reader won't follow it. The writer wants a neat shortcut; the rule says no — because code is written once but read by dozens of people for years.

How it works, intuitively

  • Save the reader's effort: let the writer type a bit more so later readers understand at a glance.
  • Every rule must earn its keep: the more rules, the harder to remember them, so only make rules for problems that are common and genuinely harmful. Mistakes nobody makes don't need a rule.
  • Same beats perfect: like the traffic code, many choices have no right answer. Pick one, everyone follows it, and moving between teams costs nothing.
  • Let machines do machine work: spacing and line breaks are fixed by an automatic tidying tool in one click, so nobody argues about them in review — people focus on what the tool can't see.
  • Rules can change: each one records why it exists, so when that reason stops being true, there is a basis for changing it.

What it buys you / how to choose

Should your team have coding rules? Look at how many people there are and how long the code must live. A handful of people on a small project can get by with a verbal agreement; dozens of people maintaining code for years should write the rules down and let tools enforce as much as possible. The honest cost: rules always flatten some personal preferences and locally better choices, and too many of them turns into bureaucracy.

Remember it in one line

Rules aren't about looking pretty — they make code written by thousands of people read as if one person wrote it.

In one sentence

You think a style guide is about whether code "looks nice"; this chapter says it is about readability and maintainability at scale: the only legitimate reason for a rule is to keep the codebase manageable over time and headcount — so every rule must pull its weight, optimize for the reader rather than the writer, and be handed to a tool whenever a tool can enforce it.

Glossary

  • Style guide: an organization's written conventions for a language — from naming and formatting to which language features may be used.
  • Code review: a colleague reads and approves a change before it is merged; every change at Google is reviewed.
  • Formatter: a program that rewrites code into one uniform layout, such as Go's gofmt or C++'s clang-format.
  • Static analysis / linter: a tool that finds suspicious code by reading the source, without running it.
  • Presubmit: automatic checks that run before a change is submitted; if they fail, the change can't land.
  • Monorepo: the whole company's code in one repository, so anyone may read or change anyone else's code.
  • Readability: Google's internal per-language certification; only engineers who hold it can approve a change's style and idiom in that language.
  • Exception: an error-handling mechanism that jumps out of the current function and up the call chain to find a handler.

Where it sits

The first chapter of Part III, "Processes." It takes Ch1's thesis — software engineering = programming × time × scale — down to the most everyday level, how each line gets written, and leads into Ch9 Code Review (human enforcement of the rules) and Ch20 Static Analysis (automated enforcement).

What problem this chapter solves

Google's single repository holds roughly 2 billion lines worked on by tens of thousands of engineers (the order of magnitude disclosed in CACM, 2016). Engineers switch teams often, and code written by one person today may be inherited tomorrow by someone on another continent. Without shared rules, every team and every person has a dialect: reading someone else's code starts with "translating" its style; reviews burn time on indentation and braces; automated refactoring tools can't cope with endless variations; and dangerous language features creep in here and there, laying traps only experts can spot.

The chapter answers three questions: why rules exist, which rules to make, and how to get tens of thousands of people to actually follow them. Its stance is clear: rules are not a display of taste but a tool with a cost — every rule must be remembered, followed and sometimes compromised on by every engineer — so it has to be paid for.

Core ideas, in depth

1. Rules vs. guidance: laws and advice are different things

The chapter first separates two words. Rules are hard requirements — "must / must not" — enforced by reviewers and tools. Guidance is recommendations and best practices — "prefer / should" — that help you write better but aren't mandatory. Google's style guides keep only the most necessary rules; guidance lives in teaching material of many shapes: language courses, C++ "Tips of the Week" (some later published through Abseil), and advice in reviews.

Why separate them? Because writing advice down as rules bloats the rulebook until nobody can remember it, while writing truly important constraints down only as advice fails to stop accidents. The split is itself a trade-off.

2. Five principles for making rules

The chapter (and the "Goals" section at the top of Google's public C++ style guide) lists the tests a rule must pass:

  • Rules must pull their weight: a rule asks everyone to remember it, so its benefit must exceed that cost. The counterexample is telling: the C++ guide doesn't discuss goto — not because goto is fine, but because it is already vanishingly rare, so a rule would only add memory burden.
  • Optimize for the reader, not the writer: code is read far more often than written, so let the writer type more and the reader relax. In practice: prefer explicit over implicit, and "leave a trace" in the code — make an ownership transfer or a call that can fail visible at the call site, instead of making readers dig into the implementation to guess.
  • Be consistent: many choices have no right answer (two-space or four-space indent); the value is in the whole codebase agreeing. Consistency makes moving between projects free, lets tools assume one shape of code, and helps the codebase survive time.
  • Avoid error-prone and surprising constructs: powerful, obscure, easy-to-misuse language features get restricted. The Python guide says of "power features" such as custom metaclasses: avoid these features in your code.
  • Concede to practicalities when necessary: rules serve goals, not faith; performance or interoperability with existing code and outside libraries can justify an exception.

3. Three kinds of rules: avoid danger, enforce best practice, build consistency

By purpose, the rules in a style guide fall into roughly three groups:

  • Avoiding danger: banning or limiting language features that produce subtle bugs. An example is the C++ guide's restrictions on static / global objects with non-trivial destructors — their construction and destruction order is hard to predict, a classic "only experts know it will blow up" trap.
  • Enforcing best practices: locking in what makes code clearer and easier to maintain, such as names that describe meaning, comments that state intent, limits on hard-to-follow implicit behavior.
  • Building in consistency: choosing one option for everyone where no option is objectively right — naming case, indentation, file layout. For this group the answer matters less than having an answer, so it is the last thing that should be re-argued in review.

The three groups differ in how strictly and how automatically they can be enforced: consistency rules can almost all go to a formatter; danger rules can mostly be caught by static checks; best-practice rules depend most on human judgment and are carried mainly by review and readability.

4. A rule must say "why" to be changeable

Rules are not frozen. The chapter stresses that each decision in the style guide comes with its rationale, precisely so that later you can judge whether it should still exist — when the original reason no longer holds, the rule should change. Each language has a small group of senior engineers acting as style arbiters, who evaluate proposed changes and make the final call; decisions rest on trade-off analysis, not anyone's personal preference. Rules also allow exceptions, but the bar is high: only when following the rule clearly costs more.

The best public example is the C++ guide's stance on exceptions. It says its "advice against using exceptions is not predicated on philosophical or moral grounds, but practical ones": Google's existing code is not exception-tolerant, so adding exceptions costs more — and it admits that "things would probably be different if we had to do it all over again from scratch." That is the template for "concede to practicalities" plus "record the rationale": a rule that admits it is a trade-off made under historical conditions.

5. Enforcement: whatever a tool can do, don't leave to people

Writing a rule down is only the start; tens of thousands of people follow it because of an enforcement chain. The chapter describes three layers:

  • Education: courses, readability certification, coaching in review — passing on the reasons behind rules and handling what tools can't judge (does this name say what it means, is this abstraction right).
  • Code review: the human backstop — but human attention is expensive and shouldn't be spent on whitespace.
  • Tools: error checkers flag violations automatically before submit or during review; formatters simply rewrite code into the compliant shape. Tool enforcement is consistent, scalable and emotion-free — nobody feels insulted when a machine flags their indentation.

The gofmt case study is the chapter's highlight. Go has shipped with the official formatter gofmt from the start, with almost no tunable layout options — it produces one format. As a result, the Go community has almost no formatting debates; more importantly, once formatting is uniform, machine rewriting of code becomes safe — an automated tool edits the code, runs gofmt, and the output is indistinguishable from hand-written code, paving the way for large-scale automated changes (Ch22).

Key trade-offs and choices

Checker / presubmitDangerous features, mechanically decidable best practicesHighToo many false positives and engineers ignore or bypass it; rules must be precise

The rule of thumb: if a machine can decide a rule, don't make people guard it; if it needs human judgment, don't make it a hard rule. A small team (under ten people, code living a year or two) often needs just a formatter plus a one-page convention; at hundreds of people and a ten-year lifespan, a written guide, arbiters and a certification process start paying off.

Why it matters / in real systems

This chapter hands you a yardstick for reviews and interviews alike: for any "should we add this rule" debate, ask whom it optimizes for, what it costs, and whether it can be automated. Asked in an interview "how do you keep a team's code style consistent," the strong answer isn't "we hold a meeting" but "formatting goes to a formatter, dangerous patterns to a linter, and review looks at design." It also explains why low- or zero-config formatters like Prettier, Black and rustfmt spread through their ecosystems — the same line of thinking as gofmt.

Pitfalls and debates

  • "Style guide = formatting spec" — a misconception. Formatting is the shallowest, most automatable layer; the bulk of Google's guides restricts dangerous features and promotes readable idioms.
  • "The more complete the rules, the better" — wrong. "Pull their weight" explicitly argues against turning every recommendation into a rule; bloated rulebooks can't be remembered and end up followed selectively.
  • Consistency isn't absolute. The chapter also cautions that consistency is a means: when it clashes with readability or correctness, or drifts too far from the wider external community's conventions, re-weigh it rather than defaulting to "we've always done it this way."
  • Rules are products of history. C++ without exceptions is a constraint of Google's existing codebase, not a universal verdict that exceptions are bad; copying Google's rules into a new project may import someone else's baggage.
  • Tool enforcement requires low false positives. If a checker is inaccurate, engineers learn to ignore it (Ch20 Static Analysis goes deeper); and a formatter's first codebase-wide pass pollutes history ("who changed this line"), so it should be done once, all at once.
  • Limited vantage point. The chapter assumes a large organization with a unified toolchain, a monorepo and a review culture; heavyweight processes like readability certification usually cost small teams more than they return.

Key takeaways

① The only reason rules exist: keep the codebase manageable over time and scale — not to display taste.

② Separate rules (must / must not, enforced) from guidance (advice, taught); don't let advice bloat into rules.

③ Five principles: pull their weight, optimize for the reader, be consistent, avoid error-prone constructs, concede to practicalities.

④ Three kinds of rules: avoid danger, enforce best practice, build consistency; for consistency, having an answer beats which answer.

⑤ Every rule records its rationale and is changed by style arbiters on trade-offs; when the reason is gone, the rule should go.

⑥ C++ without exceptions is the template for practicality: the reason is existing code, not philosophy — from scratch it might differ.

⑦ Enforcement chain: formatter → checker / presubmit → human review; what a machine can decide, people shouldn't guard.

⑧ gofmt: one format ends the debate and makes machine rewriting safe, paving the way for large-scale changes.

⑨ Pitfalls: style ≠ formatting; more rules isn't better; tools need low false positives; Google's rules carry Google's history.
