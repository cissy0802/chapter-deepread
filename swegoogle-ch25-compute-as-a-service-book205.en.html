Compute as a Service

Software Engineering at Google · Ch 25 · Compute as a Service · Onufry Wojtaszczyk · 2020

中文 →

What is this chapter about?

Once the code is written, some computer has to run it. This chapter is about that deceptively simple wish — "just give me some machines to run my stuff" — and what it grows into at a company with tens of thousands of engineers and millions of machines. Google's internal system for this is called Borg; the Kubernetes you hear about everywhere is its open-source descendant.

A strange fact first

Google engineers usually don't know, and don't care, which machine their program runs on. The system may stop it at any moment and restart it somewhere else — and that is considered normal, not an incident.

Why the old world was hard

The early way was a craft workshop: copy the program onto machines one by one, log in to each to start it, and watch each one. In 2002 Jeff Dean called running one data job a "logistical nightmare": find 50+ machines, start and babysit each; if one died, nobody picked up its work automatically; and people fought over machines using a hand-edited "sign-up" file. More machines meant more tired people.

How it works, intuitively

  • Cattle, not pets: when a pet gets sick you sit with it and nurse it back. Cattle just have numbers — if one falls, another replaces it automatically. Programs should be like that: a fresh copy can always step in, no human rescue needed.
  • One central scheduler: like a hotel front desk that knows which rooms are free, assigns guests automatically, and moves them if a room breaks.
  • Shared flat, separate rooms: one big machine hosts several programs, like flatmates — each room has a door and its own meter, so a noisy neighbour can't disturb you. That is a "container".
  • Empty seats go to the night shift: websites keep lots of spare seats for sudden rush hours, and most sit empty. Unhurried computing jobs fill those seats and give them up the moment a rush arrives — so that work runs almost "for free".

What it brings / how to choose

The win: however big you grow, the people managing machines don't have to double. But programs must be written differently — they can't keep their only copy of data on the local machine, because they may be moved at any time. As for which platform — your own machines, rented virtual machines, a container platform, or "serverless" where you don't even see servers — there is no single answer: the less you manage, the less you can tweak, and once chosen, it is hard to switch.

One line to remember

Treat machines as replaceable cattle: hand them to one shared scheduler, and write programs that don't mind being moved — the bigger you get, the better the deal.

In one sentence

You think "compute as a service" just means "renting a machine"; the chapter argues what it really changes is how you write software: treat machines and processes as cattle, not pets, hand them to one shared pool that bin-packs, self-heals and moves them, and write software that treats local state as something that can vanish. And once you pick a compute platform, Hyrum's Law will lock you into it for years.

Glossary

  • Compute as a Service (CaaS): engineers describe only what to run and how many resources it needs; the platform decides which machine.
  • Scheduler: the central service that knows which machines are free and assigns programs to them.
  • Replica: one of several running copies of the same program, any of which can do the same work.
  • Virtual machine (VM): a whole simulated computer with its own operating system on top of a physical one — strong isolation, but slow to start and heavy.
  • Container: a lightweight unit that shares the host OS kernel and only isolates a process's resources and view of the filesystem.
  • cgroups / namespaces: Linux kernel features; the first caps how much CPU and memory a group of processes may use, the second gives processes their own private view of process IDs, network and so on.
  • Bin-packing: fitting tasks of different sizes as tightly as possible onto a limited set of machines.
  • Batch vs serving: batch jobs run to completion and care about throughput; serving jobs run indefinitely, answer requests, and care about per-request latency.
  • Idempotency: sending the same request twice has the same effect as sending it once.
  • Hyrum's Law: with enough users, every observable behaviour of a system will be depended on by somebody — promised or not.

The problem this chapter tackles

The starting point is a humble wish: I wrote code, give me hardware to run it. On one machine, SFTP, SSH and a manual start are enough; the trouble is that this approach consumes people linearly or even superlinearly with scale. Jeff Dean's 2002 design doc for the "Global WorkQueue" lists every symptom: get a list of 50+ machines, start and monitor a process on each; no automatic migration if a machine dies; processes interfere, so a human-maintained "sign-up" file throttles machine use, giving poor scheduling and contention.

As an organization grows, three axes grow at once: the number of different applications, the number of copies of each, and the size of the largest one. Without automation, the organization collapses under operational load.

The core ideas, explained

1. From manual to Borg: eliminating toil step by step

The path is clear, and each step hands a class of human work to machines:

  • Simple automation: parallel deploy scripts; export metrics like "am I alive" to dashboards; an on-machine agent kills and restarts a process that hasn't reported alive for 5 minutes (in the cloud: an autohealing policy).
  • Automated scheduling: the first real "service" appears — a central scheduler that knows the full machine list and picks free machines on demand; the hand-kept sign-up file disappears. Combined with broken-machine detection (e.g. scanning logs for mass disk read errors), bad machines get no new work, and work on a dead machine is restarted on a new one, the old one abandoned.
  • Containers and multitenancy: one program per machine is wasteful — there are far more job types than machine types; buying machines takes months, so you buy big for future growth; and old and new machines mix. The fix: each program declares its CPU, RAM and disk needs, and the scheduler bin-packs replicas onto a pool.

Sharing brings its own problem, under a memorable heading: "My neighbor's dog barks in my RAM." A replica promises 1 CPU and 200 MB of RAM, then — through a bug or organic growth — uses more; neighbouring serving jobs see latency blips or get OOM-killed (Google long ago decided swap latency is so horrible that an OOM kill and migration is always preferable). Add dependency-version clashes, fights over /tmp, and sensitive data. VMs isolate well but are slow to boot and heavy, poor for short-lived batch work. So when Borg was designed in 2003, Google chose containers: cgroups (contributed by Google engineers to the Linux kernel in 2007) plus chroot jails, bind mounts and overlay filesystems.

The last piece is rightsizing. Asking humans for resource numbers is flawed: the program grows, the config doesn't, slack erodes release by release until a spike finds it insufficient — an outage. Automating it is surprisingly hard: only recently did more than half of resource usage across Google's fleet come to be set by rightsizing automation; but it covers a larger share of configurations, so most engineers no longer worry — "easy things should be easy, complex things should be possible."

2. Architecting for failure: cattle must be stamp-out-able

The scheduler may unilaterally kill your task and move it (kernel upgrade, bad disk, repacking), and as the software author, I should neither know nor care why. So every instance must be re-creatable with no human involved: a broken pet gets a panicked human nursing it; cattle are named replica001 to replica100, and when one falls another is stamped out.

But being cattle isn't the same as handling failure gracefully. The book's arithmetic: validating one million documents at one second each takes one machine about 12 days; sharded over 200 machines, about 100 minutes. With static assignment, each killed worker adds about 50 minutes, and with 200 machines a kill — likely more than one — is nearly certain. Instead, split the set into 1,000 chunks of 1,000; a worker reports each finished chunk and takes the next, so a failure loses at most one chunk.

Serving jobs fit more naturally: requests are already small chunks, dynamically spread by load balancing. When Borg plans to move a container, it gives notice; the container refuses new requests and finishes in-flight ones, and the load balancer must understand "I'm not accepting". Watch for three misfits: stateful "leaders", static sharding (100 servers each holding 1% — lose one and a slice of data is temporarily unservable), and services found by hostname.

3. Writing software for managed compute

State is the main obstacle to cattle: replace an instance and in-process state and local disk are gone. So anything that must outlive one request goes to external durable storage; that storage is itself cattle, via replication (usually 3 to 5 copies), which is hard to get right (writes need consensus) — hence GFS, Bigtable and Spanner. Locally keep only re-creatable data: caches, warm-up, batched writes, and periodic checkpoints for long computations. A hard-won cache lesson: provision the cache for your latency goals, the core application for total load — if the cache layer is lost, the uncached path is slower but survives; the cost is paying for that redundancy.

Connecting to a service: a hardcoded hostname (even as a startup flag) means you're not cattle. Add a layer of indirection: others refer to you by an identifier that survives restarts, which the scheduler writes into a resolution system as it places you — service discovery, usually with load balancing. The consequence is retries: the server may be taken away before it answers. Mutating requests must be idempotent, and a great tool is client-assigned IDs (if that order ID exists, report success). One more oddity: the scheduler loses touch with a machine, restarts its work elsewhere, then the machine comes back — two instances both believing they are replica072, one more reason for idempotency.

One-off code: scanning 1 TB of logs takes a day on one machine and minutes on a few hundred cores. A thousand core-hours costs nowhere near a day of engineering time, so approval gates to save compute are a false economy; but it's easy to take too much by accident (a new hire debugging didn't notice their workstation had spawned 8,000 full-machine workers). Google's answer: low-priority batch is effectively free anyway, so engineers get nearly unlimited low-priority quota.

4. One pool for everything: batch rides free on serving slack

In the WorkQueue era, batch jobs shared one pool and each serving job had its own dedicated machines. Borg, started in 2003, merged them into a single pool per datacenter, with two gains. First, serving machines became cattle too (the Borg design doc: machines are anonymous; programs don't care which machine they run on), instead of n teams each running their own pool with drifting practices. Second, subtler: serving jobs must be overprovisioned for spikes and outages, so their requests can fill a machine while real utilization is only 30%. Overcommitting serving jobs would defeat the slack, but the spare 70% can host batch — when serving needs resources back, batch is frozen (CPU) or killed (RAM). Batch cares about aggregate throughput and is cattle anyway, so it happily soaks up the slack. The book's conclusion: most of the time Google runs batch effectively for free.

Serving jobs in a shared pool need extras: service discovery; throttled rescheduling (restarting half a batch job's replicas is a throughput blip; half of a serving job leaves too few to carry traffic); and several seconds of warning before a kill.

5. Containers are an abstraction — so Hyrum's Law applies

Containers began as isolation, but their bigger role became an abstraction boundary between software and machine: as machines change, only the container layer (one team) adapts, and every team's application stays put. A filesystem abstraction lets outside software bring its own layout and dependencies; ports should belong to the container too — Google initially left them out, so binaries hunted for free ports themselves, and PickUnusedPortOrDie has over 20,000 call sites in Google's C++ codebase. Docker used namespaces to give containers a virtual NIC; Kubernetes went further, giving every pod its own IP.

The cautionary tale is PID exhaustion in 2011. Linux's default PID_MAX is about 32,000 and can be raised with a config change — but by Hyrum's Law, "PIDs fit in five digits" had become an implicit API: log storage put PIDs in record names, which broke past the length limit with six digits. The fix became a long project: cap PIDs per container, then split thread and process PID spaces (few depended on thread PIDs); step three, PID namespaces, revealed many systems assuming {hostname, timestamp, pid} uniquely identifies a process — still being cleaned up eight years later. The lesson isn't "use PID namespaces" but: some machine resource is always under-isolated, so prefer a container system used by a broad community, where others already hit and fixed those issues.

Configuration belongs in code too: a standard configuration language expressing "update to the new binary, never taking down more than 5% of capacity at a time" beats CLI flags kept in someone's head; shared standard snippets are what make swapping the memcache implementation or pushing a security fix company-wide feasible.

Key trade-offs and choices

The chapter's rule: first decide cattle or pets, then pick the level of abstraction. One pet machine per team per datacenter makes cost grow superlinearly — teams × datacenters.

Why it matters / in real systems

Asked in an interview "why is Kubernetes designed this way?", this chapter gives the roots you can retell: per-pod IPs, label-based grouping, declarative config, stateless replicas with external storage — nearly each maps to a pitfall Borg hit. In a platform review it warns: lock-in is extreme — code uses every feature, and a whole ring of logging, monitoring and config tools grows around it.

Pitfalls and debates

  • "Containers make you cattle" is a myth: re-creation is only recovery; smoothness needs dynamic chunking, graceful shutdown and idempotent retries.
  • Serverless is compared to the wrong baseline. Most discussions compare it with "VMs as pets", so it looks revolutionary; the chapter says compare it with persistent containers, where the gap shrinks to scale-to-zero and control.
  • "Free batch" has preconditions: serving must hold lots of reserved slack and batch must tolerate kills; other workload shapes may not qualify.
  • Don't mistake while true; do ./binary; done for self-healing. The book calls it actively harmful under Borg: it hides failure, so the platform's failure handling never kicks in.
  • Customization is a chronic disease. Every "just one flag for this one user" widens the explicit or implicit API; Kubernetes started cleaner, but the book admits it now faces the same issues with broad adoption.
  • Dated: written in 2020, GPU / TPU scheduling gets only a mention; AI-era accelerator scheduling is not covered.

Key takeaways

① Scale needs a common compute infrastructure: application count, replica count and largest-app size grow together, and manual SFTP + SSH makes ops grow superlinearly.

② The path: simple automation → central scheduling + bad-machine quarantine → bin-packed multitenant containers → rightsizing; automation sets just over half of Google's resource usage but most configurations.

③ Cattle, not pets: instances are re-created without humans; the scheduler may kill tasks unilaterally, and the author shouldn't care why.

④ Cattle only guarantees recovery; smoothness needs dynamic chunking (a million docs into 1,000 chunks), graceful shutdown, and no static sharding or hardcoded hostnames.

⑤ Put state in replicated external storage; keep only re-creatable data locally; size the cache for latency and the core for total load; retries must be idempotent — client-assigned IDs help.

⑥ One pool for everything: batch soaks up serving's reserved slack; the Borg paper measured 20–30% more machines if split.

⑦ Containers are an abstraction boundary and prime Hyrum's Law territory: five-digit PIDs, self-picked ports and the ash-for-Bash swap all bit; prefer widely used community systems.

⑧ Choosing a platform is choosing lock-in: persistent containers vs serverless hinges on state and scale; centralize vs customize and public / multi / hybrid cloud each have costs — keep an escape hatch.
