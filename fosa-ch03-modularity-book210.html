专业书籍精读 · Fundamentals of Software Architecture · 第 3 章

模块化：内聚、耦合与共生性

Fundamentals of Software Architecture · Ch 3 · Mark Richards & Neal Ford · 2020

EN →

这一章讲什么？

人人都说代码要「模块化」——拆成一块一块的。可真问一句「这样拆得好不好」，多数人只能凭感觉。第 3 章想把这份感觉变成能数、能比的东西：一块代码里的东西是不是真该待在一起？块和块之间牵扯有多深？改一处，要连带改几处？

打个比方：搬家打包

搬家时你会把碗碟装一箱、书装一箱、衣服装一箱。一个箱子里的东西彼此相关，这叫「抱团紧」；拆箱时不用满屋找东西，这叫「箱子之间牵扯少」。最糟的箱子是「杂物箱」——遥控器、袜子、螺丝刀挤在一起，只因为它们刚好在同一个抽屉里。代码里也有这种杂物箱，书里把它排在最差的那一档。

为什么好结构会自己变坏？

房间不收拾会越来越乱，代码也一样。今天赶工顺手调用一下隔壁模块的内部，明天又加一条，时间一长，模块之间的线缠成一团。作者说得直白：保持模块化需要持续花力气，它不会自己维持。

三把尺子

第一把量抱团紧不紧：一个模块里的功能是不是都围着同一件事转。可以看它内部的数据是不是被大家共用——如果一半功能只碰甲、另一半只碰乙，那它其实是两个模块硬塞在一起。

第二把量牵扯多深：有多少别的模块依赖它、它又依赖多少别人。就像公司里一个人，几十个同事都靠他交接，他一请假整层楼都停；反过来一个谁都不靠他、他却靠十个人的岗位，别人一变他就得跟着变。

第三把最细，叫「共生」：改了 A，B 就必须跟着改，才能保证系统还对。比如两张表约定「第一格写座位号、第二格写名字」，谁要是填反了，系统不会报错，只会悄悄出错。这种约定越隐蔽、隔得越远，越危险；所以原则是——离得越远，彼此之间的约定越要简单明白，复杂的牵连只留在同一个模块内部。

带来了什么

有了这三把尺子，「这个拆法好不好」就从吵架变成量一量：哪个模块是被所有人依赖、谁都不敢动的「火药桶」，哪个是没人用的空架子，一目了然，还能让工具每天自动检查。代价也得说一句：尺子只看得见结构，看不见业务含义——两样东西该不该在一起，最后还得靠人懂业务来判断。

一句话记住

好的模块 = 里面抱团紧、外面牵扯少、离得越远约定越简单；而这份整齐，要花力气天天维护。

一句话

你以为模块化是一种「品味」，其实它可以量：FoSA 第 3 章给架构师三把尺子——内聚（cohesion）量模块内部、耦合（coupling）量模块之间、共生性（connascence）量「改一处要连带改几处」；并提醒你，模块化是在和软件的熵对抗，不花力气它就会退化。

Glossary · 术语表

  • 模块（module）：一组相关代码的逻辑分组，比如 Java 的包（package）、.NET 的命名空间（namespace）。本章把它当通称用。
  • 类（class）/ 方法（method）/ 字段（field）：面向对象里的基本单位；类是一张模板，字段是它存的数据，方法是它能做的动作。
  • 抽象类 / 接口（abstract class / interface）：只声明「能做什么」、不写具体怎么做的类型；与之相对的是写满实现的具体类。
  • 依赖（dependency）：A 的代码用到了 B，B 一变 A 就可能受影响。
  • 重构（refactoring）：不改外部行为，只改内部结构，让代码更好改。
  • 竞态条件（race condition）：结果取决于两件事谁先发生，时序一变就出错。
  • 熵（entropy）：借自物理，指系统自发趋向无序的倾向。
  • 适应度函数（fitness function）：把某条架构规则写成能自动跑的检查（第 6 章展开）。

坐标

Part I「基础」第三章，接在第 2 章「架构思维」之后。前两章讲架构师怎么想，这一章给出第一套可度量的工具；第 7 章的「架构量子」会把共生性推到分布式层面，第 8 章再把模块升格为组件。现实对应：单体拆分前的依赖分析、代码评审里「这段该不该放这」的争论。

这章要解决什么

几乎所有平台都支持模块化（包、命名空间、Java 9 起的模块系统），但「怎么拆才好」长期停留在感觉层面。后果很具体：一个被 30 个包依赖、却写满具体实现的工具包，谁改一行都要回归一大片；一个「工具类」越长越大，最后什么都往里塞。作者的判断是，软件天然趋向无序——保持好结构要持续投入能量；而要投入得有方向，先得能量化「好」与「坏」。本章不发明新理论，而是把几十年来分散的度量——结构化设计年代的内聚与耦合、Robert Martin 的包度量、Page-Jones 的共生性——整理成架构师的一套语言。

核心内容，讲透

① 内聚：七个等级 + 一个能算的指标

内聚指一个模块的各部分在多大程度上应该待在同一个模块里。书沿用经典的七级划分，从好到坏：

  • 功能内聚（functional）：每部分都和其它部分相关，且模块包含完成功能所需的一切——最理想。
  • 顺序内聚（sequential）：一部分的输出是另一部分的输入。
  • 通信内聚（communicational）：几部分围绕同一份信息工作，比如「往库里加一条记录」并「据此发一封邮件」。
  • 过程内聚（procedural）：几部分必须按特定顺序执行。
  • 时间内聚（temporal）：只因在同一时刻发生而放一起，典型是启动时初始化一堆互不相干的东西。
  • 逻辑内聚（logical）：逻辑上同类、功能上无关，比如一个装满各种静态方法的 StringUtils。
  • 巧合内聚（coincidental）：除了在同一个文件里，毫无关系——最差。

书里的例子：一个「客户维护」模块有新增、更新、查询客户、通知客户，外加「取客户订单」「取消客户订单」。后两个该不该挪进独立的「订单维护」？答案是看情况：挪走后客户模块只剩两三个操作、显得过薄吗？订单模块会不会反过来需要大量客户信息、从而在两边之间拉出很多新依赖？内聚的判断，本质上是拿模块大小去换模块间耦合。

要机器能算，书引入面向对象度量里的 LCOM（Lack of Cohesion in Methods，方法间内聚缺失度）：白话就是数一数类里有多少组方法彼此不共用任何字段。

LCOM 的价值在于找出「看起来是一个类、其实是两三个」的结构问题；但书也直说它的局限：它只看结构、看不懂语义——两个方法不共用字段，并不意味着它们在业务上不该放一起。

② 耦合：传入、传出，与「主序列」

耦合度量源自 Yourdon 与 Constantine 的结构化设计（1979）：传入耦合（afferent coupling, Ca）是有多少外部代码依赖我；传出耦合（efferent coupling, Ce）是我依赖多少外部代码。在此之上，Robert Martin 派生出三个包级指标：

  • 抽象度（abstractness, A）：抽象类与接口占全部类的比例。全写在一个巨型 main() 里的代码，抽象度接近 0。
  • 不稳定度（instability, I = Ce / (Ce + Ca)）：白话是「我向外依赖的那部分，占我全部依赖关系的比例」。接近 1：谁都不依赖我、我却依赖一堆——自己好改，但别人一变我就跟着坏；接近 0：大家都依赖我——改我一行，波及一片。
  • 与主序列的距离（distance from the main sequence, D = |A + I − 1|）：理想的包落在 A + I = 1 这条线上——越被依赖越该抽象，越具体越该少被依赖。D 越接近 0 越健康。

算一个具体的：某工具包被 8 个包依赖（Ca=8）、自己只依赖 2 个（Ce=2），则 I = 2/10 = 0.2；若它没有任何接口（A=0），D = |0 + 0.2 − 1| = 0.8——深陷痛苦区。解法不一定是拆包，而是让依赖指向抽象：抽出接口，让 8 个调用方只认接口，具体实现退到后面，A 上升、D 下降。这一切都能交给工具每晚自动算，也就成了第 6 章适应度函数的原料。

论文精读 · 如何把系统拆成模块 — Parnas 1972 的信息隐藏：按「可能会变的决定」而不是按处理步骤切模块，正是让依赖指向稳定抽象的源头

③ 共生性：把「耦合」细分成九种

Meilir Page-Jones 在 1996 年提出共生性（connascence）：若改动一个组件，必须同时改动另一个组件才能保持系统正确，则二者共生。它比「有依赖 / 没依赖」细得多，分两大类。

静态共生（看源码就能发现）：名字（调用方必须知道方法名）、类型（必须对齐类型）、含义 / 约定（如约定 1 代表真、魔法数字）、位置（参数顺序——书里的例子是 updateSeat("14D", "Ford, N")，两个参数都是字符串，传反了编译器不会报错）、算法（客户端和服务端必须用同一个哈希算法校验）。

动态共生（只有运行时才暴露）：执行顺序（必须先设收件人再 send()）、时序（两个线程的先后决定结果，即竞态条件）、值（几个值必须一起变，分布式事务里尤为常见）、身份（几个组件必须引用同一个实体，比如共同更新一条分布式队列）。

共生性还有三个维度：强度（strength）——越容易重构掉越弱，静态整体弱于动态；局部性（locality）——同一模块内的共生远比跨模块的可接受；程度（degree）——波及几个类，影响面小的强共生有时也能忍。Page-Jones 给了三条指导：用封装把系统拆开以减少总共生；尽量减少跨越封装边界的共生；尽量把共生留在封装边界之内。 Jim Weirich 把它压成两条好记的规则：强度规则（把强形式重构成弱形式），局部性规则（元素相距越远，越该用弱形式）。

位置共生就是典型的「降级」示例：把 updateSeat(seat, name) 改成传一个带命名字段的对象，或用 SeatNumber 类型替代裸字符串——位置共生降为名字或类型共生，传反了编译器当场就会拦下。

④ 统一耦合与共生性，以及它们的盲区

书指出：结构化设计年代的耦合分类（数据耦合、印记耦合、控制耦合等）和共生性可以对齐——共生性其实是一套更细、更面向对象的耦合语言。但两者都诞生于单进程、面向对象的年代，没覆盖现代分布式架构的关键问题，比如服务之间同步还是异步通信、谁拥有哪份数据。作者因此在第 7 章引入架构量子（architecture quantum），把「必须一起部署、一起失效」的那团东西当作分布式层面的度量单位。

为什么重要 / 落到真实系统

这一章的度量不是纸上谈兵：二十多年来它们一直被做成工具，嵌进构建流水线。「模块化单体」的流行，本质上就是在不拆服务的前提下用这些尺子守住模块边界。

  • Shopify 的 Packwerk 自述是「用来强制边界、把 Rails 应用模块化的 Ruby gem」：把文件归组为包、声明包级可见性，并在 README 里引 Sandi Metz 的话说明动机——知道别人「是谁、做什么」本身就是一种依赖，会推高改动成本。它也诚实列出局限：只分析常量引用、不追踪方法调用和对象传递，宁可漏报也不误报——正是「工具只看得见结构」的又一例。Shopify/packwerk README（GitHub）↗

落到面试与评审：被问「这个服务边界为什么这样划」，能说出「它被谁依赖、依赖谁、跨边界的约定是哪一级共生」，比「感觉高内聚低耦合」有说服力得多。

易错点与争议

  • 「高内聚低耦合」不是口号：两者常互相拉扯——拆得越细内聚越高，模块间耦合往往越多。表 2 的「看情况」才是常态。
  • 别为了指标好看刷分：随手加接口能把 A 拉高、D 拉低，但没有多态需求的接口只是噪音；指标是体检报告，不是 KPI。
  • LCOM 低≠设计好：它只证明字段共用，不证明业务上该在一起。
  • 共生性不是越少越好：完全没有共生的两段代码根本不协作。目标是弱且近，而不是零。
  • 时代局限：这些度量生于单进程 OO 年代，对微服务间的同步调用、数据归属无能为力——书自己也承认，所以才有第 7 章的架构量子。
  • 熵是常态：一次性重构不能一劳永逸，必须把度量接进 CI 持续跑，否则结构会慢慢回到原样。

要点

① 模块化是对抗熵：不持续花力气，结构就会退化。

② 内聚七级：功能 > 顺序 > 通信 > 过程 > 时间 > 逻辑 > 巧合；StringUtils 式「工具类」是逻辑内聚。

③ LCOM 数「互不共用字段的方法组」，能揪出几合一的类，但看不懂语义。

④ Ca 被依赖、Ce 依赖别人；I = Ce/(Ce+Ca)，D = |A+I−1|，越接近 0 越健康。

⑤ 痛苦区 = 具体又被重度依赖；无用区 = 抽象却没人用。解法：让依赖指向抽象。

⑥ 共生性：改 A 必须改 B。静态五种（名字、类型、含义、位置、算法）弱于动态四种（执行顺序、时序、值、身份）。

⑦ 三维度：强度、局部性、程度；Weirich 两规则——强转弱、越远越弱。

⑧ 拆不拆模块是「模块大小 vs 模块间耦合」的权衡，答案常是「看情况」。

⑨ 这些度量看不见分布式问题（同步 / 异步、数据归属），第 7 章用架构量子补上。
