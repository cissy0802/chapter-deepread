软件趋势

A Philosophy of Software Design · Ch 19 · Software Trends · Ousterhout · 2nd ed 2021

EN →

这一章讲什么？

写软件这行，每隔几年就流行一套「正确做法」：面向对象、敏捷、测试先行、设计模式……每一套都有人奉为圭臬。这一章，作者拿出全书一直在用的那把尺子——「它让系统更简单了，还是更复杂了？」——把这些流行做法挨个量一遍。

打个比方

就像减肥圈每年都有新潮流：生酮、断食、代餐。聪明人不问「现在流行什么」，只问一句「它到底让我更健康了吗」。有的确实管用，有的只是让你短期体重变轻、长期身体更糟。

旧世界为什么难

流行做法往往打包出售：一套方法里，有一半真的好，另一半只是「顺带的习惯」。照单全收的团队，会连坏的那半一起学去，而且很难察觉——因为大家都这么做。

核心机制直觉

  • 「继承」分两种。好几样东西共用一个「插座形状」，很省心；但子女直接住进父母的房子、随手动父母的家具，两边就再也分不开了。
  • 敏捷、一小步一小步做，作者赞成。但每一小步应该是「搭好一个零件」，而不是「赶出一个功能」。
  • 写测试，作者举双手赞成。有了测试这张安全网，才敢大胆重新整理代码。
  • 「先写测试再写代码」，作者不赞成。它让人一门心思「让这一条测试通过」，像只盯着脚下的路，忘了看地图。
  • 「套路」要对症。现成的设计套路合适时很好用，硬套就像穿别人的鞋。
  • 到处开「取值 / 改值」小窗口，等于把家底换个门牌照样亮给外人看。

带来了什么 / 该怎么选

遇到任何新潮流，都别先问「大家用不用」，先问「它让系统更简单了吗」。一句诚实的代价：这把尺子只是作者的经验判断，不少同行（比如测试先行的拥护者）并不同意他的结论。

一句话记住

潮流不是理由；每个新做法都要用「降不降复杂度」这把尺子重新量一遍。

一句话

你以为这章是在点评几个时髦方法论；其实它是在示范一种检验方法：拿全书的唯一标尺——复杂度——去量面向对象、敏捷、单元测试、TDD、设计模式、getter/setter。结论并不一边倒：接口继承和单元测试降复杂度，实现继承、TDD 和滥用的模式与 getter/setter 往往在加复杂度。真正要带走的是那句收尾：遇到任何新范式，都从复杂度的角度去质疑它。

Glossary · 术语表

  • 复杂度（complexity）：本书定义为让系统难以理解和修改的一切，根源是依赖与晦涩。
  • 深模块（deep module）：第 4 章概念，接口简单、背后功能多的模块；接口复杂而功能少的叫浅模块。
  • 信息隐藏（information hiding）：把设计决策藏在模块内部，外部不必知道、也无法依赖。
  • 继承（inheritance）：面向对象里，子类从父类获得接口或实现的机制。
  • 组合（composition）：不靠继承，而是让一个类持有另一个辅助类的对象、调用它完成工作。
  • 战术式编程（tactical programming）：第 3 章概念，只求尽快让功能跑起来、不顾设计，与之相对的是战略式编程。
  • 单元测试（unit test）：开发者写的、单独检验一个类或方法的小测试。
  • 重构（refactoring）：不改变外部行为、只调整内部结构的代码修改。
  • getter / setter：只用来读取或修改对象某个内部变量的方法，如 getName()。

坐标

全书第 19 章，在讲完注释、命名、一致性、一目了然之后，把视线从「怎么写」转向「流行的做法对不对」；下启第 20 章「为性能而设计」，同样是用复杂度去检验一个常见的借口。

这章要解决什么

工程团队采纳方法论，很少是因为有人算过它对复杂度的影响，更多是因为「业界都这么做」。问题在于，一个方法论常常把好坏两部分捆在一起：敏捷的「小步迭代」是对的，但它顺带的「先交付、设计以后再说」会把团队推向战术式编程；面向对象的「私有变量」是信息隐藏，但「实现继承」却在制造跨类依赖。

不加分辨地接受，就会在一个十几人维护多年的代码库里，以「最佳实践」的名义积累复杂度——而且没人会怀疑它，因为它是「最佳实践」。本章要做的，是给每个趋势拆包：哪一部分真的降低了复杂度，哪一部分没有。

核心内容，讲透

一、继承：接口继承是杠杆，实现继承是依赖

作者先肯定面向对象里的一部分：私有方法与私有变量直接服务于信息隐藏。然后把「继承」劈成两半。

接口继承：父类只定义方法签名，不实现，各子类各自实现同一个接口。它对复杂度是杠杆：学会一个接口，就能用在多种场合。作者的例子是 I/O：同一个读写接口，既能读写磁盘文件，也能读写网络套接字。按第 4 章的术语，一个接口的实现越多，它就越深——背后藏的东西越多，而读者要学的还是那几个方法。

实现继承：父类把方法的默认实现也给了子类，子类可以沿用或覆盖。它的好处是减少重复代码，父类一改、子类自动跟上。代价是父类与子类之间产生依赖：父类和子类常常读写同一批实例变量，这就是信息泄漏；想理解或修改继承链上的任何一个类，往往得把整条层级都读一遍。作者因此建议慎用：先考虑用组合——把共享逻辑放进小的辅助类——能否得到同样的好处；实在要用，就把父类管理的状态与子类管理的状态分开，某些实例变量只由父类的方法负责，子类只读或通过父类方法访问。

论文精读 · 如何把系统拆成模块 · 信息隐藏 — Parnas 1972 的原始论证：模块边界应围绕「可能变化的设计决策」来划，父子类共享状态和 getter/setter 都是在拆这道墙

二、敏捷：增量对，但增量应是抽象，不是功能

敏捷开发（agile development）的核心是增量、迭代：先做一小部分、评估、再调整。作者认为这和他的主张一致——大系统不可能一开始就把抽象设计对，必须边做边修。

风险在于，敏捷容易滑向战术式编程：它把开发者的注意力放在「交付功能」上，鼓励为了尽快拿出可运行的软件而推迟设计决策。作者的修正是全章最该记住的一句：开发的增量应当是抽象，而不是功能。可以等到真正需要某个抽象时再做它，但一旦需要，就花时间把它设计干净，并让它带一点通用性。

三、单元测试：作者最坚定的支持

作者说自己是单元测试的坚定支持者，理由直接落在设计上：测试让重构变得安全。没有测试集，任何大的结构调整都可能引入难以察觉的 bug，开发者就会回避重构、只做最小改动打补丁——这正是复杂度累积的方式。有了覆盖良好的单元测试，改完跑一遍就知道有没有改坏，人才敢做战略式的结构改进。作者也区分了单元测试与系统测试（system test，检验整个应用各部分能否协同工作，常由独立的测试团队编写）。

四、TDD：同一句话的反面

测试驱动开发（test-driven development，TDD）要求先写测试、再写刚好让测试通过的代码。作者不喜欢它，理由和敏捷的风险一脉相承：TDD 把注意力放在让某个具体功能跑起来，而不是找到最好的设计——这是战术式编程的典型形态，开发节奏过于零碎，过程中也没有一个明显的时刻去做设计，于是容易「一路打补丁直到测试通过」。

作者给了一个例外：修 bug 时先写测试——先写一个因该 bug 而失败的单元测试，再修，确认测试转绿。这样既证明 bug 真修好了，也防止它复发。

五、设计模式：对症才有用，多不等于好

设计模式（design pattern）是解决某类常见问题的成熟方案，如迭代器、观察者。作者承认它们有价值：问题吻合时，直接套用一个人人都认得的模式，既省设计时间、又降低读者负担（这其实是第 17 章的一致性）。最大的风险是过度应用：把一个问题硬塞进某个模式，而定制方案本可以更干净。用了模式不会自动让系统变好，只有模式恰好合适时才会；模式不是越多越好。

六、getter 与 setter：给泄漏换个门牌

在 Java 社区，「变量私有、配一对 getter/setter」几乎是默认写法。支持者的理由是：读写时可以附加逻辑，将来换内部表示也不必改接口。作者的回答分两层：其一，getter/setter 是浅方法——通常只有一行——却挤进类的接口，增加噪声而几乎不提供功能；其二，更根本的是，通过 getter/setter 暴露实例变量，仍然是在暴露实现，违背信息隐藏。所以他的建议不是「写得更好」，而是尽量避免暴露实现数据；只有当实例变量非暴露不可时，getter/setter 才算有点道理。

七、收尾：一把尺子量所有潮流

本章结语是一条元规则：每当遇到一个新的软件开发范式，就从复杂度的角度去质疑它——它在大型软件系统里真的帮助降低复杂度吗？很多提议表面上听起来不错，但深究下去，有的会让复杂度更糟。

论文精读 · No Silver Bullet（没有银弹） — Brooks 1986 做的是同一件事：逐个审视面向对象、AI、图形化编程等「希望」，追问它们能削减多少本质复杂度

选型判据：问三个问题——它减少了模块间的依赖吗？它让重要信息更显眼了吗？它让人更容易做战略式而非战术式的改动吗？三个都答「否」的做法，再流行也只是习惯。

为什么重要 / 落到真实系统

本章几条判断，都能在主流语言设计和大厂规范里找到公开的同调或反驳。

大厂实证 · 公开可查

  • Go 语言（Google）干脆不提供类型继承。官方 FAQ 说，主流面向对象语言「在类型之间的关系上讨论得太多」；Go 让类型自动满足接口，接口可以只有一个甚至零个方法，「没有类型层级需要管理或讨论」，并举 fmt.Fprintf 可以写向任何输出、不只是文件为例——几乎就是本章「接口继承是杠杆、实现继承是负担」的语言级落地。出处：Go FAQ · Why is there no type inheritance?
  • Google Python 风格指南规定：getter/setter 只应在读写「提供有意义的角色或行为」时使用；如果一对 getter/setter 只是简单读写内部属性，就应该直接把属性设为公有。与作者「浅方法只添噪声」同一判断（不过它给出的出路是公开属性，作者则更进一步，主张根本少暴露）。出处：Google Python Style Guide · 3.15 Getters and Setters
  • 反方：Ousterhout 与 Robert Martin 的公开辩论（2024–2025）。Martin 指出书中对 TDD 的描述不准确：按他的三条定律，TDD 的最小循环只有几秒，外面还套着一层几分钟的「红—绿—重构」反思。Ousterhout 承认描述有误、表示下一版会修正，但坚持担忧不变，并称 TDD 是他见过「最极端的战术式编程形式之一」；他也承认自己没有亲身实践 TDD。他主张的替代是一次写一块较大的单元——几个方法或一个类、几十到几百行——写完立即补齐单元测试。出处：johnousterhout/aposd-vs-clean-code

落到日常：评审里看到新写的抽象类和三层继承，先问能不能改成接口加组合；规划迭代时，把「做完一个干净的模块」当成一个交付单位；新服务先把单元测试搭起来，再谈重构；看到一排一行的 getter/setter，先问调用方为什么需要这些内部数据。

易错点与争议

  • 「作者反对面向对象」。不对。他明确支持私有成员和接口继承，反对的只是实现继承的滥用。
  • 「作者反对测试」。恰恰相反，他对单元测试的支持比对本章任何趋势都坚定；他反对的是「测试先行、以测试驱动结构」这一特定流程。
  • TDD 之争远未结束。书中对 TDD 的描述被 Martin 指为不准确，作者已承认；而 TDD 支持者认为「重构」一步正是设计时刻。较公允的读法：本章的担忧是风险提示（容易退化为战术式），不是实证结论——作者自己也说没有亲身实践过 TDD。
  • 「增量应是抽象」不等于大设计先行。作者同样认为抽象不可能一次设计对；他要的只是每个增量完成时，抽象是干净的。
  • getter/setter 的语境差异。C#、Kotlin、Python 的属性语法让「先公开字段、需要时再加逻辑」不必改调用方，作者的批评在这些语言里成本更低；真正的问题仍是暴露了什么，而非语法。
  • 证据是经验性的。全章结论来自作者的工程与教学经验，没有对照实验；它示范的是「怎么问」，而不是一锤定音的裁决。

要点

① 本章示范一种方法：用「复杂度」这一把尺子检验每个流行做法，拆开好的一半和坏的一半。

② 面向对象：私有成员服务于信息隐藏；接口继承是杠杆，实现越多接口越深。

③ 实现继承制造父子依赖与信息泄漏；先试组合，必须用时分开父子各自的状态。

④ 敏捷的增量迭代是对的，但增量应是抽象，不是功能；需要抽象时就把它设计干净。

⑤ 单元测试是重构的安全网，作者强力支持；没有测试，人只敢打补丁。

⑥ TDD 被作者视为战术式编程；例外是修 bug 时先写失败的测试。

⑦ 设计模式对症才有用，硬套就是过度设计；多不等于好。

⑧ getter/setter 是浅方法，且换汤不换药地暴露实现；尽量别暴露实现数据。

⑨ 实证：Go 不设类型继承；Google Python 风格指南要求平凡 getter/setter 改为公开属性；Martin 与作者就 TDD 公开辩论，作者承认描述有误但立场未变。
