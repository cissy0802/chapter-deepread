测试替身

Software Engineering at Google · Ch 13 · Test Doubles · Andrew Trenk & Dillon Bly · 2020

EN →

这一章讲什么？

你在网店点「付款」，背后有一段程序去银行扣钱。工程师要检查这段程序写得对不对，总不能每检查一次就真刷一次信用卡。这一章讲的就是：检查程序时，拿什么去顶替那些「不方便请到场」的东西——以及顶替过了头会出什么事。

打个比方

拍电影有替身演员：危险镜头让替身上，主角不用真从楼上跳。程序里也一样，银行、远程服务器、数据库这些「主角」又慢又贵、还时好时坏，检查时就找个替身顶上。替身大致有三种演法：

  • 仿真替身：像飞行模拟器，有真飞机的反应，只是摔不坏。
  • 念台词替身：排练时对手只念一句写好的台词，你问什么它都照本宣科。
  • 只看动作的检查：不尝菜熟没熟，只看厨师有没有按顺序打开烤箱。

旧世界为什么难

不用替身，检查要连真服务器：成百上千个检查一跑就是几个小时，还会因为网络抖一下就莫名失败。可替身一旦太好用，又会滥用。Google 吃过这个亏：早年有了能一行代码造替身的工具，大家拿它当万能锤子，几年后才发现，那些检查写起来快，维护起来累，却很少抓到真毛病——程序内部稍一调整，它们就成片报错。

核心机制直觉

  • 能请主角就请主角：主角又快又稳，就别用替身。用真的，检查才最接近真实上线的样子。
  • 请不到，就用仿真替身：它表现得和主角几乎一样，被检查的程序根本分不出来。最好由主角的「经纪团队」亲自做一个，并定期拿它和主角对一对戏，防止演着演着走了样。
  • 念台词替身少用：每句台词都要你自己写，等于把「主角会怎么回答」抄进了检查里；主角改了说法，替身还念旧台词，检查照样通过，上线却出错。
  • 只看动作，尽量不用：「厨师打开了烤箱」不等于「菜做好了」。只有当动作本身就是目的——比如确实要发出一封邮件、或者要确认没有多跑几趟仓库——才值得这么查。

带来了什么 / 该怎么选

按「真的 → 仿真 → 念台词 → 看动作」的顺序挑，检查既快又稳，也不会因为程序内部换了写法就整片变红。Google 甚至给一些程序贴上「禁止做替身」的标签，逼大家用真的或用官方仿真版。诚实的代价是：做一个靠谱的仿真替身要花真功夫，还得一直跟着主角更新。

一句话记住

替身是不得已：先用真的，再用仿真的，最后才让替身念台词、或只检查它被怎么叫过。

一句话

你以为 mock 是单测的标配，本章说替身是退路，不是默认：首选真实现，用不了就用 fake，stub 克制地用，交互测试能免则免。Google 用了几年、写了无数测试才学到：mock 框架让测试好写难养，还很少抓到 bug。

Glossary · 术语表

  • 依赖（dependency）：被测代码要调用的别的类或服务，如数据库、信用卡服务。
  • 被测系统（system under test, SUT）：当前测试正在检查的那段代码。
  • 小测试 / 单元测试：单进程内跑完、不碰网络与磁盘的快速测试（见第 11、12 章）。
  • 接口（interface）：只规定「有哪些方法」、不含实现的类型；真实现和替身都可以实现同一个接口。
  • API 契约（API contract）：一个 API 对使用者承诺的行为，如「这个方法永不返回 null」。
  • 不稳定（flaky）：代码没变，测试却时过时不过。
  • 密封（hermetic）：测试需要的一切都由测试自己掌控，不依赖外部服务的状态。
  • 值对象（value object）：只装数据、行为简单的对象，如金额、日期、地址、列表。
  • 副作用（side effect）：调用之后改变了外部世界，如写库、发邮件、记日志。

坐标

Part III「流程」，测试四连章的第三章。上承 Ch12 单元测试（那章反复说「少用 mock、验状态不验交互」），下启 Ch14 更大范围的测试（本章多次说：替身覆盖不到的风险，要靠用真依赖的大测试补）。现实对应：Mockito、googlemock、Python unittest.mock 的日常用法与滥用。

这章要解决什么

设想一个函数：向外部服务器发请求，再把响应存进数据库。写几个这样的测试还行；写成百上千个，套件要跑好几个小时，还会因为网络随机失败、测试互相覆盖数据而变得不稳定。生产代码常常跨进程、跨机器，天然塞不进「小测试」的约束——测试替身（test double）就是为此而生：一个能在测试里顶替真实现的对象或函数，像电影里的特技替身。

但替身带来三个复杂度：可测试性（代码得留出换替身的口子，事后补很贵）、适用性（用错了测试会变脆、变复杂，代码库越大损失越大）、保真度（fidelity）（替身离真实现多远；「存什么都返回空」的假数据库毫无价值，但完美保真往往做不到）。不解决会怎样？Google 自己就是反例：mock 框架刚引入时被当成万能锤子，几年后才意识到这些测试需要持续维护，却很少发现 bug。

核心内容，讲透

一、三种技法：fake、stub、交互测试

原书刻意不用「mocking」统称替身，因为这个词同时指好几件不同的事。它分三种技法：

  • 伪实现（fake）：轻量但能用的实现，行为接近真货、只是不能上生产，典型是内存数据库。往 FakeAuthorizationService 里加一个用户，之后查询就真的能查到。
  • 打桩（stubbing）：给一个本身没有行为的函数硬编码返回值，如 when(svc.lookupUser(ID)).thenReturn(null)，意思是「被问到这个用户时，就答查无此人」。
  • 交互测试（interaction testing）：不执行函数本身，只验证它被怎么调用——调没调、调几次、参数对不对，如 verify(svc).lookupUser(ID)。

mock 框架（mocking framework）（Java 的 Mockito、C++ 的 googlemock、Python 的 unittest.mock）能一行造出替身，所以「mock」一词才会多义混用。偏好排序很清楚：真实现 > fake > stub > 交互测试。

二、接缝：可测试性要提前设计

想用替身，代码得先能「换零件」。接缝（seam）就是让被测系统在测试里换用另一套依赖的口子；最常见的做法是依赖注入（dependency injection）——类需要的依赖从外面传进来，而不是自己 new。PaymentProcessor 的构造函数接收一个 CreditCardService：生产代码传入连外部服务器的真实现，测试传入替身。手写构造太啰嗦时，Google 的 Java 代码常用 Guice、Dagger 自动组装对象图。Python、JavaScript 这类动态语言能在运行时替换单个函数，依赖注入就没那么关键：可以用真实现，只覆盖不适合测试的那一两个方法。

这是前期投资：没为测试设计的代码，往往要先重构甚至重写才能加上像样的测试。

三、首选真实现：真实胜过隔离

用真实现，测试会执行依赖里的全部代码，更接近生产，信心更足；过度依赖替身，就得另跑集成测试或手工验证，太费时就会被跳过。更深一层：把一个类的依赖全换成替身，等于把「测试范围」随意地划在了作者恰好写在这个类里的代码上，而好测试应当只依赖被测 API，不依赖实现怎么拆分。真实现有 bug 导致测试失败——这是好事，说明上线也会坏；连带失败一串时，CI 能找到肇事改动。

偏好真实现叫经典派测试（classical testing）；偏好 mock 框架的叫mock 派（mockist testing）。Google 发现后者难以规模化：它要求设计被测系统时遵守严格规范，而多数工程师的默认写法更适合经典派。

@DoNotMock 案例：Google 在 Error Prone 静态分析工具里提供了 @DoNotMock 注解，让 API 所有者声明「这个类型别 mock，有更好的替代」，有人照样用 mock 框架去造它，就会收到报错，指向真实现或 fake。最常用在简单到可直接用的值对象和已有精良 fake 的 API上。所有者为什么在乎？每次 stub 或交互测试都在复制这个 API 的行为；想改实现时，可能发现它被 mock 了成千上万次，很多还违反契约（让永不返回 null 的方法返回 null）。

System Design · Day 9 API 设计 — 契约一旦公开、被上千处调用方「复制」后，改动的代价由谁承担

什么时候真实现够用：快、确定、依赖简单，三条都满足就用真的——值对象（金额、日期、地址、list / map）永远用真的。复杂代码则按三个维度权衡：

  • 执行时间：每个用例多 1 毫秒没人在乎；10 毫秒、100 毫秒、1 秒呢？没有标准答案，要看用例数（5 个用例每个多 1 秒可以接受，500 个就不行）。边界情况先用真实现，真慢了再换替身。并行（用 CPU 时间换开发者时间）和 Bazel 的构建缓存能续命。
  • 确定性：真实现更复杂，更易不确定（如依赖线程顺序）。常见病根是不密封：读外部 HTTP 服务器，它过载或改版测试就挂——用替身，或用测试控制生命周期的密封实例（下一章）。系统时钟同理，用写死时间的替身。偶发可忍，频繁就换。
  • 依赖构造：真实现要把整棵依赖树造出来，new Foo(new A(new B(new C()), new D()), new E(), …, new Z()) 既难写，构造函数一改还得跟着改；而 @Mock Foo mockFoo; 只要一行，诱惑极大。原书的理想解：复用生产代码的对象构造逻辑（工厂方法或自动依赖注入），只要它灵活到能换入替身。

四、用不了真实现：首选 fake

fake 行为接近真货，被测系统甚至分不出自己在和谁打交道。原书的 FakeFileSystem 用一个内存 map 存「文件名 → 内容」，而且真实现找不到文件会抛 FileNotFoundException，fake 也必须抛。fake 稀缺的组织，工程师要么忍受慢而不稳的真实现，要么退回 stub 与交互测试。

谁写、写在哪：fake 要领域知识，真实现变了它也得跟着变，所以应由真实现的所属团队编写和维护。几个用户可能不划算，几百个用户就收益明显。只在不能用于测试的代码根部做一个——给数据库 API 做 fake，而不是给每个调用它的类各做一个。多语言客户端的服务，可以只写一个 fake 服务让各客户端连过去，跨进程稍重，但只要仍快就划算。

保真度是 fake 的核心概念。不必在磁盘存储、延迟、资源消耗上保真（要测性能就得用真实现），但必须忠于 API 契约：同样的输入，返回同样的输出、产生同样的状态变化——真 database.save(itemId) 遇到重复 ID 报错，fake 也要报错。原书的说法是：fake 要对真实现完美保真，但只从测试的视角。哈希 API 的 fake 不必算出和真实现一模一样的哈希值，只要契约没承诺具体值、同一输入结果唯一即可。罕见边界路径可以不实现，但应快速失败，明确告诉工程师「这里 fake 不适用」。

fake 必须有自己的测试，否则会随真实现演进而悄悄走样。做法是契约测试（contract tests）：针对 API 公开接口写一套测试，同时跑在真实现和 fake 上。跑真实现的那份较慢，但只有 fake 的所有者需要跑。

没有 fake 怎么办：先请 API 所有者做；不行就把对该 API 的调用包进一个类，给这个类写 fake，只覆盖用到的子集（Google 有团队把这种 fake 回馈给了所有者）。fake 也可看成优化：提速抵不过成本，就继续用真实现。

五、stub：好用，但会让测试不清晰、脆、少验证

stub 来得快，于是凡是真实现不顺手就想打桩。原书点了三宗罪：不清晰——多出来的桩代码冲淡了测试意图，不熟悉实现的人看不懂；如果你得在脑子里把被测系统走一遍，才明白为什么要桩这几个函数，就说明 stub 用错了。脆——桩把实现细节泄漏进测试，实现一改测试就得跟着改。少验证——when(calc.add(1, 2)).thenReturn(3) 等于在测试里手抄了一段契约，无从保证抄得对；stub 也存不了状态，save(item) 之后没法 get(item.id())。

原书的反例桩了五个函数（服务器可用、开启事务、初始化、支付、结束事务），最后只能 verify(server).pay(…)，因为没法知道钱扣没扣。换成 fake 信用卡服务器，测试只剩「调用 → 断言 getMostRecentCharge(card) 等于 500」。

stub 什么时候合适：需要某个函数返回特定值、把被测系统推进某个状态时（如返回三笔交易来测计数），以及模拟真实现或 fake 很难触发的错误和异常。规矩是：每个被桩的函数都应和断言直接相关，所以一个测试只桩少数几个；需要桩很多，要么是 stub 用滥了，要么是被测系统太复杂该重构。即便合适，真实现或 fake 仍然更好。

六、交互测试：能免则免，只验有副作用的调用

原书对照了两个排序测试：状态测试调用 sortNumbers([3,1,2])、断言结果是 [1,2,3]，用快排还是冒泡无所谓；交互测试只 verify(mockQuicksort).sort(…)——它根本无法知道数字排好没有，因为替身不会排序。交互测试的主要问题就在这：它只能验证「某函数按预期被调用了」，然后假设「调用了 save 就等于存进去了」；状态测试则真的去验证这个假设。它还把「被测系统调用了哪个函数」这一实现细节写进测试，Google 有人戏称这类测试为变更探测器测试（change-detector tests）：生产代码任何改动都让它失败，哪怕行为没变。

交互测试只在两种情况下值得：一是做不了状态测试——真实现太慢又没有 fake，退而求其次验证调用，至少有点信心；二是调用次数或顺序本身就是行为——比如缓存应当减少数据库访问，用 verify(db, atMostOnce()).selectRecords() 断言「最多查一次」。单测里做不了的状态验证，用对真数据库的集成测试补上。

两条最佳实践：只对改变状态的函数做交互测试——sendEmail()、saveRecord()、logAccess() 有副作用，值得验；getUser()、readFile() 这类只读函数的返回值会被被测系统拿去做别的事，那些结果本就能断言，再 verify 一遍只是冗余和脆弱。避免过度指定——测「问候语含用户名」，就只用 setText(eq("Fake User"), any(), any()) 校验相关参数，别把问候语、版本号、图标全钉死，不同行为拆成不同测试。

关键权衡与选型

表 1 · 四种选择，诚实的代价

选择保真度抓真 bug维护成本适用场景
真实现最高强，连依赖的 bug 也抓构造依赖树、可能慢 / 不确定快、确定、依赖简单；值对象一律用
fake契约层面高强编写 + 跟随真实现更新 + 契约测试，由所有者承担真实现慢或不密封，且用户多

交互测试不执行实现最弱，只知「被调用过」变更探测器，任何改动都红无法做状态测试，或调用次数 / 顺序本身是行为

表 2 · 真实现还是替身：三个维度怎么判

维度倾向真实现倾向替身原书的建议
执行时间每例多 1 毫秒量级；用例少每例多 1 秒量级 × 数百用例先用真的，真慢了再换；并行与构建缓存可续命

这不是「替身越少越好」的教条：原书反复说没有精确答案，fake 本身也要成本。但默认值在真实现那一端，偏离要有理由。

为什么重要 / 落到真实系统

在 Google 的规模上，一个类型被 mock 上万次，所有者就改不动它；一个好 fake 却能被上千个测试共享。替身策略不是个人测试风格，而是 API 演进能力的一部分。面试被问「你怎么 mock 依赖」，好答案是先问能不能不 mock。

易错点与争议

  • 「mock = 替身」——混用是混乱之源。本章把 fake、stub、交互测试分开讲，mock 框架只是造 stub 和做交互测试的工具。
  • 「stub 和 fake 差不多」——差在有没有行为。fake 有状态、能存能取、忠于契约；stub 只会背你给它的答案。
  • 「单测就该把依赖全隔离」——Google 倾向相反。按类边界切依赖，是把测试范围随意绑在实现拆分上。
  • 「fake 要和真实现一模一样」——只需对测试关心的契约保真。延迟、存储介质、具体哈希值都可以不同；不支持的路径要快速失败。
  • 争议：经典派 vs mock 派。本章明确站经典派，但承认最早的 mock 框架作者就是 mock 派；Mockito wiki 也推荐读倡导 mock 派的《Growing Object-Oriented Software, Guided by Tests》。Google 的理由是「难以规模化」，这是组织规模下的判断，不是普适定论。

要点

① 替身解决真依赖慢、贵、不确定的问题，但带来可测试性、适用性、保真度三个代价。

② 三种技法：fake（能用的轻量实现）、stub（硬编码返回值）、交互测试（只验调用）；别用「mock」一词混称。

③ 接缝靠依赖注入，可测试性是前期投资，越晚越贵。

④ 首选真实现：快、确定、依赖简单就用真的，值对象永远用真的；真实现的 bug 让测试红是好事。

⑤ 判据三维：执行时间（先用真的，慢了再换）、确定性（不密封就换替身或密封实例）、依赖构造（复用生产的工厂 / DI）。

⑥ 用不了真实现就用 fake：所有者写、建在根部、对测试视角下的契约保真、不支持就快速失败、用契约测试防走样。

⑦ stub 三宗罪：不清晰、脆、少验证；只在推进状态、模拟错误时用，且每个桩都要和断言直接相关。

⑧ 交互测试能免则免：只在做不了状态测试、或调用次数 / 顺序就是行为时用；只验有副作用的调用，别过度指定。

⑨ @DoNotMock 的启示：被 mock 上万次的 API 改不动，替身策略决定 API 的演进能力。
