为性能而设计

A Philosophy of Software Design · Ch 20 · Designing for Performance · Ousterhout · 2nd ed 2021

EN →

这一章讲什么？

你点开一个 App，转圈转了三秒——背后往往是某段程序「太慢」。很多程序员觉得：要快，就得把代码写得又绕又难懂。这一章的作者说：恰恰相反，干净简单的代码，多数时候本来就更快。

先说个怪事

作者曾把自己团队里一段处理「数据包裹」的代码推倒重写，目标是提速。结果新版本速度快了将近一倍，代码反而更短了。快和简单，在这里是同一件事。

旧世界为什么难

常见的两种极端都有问题：一种人从第一天起就到处「抠速度」，把代码写成一团乱麻；另一种人完全不管快慢，等系统慢到不行时才发现——慢在每个角落都有一点，找不到一个能下手的地方。

核心机制直觉

  • 先知道什么「贵」。在电脑里，查自己手边的东西像从口袋里掏钥匙；跨网络问另一台机器，像打电话去外地；读老式硬盘，像寄一封信等回音。差距是成千上万倍。
  • 简单本身就快。少绕弯、少「万一」的检查，机器要干的活就少；绕来绕去的代码，常常是在做重复的活。
  • 两条路一样干净，就挑快的那条。不用多花力气，养成习惯就行。
  • 先量，再动手。人对「哪里慢」的直觉经常错，像医生不验血就开刀。
  • 只为「最常走的那条路」优化。就像超市专门开一条「五件以下」快速通道：大多数顾客走快道，少数复杂情况统一去普通柜台，别让每个顾客都排同一条长队。

带来了什么 / 该怎么选

平时写得简单、顺手挑快的；真的需要提速时，先量出慢在哪，再把最常走的那条路修得又直又短。一句诚实的代价：重新设计那条最常走的路，往往要推翻已有的结构，花的功夫不小，所以只在量过、确认值得时才做。

一句话记住

简单通常就是快；要更快，先量，再把最常走的那条路修直。

一句话

你以为性能和整洁是一对冤家；其实本章的结论是：干净的设计与高性能大体兼容，复杂的代码往往更慢——因为它在做多余或重复的事。作者的性能观可以压成三步：平时对「什么贵」有感觉、在同样干净的方案里挑快的；真要提速时先测量；需要根本性改进时，围绕关键路径重新设计。

Glossary · 术语表

  • 延迟（latency）：完成一次操作要等多久，常以纳秒（ns）、微秒（µs）、毫秒（ms）计；1 ms = 1000 µs = 100 万 ns。
  • 缓存未命中（cache miss）：CPU 要的数据不在高速缓存里，只好去更慢的主存取。
  • 动态内存分配（dynamic memory allocation）：程序运行时临时向系统申请一块内存，如 C 的 malloc、C++ 的 new。
  • 微基准（micro-benchmark）：单独测一个小操作耗时的小程序。
  • 剖析（profiling）：测量程序各部分花了多少时间，找出最耗时的「热点」。
  • 关键路径（critical path）：最常见情况下，完成一项任务必须执行的那条代码路径。
  • 特殊情况（special case）：偏离常见情况、需要额外分支处理的情形。
  • 深模块（deep module）：第 4 章概念，接口简单、背后做很多事的模块。
  • RPC（远程过程调用）：像调用本地函数一样，请求另一台机器执行操作并返回结果。

坐标

全书第 20 章，紧接第 19 章用复杂度检验软件潮流，这里检验的是另一个常见借口——「为了性能，只能写复杂」；下启第 21 章「分清什么重要」。对应现实里每次「要不要为了快而加一层缓存 / 改一种结构」的评审。

这章要解决什么

前 19 章都在劝人把代码写简单。一个合理的反问是：简单会不会很慢？如果答案是「会」，那全书的建议在性能敏感的系统里就站不住。

现实里有两种失败。一种是处处抠性能：为了几纳秒引入特殊分支、手写缓存、打破抽象，代码难懂，而且省下的时间多半落在不重要的地方。另一种是完全无视性能：每个模块都「慢一点」，累积起来系统慢了数倍，却没有一个明显的热点可以下手。本章要给出的是一条中间路线：花最少的复杂度，拿到大部分该拿的性能。

核心内容，讲透

一、性能思维：对「什么贵」有数量级的感觉

作者不主张从第一天起就为性能做大量工作，也不主张完全不管。他的做法是：在几个同样自然的方案之间，挑更快的那个——前提是它一样干净。要做到这一点，就得知道哪些操作根本上昂贵。书里点名了四类：

  • 网络通信：同一数据中心内一次往返约 10–50 µs，相当于上万条指令的时间；跨广域网往返 10–100 ms。
  • 二级存储 I/O：磁盘一次约 5–10 ms，闪存约 10–100 µs。
  • 动态内存分配：malloc / new 涉及分配、释放和垃圾回收的开销，比普通指令贵得多。
  • 缓存未命中：从主存取一次数据，要花几百条指令的时间。

知道这些，日常选择就有了依据。作者的例子：需要按键查找大量数据时，哈希表通常比有序映射（ordered map）快好几倍；在 C/C++ 里要一组结构体时，一次分配一整块，往往比逐个分配、再存指针更快。这些选择并不更复杂，只是需要你心里有数。拿不准就写个微基准测一下。

二、简洁与快通常同向

这是本章最反直觉的一句：更简单的代码往往跑得更快。理由有三。其一，如果已经按第 10 章把特殊情况和异常「定义掉」了，就不需要代码去检查它们。其二，深模块比浅模块高效：一次调用做更多事，跨越的层次更少，而每跨一层都有调用开销。其三，复杂的代码常常在做多余或重复的工作。

那么，当更快的方案确实更复杂时怎么办？作者的判据是看「代价换来的收益」：如果复杂度只增加一点、性能收益显著（比如加一个缓存），可以考虑；如果会显著增加实现复杂度或让接口更复杂，先用简单方案，等性能真成了问题再优化。但若有明确证据表明性能就是核心目标，就值得一开始就为它设计——作者的 RAMCloud 项目以最低远程访问延迟为目标，因此采用了绕过操作系统内核、直接操作网卡的网络通信方式，尽管这更复杂。

三、先测量，再修改

当系统确实太慢，「凭直觉改」是最常见的错误。作者说，即使是经验丰富的程序员，对性能的直觉也不可靠；按直觉动手，往往把时间花在根本不影响性能的地方，还白白增加了复杂度。测量有两个用处：找出改动影响最大的地方——光知道「哪里慢」不够，还要找到那个能带来最大收益的点；以及留一条基线，改完再测一次，确认真的变快了。如果一个改动没有带来可测量的提升，就把它撤回——除非它同时让系统更简单了。保留它只会留下复杂度。

四、围绕关键路径设计

最好的优化往往是「根本性」的：加一个缓存、换一种算法（比如把平衡树换成哈希表）。没有这种机会时，作者给出的方法是围绕关键路径重新设计：

  • 先问「理想代码」长什么样：在最常见的情况下，完成这件事最少需要执行哪些代码？暂时不管现有代码结构，假设你在写一个只服务于关键路径的新方法。这段理想代码通常既简单、又快。
  • 把特殊情况赶出关键路径：理想状态是开头只用一个 if 就检测出所有特殊情况，其余全部挪到单独的慢路径去处理。必要时可以调整数据结构，比如把几个零散的判断条件合成一个值，一次就能测完。
  • 再把系统其余部分围绕它重构：在不破坏理想关键路径的前提下，加回所有功能。

五、例子：RAMCloud 的 Buffer

RAMCloud 是作者团队做的全内存键值存储，Buffer 类用来装变长的 RPC 请求与响应消息。一个 Buffer 由若干内存块（chunk）组成，块的内存可以由 Buffer 自带（对象内约 1KB 的空间，不够再申请），也可以来自外部（比如网络包）。

旧版里，申请新空间这一最常见操作要穿过好几层方法调用，每层基本只是转发参数，还带着不少特殊情况检查。作者把它当成关键路径重写：常见情况只需判断一次「最后一个块的末尾还有没有足够空间」，够就直接在那里划出新区域并返回；所有别的情况——新建块、空间不足、外部内存——都集中到慢路径。结果是关键操作快了近一倍（书中测得约 8.8 ns 降到 4.75 ns），而且新版本的代码量反而少了约 20%。性能与简洁在这里一起赢了。

关键权衡与选型

表 1 · 「更快的方案」值不值得做：按代价分档

情形例子作者建议代价 / 风险
快方案一样干净哈希表 vs 有序映射；一次分配整块数组直接选快的，当作习惯几乎为零，只需对开销有感觉
复杂度小增、收益大加一个缓存可以考虑缓存失效、一致性等新状态要维护
复杂度大增、收益不明为几纳秒到处加特殊分支先写简单的，测出问题再改若到处都慢，后期难找热点

选型判据：一个性能改动要过两道关——测得出提升吗？测不出就撤回；复杂度换得值吗？能让关键路径更短更直的改动，往往两样都赢。

为什么重要 / 落到真实系统

这章的价值在于把「性能 vs 可读性」的对立拆掉：大多数时候，深模块、少特殊情况的代码正是快的代码；真正需要牺牲清晰的地方很少，而且应当由测量来决定。

大厂实证 · 公开可查

  • Google · Jeff Dean 与 Sanjay Ghemawat《Performance Hints》（2023 首发，2025 更新）指出 Knuth 那句「过早优化是万恶之源」常被断章取义，原文后半句是「但我们不应放过那关键的 3% 中的机会」。他们还直接反驳「先写最简单的、以后用剖析再处理性能」：若开发大型系统时完全不顾性能，最终会得到一个「平坦的剖析图」，没有明显热点，因为性能散失在各处。建议是：只要不明显影响可读性 / 复杂度，写代码时就选更快的那个方案——与本章第一条几乎同一句话。出处：abseil/abseil.github.io · fast/hints.md
  • RAMCloud（Stanford）把「性能是核心目标」落到了指标上：项目 README 写明数据全程放在内存里，读一个对象最快约 5 µs，写不到 15 µs。它的 Buffer 源码里，alloc() 开头就是本章那个快路径判断，注释写着「最后一个块末尾还有多余空间，所以直接在那里分配新区域」。出处：PlatformLab/RAMCloud README · src/Buffer.cc

落到日常：评审时，看到「为了性能」的复杂改动，先要测量数据和基线；选数据结构时，把网络往返、磁盘 I/O、内存分配当成要数的「贵东西」；接手一段慢代码，先问「常见情况最少需要做什么」，再看现有代码多做了哪些。面试里被问「怎么优化这段代码」，先说测量，再说关键路径，比直接报技巧更像有经验的人。

易错点与争议

  • 「作者说别管性能」。不对。他反对的是两个极端，主张对开销有感觉、在同样干净的方案里选快的。
  • 「过早优化是万恶之源」不是免死金牌。Knuth 原话说的是约 97% 的小效率；Google 的文档提醒，处处不管会得到平坦剖析图——这与作者「平时就挑快的」一致，但比作者「复杂就先写简单的」更强调早期投入。两者分歧在于「多少复杂度算可接受」。
  • 关键路径重设计 ≠ 打补丁加快路径。在旧结构上再加一个特殊分支只会增加复杂度；作者的做法是先想清楚理想代码，再让其余部分围绕它重组。
  • 测量也会骗人。微基准测的是孤立操作，忽略缓存状态、并发等因素；改动要在真实负载下复测。
  • 数字会过时。具体耗时随硬件变化（闪存、网络都在变快），但几个数量级的阶梯基本稳定，要记的是阶梯。
  • 例子偏系统软件。RAMCloud 是微秒级系统；在一次请求本就要几十毫秒的业务代码里，纳秒级的关键路径收益可能不值重构的代价——先测量依然是前提。

要点

① 干净的设计与高性能大体兼容；复杂代码常因做多余或重复的工作而慢。

② 对「什么贵」要有数量级感觉：网络往返、磁盘 / 闪存 I/O、动态内存分配、缓存未命中。

③ 几个同样干净的方案里，挑更快的那个——成本几乎为零。

④ 复杂度小增、收益大可以做；复杂度大增就先写简单的；性能是核心目标时一开始就为它设计。

⑤ 修改前先测量：找影响最大的点，留基线；测不出提升的改动要撤回。

⑥ 根本性改进优先：缓存、换算法；没有时就围绕关键路径重设计。

⑦ 关键路径：先写只服务常见情况的理想代码，用一个 if 挡住所有特殊情况，其余挪去慢路径。

⑧ 实证：RAMCloud Buffer 重写快近一倍、代码少约 20%；Google《Performance Hints》也主张不伤可读性时就选更快方案，警告「平坦剖析图」。
