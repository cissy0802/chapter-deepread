What is this chapter about?

Behind every app on your phone and every website you visit, engineers write "instruction manuals" for each other: how this feature is used, what that button actually does, where a new hire should start reading on day one. This chapter is about how Google keeps those manuals accurate, current and easy to find.

A strange thing first

Nearly every engineer complains that the docs are bad, and nearly every engineer avoids writing them. It isn't laziness: the benefits of writing docs mostly land on other people and the future, while all the hassle lands on you, today.

Why the old world was hard

Early on, Google kept its docs on an internal wiki that anyone could edit. The result: several versions of the same story and nobody sure which was right; pages abandoned when their author changed teams; readers who spotted a mistake with nobody to tell. Docs and code lived in two different places, so whenever the code changed, the docs quietly turned into lies.

How it works, intuitively

  • Move the docs in with the code: the manual sits in the same folder as the code it describes. Whoever changes the code updates the manual too, like replacing the instruction sticker on an appliance while you repair it.
  • Every doc has an owner: like every notice board in an apartment block having someone in charge, so stale notices get taken down and errors have someone to report to.
  • Decide who it's for before writing: a map for a first-time tourist and a map for a local cab driver look completely different.
  • One doc, one job: a recipe lists the cooking steps. Don't stuff the dish's history and a nutrition lecture into it; if you want those, write them separately.
  • Stamp an expiry date: each doc records when it was last checked. If nobody has looked at it for too long, the system nudges its owner to review it, like milk in the fridge reminding you it's time to toss it.

What it buys / how to choose

What should your team do? Move the handful of most-used docs next to the code, update them in the same change and have a colleague look at both; boldly delete the ones nobody uses. The honest cost: every change takes a little longer, and without dedicated writers, the quality of the prose depends entirely on the engineers.

One line to remember

Docs are code: same home, same review, an owner, and an expiry date.

One line

You think bad docs mean "engineers can't write". This chapter says it is mostly that the process puts docs in the wrong place: away from the code, with no owner, no review and no expiry. Google's answer is to treat documentation like code: same repository, same change, same review, plus a writing discipline of knowing your audience and giving each doc a single purpose.

Glossary

  • Change / changelist (CL): one modification to be merged into the codebase; Google's equivalent of a GitHub pull request.
  • Source control: a version-control system such as Git that records every change, who made it, and lets you roll back.
  • Code review: the process where a colleague reads and approves a change before it is merged (see Chapter 9).
  • Wiki: a collection of web pages anyone can edit online, like an internal Confluence.
  • Markdown: a plain-text format that marks headings and lists with symbols such as # and *; the source is readable as is.
  • API: the interface a piece of code exposes to callers, e.g. a function's name, parameters and return value.
  • Code comment: explanatory text inside the source, written for humans and ignored by the machine.
  • Design doc: a document written before coding that lays out the plan, goals and alternatives so colleagues can review it.

What problem this chapter solves

The chapter opens with an observation: in surveys of Google engineers, documentation regularly ranks among the biggest pain points, yet few people write it. The author lists why: engineers see writing as a separate skill from programming; doc tools live somewhere other than code tools, so switching is costly; and most fundamentally, the benefits are downstream. The writer pays now; the reader (including the writer, three months later) collects.

Yet docs do pay the writer directly: writing an API description forces you to work out what the interface should look like; it is a roadmap for future maintenance; it makes code look professional and trustworthy; and it heads off a flood of repeated questions. What happens if you don't fix this? Ch1 calls software engineering "programming integrated over time": when code lives for ten years and passes through a hundred hands, undocumented knowledge lives only in a few heads, and leaves when they do. The chapter asks: how do you keep docs trustworthy at that scale and over that time?

The core ideas, in depth

1. Documentation is like code: seven parallels

The chapter's central claim: documentation is so tightly coupled to code that it should, as much as possible, be treated as code. Concretely, documentation should:

  • Follow internal policies: a shared style and format, just like a code style guide.
  • Live in source control: with history, rollback and a record of who changed what.
  • Have clear ownership: someone is responsible for keeping it right over time.
  • Be reviewed: doc changes are reviewed alongside code changes (see part 5 below).
  • Have issues tracked: readers who find errors can file them with the owner, like bugs.
  • Be evaluated periodically: checked on a schedule, like tests, to see whether it still holds.
  • Avoid duplication: one authoritative version of each fact; everything else links to it.

Why this design? Because code already has infrastructure for every one of these: the repository, review, OWNERS, the bug tracker. Hook docs onto rails that already exist, and you don't need to invent a separate process nobody uses. The chapter's TL;DR says the same: documentation changes should leverage the existing developer workflow.

2. Case study: from GooWiki back to the code

Early on, Google kept most engineering docs on an internal wiki, GooWiki. A wiki is easy to write in, but at scale the problems showed: many pages had no clear owner and went stale unchecked; one topic spawned several contradictory pages; readers who found errors had no channel to report them. The wiki was easy to write and nobody's job to maintain.

The turning point was moving docs into source control: docs written in Markdown inside the code directories, rendered as web pages by an internal system called g3doc. Docs now came with an owner (the directory's OWNERS), review (the same CL) and history, and engineers no longer had to leave their coding environment. The book admits the migration was not smooth and some people resisted changing habits, but it made "update the docs while you change the code" natural for the first time.

3. Know your audience: the classic mistake is writing for yourself

The chapter says the most important mistake in writing docs is not knowing your audience. Readers differ by experience level (expert or novice), domain knowledge, and purpose (end user, or developer who will change the code). Two more memorable splits:

  • Seekers vs. stumblers: seekers know what they want and need to find it fast in consistent material; stumblers have only a vague idea and need a clear overview and guidance.
  • Customers vs. providers: API users only care how to call it; team members need implementation details and on-call runbooks. Write these separately; don't mix them in one doc.

The chapter quotes Pascal: "If I had more time, I would have written you a shorter letter." Short and precise is harder to write than long and exhaustive, but far kinder to the reader.

4. Five doc types, each with one job

  • Reference documentation: most commonly code comments. A file comment says what the file is for; a class comment says what the class does and how to use it; a function comment starts with a verb saying what it does and returns ("Returns…", "Deletes…"). It is part of the API.
  • Design docs: written before building, from a team template, covering goals, implementation strategy, key decisions and their trade-offs, and alternatives with their pros and cons, often with required sections on security and privacy. Once approved, it mostly serves as a historical record of decisions.
  • Tutorials: take the reader from nothing to a working "Hello World". The best time to write one is when you are new yourself: write as you go, number every step, assume nothing is pre-installed, and separate "what you do" from "what the system does".
  • Conceptual documentation: explains the ideas and big picture behind a system or API. It is the hardest kind to write and often trades some completeness and precision for clarity.
  • Landing pages: traffic cops that only point people to the right place. Keep the customer-facing entry point separate from team-internal on-call and process information.

5. Three reviews, three questions

Mirroring Chapter 9's three approvals, an important doc should answer three different questions:

  • Technical review: is it right? An engineer who knows the area confirms accuracy, usually as part of code review.
  • Audience review: can a reader follow it? Someone unfamiliar with the domain reads it; wherever they get stuck is what the doc is missing.
  • Writing review: is it consistent? A technical writer or someone versed in the style checks wording, structure and conventions.

6. Philosophy: the 5 Ws, one purpose, and expiry

Answer the 5 Ws up front: who it is for, what its purpose is, when it was written and last reviewed, where it should live, and why: what the reader can do after reading it. A doc needs a beginning, middle and end, organized into sections, not a wall of text.

Good documentation is complete, accurate and clear, but rarely all three at full strength in one doc: API comments favor accuracy and completeness; conceptual docs favor clarity. Hence the rule that each document should serve a single purpose: a doc trying to be a tutorial, a reference and a design rationale at once does all three badly.

Docs go stale and must be deprecable. An old doc is worse than none, because it misleads. The book describes embedding a "freshness" date in each doc recording its last review; if it goes untouched past a set window (the book's example is three months), the system reminds the owner to review it. Docs that no longer apply should be clearly marked deprecated, or deleted.

Rule of thumb: the closer a doc lives to the code, and the more it is reviewed with the code, the less likely it is to lie. Content far from code (product, process) can stay in a wiki, but link to it from the README so there is only one authoritative version. A second rule is about people: the book holds that engineers should write most team-internal docs, and technical writers are best spent on docs that cross team or company boundaries, such as external API docs, where the knowledge gap between writer and reader is largest.

Why it matters / in real systems

"Docs as code" is now mainstream: GitHub repos' README and docs/ folders, Python docstrings with Sphinx, Rust's cargo doc with doc examples that run as tests all follow the same path: docs in the same repo, same version, same review as the code. The directory-level READMEs scattered through Google open-source projects like Chromium are the same practice. Asked in an interview or architecture review "how do you keep docs from going stale?", the strong answer is not "tidy the wiki regularly" but "docs in the repo, reviewed in the same CL as the code, with an owner and freshness reminders".

Pitfalls and debates

  • "More docs is better": wrong. Stale docs mislead and are worse than none; Google's guide argues for few and fresh, with deletion as the default.
  • "Code is the documentation; good code needs no comments": half right. Good names replace many comments, but code can't say why it was done this way, nor state a function's contract to its callers.
  • Treating design docs as living docs. A design doc records decisions as of then; after launch, treat it as an archive and look to docs near the code for the current state.
  • One doc for everyone. Novices, experts, customers and maintainers want conflicting things; cram them into one doc and nobody finds their part.
  • "Moving it into the repo fixes it": not enough. Without owners and freshness checks, in-repo Markdown rots too; tooling makes the discipline cheap, it doesn't replace it.
  • Context limits. g3doc, OWNERS and a company-wide monorepo are Google-specific infrastructure; the book itself concedes documentation is still a slow-moving area at Google, technical writers are scarce relative to engineers, and much of this covers engineering docs, not necessarily user-facing product docs.

Key takeaways

① Bad docs are mostly a process problem: the payoff is downstream, the tools are elsewhere, nobody owns them.

② Core claim: docs are tightly coupled to code, so treat them like code: policies, source control, owners, review, issue tracking, periodic evaluation, no duplication.

③ Case study: GooWiki was ownerless, duplicated and stale → docs moved into code directories, rendered by g3doc, reviewed with the CL.

④ The biggest mistake is not knowing your audience: seekers vs. stumblers, customers vs. providers; write for them separately.

⑤ Five types: reference / comments, design docs, tutorials, conceptual docs, landing pages, each with one job.

⑥ Three reviews: technical (is it right), audience (can a reader follow), writing (is it consistent).

⑦ Answer the 5 Ws up front; completeness, accuracy and clarity rarely coexist, so each doc serves one purpose.

⑧ Docs expire: record a freshness date, remind owners when it lapses, deprecate or delete what no longer applies.

⑨ Pitfalls: more isn't better; good code doesn't replace contracts and the "why"; in-repo docs still need owners and reviews.
