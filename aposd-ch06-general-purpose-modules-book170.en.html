General-Purpose Modules are Deeper

A Philosophy of Software Design · Ch 6 · General-Purpose Modules are Deeper · Ousterhout · 2nd ed 2021

中文 →

What is this chapter about?

Every time you build a part, you face a question: do you build it just for the one job in front of you, or make it a bit more general so it could serve other uses later? Most people's instinct is "build the special one, it's quicker." This chapter gives a counterintuitive answer: making it "somewhat general" actually makes it simpler. Copy and paste on your phone is an example. It doesn't care whether you copied a chat message, a link or a photo, and precisely because it doesn't care, every app can use it.

A strange thing first

A group of students builds a text editor. They design the part that stores the text around the keys on the keyboard: one function is "Backspace was pressed," another is "Delete was pressed," a third is "delete the highlighted part." It looks thoughtful, but every new key or menu item forces the text part to grow another function. It should only care about text, yet it's forced to know about the keyboard.

Why the old world was hard

The trouble with special-purpose design is that it's welded to one situation: the part is full of details of today's use, so a new use means rewriting it, and nobody else can use it. But going the other way, trying to build a do-everything part from day one, also fails: you can't guess the future, and what you build tends to be big and awkward. Both ends are traps; the hard part is finding the spot in between.

How it works, intuitively

  • Build the features you need today, but shape the doorway to be general. Like a kitchen: you only buy tonight's groceries, but the knife and pan are general, so tomorrow you can cook something else.
  • A general part offers a few basic moves. The text part only does two things: "put some words here" and "remove the words between these two spots." Backspace, Delete and "delete the highlight" are all combinations of those two.
  • Push the special stuff outward. "Which letter does Backspace remove?" is the keyboard layer's business, so the keyboard layer handles it. The text part never learns the keyboard exists.
  • Make special cases disappear. "Nothing is highlighted" can be treated as "a highlight with zero length," so the delete code no longer needs "if nothing is highlighted, then…" everywhere.
  • Three questions to ask. What's the simplest doorway that covers everything I need today? How many places will use this feature? Is it pleasant to use for today's needs?

What it buys you / how to choose

A somewhat general part has fewer functions to learn, and each one does more work. That is what "deeper" means. Redesigning the screen or adding keys never touches it, because it never knew what the screen looks like. One honest cost: overdo the generality and it backfires. If the part only offers the tiniest moves, users have to assemble a pile of them every time, and that's gone too far.

Remember it in one line

Build features for today, shape the doorway to be general; push the special stuff outward, and give the part a few basic moves that can build everything else.

In one sentence

You think general-purpose design is "extra cost paid for the future"; Ousterhout says its biggest payoff arrives today: a somewhat general-purpose interface is usually simpler and deeper than a special-purpose one, with fewer methods that each do more, and with special-purpose knowledge kept out of the module. The recipe: implement functionality for current needs, but design the interface to support multiple uses.

Glossary

  • Deep / shallow module: from Chapter 4. A module with a simple interface and powerful functionality is "deep"; one whose interface is about as complex as what it does is "shallow."
  • Interface: everything a user must know to use a module, including method signatures and behavioral promises.
  • API: application programming interface; here, the set of public methods a class exposes.
  • Information hiding / leakage: from Chapter 5. Keeping a design decision inside one module is hiding; the same decision showing up in several modules is leakage.
  • GUI text editor: a text-editing program with a graphical interface; the UI layer handles keys and mouse, the text layer stores the characters.
  • Cursor / selection: a cursor is one insertion point in the text; a selection is a range the user dragged over, defined by a start and an end position.
  • Undo / redo: reversing the most recent change, and re-applying a change that was undone.
  • Device driver: the part of an operating system that talks to one specific kind of hardware.
  • YAGNI: "You Aren't Gonna Need It," the Extreme Programming (XP) slogan: don't build a feature until you're sure you need it.

What problem this chapter solves

Every new module forces a choice. The case for special-purpose sounds solid: implement only what's needed today, YAGNI, don't pay for guesses. The case for general-purpose comes from Chapter 3's strategic programming: spend a bit more now, get reuse later. The author says both fail in their own way. Over-specialization makes the module sprout a new method for each new need, so the interface keeps widening and getting shallower while pulling caller details inside. Over-generalization builds machinery nobody uses, and because the future is hard to predict, the general parts are often guessed wrong.

The chapter asks: where is the sweet spot in between? How do you tell you've drifted? And, most importantly, why does the benefit of generality not have to wait for reuse to pay off?

The core ideas, in depth

1. "Somewhat general-purpose": functionality from today, interface from the uses

The author's definition is precise: a module's functionality should reflect your current needs, but its interface should not. The interface should be general enough to support multiple uses, without implementing features you don't need today. This isn't "write code for the future"; it's "don't carve today's call sites into the interface."

He stresses that the most important, and perhaps most surprising, benefit of the general-purpose approach is a simpler, deeper interface. Even if the class is never reused elsewhere, it is already easier to use today. Reuse is a bonus.

2. Case study: the editor's text class, two APIs

In CS 190, students build GUI text editors and must separate text storage (a text class) from the UI. Many teams gave the text class methods that mirror the UI:

void backspace(Cursor cursor) · void delete(Cursor cursor) · void deleteSelection(Selection selection)

Each method matches one specific UI action and looks "just enough." Three problems: first, it's shallow. Each method does one narrow thing, and adding "delete word," "cut" or "find and replace" means more methods, so the interface keeps widening. Second, it leaks information: UI knowledge like "Backspace deletes the character before the cursor" now lives in the text class. Third, UI developers must learn a pile of small, scattered methods.

The more general version offers only basic operations:

void insert(Position position, String newText) · void delete(Position start, Position end) · Position changePosition(Position position, int numChars)

The third returns the position a given number of characters away (negative allowed). So Backspace becomes text.delete(text.changePosition(cursor, -1), cursor), Delete becomes text.delete(cursor, text.changePosition(cursor, 1)), and deleting a selection is delete(sel.start, sel.end). The UI writes one more line, but every line reads at a glance.

The author points out that generality leads to better information hiding. The general text class has no notion of a "Backspace key," so UI changes never touch it; the special version ties text and UI together.

3. Three questions: have you drifted?

  • What is the simplest interface that will cover all my current needs? If you can cut the number of methods without cutting capability, you're moving toward generality. Beware: merging methods into one method with a long list of arguments doesn't count as simpler.
  • In how many situations will this method be used? A method designed for one particular use (like backspace) is a red flag; see whether one method could cover several uses.
  • Is this API easy to use for my current needs? This is the guard against over-generalizing: if callers must write lots of extra code for common operations (say the text class only offered single-character insert and delete, so deleting a selection needs a loop), the interface is too low-level, too general.

4. Push specialization upward (and downward)

Special-purpose code doesn't vanish; the question is where it lives. The principle is to separate special-purpose code from general-purpose code. The special part goes either up toward the application (in the editor, "which character Backspace deletes" belongs in the UI) or down to the bottom layer (an operating system defines one general interface for all devices, and each device's quirks go into its own driver). The general core in the middle stays clean and becomes a foundation others can depend on.

5. Case study: undo, a general history plus special actions

The same course's editors must support undo / redo. A common design is a history class that knows every undoable operation: how to undo a text insertion, a selection change, a formatting change… and it must change whenever a new operation appears. The better split: the history class is general. It just manages a list of "action" objects and lets you group adjacent actions into a single undo with a marker (the book calls it a fence). Each action knows how to undo and redo itself (implementing a shared undo() / redo() interface) and is created by the text class or the selection code.

Both sides get simpler: the history class can be reused unchanged in another program, and adding a new undoable operation means writing one new action class without touching the history. It's a complete demonstration of "push the special outward, keep the general in the middle."

6. Eliminate special cases in code

Another face of specialization is special cases in code: screens full of if statements, each one handling a corner case. The advice is to design so the normal code path handles the special cases automatically. The editor again: if "no selection" is a separate state, the code for delete, copy and replace must each first check "is there a selection?"; if it is represented as an empty selection whose start equals its end, the delete-selection code naturally deletes nothing, and all those checks vanish.

Key trade-offs and choices

One test: when a new requirement arrives, ask "does this add a method, or can existing methods compose it?" If every new requirement adds a method, the interface is getting shallower.

Why it matters / in real systems

The most common specialization in practice is the slow bloat of utility classes and service interfaces: each product team asks for something, and in goes getUserForCheckoutPage, then getUserForProfilePage. In review you can apply this chapter's three questions directly: how many places will use this method? Could one or two general queries cover it? The chapter's vocabulary turns "this interface is getting shallow" into a discussable judgment rather than a matter of taste.

Evidence and sources · publicly verifiable

  • Go's io.Reader: a one-method general interface. The docs say Reader is "the interface that wraps the basic Read method"; io.Copy only needs that interface, copying from src to dst until EOF. Files, network connections and compressed streams move data through the same function, with each one's special handling hidden in its implementation. Source: pkg.go.dev · io (Reader, Copy)
  • Go's sort.Interface: special knowledge pushed to the caller. The docs say an implementation of the interface can be sorted by the package's routines, with methods referring to elements by integer index; Sort makes one call to Len and O(n log n) calls to Less and Swap. The algorithm is general; "how to compare" comes from the caller. The same page honestly notes that in many situations the newer slices.SortFunc is more ergonomic and faster: how usable a general interface is gets re-evaluated as the language evolves. Source: pkg.go.dev · sort (Interface, Sort)
  • UNIX: devices are files. Ritchie and Thompson describe a UNIX in which ordinary files, directories and special files (devices) use the same read and write calls, with device differences handled inside the system: exactly "push specialization down." Source: D. M. Ritchie & K. Thompson, The UNIX Time-Sharing System, CACM 1974

Pitfalls and debates

  • "General = writing code for the future." No. The chapter is explicit: functionality is built for today only; what's general is the interface's shape. The payoff is immediate.
  • "Fewer methods means more general." Merging three methods into one with ten arguments and a bag of flags doesn't make the interface simpler.
  • "General means offering the lowest primitives." The third question exists to catch this: if callers have to write loops for common operations, you've over-generalized.
  • "Special-purpose code is bad code." Special-purpose code is necessary; the mistake is mixing it into the same module as general code. Push it up or down; don't delete it.
  • Debate: the tension with YAGNI. Extreme Programming says don't build what you aren't sure you need. The two don't fully conflict: Ousterhout also opposes implementing unused features; the disagreement is about interface shape, which he thinks costs almost nothing extra to keep general. But "somewhat general" depends heavily on experience, and novices easily over-engineer in its name; the book's only guardrail is the three questions.

Key takeaways

① Somewhat general-purpose modules are deeper: implement functionality for current needs, design the interface for multiple uses.

② The biggest benefit of generality is being simpler today; reuse is a bonus.

③ Editor case: backspace / deleteSelection is a shallow special-purpose API; insert / delete(range) / changePosition covers every edit with three methods.

④ Generality improves information hiding: the text class doesn't know the keyboard exists, so UI changes never touch it.

⑤ Three questions: what's the simplest interface covering current needs? How many situations use it? Is it easy to use today?

⑥ Push special-purpose code up (UI layer) or down (drivers), separate from the general core.

⑦ Undo: a general history class plus special action objects that each implement undo / redo.

⑧ Eliminate special cases: represent "no selection" as start equals end, and the normal code covers it.

⑨ Both ends are shallow: over-specialization widens the interface; over-generalization makes callers assemble everything.
