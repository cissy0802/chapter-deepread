通用模块更深

A Philosophy of Software Design · Ch 6 · General-Purpose Modules are Deeper · Ousterhout · 2nd ed 2021

EN →

这一章讲什么？

写一个零件时，总要先回答一个问题：它是专门为眼下这一件事做，还是做得通用一点、以后别处也能用？大多数人的直觉是「先做专用的，省事」。这一章给出一个反直觉的答案：做得「稍微通用一点」，反而更简单。你手机上的「复制、粘贴」就是例子：它不关心你复制的是一段聊天、一个网址还是一张照片，正因为它不管这些，任何 App 都能用它。

先说个怪事

一群学生写文字编辑器。管文字的那个零件，被他们按键盘上的键来设计：一个功能叫「按退格键」，一个叫「按删除键」，一个叫「删除选中的部分」。看起来贴心，结果每加一个新按键、新菜单，管文字的零件都得跟着加一个功能。它明明只该管文字，却被迫懂键盘。

旧世界为什么难

专用设计的麻烦在于「绑死」：零件里写满了眼下这个场景的细节，换个场景就得重写，别处也用不上。可反过来，一上来就想做「什么都能干」的万能零件也不行——你猜不准将来要什么，做出来的东西往往又大又难用。两头都是坑，难的是找中间那个点。

核心机制直觉

  • 功能按今天的需要做，接口按「通用」的样子留。就像厨房只备今晚要用的菜，但刀和锅是通用的，明天做别的菜照样能用。
  • 通用的零件只提供几样基本动作。管文字的零件只会两件事：「在某处插入一段字」和「删掉某两处之间的字」。退格、删除、删选中，全都是这两样动作的组合。
  • 专门的事往外推。「按退格到底删哪个字」是键盘那一层的事，就让键盘那一层去管；管文字的零件从此不用知道键盘的存在。
  • 把「特殊情况」消掉。「没选中任何字」可以看成「选中了一段零长度的字」，于是删除代码里不用再到处写「如果没选中就……」。
  • 三个自问。能覆盖今天所有需要的最简单接口是什么？这个功能会被几个地方用？今天用起来顺不顺手？

带来了什么 / 该怎么选

通用一点的零件，要记的功能更少，每个功能干的活更多——这就是「更深」。改界面、加按键都不用碰它，因为它从来不知道界面长什么样。一句诚实的代价：通用过头也会出事，如果零件只给最底层的动作，用的人每次都得自己拼一大堆，那就是做过头了。

一句话记住

功能按今天做，接口按通用留；专门的事往外推，零件只提供几样能拼出一切的基本动作。

一句话

你以为通用设计是「为将来多付的成本」，Ousterhout 说它最大的好处恰恰在今天：稍微通用（somewhat general-purpose）的接口，往往比专用接口更简单、更深——方法更少、每个方法能干的事更多，而且把专用知识挡在模块外面。做法是：功能按当下需求实现，接口按能支持多种用途来设计。

Glossary · 术语表

  • 深模块 / 浅模块：第 4 章的概念——接口简单而功能强大的模块叫「深」；接口和它提供的功能差不多复杂的叫「浅」。
  • 接口（interface）：使用者为了用这个模块必须知道的一切，包括方法签名和行为约定。
  • API：应用程序接口，这里就是一个类对外公开的那组方法。
  • 信息隐藏 / 泄漏：第 5 章的概念——模块把设计决策藏在内部是隐藏；同一个决策出现在多个模块里就是泄漏。
  • GUI 文本编辑器：带图形界面的文字编辑程序，界面层负责按键与鼠标，文本层负责存储文字。
  • 光标 / 选区（cursor / selection）：光标是文字里的一个插入位置；选区是用户拖选出的一段文字，由起点和终点两个位置确定。
  • 撤销 / 重做（undo / redo）：撤销最近的修改，以及把撤销的修改再做回来。
  • 设备驱动（device driver）：操作系统里专门和某一种硬件打交道的代码。
  • YAGNI：「You Aren't Gonna Need It」，极限编程（XP）的口号：没确定要用的功能就别做。

坐标

全书第 6 章。第 4 章定目标（模块要深），第 5 章给手段（信息隐藏），这一章回答造深模块时一个具体的岔路口：接口做专用还是做通用。下一章「不同层，不同抽象」转向层与层之间。现实里对应每一次「这个工具类要不要为这个需求再加一个方法」的评审。

这章要解决什么

每个新模块都面临选择。专用的理由听上去很硬：只实现今天要的，YAGNI，不为猜测买单。通用的理由来自第 3 章的战略编程：多花一点时间，换以后复用。作者说这两种都有失败方式——过度专用会让模块随每个新需求长出新方法，接口越来越宽、越来越浅，还把调用方的细节吸进来；过度通用会做出一大堆用不上的机制，而且因为猜不准未来，通用部分常常猜错。

本章要回答：中间那个「甜点」在哪？怎么判断自己偏了？以及最重要的——为什么通用的好处不需要等到复用那天才兑现。

核心内容，讲透

一、「稍微通用」：功能看今天，接口看用途

作者的定义很精确：模块的功能应当反映你当前的需求，但接口不应当。接口要足够通用，能支撑多种用途；但别去实现今天用不到的功能。这不是「为未来写代码」，而是「不要把今天的调用场景刻进接口」。

他强调：通用设计「最重要、也许最令人意外」的好处，是它带来更简单、更深的接口。就算这个类日后从未在别处复用，它今天也已经更好用了。复用只是附赠。

二、案例：编辑器的文本类，两版接口

CS 190 课上学生做 GUI 文本编辑器，要把文字存储（文本类）和界面分开。很多小组给文本类设计了贴着界面的方法：

void backspace(Cursor cursor) · void delete(Cursor cursor) · void deleteSelection(Selection selection)

每个方法对应界面上一个具体动作，看起来「刚好够用」。问题有三：一是浅，每个方法只干一件很窄的事，界面加「删一个词」「剪切」「查找替换」就要再加方法，接口不断变宽；二是信息泄漏，「退格删光标前一个字」这种界面知识住进了文本类；三是界面开发者要学一大堆零碎方法。

更通用的版本只给基本操作：

void insert(Position position, String newText) · void delete(Position start, Position end) · Position changePosition(Position position, int numChars)

第三个方法返回距某位置若干字符的新位置（可为负）。于是退格是 text.delete(text.changePosition(cursor, -1), cursor)，删除键是 text.delete(cursor, text.changePosition(cursor, 1))，删选区就是 delete(sel.start, sel.end)。界面层多写了一行，但每一行都一眼能懂。

作者特别指出：通用带来了更好的信息隐藏。通用版文本类根本不知道「退格键」这个概念，界面怎么改都不用动它；专用版则让文本类和界面互相牵连。

System Design · Day 45 协作编辑系统 — 「在某位置插入 / 删除一段范围」正是 OT 与 CRDT 的操作模型：基本操作够通用，多人并发才收敛得了

三、三个自问：判断自己偏没偏

  • 能覆盖我当前全部需求的最简单接口是什么？如果能在不减少能力的前提下减少方法数，说明你在往通用走。但要警惕：靠把方法合成「一个参数超多的方法」来减方法数不算简化。
  • 这个方法会在多少种情况下被用到？如果一个方法只为一个特定用途设计（如 backspace），这是红灯，看能否换成一个能覆盖多种用途的方法。
  • 这个 API 对我当前的需求好不好用？这是防过度通用的闸：如果调用方要写一大堆额外代码才能完成常见操作（比如文本类只给单字符插入删除，删选区就得自己写循环），就说明接口太底层、通用过头了。

四、把专用代码往上推（也往下推）

专用代码不会消失，问题是它住在哪里。作者的原则是把专用代码和通用代码分开：专用部分要么往上推到靠近应用的那一层（编辑器里「退格删哪个字」放进界面层），要么往下推到底层（操作系统给所有设备定一套通用接口，每种硬件的特殊处理写进各自的设备驱动）。中间那层通用核心于是保持干净，变成别人可以放心依赖的底座。

论文精读 · The UNIX Time-Sharing System — 「往下推」最经典的样子：文件、设备、管道共用 open / read / write，差异全压进驱动

五、案例：撤销机制，通用历史 + 专用动作

同一门课的编辑器还要做撤销 / 重做。常见做法是一个历史类懂每种可撤销操作：文字插入怎么撤、选区变化怎么撤、格式变化怎么撤……每加一种操作都要改它。更好的拆法是：历史类是通用的，只管理一串「动作」对象，并支持把相邻几个动作用分组标记（书里叫 fence）合成一次撤销；每种动作自己知道怎么撤销和重做（实现统一的 undo() / redo() 接口），由文本类、选区代码各自创建。

好处是两头都简单：历史类可以原封不动用到别的程序；新增一种可撤销操作，只写一个新动作类，历史类一行不改。这正是「专用往外推，通用留中间」的完整示范。

六、消除代码里的特殊情况

专用的另一种形态是代码里的特殊情况：满屏的 if，每个都为某个边角场景开小灶。作者的建议是设计成让常规代码自动覆盖特殊情况。例子还是编辑器：如果「没有选区」是一种单独状态，删除、复制、替换的代码都得先判断「有没有选区」；如果把它表示成起点等于终点的空选区，删选区的代码对空选区自然什么都不删，那些判断全都消失。

为什么重要 / 落到真实系统

工程里最常见的「专用化」是工具类和服务接口的慢性膨胀：每个业务方提一个需求，就加一个 getUserForCheckoutPage、getUserForProfilePage。评审时可以直接套本章三个自问——这个方法会被几处用？能不能用一两个通用查询覆盖？本章给的语言让「这个接口在变浅」变成一个可讨论的判断，而不是品味之争。

实证与出处 · 公开可查

  • Go 的 io.Reader：一个方法的通用接口。文档写明 Reader 是「包裹基本 Read 方法的接口」；io.Copy 只认这个接口，从 src 一直读到 EOF 写入 dst——文件、网络连接、压缩流用同一个函数搬数据，专用差异各自藏在实现里。出处：pkg.go.dev · io（Reader、Copy）
  • Go 的 sort.Interface：专用知识推给调用方。文档写明，实现了该接口的类型就能被本包的例程排序，方法通过整数下标引用集合元素；Sort 调一次 Len、O(n log n) 次 Less 和 Swap。排序算法通用，「怎么比大小」由调用方给。同一份文档也诚实写着：很多场景下更新的 slices.SortFunc 更顺手、也更快——通用接口好不好用，要随语言能力重估。出处：pkg.go.dev · sort（Interface、Sort）
  • UNIX：设备也是文件。Ritchie 与 Thompson 描述的 UNIX 让普通文件、目录和特殊文件（设备）用同一套读写调用，设备差异由系统内部处理——正是「专用往下推」。出处：D. M. Ritchie & K. Thompson，The UNIX Time-Sharing System，CACM 1974

易错点与争议

  • 「通用 = 为将来写代码」。不是。本章明确：功能只按今天实现，通用的是接口形状。好处今天就兑现。
  • 「方法越少越通用」。把三个方法合成一个带十个参数和一堆标志位的方法，接口并没有变简单。
  • 「通用就是给最底层原语」。第三个自问专门防这个：常见操作要调用方写循环，就是通用过头。
  • 「专用代码是坏代码」。专用代码必不可少，错的是它和通用代码混在同一个模块里。把它推到上层或下层，而不是删掉。
  • 争议：和 YAGNI 的张力。极限编程主张别做没确定要用的东西。两者其实不完全冲突：Ousterhout 也反对实现用不到的功能，分歧在接口形状——他认为按通用的样子留接口几乎不花额外成本。但「什么算稍微通用」高度依赖经验，新手很容易借「通用」之名过度设计，这一点原书给的护栏只有三个自问。

要点

① 稍微通用的模块更深：功能按当前需求实现，接口按能支撑多种用途设计。

② 通用最重要的好处是今天就更简单，复用只是附赠。

③ 编辑器案例：backspace / deleteSelection 是专用浅接口；insert / delete(范围) / changePosition 三个方法覆盖全部操作。

④ 通用带来更好的信息隐藏：文本类不知道键盘的存在，界面怎么改都不用动它。

⑤ 三个自问：最简单的覆盖接口是什么？会被几处用？今天好不好用？

⑥ 专用代码往上推（界面层）或往下推（驱动），和通用核心分开。

⑦ 撤销机制：通用历史类 + 各自实现 undo / redo 的专用动作对象。

⑧ 消除特殊情况：空选区表示成起点等于终点，常规代码自动覆盖。

⑨ 两端都浅：过度专用让接口变宽，过度通用让调用方每次都要自己拼。
