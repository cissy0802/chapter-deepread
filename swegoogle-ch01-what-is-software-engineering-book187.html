何谓软件工程

Software Engineering at Google · Ch 1 · What Is Software Engineering? · Titus Winters · 2020

EN →

这一章讲什么？

你手机里的搜索、地图、邮箱，背后的代码有的已经活了二十多年，每天还在被成千上万个工程师修改。这一章问了一个看似简单的问题：「写程序」和「做软件工程」到底差在哪？答案是：差在时间和人数。

打个比方

给自己写一张购物清单，写完就扔，字迹潦草也无所谓。可要是写一本菜谱，会被几百个厨房用上二十年，中间还要换锅、换食材、换口味——你就得想：别人看得懂吗？以后好改吗？哪天要把「克」换成「盎司」，改得过来吗？购物清单是编程，那本要用二十年的菜谱才是软件工程。

先说个怪事

超市从来没承诺过「牛奶永远放在门口」，可时间一长，总有老顾客闭着眼直奔门口拿牛奶。某天超市调整货架，这些人就扑了空。软件也一样：用的人一多，你做过的每一个小习惯，哪怕从没承诺过，都会有人依赖。作者的同事 Hyrum 把这总结成了一条「定律」。所以老代码最难的往往不是写，而是改。

核心机制直觉

  • 时间：一段代码要活多久，决定了它要不要准备「被升级」。只活几分钟的，不用管；要活十年的，迟早要换零件——第一次换最痛，因为从没人练过。
  • 规模：人一多，凡是「每个人都得手动做一遍」的事都会越来越贵。好办法是让负责改底层的团队自己把大家的代码一起改好，并且用自动检查兜底：哪个功能没装自动检查，改坏了就不算别人的错。
  • 代价：每个决定都要算账，不只是钱，还有工程师的时间、错过的机会。Google 宁可白板笔堆成山，也不让工程师为找一支能写的笔浪费时间。
  • 越早越省：问题在写代码时发现，比上线后被用户发现便宜得多，所以把检查尽量往前挪。

带来了什么 / 该怎么选

判断一段代码该按哪个标准写，先问一句：它要活多久、会被多少人改？只用一次的脚本，追求快就好；要长期维护的系统，就得为「以后能改」付出额外功夫。诚实的代价是：这套做法前期更慢，在小团队、短项目里可能纯属多余。

一句话记住

编程是让代码今天跑起来；软件工程是让它在很多年、很多人手里，一直改得动。

一句话

你以为软件工程 = 写得更好的编程；本章说，它们差的是维度：软件工程是「对时间积分的编程」（programming integrated over time）——再乘上参与的人数，并在每一步明码标价地做权衡。同一段代码，活五分钟和活二十年，是两门不同的学问。

Glossary · 术语表

  • 代码库（codebase）：一个组织所有源代码的集合；Google 几乎全部放在一个仓库里。
  • API / 接口契约（contract）：一段代码对外承诺「你这样调用，我保证这样表现」的约定。
  • 依赖（dependency）：你的代码用到了别人的代码，别人一改，你可能跟着坏。
  • 升级 / 迁移（upgrade / migration）：把底层的编译器、库、操作系统换成新版本，并让上层代码继续能用。
  • 持续集成（CI）：每次提交改动都自动构建并跑测试，尽早发现谁改坏了什么。
  • 哈希表（hash table）：按键快速查值的数据结构；遍历它时元素出现的先后顺序，原则上没有保证。
  • 弃用（deprecation）：宣布某个旧系统 / 旧接口将下线，并让用户迁走。
  • 技术债（technical debt）：为了眼前快而留下的、以后要花更多力气偿还的问题。

坐标

全书开篇、Part I「论题」唯一一章，由 Titus Winters 执笔。它立下全书的母命题——时间、规模、权衡——后面的文化（Ch2–7）、流程（Ch8–15，评审 / 测试 / 弃用）与工具（Ch16–25，单体仓、构建、依赖、大规模变更、CI/CD）都是在回答本章提出的问题。

这章要解决什么

「软件工程」这个词被用得很随意：写个脚本也叫工程，维护一个二十年的搜索系统也叫工程。如果两者是一回事，那 Google 花大力气做的单体仓、强制测试、自动化迁移，就都像官僚主义。

本章要讲清：为什么一段代码的寿命和参与人数会彻底改变「什么是好做法」。不想清楚这一点会怎样？要么把一次性脚本当航天工程来写，白白浪费；要么把要活十年的系统当脚本来写，直到某天必须升级编译器或打安全补丁，才发现根本改不动——系统还在跑，但已经失去了应对变化的能力。

核心内容，讲透

一、三个维度：时间、规模、权衡

作者给出编程与软件工程的三处根本差别：

  • 时间与变化（time and change）：代码要活多久，要为多少次变化做准备。
  • 规模与增长（scale and growth）：多少人参与，组织和代码库变大时，做法还撑不撑得住。
  • 权衡与成本（trade-offs and costs）：决策的复杂度更高、牵涉的时间与人更多，所以决策本身要讲究。

本章有一句很好记的检验：如果「聪明（clever）」是夸奖，你在编程；如果「聪明」是指控，你在做软件工程。在长寿代码里，一个精巧但别人看不懂的写法，是在给未来的维护者埋雷。

二、时间：寿命跨度十万倍，与「第一次升级」

代码的预期寿命从几分钟（一次性脚本）到几十年（Google 搜索这类系统）不等，作者估计两端相差至少 10 万倍。这个跨度决定了一件事：升级（应对底层变化）到底重不重要。活几小时的代码几乎不会遇到依赖变动；活五年以上的代码，几乎一定会遇到。

由此引出本章对可持续（sustainable）的定义：在软件的预期寿命内，你有能力对任何有价值的变化做出响应——无论是技术原因还是业务原因。注意是「有能力」，不是「必须每次都改」：你可以选择不升级，但如果你没有能力升级，你就是在押注「什么都不会变」，而这几乎必输。

作者特别点出：第一次大升级往往最痛。项目一路写来，从没换过底层，于是积累了大量隐含假设——哪些行为「恰好」成立、哪些依赖从没被记录。这次升级没人做过、没有工具、没人知道会坏什么，所以代价惊人；之后再升级，就有了经验和工具。

三、Hyrum 定律：你的「没承诺」也会被依赖

本章最出名的一条，以合著者 Hyrum Wright 命名：

当一个 API 的用户足够多时，你在契约里承诺了什么已经无所谓：系统所有可观察到的行为，都会被某个人依赖。

直觉：契约是你画的一个小圈，但用户看到的是整个系统——返回顺序、耗时、报错文案、内存占用。用户一多，总有人有意或无意地依赖了圈外的东西。于是任何改动，哪怕完全在契约之内，都可能弄坏某人。

书中的例子是哈希顺序（hash ordering）：哈希表的遍历顺序从不保证，可代码里总有人假设「顺序是固定的」，比如拿遍历结果直接比对测试期望值。等到底层哈希函数换成更快、更安全的版本，顺序一变，这些代码就坏了。书里的结论很务实：既然理论上「不该依赖」挡不住实际依赖，就让坏习惯尽早暴露——例如每次运行都把顺序打乱，谁依赖顺序，谁在测试里马上就失败。

本章还反问：那干脆什么都不改行不行？不行。安全漏洞（书中举了 Heartbleed、Meltdown/Spectre）、新硬件、新的性能机会、业务变化，都会逼你改。「永不升级」不是选项，只是把账推迟、并让它变大。

System Design · Day 9 API 设计 — 契约一旦公开，破坏它的代价由所有调用方承担：版本化、兼容性与弃用策略

四、规模：凡是重复做的事，人力成本都要能扩展

本章的规模原则是：组织里凡是需要反复做的事，所需的人力投入都应当随规模线性甚至更好地增长，否则组织越大越被拖垮。作者点名两种不能扩展的政策：

  • 让用户自己迁移的弃用：底层团队宣布「旧接口下线，请各位自行迁移」，工作量 = 用户数 × 每人成本，代码库越大越不可能完成。
  • 传统的长命开发分支：每多一个分支，合并回主干的代价就多一份，规模一大，大量时间花在合并上。

对应两条能扩展的政策：

  • churn 规则（churn rule）：谁改底层，谁负责把用户迁过去——要么自己动手改所有调用处，要么保持向后兼容。专家集中做一次，比几千个团队各自摸索便宜得多，还能写工具批量改。
  • 碧昂丝法则（Beyoncé Rule）：「If you liked it, then you shoulda put a CI test on it.」——如果底层改动弄坏了你的产品，而 CI 里没有测试抓到它，那不是底层团队的错。它把「谁的东西要被保护」划成清晰的边界：你要被保护，就写测试。

书中的编译器升级故事把这些串起来：早年 Google 升级编译器极其痛苦，因为隔得久、隐含依赖多；后来升级变得常规，靠的是五样东西——专长（做过多次的人）、稳定（更频繁、更小的升级，每次变化更少）、一致（代码经历过升级，更少「只有它能跑」的特例）、熟悉（做得多了就去自动化）、政策（如碧昂丝法则）。核心洞察：越频繁升级，每次越便宜——这和「越久不动越安全」的直觉正好相反。

五、左移：问题越早发现越便宜

把开发流程画成一条从左到右的时间线：构想 → 设计 → 开发 → 测试 → 提交 → 集成 → 上线。同一个 bug，越靠右被发现，修复成本越高：开发时编译器报一句，几秒就改；上线后被用户发现，要排查、回滚、写复盘。左移（shifting left）就是把静态分析、代码评审、测试尽量往左挪——这正是全书后面 Ch9 评审、Ch11–14 测试、Ch20 静态分析的共同动机。

六、权衡与成本：把决策当成算账

本章要求每个决策都能讲出理由，「因为我说了算」是最糟糕的理由。成本至少有六类：财务成本（钱）、资源成本（如 CPU 时间）、人力成本（工程投入）、交易成本（采取行动要花多少）、机会成本（不采取行动错过了什么）、社会成本（对社会整体的影响）。

两个书中例子很有画面感：

  • 白板笔：Google 的储物柜里白板笔总是满的。笔很便宜，而工程师因为笔写不出字打断一场头脑风暴的成本高得多——这是用小额财务成本，换人力和机会成本。
  • 分布式构建：Google 把构建搬到分布式系统后，构建时间先大幅下降；可没过多久又涨了回去，因为构建变便宜了，大家不再在意引入多余依赖。这就是杰文斯悖论（Jevons paradox）：资源效率一提高，消耗反而上升。效率工具要配上依赖治理才守得住。

最后，本章承认决策会错：多数决策基于数据、假设和论证的混合，数据驱动是好起点，但环境在变，要定期回头检视；能说「我们错了，改」的组织，才配谈长期。

关键权衡与选型

为什么重要 / 落到真实系统

这章给了评审和面试一把通用尺子：评估任何工程实践，先问它在时间和规模两个轴上怎么表现。「要不要写单测」「要不要统一代码风格」「要不要升级依赖」，答案都取决于代码要活多久、多少人碰。面试被问技术债，可以用「可持续 = 有能力应对变化」来定义，用 Hyrum 定律解释为什么老系统越改越怕。

大厂实证 · 公开可查

  • Google · 单体仓的规模：Google 自己发表的论文披露，其单一代码库约有 10 亿 个文件、约 20 亿行代码、3500 万次提交，并采用主干开发、几乎没有长命分支——这正是本章「长命分支不可扩展」与 churn 规则得以落地的土壤：底层团队能看见并直接修改所有调用方。Potvin & Levenberg《Why Google Stores Billions of Lines of Code in a Single Repository》, CACM 2016 ↗
  • Google · Abseil 哈希表主动打乱遍历顺序：开源的 Abseil C++ 库在 raw_hash_set.h 的注释里写明，每张表混入一个种子来随机化遍历顺序，「这个种子用来确保遍历顺序的不确定性」；另一处注释说，为了防止用户代码依赖小表的遍历顺序，需要以某种方式把它打乱——Hyrum 定律的工程对策，写在了源码里。abseil-cpp · absl/container/internal/raw_hash_set.h ↗
  • Go 语言 · 同一招的另一家：Go 1（2012）的发布说明把 map 的遍历顺序定义为「不可预测」，同一个循环跑两次顺序也可能不同；说明里给的理由是：依赖顺序的代码会很早就坏掉，在酿成问题之前被修好。Go 1 Release Notes, 2012（文字出处）

易错点与争议

  • 「软件工程比编程高级」——误解。作者明确说这不是价值判断：一次性脚本按工程标准写，是浪费。区别在约束，不在高下。
  • Hyrum 定律不是「永远别改」。它说的是改动会有成本、要有工具和测试兜底，并主动打破偶然依赖；结论是更频繁、更有准备地改，而不是冻结。
  • 碧昂丝法则的前提是好测试。测试薄弱的组织照搬它，会变成「你没写测试，坏了活该」的推卸；它和 churn 规则必须一起用。
  • churn 规则依赖单体仓与全局可见性。开源库作者看不到下游用户，只能靠语义化版本和长期兼容——本章的方案不能原样搬到公开生态（Ch21 依赖管理会专门讨论）。
  • 「10 万倍」「越频繁越便宜」是经验判断。书中没有给出对照实验，复述时说清这是 Google 的经验总结。
  • 时代与视角局限。全书写的是一家有数万工程师、统一工具链的公司；小团队直接照搬单体仓、自研大规模变更工具，成本可能远超收益。

要点

① 软件工程 = 对时间积分的编程，再乘上人数与权衡；三维度：时间与变化、规模与增长、权衡与成本。

② 代码寿命从几分钟到几十年，相差至少 10 万倍；寿命决定升级有多重要。

③ 可持续 = 在预期寿命内有能力响应有价值的变化；第一次升级最痛。

④ Hyrum 定律：用户足够多时，所有可观察行为都会被依赖；对策是主动打破偶然依赖（如随机化哈希顺序）。

⑤ 「聪明」在编程里是夸奖，在软件工程里是指控。

⑥ 重复性工作的人力必须能扩展：用户自迁的弃用、长命分支不可扩展；churn 规则与碧昂丝法则可扩展。

⑦ 编译器升级的教训：专长、稳定、一致、熟悉、政策——越频繁升级，每次越便宜。

⑧ 左移：缺陷越早发现越便宜，是评审、测试、静态分析的共同动机。

⑨ 决策要算六类成本，「因为我说了算」最糟；警惕杰文斯悖论，并定期回头修正决策。
