这一章讲什么？

你在电脑上改了一个文件，手机上一打开就是新的。这一章问：把这件事做给几千万人用，背后要建些什么？答案有点反直觉——存文件反而是最容易的一步，难的是让你那五台设备对「现在到底哪一版才算数」始终说法一致。

先说个怪事

你在一份两百页的文档里改了一个字，网盘并没有把这两百页重传一遍。它只补了改动落在的那一小段——在它眼里，你的文件早就被剪成了一叠小卡片，你动了哪张，它就补哪张。

旧世界为什么难

早年的做法是「整份重传」。文件小的时候没人在意，可一旦你天天改一个几百兆的设计稿、还开着手机热点，代价立刻变得荒唐：改一个字，传半小时。更麻烦的是设备从不同时在线——笔记本改完就合上，平板三天后才开机，中间两边可能各改过一次。系统必须替你把这笔糊涂账理清楚。

核心机制：三个直觉

① 把文件剪成小卡片。上传前先切成大小差不多的小块，每块单独压缩、加密、存进仓库。以后改一处，只补那一张卡片。

② 货和账分开放。网盘其实是两套系统：一套放「货」（那些小块），一套记「账」（谁有哪些文件、第几版、由哪些块拼成）。你看到的目录、文件名、历史版本全在账本里。货那半边早就被云仓库解决了，剩下的难题几乎全在账上。

③ 谁先记上账，谁就算数。两台设备离线各改一次，最后同时上线——账本只认先到的那一版；后到的不会被悄悄盖掉，而是另存一份「冲突副本」摆在你面前，让你自己决定留哪个。

该怎么选

所有取舍最后都指向同一个问题：卡片切多大。切得太碎，账本上的条目会暴涨，光记账就把系统压垮；切得太大，改一个字又要重传一大坨。业界的答案落在几兆这个量级——大到账记得过来，小到重传不心疼。

代价很诚实：省下来的是带宽，赔进去的是账本——文件一多，慢的往往不是传输，而是「算清楚这次到底该传哪几块」。

一句话记住

网盘不是存储系统，是同步系统：文件切成块丢给云仓库，真功夫全在那本记着「谁有什么、第几版、由哪些块拼成」的账上。两边打架时，它选择让你看见冲突，而不是替你做决定。

一句话

你以为设计网盘是设计一个存储系统，其实存储那一半早被对象存储买断了——这一章真正在设计的是一本账：把文件切成不可变的块交给云存储，用一套元数据（metadata）记录「谁有哪些文件、第几版、由哪些块拼成」，再用增量同步（delta sync）压住带宽、用通知服务把多台设备拉回同一版本。全章的难点、一致性要求与成本，几乎全压在元数据这一面。

Glossary · 术语表

  • 块（block / chunk）：把一个文件切成的定长小段，各自独立存储、独立传输；本章取上限 4 MB。
  • 对象存储（object storage）：像 Amazon S3 那样按「整个对象」存取的仓库——不能改中间一段，只能整个覆盖。
  • 元数据（metadata）：关于文件本身的信息——文件名、大小、版本号、属于谁、由哪些块拼成，不含文件内容。
  • 增量同步（delta sync）：只传改动过的那几个块，而不是整份文件。
  • 去重（deduplication）：内容相同的块只存一份，靠对块内容取哈希来判定「相同」。
  • 哈希（hash）：把任意内容压成一串定长指纹，内容一样指纹就一样。
  • 长轮询（long polling）：客户端发一个请求挂在服务端不返回，等有事件才回；回完立刻再发一个——用普通 HTTP 模拟「服务端主动推」。
  • WebSocket：一条建立之后双向都能主动说话的长连接。
  • 冷存储（cold storage）：给极少访问的数据用的便宜档位（如 Amazon S3 Glacier），单价低但取回慢、还要另收取回费。
  • 强一致性（strong consistency）：写完之后任何一次读都能读到最新值，不会读到旧版本。
  • QPS：每秒请求数。

坐标

本章是 Vol 1 案例部分的收官之作（Ch16 是收尾励志章、无实质内容），也是全书唯一一道客户端占一半戏份的题：前面几章的主角都是服务端集群，这里有相当一部分设计发生在你电脑上那个同步客户端里。它把 Ch6 键值存储的复制思路、Ch14 YouTube 的对象存储与分片上传都接了过来，对应现实里 Dropbox / Google Drive / OneDrive / iCloud Drive 这一类个人云存储。

这章要解决什么

先把规模摆出来（书里的口径）：5000 万注册用户、1000 万日活，每人 10 GB 免费空间，人均每天上传 2 个文件、平均 500 KB，读写比 1:1。算下来总存储 5000 万 × 10 GB = 500 PB；上传接口 QPS 只有 1000 万 × 2 ÷ 86400 ≈ 240，峰值按两倍算也就 480。

这组数字本身就是题眼：QPS 低得离谱，存储量高得离谱。480 QPS 一台像样的机器就能扛住，可 500 PB 数据、上百亿个块的账，以及「一份文件在五台设备上都得是最新的」这件事，才是真正的工程量。不解决会怎样？账单和体验会同时崩：整份重传让一个几百兆的文件每改一次就吃掉几百兆上行带宽；没有版本与冲突处理，两台设备同时编辑就会静默丢数据——而本章把「绝不丢数据」列为第一条非功能需求，一次静默覆盖就足以让用户永久离开。

核心内容，讲透

一、先把系统劈成两半：数据面与元数据面

起点是一台机器：Web 服务器收文件、写进本地目录、把文件名和大小记进 MySQL。它一定会撞墙——单机的盘装不下 500 PB。于是文件本体交给 Amazon S3 一类对象存储（靠跨区域复制换持久性与可用性），自家机器只留账本。

这一刀劈下去，系统就长成了两条独立的路：数据面（客户端 → 块服务器 → 对象存储，走的是字节，量大、可异步、可重试）与元数据面（客户端 → API 服务器 → 元数据缓存 / 元数据库，走的是账，量小但要求强一致）。再补三个部件就是本章的完整骨架：通知服务（文件变了通知其它设备）、离线备份队列（设备不在线时把变更排着队，上线再消费）、冷存储（久无人问津的块挪去便宜档位）。

这个「劈两半」不是面试书的发明，而是大规模存储的通行结构：Google 的 Colossus 就是把元数据放进 BigTable、让数据在客户端与磁盘服务器之间直连（见 §6）。

System Design · Day 29 文件存储 — 对象存储为什么适合放这些不可变的块，以及分片上传、复制与纠删码怎么在成本和持久性之间取舍

二、块级切分与增量同步：为什么偏偏是 4 MB

上传前，客户端（或块服务器）把文件切成上限 4 MB 的块，每块单独压缩（按文件类型挑算法）、加密，再送进对象存储。此后改动只重传受影响的那几块——这就是增量同步。

给个量级感：一个 300 MB 的工程文件，你改掉其中一小段。全量重传要走 300 MB 上行；块级只需重传 1 个块，最多 4 MB，差了约两个数量级。在人均上行带宽只有几兆的年代，这是「能不能用」与「不能用」的区别。

那为什么不切得更小？因为每个块在元数据库里都是一行，还带一个哈希。若切成 4 KB，500 PB 就意味着上百万亿行块记录——省下的带宽全赔在元数据的存储、索引与查询上。切得太大又退回全量重传。4 MB 是这两条曲线的交点，不是什么魔法数字：它是「账记得过来」与「重传不心疼」之间的那个折中。

还有一条容易被略过、却支撑起整章的性质：块一旦写入就不再修改。改文件等于写新块 + 在元数据里换指针。不可变让去重、缓存、跨区域复制都变得简单（内容永不变，缓存就永不失效），代价是旧块会堆积，要靠版本策略和垃圾回收慢慢收。

三、元数据模型与上传流程：为什么是两个请求

元数据这一侧的表大致是：user（用户）、device（设备，用来推通知）、namespace（用户的根目录）、file（文件）、file_version（版本）、block（块，记录它属于哪个版本的第几块）。一个文件的内容 = 按顺序拼起来的一串块 id，这是整本账的核心一行。

上传不是一个请求，而是两条并行的路：先 POST 一条文件元数据、状态标成 pending（待确认），同时把变更块推给块服务器；块全部落进对象存储后回调 API 服务器，元数据状态才改成 uploaded（已完成），再交给通知服务广播出去。

为什么非要 pending？因为两条路是异步的：没有它，系统就分不清「正在上传」和「上传失败」，别的设备还可能读到一条指向尚不存在的块的记录、下载时直接 404。pending 是把两条异步的路重新缝在一起的那一针。

元数据这一侧还必须强一致：同一个文件在五台设备上显示的必须是同一版。所以缓存要在写入时同步失效、元数据库选带 ACID 的关系型。书里点破了一个很容易踩的坑：主从复制的异步滞后本身就会破坏强一致——从库返回旧版本，用户就会看见「文件回退了」，而在同步语义里，回退和丢数据是一回事。

System Design · Day 6 一致性 — 从强一致到最终一致的整条光谱，以及复制滞后为什么会让「读到旧值」变成业务事故

四、通知服务：为什么是长轮询而不是 WebSocket

需求很简单：设备 A 改了文件，其它在线设备要尽快知道。书的选择是长轮询，理由两条，都很朴素：一是这里的通信不是双向的——服务端要告诉客户端「变了」，客户端并不需要通过这条通道频繁回话；二是通知本身很稀疏——按前面的量级，一个用户一天也就两三次文件变更，不是聊天那种每秒好几条。WebSocket 的双向实时能力在这里用不上，却要付出连接管理与协议升级的复杂度。

把它和 Ch12 聊天系统对照着看，是全书最值得记住的一次对比：同样是「服务端主动推」，负载性质不同，答案就完全不同——聊天必须 WebSocket，因为消息双向且高频；网盘用长轮询就够。面试里能主动做出这个对照，比背下任何一个结论都值钱。

代价也要诚实说：长轮询同样要维持海量挂起连接，一个通知节点挂掉，挂在上面的客户端会同时重连，形成一次自制的惊群；离线设备错过的变更，则靠离线备份队列在它上线时补齐。

五、省空间的三招

500 PB 的账单会逼出三个动作：① 块级去重——对块内容取哈希，内容相同只存一份，一个热门安装包被一万人上传也只占一份；② 限制版本数——只留最近 N 个版本，别让「无限历史」变成无限账单；③ 冷热分层——几个月无人访问的块挪去 Glacier 这类冷档，单价低一个数量级，代价是取回慢、还按取回量另收费。三招都不动功能，只动成本曲线。

还有一处书在收尾时留下的开放权衡：切块该放客户端还是服务端。放客户端（直传对象存储）省掉一跳、更快也更省服务端带宽，代价是切块 / 压缩 / 加密要在每个平台各实现一遍，且客户端可被逆向、加密逻辑会暴露；放服务端则统一可控，但所有字节都得先过你的机器。

为什么重要 / 落到真实系统

这一题的价值在于，它是全书唯一一道必须回答「客户端该做多少事」的题——当纯服务端题来答就答偏了。而它建立的那套心智——数据面 / 元数据面分离、内容切成不可变块、状态机式的上传流程、按负载性质挑通知通道——是所有同步类产品的通用骨架：备份工具、代码托管、照片流、离线优先的移动应用，结构都长得很像。

大厂实证 · 这些主张不是书里说的，是公司自己公开说的
  • Google 的 Colossus 正是「元数据面 / 数据面分离」的实物：文件元数据放进 BigTable，数据则在客户端与磁盘服务器之间直连——「把文件元数据存进 BigTable，让 Colossus 相比最大的 GFS 集群扩展了 100 倍以上」。Google Cloud Blog「Colossus under the hood」, 2021-04 ↗
  • Google Cloud Storage 把全部对象元数据迁到了 Spanner，只为拿到包括「列目录」在内的强一致：迁移前用 Megastore，list 操作只有最终一致——印证了本章「元数据面必须强一致」不是理论洁癖，而是真会掏钱解决的问题。Google Cloud Blog「strongly consistent object listing thanks to Spanner」, 2018-02 ↗
  • Google Cloud Storage 对持久性的公开口径是设计目标 11 个 9：「我们总是在写入被确认成功之前把数据冗余地存到多个可用区」，并定期校验校验和、发现不匹配就用冗余自动修复——这正是本章敢把文件本体外包给对象存储的底气。Google Cloud Blog「11 nines of durability」, 2021-01 ↗
  • Dropbox 公开介绍过其自建存储系统按最大 4 MB 的块存放数据、块写入后不可变——本章那个 4 MB 就出自这一系谱。Dropbox 工程博客《Inside the Magic Pocket》, 2016（本次未能验证链接可达，故只留文字出处）

易错点与争议

  • 把它当「存储题」答：只讲 S3、分片上传、CDN，不讲元数据模型与同步语义——这是本章最常见的翻车方式。存储是外包出去的那一半，同步才是要你设计的那一半。
  • 以为块越小越省：忽略了元数据行数会跟着爆炸。带宽和元数据是一对此消彼长的成本，4 MB 是折中点而非最优解。
  • 以为「强一致」自动就有：主从异步复制会破坏它；缓存不同步失效也会破坏它。强一致是要专门花代价买的。
  • 把长轮询当通用答案：本章选它是因为「单向 + 稀疏」这个具体判据，换成高频双向就该换 WebSocket。记判据，别记结论。
  • 去重的隐私副作用：跨用户块级去重会带来一个副信道——通过「上传是否秒传」可以探测某个文件是否已存在于系统中。这一点在安全研究里早有讨论，也促使一些厂商改成按用户去重。书里没展开，但面试里提一句是加分项。
  • 时代局限：本书 2020 年成书，没覆盖端到端加密与去重的天然冲突（内容加密后哈希各不相同，跨用户去重直接失效），也没覆盖今天已成主流的「按需下载 / 占位文件」形态——本地只放一个占位符，双击才真正拉取。

要点

① 一句话：网盘不是存储系统而是同步系统；存储可以外包给对象存储，元数据与同步语义外包不掉。

② 规模的题眼：500 PB 存储 vs 峰值仅 480 QPS——难的从来不是并发，是数据量与多端一致。

③ 骨架是一刀两断：数据面（块服务器 → 对象存储，量大可异步）与元数据面（API → 缓存 / 库，量小须强一致）。

④ 文件切成上限 4 MB 的不可变块，改动只重传受影响的块；块大小是「带宽 vs 元数据行数」的折中。

⑤ 上传是两条并行的路 + 一个 pending → uploaded 状态机；pending 是异步流水线的事务边界。

⑥ 通知选长轮询，判据是「通信不双向 + 通知不频繁」；聊天系统换成 WebSocket，因为负载性质变了。

⑦ 冲突处理是先到先得 + 冲突副本：宁可把决策还给用户，也绝不静默覆盖；自动合并只在结构化文档上成立。

⑧ 省空间三招：块级去重、限制版本数、冷热分层；三招都只动成本曲线，不动功能。
