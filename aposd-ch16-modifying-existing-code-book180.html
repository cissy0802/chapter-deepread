修改已有代码

A Philosophy of Software Design · Ch 16 · Modifying Existing Code · Ousterhout · 2nd ed 2021

EN →

这一章讲什么？

你手机里的每个应用，第一版上线之后，往后好多年其实都在被修改：加功能、修毛病、换样式。程序员花在「改」上的时间，远多于「从零写」。每次接到新需求，最省事的办法是找到最少的几行，把新东西塞进去，能跑就交差。这一章说：别这样改。

打个比方

想象一栋老房子要加一个插座。最快的办法是从隔壁插座拉一根明线，沿着墙用胶带粘过去。一次两次没事；十年后满墙乱线，谁也不敢动，因为不知道哪根连着哪里。更好的做法是先问一句：「如果当初盖房时就知道这里要插座，线会怎么走？」然后照那个样子去改，哪怕要开一下墙。

旧世界为什么难

每一次「拉明线」单独看都很合理：快、不碰别的地方、看起来风险最低。麻烦在于它会一层层叠起来。没有哪一次改动是罪魁祸首，可一百次之后，系统已经乱到每改一处都要提心吊胆。房子里的说明书也是一样：说明写在离电线很远的地方，改线的人看不见，说明就慢慢变成了错的。

核心机制直觉

  • 每次都问那个问题。「要是一开始就知道这个需求，会怎么设计？」然后尽量让改完的样子接近那个答案。
  • 赶时间也别放弃。换个问法：「在现在的条件下，我能做到的最整齐的办法是什么？」常常有一个差不多整齐、又没那么费事的办法。
  • 说明贴着东西放。就像插座旁边贴的标签，改的人一眼就看见，顺手就改了。
  • 一件事只写一遍。其他地方写「详见那里」，免得改了一处、忘了另一处。
  • 交差前翻一遍改动。逐条对一对，说明是不是跟着改了。

带来了什么 / 该怎么选

这样改，系统会越改越清楚，而不是越改越乱，下一个人接手也更容易。一句诚实的代价：每次都要多花一点时间，有时比直接打补丁慢不少，尤其在赶工的时候。

一句话记住

改代码时别只求最少几行：改完的样子，应当像是一开始就为这个需求设计的。

一句话

你以为改已有代码的最高原则是「改动最小、风险最低」；Ousterhout 说那正是第 3 章批评的战术式编程。理想的标准是：每次改完，系统的结构应当像是从一开始就考虑到这个改动而设计出来的那样——如果你没有让设计变得更好，你多半正在让它变得更糟。

Glossary · 术语表

  • 战术式编程（tactical programming）：第 3 章概念，只求尽快让功能跑起来，不为设计多花一分钟。
  • 战略式编程（strategic programming）：把「好设计」当作目标，每次多投入一点时间改善结构。
  • 重构（refactoring）：不改变外部行为，只调整代码内部结构。
  • 版本控制（version control）：如 git，记录代码每一次改动的历史。
  • 提交与提交日志（commit / commit log）：一次保存到版本历史的改动，以及附在它上面的说明文字。
  • diff：两个版本之间逐行的差异列表，一般在提交或评审时查看。
  • 接口注释 / 实现注释：前者写在声明处讲「怎么用」，后者写在函数内部讲「这段在做什么」。
  • 技术债（technical debt）：为了快而留下的粗糙设计，以后要花更多代价偿还。

坐标

这章要解决什么

第 1 章说过，复杂度是增量累积的：没有单独一次改动能毁掉系统，但几百次小的妥协可以。而大型系统的生命主要花在被修改上，所以「改」才是复杂度真正的入口。

典型场景：一个导入模块最初只处理一种文件格式。第二种格式来了，加一个 if；第三种来了，再加一个参数开关；到第六种时，函数里满是特例，参数之间互相牵制，谁都说不清某个开关在哪些组合下生效。每一步都是「最小改动」，合起来却是一团乱麻。

与此同时，注释也在悄悄失效：改代码的人没看见远处的注释、或者把解释写进了提交日志，读代码的人一无所知。本章要回答两件事：改代码时用什么标准做决定；改完以后怎样让注释不过期。

核心内容，讲透

一、保持战略：用「从一开始就知道」当标尺

改动时有一种强烈的诱惑：找到能让新功能跑起来的最小改动，尽量不碰其他代码，觉得这样风险最低。作者认为这种心态正是战术式编程，结果是每次留下一点特例、一点依赖，复杂度不断累积。

他给的标准是一个思想实验：假如当初设计时就知道这个需求，系统会长什么样？理想情况下，每次改完，系统就该是那个样子。做到这一点，往往需要顺手重构：把原本的特例并进一个更通用的机制、把一个已经不合适的抽象换掉、把分散的逻辑收到一处。

这也是战略式编程里「持续投资」的具体形态：作者主张每次修改任何代码，都至少找一点办法让设计变好。改动是改善设计的天然时机，因为你此刻正好理解这块代码。

二、现实约束：没时间时换一个问法

作者并不天真。他承认，有时 deadline 逼得很紧，有时理想的重构牵涉太广、此刻做不完。他的建议不是放弃，而是换一个问题：「在当前约束下，这是我能做出的最干净的设计吗？」很多时候，存在一个几乎同样干净、但代价小得多的方案，比如先把新逻辑放进一个设计合理的新方法里，而不是塞进旧方法中间。

如果实在只能打补丁，也要清楚自己在借技术债：这一笔该记下来，等时间允许时还上。真正危险的不是某一次妥协，而是「最小改动」成了团队的默认习惯。

三、维护注释：放在离代码最近的地方

第 12 章有个常见借口：注释会过期。作者承认这是真问题，但认为可以靠做法解决，而第一条就是位置：注释离它描述的代码越远，改代码的人越看不见它，它就越容易过期。

  • 方法的说明写在方法声明处，而不是集中堆在文件开头；
  • 实现注释写在它解释的那几行旁边；
  • 一条注释描述的范围尽量窄：讲一个变量的事，就写在那个变量旁边。

这样，改代码时注释就在眼前，「顺手改一下」才可能真的发生。

四、注释属于代码，而不是提交日志

一种常见做法是：改了一段微妙的逻辑，把详细原因写进提交说明，代码里什么也不留。作者认为这是错的。未来读这段代码的人，几乎不会去翻版本历史；即便想翻，也很难从成百上千条提交里找到对应的那一条。

他的判据很简单：只要一条信息对将来理解这段代码有用，就放进代码里。提交日志适合描述「这次改了什么、为什么改」这段历史，可以引用注释，但不能替代注释。

五、避免重复：每个设计决策只记录一次

同一段说明复制在三个地方，改的时候几乎一定会漏掉一处，于是三份说法互相矛盾。作者的规则是：每个设计决策只写一次，放在开发者最可能先找到的位置；其他相关地方写一句「见某某处的注释」。如果信息已经在程序之外的文档里（比如协议规范），就在代码里引用它，而不是抄一遍。

六、提交前检查 diff

一个便宜又有效的习惯：提交之前把 diff 从头扫一遍，确认每一处改动在文档里都有相应的反映，也顺便看看有没有遗留的调试代码。几分钟的成本，挡住的是注释和代码悄悄分家。

七、越高层的注释越好维护

比代码更抽象的注释，只描述「做什么、为什么」，不描述「一行行怎么做」，所以代码的小改动通常不会让它失效。反过来，逐行复述代码的注释，代码一改就过期。这和第 13 章的要求一致：注释应当写代码表达不了的东西。

关键权衡与选型

表 1 · 接到一个新需求：三种改法

改法做法短期长期
战术补丁找最少几行塞进去，加特例、加开关最快，评审 diff 最小特例累积，下一次改动更贵、更易出错
约束下的最佳（本章兜底）问「当前约束下最干净的方案」，常是新抽象 + 少量重构略慢结构基本保持；债务有记录、可还

表 2 · 一条信息该放在哪

位置适合放读者何时看到过期风险
声明旁的接口注释抽象、用法、前置条件、副作用每次读或调用时低，改代码时就在眼前

选型判据：越是要长期存活、会被很多人改的代码，越该走战略改动；一次性脚本或即将下线的模块，战术补丁也许是理性的。真正的问题从来不是某一次选了补丁，而是从不再问那个问题。

为什么重要 / 落到真实系统

代码评审、重构、注释规范，在大型工程组织里都围绕同一件事：守住每一次改动不让整体变差。本章把这个目标从「团队流程」压到了「每个人每次改动时的自问」。

大厂实证 · 公开可查

  • Google 代码评审准则：评审者的职责是确保每个改动（CL）的质量不会让代码库整体健康度随时间下降，并指出代码库往往正是通过「一次次小幅下降」变差的，尤其在团队时间紧、觉得必须走捷径时。准则把「只要 CL 确实改善了系统整体代码健康，即使不完美也应倾向批准」称为所有评审准则中最高的一条。出处：Google Engineering Practices · The Standard of Code Review
  • Ousterhout 与 Robert C. Martin 的公开辩论：Ousterhout 在其中认为 TDD 迫使开发者「过于战术式地工作」，并指出 Red-Green-Refactor 循环几乎没告诉人何时、重构什么，于是重构容易被一拖再拖；Martin 则认为设计来自战略思考，与 TDD 或先写代码再补测试的战术做法无关。出处：GitHub · johnousterhout/aposd-vs-clean-code
  • Linux 内核提交规范：要求提交说明先讲清「要解决的问题」与用户可见的影响，再讲具体做法，并量化性能权衡。这是提交日志的正确用途——记录改动的历史；本章强调的是，理解代码本身所需的信息仍应留在代码里。出处：Linux kernel · Submitting patches

落到日常：接需求时先花几分钟想「如果从零设计会怎样」，再决定改法；评审时不只看 diff 本身对不对，也看它让周边结构变好还是变坏；让 AI 助手改代码时，同样要求它给出「理想结构」而不仅是最小补丁，并在提交前检查注释是否同步。

易错点与争议

  • 「战略改动 = 每次大重写」。不对。作者要的是改完的结构合理，很多时候只需小范围重构；兜底的问法本身就承认约束。
  • 「最小改动最安全」。对单次改动而言也许如此，但风险被推迟和累积了：特例越多，后面每次改动的出错概率越高。
  • 「原因写在提交说明里就够了」。读代码的人默认不翻历史；理解代码需要的信息要留在代码里，提交日志可以引用它。
  • 「注释会过期，所以少写」。本章的回答是改做法：放近、只写一次、提交前查 diff、写高层注释。
  • 前提是能放心重构。书里没有展开测试覆盖不足的老代码怎么办；在没有测试兜底的遗留系统里，「顺手重构」本身有风险，业界常配合 Michael Feathers《Working Effectively with Legacy Code》一类先补测试再改的做法。
  • 证据是经验性的。和全书一样，结论来自作者的工程与教学经验，没有对照实验；「多投入一点」到底多少合适，需要团队自己判断。

要点

① 系统的生命主要花在被修改上，复杂度经由一次次小改动累积。

② 「最小改动」的诱惑就是战术式编程。

③ 标尺：每次改完，结构应像是一开始就考虑到这个需求而设计的。

④ 如果你没有让设计更好，你多半在让它更糟；每次改动都顺手投资一点。

⑤ 没时间时换个问法：在当前约束下，这是最干净的方案吗？

⑥ 注释放在离代码最近的地方，范围尽量窄。

⑦ 理解代码所需的信息属于代码，不属于提交日志。

⑧ 每个设计决策只记录一次，其余处引用；外部文档也引用而不抄。

⑨ 提交前扫 diff；越高层的注释越不容易过期。
