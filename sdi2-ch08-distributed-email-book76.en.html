What is this chapter about?

The mailbox you open every morning has to run a billion private mailboxes at once: take everything in, let you find any of it again, and look identical when you pick up a different phone. This chapter builds one of those from scratch.

A strange thing first

The rules for moving mail around were written in the 1980s and have barely changed. Yet this is one of the heaviest chapters in the book — because the hard part was never "how do I get the letter there", it's "where do I put it once it lands, and how do I ever find it again". A mail service is not really a messaging system. It's an enormous warehouse.

Why the old world couldn't cope

Early mail servers were charmingly simple: one machine, and everybody's letters piled up in a folder on it. That falls over on every axis once the crowd arrives — a single day's incoming mail can fill a machine; when the machine dies, that whole group of people goes dark; and mail is essentially never deleted (lawyers and auditors want it kept), so the pile only grows.

There's a counter-intuitive part too. What actually strains the system isn't receiving mail — it's the little taps you don't think about. Marking something read, adding a label, dragging it to archive: every one of those is a write. Read forty letters a day and that's forty more writes.

The core ideas

1. One cubby per person. Mail has a luxury other systems envy: nobody ever looks inside someone else's mailbox. Every operation concerns exactly one person. So you cut the warehouse into one cubby per person, and every read and write touches only one cubby — which makes the whole category of "coordinate five machines to get one thing done" problems simply disappear.

2. Letters and parcels get stored apart. The text is light; the attachment is heavy. So attachments go to the big depot next door, and the cubby holds only a claim ticket. Flipping through your inbox then never has to drag the parcels along.

3. Everyone gets their own little catalogue. Searching mail and searching the web are different animals: web search is a billion people consulting one giant catalogue; mail search is a billion tiny catalogues, each serving one person. Yours is thin — which is exactly why a letter that landed a second ago is already findable.

4. The doorman only signs for it. When mail arrives you can't leave the courier standing outside: sign for it, drop it on the conveyor belt, and do the slow work — virus scan, spam filter, sorting — further down the line.

The honest cost

One letter actually gets written to three places: the cubby, the depot, and the catalogue. So deleting one means deleting three — and for a short while those three can disagree. You delete a message and search may still show a ghost of it for a moment.

Remember this

The hard part of a mail service is storing and finding, not sending. Its great asset is that nobody reads anyone else's mailbox: cut the warehouse into one cubby per person and the expensive work collapses into single-cubby work. Heavy attachments move to the depot next door; catalogues are per-person. The cost is that one letter lives in three places and they briefly disagree.

In one sentence

On the surface this chapter builds a Gmail. In substance it is the cleanest partition key in the entire Xu series: the mail protocols froze forty years ago, and the whole engineering budget goes into a billion mutually irrelevant private mailboxes — and precisely because every query lands on exactly one person, the most expensive items in distributed systems (cross-partition transactions, global ordering, global indexes) never have to be bought. What the chapter really teaches is recognising that gift of a partition key and spending all of it.

Glossary

  • SMTP — the delivery protocol. It moves a message from the sender's server to the recipient's server and says nothing about how it is stored afterwards.
  • POP3 / IMAP — the retrieval protocols. POP3 downloads and deletes from the server (one device); IMAP keeps the server authoritative and syncs a view to each device.
  • MX record — a DNS record naming which server should receive mail for a domain.
  • Metadata — here, everything except the body: sender, subject, timestamp, read flag, labels, folder.
  • Object storage — a "one key, one whole file" store (S3 and friends). Great for large immutable blobs, bad at frequent small edits.
  • Wide-column store — the Bigtable / HBase / Cassandra family. A row can hold an enormous number of columns, columns are kept sorted by name, and a read can touch only the column families it needs.
  • Row key / column key — the two levels of address in a wide-column store. The row key decides which machine holds the data; the column key carries sort order within the row.
  • Inverted index — a table from term to the documents containing it; the basic structure behind full-text search.
  • Idempotent — doing it once and doing it ten times give the same result. Delivery retries, so receiving must be idempotent.
  • SPF / DKIM / DMARC — three mechanisms for checking "did this message really come from that domain", and the first gate in modern spam defence.

Where it sits

Chapter 8 of Volume 2. It follows Ch7 (hotel reservations, contention over finite inventory) and leads into Ch9 (object storage). It opens the volume's "build the thing yourself" thread: this chapter spreads out the problem of metadata over huge numbers of tiny objects, and the next one dissects the storage layer that holds the attachments. Real-world counterparts: Gmail, Outlook, corporate mail gateways — and in fact any system where each user owns a private data space, such as file sync, notes, or a DM inbox.

The problem it attacks

Start with the book's assumptions: 1 billion users, each sending 10 and receiving 40 messages a day, body averaging 50KB, 20% carrying an attachment averaging 500KB.

  • Sending: 10^9 × 10 / 86400 ≈ 116,000 messages/s. Receiving: 10^9 × 40 / 86400 ≈ 463,000 messages/s.
  • New storage per day: bodies 10^9 × 40 × 50KB ≈ 2PB, attachments 10^9 × 40 × 20% × 500KB ≈ 4PB — about 6PB a day, and it essentially only grows.

The traditional answer is a Maildir on one box, each user's mail sitting there as files. Against 6PB/day that breaks in three places at once: it doesn't fit (single-machine capacity), it can't be searched (full text means scanning files), and one dead machine takes a whole cohort offline (no replicas).

The subtler failure is write amplification in the flag bits. A body is written once and never touched again — but read/unread, labels and folder moves change constantly. On the assumptions above, "mark as read" alone is roughly 463,000 small updates per second globally, the same order as receiving mail itself. A mail service is not a read-mostly system, and that single fact rules out any storage engine tuned for read-mostly workloads.

The core content, properly

1. The protocol layer is a given; the freedom is behind it

Outward, you must speak SMTP: look up the recipient domain's MX record, open a connection, push the message. You cannot change this layer, and more importantly you do not control the far end — it may be down, rate-limiting you, or classifying you as spam and bouncing you.

That yields the first hard architectural constraint: outbound can never be synchronous. "Send" must return immediately, while actual delivery is a background job that may retry for hours or days. So outbound is a queue plus exponential backoff plus a dead-letter/bounce path.

Inward is a different story. POP3 is a relic of the single-device era; IMAP makes the server authoritative and syncs multiple devices; and what web and mobile clients actually use today is your own HTTPS API plus a WebSocket push channel — real IMAP is only needed when third-party clients such as Outlook or Apple Mail have to connect.

2. Where metadata lives: why not a relational database

The book first characterises the data, then derives the choice from the character:

  • Huge and append-only — petabytes, and compliance means it can't be pruned.
  • Each user touches only their own data — no query ever spans users.
  • The bulk of writes are tiny updates — read flags, labels, folder moves.
  • Strong consistency within a user, none required across users — mark something read on your phone and your laptop must see it on refresh; but your mailbox and mine need no consistency guarantee whatsoever.

That last point is the hinge of the whole chapter. It means the consistency boundary can be drawn exactly around one user. Make the row key user_id — one user, one row — and every operation that needs atomicity (receiving a message, marking read, bulk-archiving) falls inside a single row. Nearly every wide-column store offers atomic single-row writes, so the most expensive item on the menu, the distributed transaction, is never ordered. Google's Megastore paper (CIDR 2011) uses a mail account as its canonical "entity group" example for exactly this reason: ACID inside the group, no guarantees across groups — mail is born that shape.

The column key buys a second free lunch. Compose it as folder:timestamp:message_id; wide-column stores keep columns sorted by key, so "give me the 20 most recent inbox messages" degenerates into one reverse range scan — no secondary index, no ORDER BY, no offset pagination.

3. Bodies and attachments part ways

A body is a few KB to a few tens of KB; an attachment starts in the hundreds of KB and runs to a 25MB ceiling (Gmail's published limit). Put attachment bytes inside the metadata row and the single most frequent operation — listing the inbox — has to drag hundreds of megabytes of irrelevant data along. So the book parks attachments in external object storage and keeps only a key in the metadata.

That hands you a neat bonus: content-hash deduplication. One message with a 10MB attachment sent to 100 people stores the bytes once and hands out 100 claim tickets — a 99% saving. The cost is that deletion stops being a single write and becomes a reference-counting and garbage-collection problem: the bytes cannot go until the last ticket does.

Large uploads also need multipart upload with resume: pushing 25MB in one PUT over a flaky mobile link fails often enough that only 5MB chunks with per-chunk retry are workable.

4. Search: a billion small indexes, not one large one

This is where intuition most often misleads. Mail search differs from web search on three axes:

  • Scope — web search is one giant index serving a billion people; mail search is a billion small indexes each serving one person. Even a heavy user has tens to hundreds of thousands of messages: a corpus small enough to give everyone their own.
  • Ranking — the web ranks by relevance; mail is overwhelmingly ranked by time, newest first. People are looking for "that one from last week", not "the most relevant one".
  • Freshness — hours of web index lag are fine; in mail, a message that arrived a second ago must already be findable. That single requirement kills offline batch indexing outright.

Put the three together and the shard key has only one candidate: user_id again. One search hits one shard — no scatter-gather across thousands of shards, then merge. That is precisely why mail search can be tens of milliseconds without the cost exploding.

Search therefore reshapes the write path: an incoming message must be written to metadata, object storage and the index. Those three are not in one transaction, so the book's answer is asynchronous writes plus retries plus a periodic reconciliation sweep, accepting an inconsistency window measured in seconds. Treating search as a feature to bolt on later is the classic way to fail this question — it dictates the shape of the write path, it is not decoration on the read path.

Why it matters / in real systems

What makes this question distinctive in an interview is that it is the one problem whose partition key is written into the prompt. The interviewer is not checking whether you can recite the SMTP handshake; they are watching whether you notice that "nobody reads anyone else's mailbox" buys out cross-partition transactions, global ordering and search fan-out in one move — and whether you then spend that dividend. Miss that layer and the whole question collapses into a pile of boxes and arrows.

Pitfalls and open questions

  • Thinking the difficulty is in the protocol. SMTP and IMAP are the most settled, least interesting layer here. Spending your time on the handshake means answering a different question.
  • Thinking "partition by user_id" ends the discussion. Corporate mailboxes with hundreds of thousands of messages and tens of gigabytes turn one row into a fat row and a hot spot. Real systems split again below the user, by folder or time window — the book names this but doesn't develop it.
  • Treating the read flag as a minor detail. Flag updates run at the same QPS as message arrival, and that is the constraint that actually picks your storage engine. Size the system on bodies alone and you choose the wrong foundation.
  • Mistaking three replicas for a backup. Replicas defend against hardware and datacenter failure, never against a software defect that deletes data — that gets copied three times, faithfully. Mail needs a separate offline, immutable, different-medium backup.
  • Dated in one visible way (written in 2022): end-to-end encrypted mail (the Proton family) is barely discussed. Once the server cannot read the body, server-side search and spam filtering both stop working and the index has to move to the client — the entire architecture here would need rebuilding for that world.
  • The engineering the chapter doesn't cover: deliverability. IP reputation, warming up a sending domain, bounce classification, actually deploying SPF/DKIM/DMARC — real mail teams spend half their lives there, and the book only names it. Likewise the conflict between GDPR's right to erasure and legal hold is a genuinely hard problem under "mail is never deleted", and goes undeveloped.

Takeaways

1. A mail service is a storage-and-retrieval system, not a messaging one: the protocols have been frozen for forty years; all the work is in where things go and how they are found.

2. Scale: at 1B users, ~116K sends/s, ~463K receives/s, roughly 6PB of new storage a day, essentially append-only.

3. The real write pressure sits in read flags and labels, at the same order as arrival — which rules out read-optimised storage.

4. The hinge: nobody reads anyone else's mailbox. The consistency boundary lands on one user, the row key is user_id, and distributed transactions are never purchased.

5. Make the column key folder:timestamp:message_id and "newest 20" degenerates into a range scan — ordering becomes a by-product of layout.

6. Bodies and attachments separate: blobs go to object storage with content-hash dedup, metadata keeps a key; the cost is refcounting and GC on delete.

7. Mail search is not web search: a billion small indexes, time-ordered, findable within a second; the shard key is again user_id, so one query hits one shard.

8. One message lands in three stores (metadata / attachment / index), outside any single transaction, eventually consistent — search shapes the write path, it doesn't decorate the read path.

9. Selection: wide-column NoSQL beats both relational and pure object storage; search trades off between buying Elasticsearch and growing an index on the LSM store.

10. Two lessons paid for in incidents: replicas are not backups (2011 Gmail was recovered from tape), and spam defence is the main path, not an add-on (over 100M phishing mails blocked daily).
