检索增强生成：你以为是在给模型补知识，其实是在给它装一条能被核对的证据链

EN →

这一章讲什么？

你问公司的 AI 助手「出差住宿能报多少」，它答得又快又顺——可这条规定上个月才改，它凭什么知道？这一章讲的就是让机器先翻资料、再开口的那套办法。

先说个怪事

一个不知道答案的人，通常会说「我不清楚」。可这类机器不会。它没学过的事，它照样答，而且答得和真话一模一样顺。更糟的是你没法追问它「这是哪来的」——它自己也说不清，一切都糊在它读过的几万亿字里，指不出具体哪一句。

旧世界为什么难

两条老路都走不通。一条是重新教它一遍：把新文件塞进教材让它重读——这像为改一个电话号码重印整本字典，贵、慢，而且下周文件又改了。另一条是全摊在桌上：把整个档案室搬到它面前。桌子就那么大，摊不下；勉强摊下了，一屋子纸里找一句话也容易看花眼，越靠中间的越容易被跳过去。

它是怎么做到的

真正管用的办法是请一个图书管理员，分两步走。

第一步是平时的活：整理卡片柜。把文件提前裁成一段段卡片，再按意思归档——说同一件事的放一起，哪怕用词完全不同（「住宿标准」和「酒店费用上限」进同一格）。这活在没人提问时就做完了。

第二步是你提问的那一刻：管理员冲进卡片柜抓出最像的一百张，筛一遍留下最相关的五张，连同问题递给答题的人。答题人手上只有这五张，规矩只有一条：只准照卡片上写的答，还得标出这句出自哪一张。没抓到卡片时，正确答法是「档案里没有」。

带来了什么 / 该怎么选

三样好处立刻到手：文件今天改今天生效，不用重教；答案能顺着标注翻回原文核对；不许这个人看的文件，在抓卡片那步就拦掉了。代价只有一句，但很硬：上限被「抓卡片」那一步锁死——卡片抓错，后面答得越流畅越糟，因为错得像真的。

一句话记住

它的产出不只是一个答案，而是一个答案外加它的出处。你以为这套东西是在给机器补知识，其实是在把「凭空说」改成「照着说」——从此每句话都有地方可查。

一句话

你以为检索增强生成（RAG，retrieval-augmented generation）是「给模型补知识」的省钱替代品，其实它真正交付的是一条可核对的证据链：知识当天可换、来源可点回、答错了能定位到是哪一环坏的——这三样微调和超长上下文都给不了。而整章最该记住的工程结论只有一句：RAG 的质量上限由检索那一半决定，生成模型只是在这个上限之下打折。

Glossary · 术语表

  • 参数记忆（parametric memory）：模型训练时把知识压进权重里，用的时候凭「记得」作答，指不出出处。
  • 嵌入（embedding）：把一段文字表示成一串数字（常见 384–1536 维），意思相近的文字数字也相近。
  • 分块（chunking）：把长文档切成一段段可单独检索的片段。
  • 向量数据库（vector database）：专门存嵌入、并能快速找出「最像的几条」的存储。
  • 稀疏检索 / BM25：按关键词计分的经典检索，词对上才算命中。
  • 稠密检索（dense retrieval）：按嵌入的距离找相近的，词不同也能命中。
  • ANN（近似最近邻）：不逐条比对，用索引结构快速找出「大概率最近」的那几条，拿一点召回换几个数量级的速度。
  • HNSW：一种分层图式 ANN 索引，查询时从稀疏的高层往下跳、逐层逼近目标。
  • recall@k：正确答案所在的片段，出现在返回的前 k 条里的比例——检索侧最该盯的指标。
  • 重排序器（reranker）/ cross-encoder：把「问题 + 片段」拼成一条一起算分的模型，准得多也慢得多，只用来精排少量候选。
  • 接地（grounding）：让回答严格依据给定材料，而不是模型自己的记忆。
  • 忠实度（faithfulness）：回答里的每句话，是否都能在给它的片段中找到支撑。

坐标

Part II 十道真题的第五道，也是文本簇的收官题。上承 Ch4 ChatGPT——那里的知识全靠参数记忆；这一章第一次把外部知识库接进生成链路，Ch7 起则转入图像生成。现实对应企业知识库问答、客服助手、文档助理，以及今天所有带「引用来源」的搜索型 AI 产品。

这章要解决什么

参数记忆有三宗罪，且每一宗都不是把模型做大能解决的。

一是过期。权重冻结在训练截止那天，而知识库每天都有文档在改。为一次政策更新重跑微调，从数据准备到评估上线通常以周计，而文档改动以分钟计——差了四五个数量级，不是调优能补上的。

二是指不出出处。模型说「住宿上限 800 元」时，这个数字糊在几万亿 token 的语料里，定位不到任何一句原文。而在法务、医疗、金融场景，不能核对的正确答案和错误答案价值相同——你分不出手里这条是哪种。

三是私有数据进不去。内网文档、用户自己的资料、有权限分级的材料，不该也不能塞进一份全员共享的权重——权重没有 ACL（访问控制表），一旦记住，就没法只对一部分人忘掉。

不解决会怎样？模型在它不知道的事情上依然流畅作答，且全链路没有任何一处可供核对。这正是上一章那个结论的升级版：生成式系统最危险的失败不是答不上来，是错得流畅。

核心内容，讲透

① 两个阶段：离线把知识摆好，在线只做取用

整条流水线被一条硬边界切成两半，看懂它，后面所有权衡都好解释。

离线（索引期）：文档 → 分块 → 逐块算嵌入 → 写进向量索引。百万级文档切成千万级片段、算完嵌入建好索引，是个批处理作业，耗时按小时算——因为没人在等。

在线（问答期）：问题 → 算嵌入 → 检索 → 重排序 → 拼进 prompt → 生成。整体要压在一两秒内，而生成往往就吃掉一秒以上，留给检索加重排的常只有 100–300 毫秒——这个预算才是后面索引选型的真正约束。

② 分块：全链路最被低估的一个决策

检索的单位不是文档，是块。块怎么切，几乎决定了后面能不能检到。

直觉是「越小越准」：一块只讲一件事，嵌入不被稀释，容易对上。但小块会把完整论述撕成两半——模型拿到半截话，更容易自行补全出错的那一半。块太大则一块混了五六个主题，嵌入被平均成一个谁也不像的向量，检索分数低，还白占 prompt 预算。

常见落点是 200–500 token 一块、相邻块留 10%–20% 重叠（overlap，防止答案正好卡在切口上）。但比调参更重要的是三件事：按结构切（沿标题与段落边界，别按固定字数把表格拦腰砍断）；带上元数据（标题、章节路径、日期、权限标签，既用于过滤也用于排序）；上下文化——把所属章节标题或一句摘要拼回块首。最后一条针对一个具体毛病：一块写着「该上限自次月起调整为 1000 元」，孤立看根本不知道说的是哪项费用，检索永远对不上。

③ 检索：关键词、向量与它们的合并

两条路的失手方式几乎正好互补。

BM25（关键词）在精确串上无敌：错误码 ERR_5021、型号 X-200、人名、法条编号——这些东西算嵌入毫无意义，字面匹配却百发百中。死穴是同义改写：用户问「怎么退钱」、文档写「退款流程」，词面不重合就是零分。

稠密检索（向量）正好相反：能跨过用词差异抓语义，却常在罕见专名上翻车——嵌入模型没见过这个型号，就当它是一串普通字符，返回一堆「看着像技术文档」的无关块。

混合检索把两路的排名合起来（常用倒数排名融合 RRF：按名次而非分数加权，省掉两套分数量纲不一致的麻烦）。这是绝大多数生产系统的默认选择，代价是两套索引都要维护、还多一个融合权重要调。

另一层是怎么在千万级向量里快速找出最近的几条。逐条算距离召回 100%，但千万量级下单次查询要几百毫秒到秒级，直接撑爆预算。ANN 用结构换速度：HNSW 建一张分层邻居图，查询从稀疏的顶层起跳、逐层逼近，能压到毫秒级，代价是可能漏掉真正的最近邻。漏多少由搜索宽度这一个旋钮控制，调大则召回和延迟同涨。它是连续可调的旋钮、不是开关——该当成 SLO 的一部分来定，而不是抄个默认值。

④ 重排序与上下文装配：把一百条压成五条

检索阶段是双塔：问题和片段各自独立编码，片段向量能离线算好存起来——这正是它快的原因，但两边从未「见过面」，只能比粗略的相似度。

重排序器反过来：把问题和片段拼成一条送进模型一起算，能捕捉「这段是否真的回答了这个问题」。代价是它没法预计算，每个候选都要现场跑一次——所以它比双塔慢一到两个数量级，只能用在少量候选上。标准做法因此是漏斗：ANN 粗召 100 条 → 重排精算 → 留 3–5 条进 prompt。

「装配」还有两个易漏的细节。其一，位置有影响：摆在长上下文正中间的材料最容易被忽略，所以最相关的片段该放首尾，而不是按相似度一路铺下去。其二，每块都按 token 收费、也按 token 吃延迟：5 块 × 400 token = 2000 token，每问一次付一次。k 从 5 调到 20，答对率通常不怎么涨，账单和首字延迟却实打实地涨。

⑤ 生成侧：接地、引用与拒答

拿到片段后，生成的任务不是「发挥」，而是受约束地复述。三条落地要求：提示里写死「只依据给定材料作答」；逐句挂片段编号，让引用能被程序校验而不只是给人看；允许说不知道——检索分数低于阈值或片段互相矛盾时，正确输出是「材料中未提及」。

最后一条是整套系统里最反直觉的产品决策：拒答率是一个要主动调的旋钮，不是一个越低越好的缺陷。企业问答场景宁可多拒答几个百分点，也不愿放出一条看不出错的编造。

为什么重要 / 落到真实系统

三个落点已在大规模跑：企业知识库问答（内网文档 + 权限过滤，商业价值最集中）、带引用的搜索型回答（答案下方挂可点来源，用户自己核对）、客服与技术支持（工单、手册、变更记录一起索引，答案能追到具体哪份文档的哪一段）。第三个最能看出它的真身：这不是一个更聪明的模型，而是把组织已有文字资产接进生成链路的基础设施。

易错点与争议

  • 只评生成、不评检索。 最常见的错误。要分两段量：检索侧看 recall@k，生成侧看忠实度与拒答率。答得不好，八九成是没检到，不是模型笨。
  • 把「相似」当成「相关」。 向量检索永远返回 k 条，哪怕库里根本没有答案——它没有「查无此项」这个输出。不自己设分数阈值，模型就会拿着一堆无关片段硬答。
  • 以为块越小越好。 块小提升的是命中率，牺牲的是完整性；被撕成两半的论述反而更容易诱发编造。
  • 引用变成装饰。 模型标了片段编号，不等于那句话真的出自那一块。引用必须被程序校验，否则它只是幻觉的一层包装。
  • 权限靠提示词兜底。 「不要透露 HR 文档」这种话挡不住任何东西。过滤必须发生在检索层：无权的片段根本不该进候选集。
  • 索引陈旧无人察觉。 文档改了、嵌入没重算，系统会自信地给出旧答案且毫无异常信号。索引新鲜度要像数据管道一样监控。
  • 争议：长上下文会不会吃掉 RAG。 窗口越做越大，「全塞进去」看着越发可行。但三件事没变：每次问答都为整份资料付 token 费、延迟随材料线性涨、整个知识库本来就塞不进任何窗口。更现实的判断是二者合流——用检索收窄范围，再用大窗口容下更多候选。
  • 时代局限。 本章以「一次提问 → 一次检索」的单轮形态为主线；此后实践大量转向多轮与代理式检索（模型自己决定要不要再查、查什么），以及 GraphRAG 这类针对全局性问题的结构化路线。底层结论一条没变：检索决定上限。
AI/ML · Day 4 RAG 体系 — 嵌入模型怎么选、分块与重排的消融实验怎么做，以及 RAG 各环节的评估指标体系

要点

① RAG 的真正产出不是答案，是可核对的证据链：知识分钟级更新、来源可点回、错了能定位到哪一环。

② 参数记忆的三宗罪——过期、指不出出处、私有数据进不去（权重没有 ACL）——做大模型都解决不了。

③ 流水线被切成两半：离线建索引按小时算，在线问答全程 1–2 秒，检索加重排只分到 100–300 毫秒。

④ 检索决定上限，生成只在上限之下打折；正确片段没召回，后面再强也救不回来。

⑤ 分块是最被低估的决策：常见 200–500 token、10%–20% 重叠，但按结构切、带元数据、把章节标题拼回块首，比调参更重要。

⑥ BM25 和向量的失手方式互补——前者死于同义改写，后者死于罕见专名；混合检索是生产默认。

⑦ ANN 用召回换速度，搜索宽度是连续旋钮；先用暴力检索量一条 recall@k 基准线，再谈掉多少值不值。

⑧ 漏斗形状固定：粗召 100 条 → 重排留 3–5 条；重排慢一到两个数量级，所以只能用在少量候选上。

⑨ 装配两条纪律：最相关的放首尾（中段易被忽略）；k 调大账单和延迟实打实涨，答对率往往不涨。

⑩ 拒答率是要主动调的旋钮，不是缺陷；引用必须被程序校验，权限必须在检索层过滤。
